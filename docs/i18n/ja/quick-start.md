# クイックスタート

*インストール後に最初の実タスクを証明します。*

> **役割:** このページは herdr-mcp がインストールされ接続された後から始まります。実行可能なインストール契約は [Agent インストール](agent-install.md) を参照してください。手動でのインストールと運用は [インストール](install.md) を参照してください。

このページをなぞるためだけに Edge を再デプロイしたり、runtime を再インストールしたり、ブラウザ拡張を追加したりしないでください。目標はもっと単純です。Web AI が実際にあなたのワークステーションへ到達し、実リポジトリで検証可能なタスクを一つ完了できることを証明することです。

## 1. まず読み取り専用のチェックから始める

新しい ChatGPT の会話を開き、次のように依頼します:

```text
現在の Herdr workspace を表示し、その managed project に未コミットの変更があるかどうかを示してください。読み取り専用のベースラインを一度だけ使い、何も変更しないでください。
```

健全な経路は次のようになります:

```text
herdr_inspect
  ↓
ワークステーションの事実に基づく回答
```

これは Connector の緑のバッジ以上のものを証明します。公開 MCP 経路、ワークステーション Link、runtime、Herdr の作業現場が実際につながっているということです。

このステップで `workstation_offline`、tools が 0 個、OAuth ループ、または managed-root の拒否が報告された場合は、mutation のテストに進む前に止まり、[トラブルシューティング](troubleshooting.md) で失敗している層を特定してください。

## 2. 決定的な変更を一度だけ行う

ドキュメントの修正、テスト fixture、範囲の狭い設定変更など、安全で検証が容易な変更を選びます。Web planner には次のように依頼します:

```text
現在の workspace を再利用してください。この変更に必要な Git/ファイル状態だけを読み、小さな編集を一つ行い、安全な場合は関連する検証と最終 diff をまとめて実行してください。ローカル Agent には委任しないでください。
```

望ましい形は次のとおりです:

```text
ベースラインの再利用 → 焦点を絞った読み取り → patch → 検証 + diff
```

これは、Web planner がすべての編集を別の Coding Agent タスクに変えるのではなく、決定的な作業を直接実行できることを証明します。

## 3. 次に委任する価値のあるタスクを試す

独立した推論、並行した調査、またはより長い実行が本当に役立つ場合にだけ委任してください。例えば:

```text
この失敗しているテストの根本原因を調査し、最小限の修正を実装してください。無関係なファイルは変更せず、その後 Git diff とテストをご自身で再確認してください。
```

worker の最終的な文章は source of truth ではありません。Web planner は結果を受け入れる前に、リポジトリの状態、テスト、runtime の事実を読み直すべきです。Agent の選択、タイムアウト、代替 worker のルールは [Agent 委任](worker-fallbacks.md) にあります。

## 4. 長時間の Web 作業にだけブラウザ拡張を追加する

標準の MCP はファイル、Git、shell、Agent、複数の workspace をすでにカバーしています。拡張を追加するのは、次のいずれかが特に必要なときです:

- ローカルの `working / progress / settled` イベントを正しい Web 会話へ返す。
- ページの復旧と長い会話の handoff（引き継ぎ）。
- Chrome Side Panel での workspace、pane、Agent の可視化。
- Queue。現在の返信が終わった後に、明示的な次ターンのユーザー指示を送信します。

初回使用時は Auto をオフのままにし、binding と live 状態を手動で確認してください。製品概要は [ブラウザ拡張](extension.md)、戻り経路は [ブラウザ Continuity](browser-continuity.md)、Side Panel の操作は [ブラウザ Control Center](browser-control-center.md) を参照してください。

## 5. 最初の体験として成功と言える条件

最低限の受け入れ条件は次の四つすべてです:

1. Web AI が実際の Herdr 作業現場とリポジトリを読み取れる。
2. 小さな決定的編集が検証され、実際の Git diff に見える。
3. 委任が有用な場合に、Web planner が worker の結果を独立に検証する。
4. 拡張が有効な場合、長いタスクが元の mutation を再生することなく、正しい会話へ安全に戻れる。

ここまででインストールは完了です。日々のワークフローは [ベストプラクティス](best-practices.md)、システムモデルは [アーキテクチャ](architecture.md) に進んでください。
