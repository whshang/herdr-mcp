### 2026-09-14 — DEV sync protected source identity: two-phase broker implementation

Branch `fix/v1-dev-source-identity-broker-20260914` (off `dfd3a62e`) closes the audit's `fix/v1-dev-sync-tcc-git-20260912` gap in two phases.

Phase 1, broker: `tcc_broker::BROKER_COMPAT_REVISION` moves 2 → 3 to declare the new capability, and the stable broker's existing `git` operation gains `action=identity` — fixed `rev-parse HEAD` / `rev-parse --abbrev-ref HEAD` argv, no caller-supplied Git argument, the same `fs_security` managed-root and secret-path validation as every other operation, and a structured result (`commit` full object id, `branch` or null, `detached`). `installed_supports_git_identity(config_dir)` fails closed when the installed revision is missing or older.

Phase 2, dev sync: for a checkout whose Git metadata is privacy-protected (a protected folder, or a `.git` marker pointing into one) `source_identity` calls the broker only. Commit and branch come from `identity`, dirtiness from the existing `status` operation, and the DEV target version from the two manifests that can carry the `herdr-mcp` package version through the existing `fs_read` operation. It never shells `git`, never names a `gitdir` path, and never parses `commondir`/loose refs/`packed-refs`. A missing socket, snapshot, identity-capable broker, or any broker failure is a hard error carrying the established upgrade flow: `herdr-mcp permissions setup --upgrade-broker`, grant Full Disk Access to the stable broker, `herdr-mcp permissions verify`, then re-run `dev sync`. `dev sync` never installs, authorizes, or activates anything. Non-protected checkouts keep the existing direct path.

Evidence: a broker built from this branch answers `git action=identity` with the exact `rev-parse HEAD` object id for the linked-worktree root (`82e26baaf18c075f9d16d1f3fd4c968c99127220`) and for a scratch repository (`23fb827fd56205e96844c5a05b3de1cc6463934c`), while `fs_read` of a worktree `gitdir` on a worktree-only snapshot is still refused `outside_managed_roots` — the failure mode that made the superseded `fs_read`-based design unusable. Against the machine's actual active broker (sha256 `e33beb81…`, revision 1) the candidate runtime fails closed with the upgrade hint under both a real `PATH` and a `PATH` that breaks direct `git`/`cargo`, and candidate `tcc-broker status` reports `candidate_revision: 3`, `update_available: true`, `update_requires_reauthorization: true`. ### TCC docs adjudication for `preserve/main-dirty-20260911-2358`

The preserved commit's only unreviewed deltas were four docs lines in `docs/i18n/{en,zh-CN}/{install,agent-install}.md`. Current `main` code supports the preserved wording's substance:

- The stable broker's request surface is a fixed allowlist of eight protected-folder file/Git operations (`crates/herdr-mcp/src/tcc_broker.rs` `ALLOWED_OPS`: `fs_read`, `fs_list`, `fs_grep`, `fs_image`, `fs_edit`, `fs_write`, `fs_patch`, `git`), dispatched only to those bounded functions. It is not an arbitrary shell/exec surface, so it is not a general pane shell executor.
- macOS TCC responsibility follows the execution host. `macos_permissions.rs` states protected I/O "belongs to the stable broker (or to the Herdr terminal that already owns the user's interactive workspace)", and `tcc_broker::run_herdr_host` deliberately keeps the managed `herdr server` as a normal descendant of the stable broker so its panes/Agents reuse the broker identity; a Herdr host started outside that managed path keeps its own host's TCC boundary.

Therefore the earlier claim that the broker is the *single* TCC responsibility boundary "for MCP and native Herdr panes/worktrees" was overbroad. The four docs lines are corrected: `docs/i18n/{en,zh-CN}/install.md` now state the fixed eight-operation file/Git allowlist and the execution-host rule (the managed `herdr server` reuses the broker identity; any other Herdr host keeps its own TCC boundary), and `docs/i18n/{en,zh-CN}/agent-install.md` carry the compact equivalent — the broker's TCC is MCP file/Git, not pane shell, and panes follow their execution host's TCC — kept short to satisfy that document's existing compact-contract budget (the `--upgrade-broker` migration flag remains documented in `install.md` and `cli-reference.md`). With that correction the preserved ref holds no unreviewed content and is retireable.
