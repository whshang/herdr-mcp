# Herdr-MCP 1.0 Alpha 7 — Grok provider vertical

Add Grok as the next Browser Registry provider vertical by reusing the Browser Registry, Work Memory, consent, generation fencing, idempotency, optional-origin permission lifecycle, and single-attempt browser actuation contracts established by Alpha 4–6.

Alpha 7 is not a generic provider-framework rewrite. Grok-specific URL, DOM, and account details stay in `extension/content/injector/grok.js`; browser authority and dispatch semantics stay provider-neutral.

## Scope

Alpha 7 includes:

- experimental provider token `grok`, disabled by default;
- exact optional origin `https://grok.com/*` only;
- concrete Grok session identity for both direct `https://grok.com/c/<chat_uuid>` chats and project chats at `https://grok.com/project/<project_uuid>?chat=<chat_uuid>`;
- no support for `/imagine`, root pages, x.com, or non-concrete conversation routes;
- opaque account identity derived from the same-origin authenticated session `userId` and SHA-256 hashed in-page before Browser Registry;
- Browser Registry topology `account -> session` for direct chats and `account -> space(project) -> session(chat)` when Grok exposes a concrete project UUID;
- listener-less tab recovery through the existing bounded URL recovery path;
- the existing typed `herdr_mcp.browser_dispatch.submit` single-attempt actuation path;
- targeted adapter, permission, Browser Registry, recovery, i18n, and regression tests;
- real signed-in Grok browser UAT after the local contract is green.

Alpha 7 does not include:

- x.com integration;
- Grok Imagine or media-generation surfaces;
- generic Page Assist / arbitrary page control;
- Grok-specific runtime, Edge, reasoning, apps, retry, or postcondition branches;
- production Edge deployment or caller-grant mutation;
- ChatGPT/Claude/Gemini permission migration;
- contract epoch changes.

## Identity

The canonical direct-chat shape is:

```text
https://grok.com/c/<chat_uuid>
```

The canonical project-chat shape is:

```text
https://grok.com/project/<project_uuid>?chat=<chat_uuid>
```

The native session identity is always the lowercase chat UUID. For project chats, the lowercase project UUID is the Browser Registry `space` native identity. Unrelated query parameters are removed from the canonical key, and project routes fail closed unless there is exactly one valid `chat` UUID.

Account identity is derived from the signed-in same-origin session response and returned only as:

```text
grok-account-sha256:<64 lowercase hex>
```

Raw account identifiers must not be sent to Browser Registry or portable Work Memory evidence.

## DOM boundary

The adapter uses bounded semantic selectors only. Initial selectors are limited to the currently evidenced Grok chat surface:

- composer: `data-testid="chat-input"` + ProseMirror textbox, with bounded semantic fallbacks;
- user turns: `data-testid="user-message"`;
- assistant turns: `data-testid="assistant-message"`;
- send: `button[data-testid="chat-submit"]` first, with bounded localized submit/send fallbacks;
- generation: visible stop control or bounded busy state.

When a turn node does not expose its own stable message id, the adapter may recover the nearest bounded `id="response-<uuid>"` ancestor and derives a role-scoped `<uuid>-user` / `<uuid>-assistant` observation id. It does not persist DOM paths or selectors as resource identity.

Alpha 7 must fail closed when these selectors do not resolve. It does not introduce arbitrary CSS/XPath input from callers, page eval, CDP, cookies, storage scraping, or cross-origin DOM control.

## Permission boundary

Grok remains experimental and disabled by default.

Enabling it from Options requests only:

```text
https://grok.com/*
```

The dynamic content script contains the Grok adapter, shared performance/HUD code, and `wake.js`. It does not inherit the z.ai/DeepSeek JSON bridge.

Disabling Grok unregisters the dynamic content script. Registration while disabled fails closed before Browser Registry mutation.

The manifest does not add Grok to static `host_permissions`.

## Browser Registry

A concrete signed-in direct Grok chat observes exactly:

```text
provider: grok
  -> account
     -> session
```

A concrete signed-in Grok project chat observes exactly:

```text
provider: grok
  -> account
     -> space(project)
        -> session(chat)
```

The project space is created only from the real `/project/<uuid>?chat=<uuid>` URL identity. No project/space is synthesized for direct `/c/<uuid>` chats.

Provider/session/account observation reuses the existing observation generation and endpoint ownership rules. A newly registered dynamic script reloads an already-open complete Grok tab once; listener-less recovery reuses the same bounded reload path as the other Browser Registry providers.

## Dispatch

Grok reuses `herdr_mcp.browser_dispatch.submit` through the same single-attempt page actuation path as ChatGPT/Gemini/Claude.

Alpha 7 does not add a Grok-specific mutation branch. The operation keeps:

- expected observation-generation fencing;
- exact conversation-key fencing;
- empty-composer / no-generation preconditions;
- no `reasoning_effort` and no `required_apps` in this vertical;
- one submission attempt;
- provider-neutral DOM postcondition evidence.

## Test-first evidence

The initial adapter test failed because no `grok.js` adapter existed.

After adding the adapter:

- URL/session identity: GREEN;
- bounded composer/message/generation selectors: GREEN;
- same-origin session userId hashing: GREEN;
- provider-neutral account/dispatch assertion remained RED until shared wake plumbing admitted `grok`.

Background Browser Registry tests then produced exactly eight Grok failures before plumbing:

- no dynamic script registration;
- no exact-origin script contract;
- disabled registration did not fail closed;
- re-enable did not register;
- first registration did not reload an open Grok tab;
- listener-less recovery did not identify Grok;
- no opaque browser session/generation returned;
- no `account -> session` observation.

All eight are GREEN after the provider-neutral background plumbing was extended.

Options/packaging smoke then had exactly one Grok failure before the UI/config surface was added; it is GREEN after adding the default-off Grok switch and exact optional-origin request.

A later live-contract audit against a recently exercised Grok browser adapter found two additional mismatches in the first implementation: the current primary submit control is `data-testid="chat-submit"`, and stable turn ids are commonly carried by the nearest `response-<uuid>` ancestor rather than the message node itself. Two regression assertions were added first and failed exactly on those paths; after the adapter-only correction the Grok suite is 5/5 GREEN. Claude/Gemini/Grok focused adapter regression, background bind, extension smoke, and `git diff --check` remain GREEN.

Subsequent real-browser evidence showed that Grok project conversations use `/project/<project_uuid>?chat=<chat_uuid>` rather than `/c/<uuid>`. Regression coverage was added before implementation: the adapter project-route identity assertion failed while the existing four Grok assertions stayed green, and background recovery/registration/topology added exactly three project-route failures. The parser now canonicalizes the project route, uses `chat` as session identity, uses the path UUID as the real project space identity, and keeps direct `/c/<uuid>` behavior unchanged.

## Acceptance

Local acceptance requires:

1. `node --test tests/grok-adapter.test.mjs` passes 5/5;
2. Grok dynamic permission lifecycle and listener recovery pass in `background_bind_test.mjs`;
3. Browser Registry observes `account -> session` for direct chats and exactly `account -> space(project) -> session(chat)` for concrete project chats;
4. disabled Grok registration fails closed before Browser Registry mutation;
5. Options requests only `https://grok.com/*` for Grok;
6. Grok stays outside the JSON bridge;
7. ChatGPT/Gemini/Claude existing extension paths remain green;
8. `scripts/release-gate.sh node` passes;
9. `scripts/release-gate.sh hygiene` passes;
10. `git diff --check` passes.

Real-browser acceptance requires one signed-in Grok concrete chat tab, prioritizing the currently observed `/project/<project_uuid>?chat=<chat_uuid>` shape, to prove the live URL, composer, turn selectors, account identity source, project/session topology, and sole active endpoint observation. A fenced/idempotent real dispatch remains dependent on the production Browser Control Edge route and caller-grant surface; Alpha 7 must not deploy or widen production Edge merely to manufacture that evidence.
