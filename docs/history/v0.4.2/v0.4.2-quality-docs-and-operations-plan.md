## 1. Baseline inherited from v0.4.1

v0.4.1 establishes the baseline this plan must preserve:

- Rust runtime owns production MCP/service/updater/Link/Native Messaging paths;
- public MCP contract remains epoch 2 / 18 tools;
- `herdr-mcp scan` records evidence-backed client Agent capabilities without replacing Herdr's live-agent authority;
- Herdr remains authoritative for live agents (`agent.list` / snapshot), loaded detection manifests and supported agent start behavior;
- `herdr_inspect.capability_inventory.available_agents` exposes locally startable Agent kinds only after current visibility-policy filtering;
- Chrome Web Store identity has one machine-readable SSOT in `contracts/browser-extension-store.json`; the Store ID is not duplicated as a Rust source literal;
- normal Native Messaging install is Store-first; unpacked/dev identity requires an explicit maintainer override;
- Runtime GitHub Releases no longer distribute the browser extension;
- `bin/herdr-extension-host` is compatibility delegation to the Rust owner, not a second installer/broker;
- browser extension has its own release cadence and automatic Store update path;
- end-user browser docs are Store-first; historical unpacked installation is history/maintainer-only evidence.

Do not regress any of these boundaries in v0.4.2.

## 3. P0 — one authoritative release/test execution profile

### Problem observed during v0.4.1

The local pre-PR gate and GitHub CI were not initially identical. GitHub runs:

```text
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace
```

while a narrower local package-only gate initially passed. Managed Herdr execution also injects values such as `HERDR_MCP_PORT=8772`; a HOME-only Native Host UAT inherited a real `HERDR_MCP_CONFIG_DIR`, proving that test/release commands must not silently inherit production-scoped overrides.

### Required implementation

Create one maintainer-facing gate entrypoint (for example `scripts/release-gate.sh`; exact name may change after audit) and make both local release validation and CI consume the same command sequence.

It must cover at least:

- `cargo fmt --check`;
- `cargo clippy --workspace --all-targets --all-features -- -D warnings`;
- `cargo test --workspace`;
- Node build/tests;
- docs-site build;
- Edge tests;
- browser-extension smoke;
- package/shell/diff hygiene;
- release-surface / Store-identity contracts.

Define an explicit **release/test environment profile**. At minimum audit and deliberately scrub or set:

- `HERDR_MCP_PORT`;
- `HERDR_MCP_CONFIG_DIR`;
- `HERDR_MCP_INSTANCE`;
- `HERDR_EXTENSION_PATH`;
- `HERDR_EXTENSION_ORIGIN`;
- `HERDR_MCP_ROOT`;
- production contract/runtime overrides.

Do not globally remove production environment behavior from the runtime. The gate must isolate tests; runtime semantics remain explicit and backwards compatible.

### Parallel-test hardening

Audit tests that mutate process-global environment (`HOME`, `HERDR_MCP_*`). Prefer, in order:

1. dependency/path injection;
2. explicit fixture parameters;
3. a shared process-global test guard only when injection is impossible.

Do not hide flaky parallel behavior by globally forcing `--test-threads=1` unless a specific external dependency genuinely requires serialization.

### GitHub Actions maintenance

The v0.4.1 Release run emits GitHub's warning that `actions/checkout@v4` / `actions/setup-node@v4` still target deprecated Node.js 20 and are being forced onto Node 24. Audit the current recommended action versions and repository supply-chain policy, then upgrade/pin deliberately. Do not blindly float security-sensitive release actions.

### Acceptance

- one command reproduces CI locally;
- CI calls the same maintained gate or an exact shared script fragment;
- no release-only lint surprise after local PASS;
- environment-sensitive tests pass repeatedly under parallel execution;
- production config/native-host files are SHA-identical before/after isolated test/UAT runs;
- no new release workflow warning that is already actionable in the repository.

## 4. P0 — control-plane reliability blockers

The 2026-08-29 dogfood incident established a release-blocking failure class that v0.4.2 must close before execution-efficiency work is considered complete. These are reliability requirements, not speculative performance refactors.

### 4.1 Stable macOS code identity / TCC continuity

The current dogfood Rust runtime is linker/ad-hoc signed. Its designated requirement resolves to a code-directory hash, so every generation can present a different macOS identity even though `runtime/current/herdr-mcp` is a stable path. This can invalidate Documents/Desktop privacy authorization after updater activation.

Required implementation:

- tagged macOS release assets must be Developer ID signed with one stable explicit code identifier and stable Team identity;
- updater generations may remain content-addressed, but the signed designated requirement must remain stable across versions;
- CI/local development builds may remain ad-hoc and must report that condition explicitly rather than pretending to be production-signed;
- release verification must fail closed for a tagged macOS asset that lacks the expected stable identifier/Team identity/signature;
- GitHub/Sigstore provenance remains required and covers the final signed asset digest; code signing is an additional macOS runtime-identity layer, not a replacement for provenance.

Acceptance:

- two independently built/tagged macOS release versions satisfy the same intended Developer ID designated requirement identity;
- updater activation from version N to N+1 does not require a new Documents permission grant solely because the generation path/hash changed;
- `herdr-mcp doctor` exposes whether the running binary is production-signed, ad-hoc, unsigned, or unverifiable without leaking certificate material.

### 4.2 Herdr dependency supervisor and socket self-healing

Add an internal Herdr dependency supervisor. It must not add a 19th MCP tool or change contract epoch 2. The supervisor owns only the Herdr dependency lifecycle; `dev.herdr-mcp.server` continues to own the MCP runtime and `dev.herdr-mcp.health-watchdog` continues to own MCP HTTP-health recovery.

Required states must distinguish at least:

- `healthy`;
- `socket_missing`;
- `server_not_running`;
- `ping_timeout`;
- `snapshot_timeout`;
- `snapshot_unavailable`;
- `session_restore_blocked`;
- `recovery_cooldown`;
- `user_stopped`.

Required behavior:

- socket missing + no Herdr server -> single-flight bounded start/recovery when desired state is running;
- socket exists but bounded ping or snapshot cannot complete -> unhealthy, never reported merely as connected;
- reconnect/recovery uses bounded exponential backoff and a cooldown so one failure cannot create connection or process storms;
- only exact owned PID/process-group/socket identities may be terminated; never broad process-name matching;
- recovery must preserve persisted Herdr session files and fail closed as `session_restore_blocked` rather than deleting/replacing session state;
- bounded evidence records last transition, reason, attempt count, PID when owned, timestamps, and cooldown; no always-on analytics;
- explicit supervisor stop/disable records `user_stopped` and suppresses automatic restart until re-enabled/started.

Herdr 0.8.2 does not currently expose a durable API contract that distinguishes every native UI/TUI manual Quit from a crash. v0.4.2 must implement exact desired-state semantics for herdr-mcp-owned lifecycle commands and document the remaining upstream requirement for Herdr to expose a clean user-stop marker/event. Do not infer perfect manual-Quit intent from exit status alone.

Acceptance:

- missing socket + absent server recovers without duplicate Herdr processes;
- stale socket and ping/snapshot failures are classified explicitly;
- repeated failure does not monotonically increase Herdr-server FD count or accepted socket count;
- a failed recovery never mutates/deletes the saved session;
- non-Herdr socket/process ownership refuses mutation;
- explicit `user_stopped` prevents supervisor restart;
- supervisor status is visible through existing status/doctor/inspect metadata or maintainer CLI, without adding a public MCP tool.

### 4.3 Restore must degrade around Git discovery

Herdr session restore must not be globally blocked because one workspace cannot complete Git identity/metadata discovery. herdr-mcp already applies bounded Git topology probes; v0.4.2 must preserve that property and report degraded project metadata rather than treating it as transport failure.

The persisted-session hang observed with Herdr 0.8.2 is also an upstream Herdr issue. Prepare reproducible bounded evidence for the Herdr project: Git identity/discovery needs its own timeout and a per-workspace failure must degrade that workspace while allowing the rest of the session to restore. herdr-mcp must not claim that an upstream restore hang is fixed until a Herdr build containing that behavior passes UAT.

Acceptance:

- herdr-mcp Git topology discovery is bounded and reaps its child process group on timeout;
- one Git metadata failure leaves other current projects inspectable;
- doctor distinguishes Git/project-metadata degradation from Herdr socket/snapshot failure;
- upstream Herdr reproduction evidence contains the exact timeout/failure boundary without destructive session experiments.

### 4.4 Request child-process lifecycle and orphan diagnostics

Every request-scoped external child (`rg`, Git probes, schema/capability probes, test helpers where applicable) must have a bounded lifetime and an ownership model. The 2026-08-29 incident directly observed four `rg` processes surviving for minutes as children of the production herdr-mcp runtime after caller request timeouts.

Required implementation:

- direct-tool children run in an owned process group where supported;
- request timeout/cancellation terminates the exact owned group and synchronously reaps the direct child;
- output readers must not leave a child blocked on a full pipe;
- server startup may reap only persisted/marked children whose ownership can be proven; uncertain processes are diagnostics-only;
- bounded diagnostics include child kind, PID/PGID, age, command identity and lifecycle state;
- error text reports the actual configured timeout, never a stale hard-coded duration.

Acceptance:

- forced `rg`/Git timeout tests leave no live child/group after return;
- repeated timeout soak shows stable process and FD counts;
- server restart recovery never kills an unowned process;
- `herdr_exec` durable-session reaping behavior remains intact.

### 4.5 macOS privacy-permission doctor

On macOS, `herdr-mcp doctor` must run a bounded Documents access probe attributable to the herdr-mcp code identity. A privacy denial or blocked TCC request must not surface later as a misleading Git timeout or Herdr transport failure.

Required output includes explicit states such as:

```text
PASS macOS Documents permission
FAIL macOS Documents permission — macOS Documents permission unavailable
FAIL macOS Documents permission — probe timed out
```

The probe must be bounded, reaped on timeout, and skipped as not-applicable on non-macOS hosts. It must not enumerate or print document names/content.

Acceptance:

- readable `~/Documents` passes without exposing directory contents;
- `PermissionDenied` maps to `macOS Documents permission unavailable`;
- a blocked probe terminates within its budget and leaves no child process;
- doctor continues to report Herdr transport/snapshot health independently so TCC and transport failures cannot masquerade as each other.

### 4.6 Browser extension Store/Dev coexistence with one active owner

The browser extension has three legitimate installation/development paths:

1. normal users install the official Chrome Web Store build;
2. maintainers can explicitly enable a local Dev build from the CLI;
3. contributors can clone the repo, load `extension/` as an unpacked Chrome extension, then explicitly register that Dev identity with herdr-mcp.

Store and Dev extension packages may coexist in Chrome. **Herdr must still authorize exactly one active/default Native Messaging origin at a time.** Do not solve coexistence by putting both origins in one `allowed_origins` array: Chromium does not reliably append the caller origin when launching the host, so a multi-origin manifest would weaken owner attribution.

Required lifecycle:

```text
herdr-mcp native-host install
herdr-mcp native-host dev enable [PATH]
herdr-mcp native-host use store
herdr-mcp native-host use dev
herdr-mcp native-host dev disable
herdr-mcp native-host status
```

Rules:

- a fresh normal install remains Store-first;
- `dev enable [PATH]` derives the unpacked Chromium ID from the normalized extension path, remembers that Dev origin, and makes Dev active;
- `use store` makes Store active without forgetting the registered Dev origin;
- `use dev` reactivates the remembered Dev origin without requiring the Store extension to be uninstalled;
- `dev disable` clears the remembered Dev origin and returns Store to active ownership;
- the Native Messaging manifest always contains exactly one exact active origin;
- the remembered Dev candidate is owned wrapper metadata, so existing install/rollback fingerprints restore it byte-for-byte without adding a second state database;
- moving the unpacked directory changes its Chromium path-derived identity and therefore requires a new `dev enable`;
- the legacy `HERDR_EXTENSION_PATH=... herdr-mcp native-host install` path remains a maintainer compatibility entry, not the primary 0.4.2 lifecycle;
- an existing owned 0.4.1 Dev install upgrades without silently switching the active owner to Store;
- the 0.1.76+ extension asks the Native Host for an `identity` response; an inactive co-installed build is rejected by Chromium's exact-origin admission and enters standby before starting the shared stream/HUD control path. The Rust Native Host also re-checks the currently registered managed origin before requests and on a 1-second fence while a persistent stream is open, so an old connection cannot retain ownership after Store/Dev switching. Missing/old Native Host behavior remains distinguishable from explicit standby so offline diagnostics still work.
- switching the active owner does not mutate already-injected content scripts in-place; refresh already-open supported Web AI tabs after `use store|dev` so the newly active 0.1.76+ build acquires page ownership and the former owner exits at injection time.
- collision-free Store+Dev coexistence is a 0.1.76+ browser contract on both installed builds. The already-submitted 0.1.75 Store candidate remains unchanged and is validated Store-only first; after that review/install UAT, a normal 0.1.76 Store update can carry the coexistence gate.

Acceptance:

- Store and one Dev build can both remain installed in Chrome while `native-host status` reports one `active_channel`;
- Store → Dev → Store switching is transactional and rollbackable;
- every managed browser Native Messaging manifest has exactly one `allowed_origins` value after every switch;
- `status` reports the official Store ID, active channel, whether Dev is enabled, and the remembered Dev ID/origin;
- inactive 0.1.76+ build does not start the local shared stream or render the operational HUD;
- a page refresh after owner switching results in exactly one build claiming HUD/Queue/page listeners;
- Store review/package lifecycle stays independent from Rust runtime release cadence; the already-submitted 0.1.75 Store candidate is not mutated in place.

## 5. P1 — direct execution vs Agent delegation efficiency

The desired default is:

- deterministic filesystem/Git/status/build/test work -> direct `herdr_fs_*`, `herdr_git`, `herdr_exec*`;
- independent, reasoning-heavy or long-running work -> Agent delegation;
- never launch an Agent merely to run a trivial `git status`, `rg`, one-file edit or short test.

### Audit first

Measure before changing behavior:

- `herdr_inspect` latency and payload size;
- `herdr_git` status/diff/log latency;
- `herdr_exec` short-command latency;
- `herdr_exec_start/read` startup/reap latency;
- command-size / shell-delivery behavior: oversized or malformed command payloads must fail fast with an explicit error rather than leave a zero-output session running with no useful child process;
- repeated project-topology derivation cost;
- repeated full snapshot vs incremental/since cost;
- time from Agent prompt -> useful first result;
- duplicate work caused by unnecessary delegation.

Store bounded benchmark evidence under `docs/benchmarks/`.

### Optimization principles

- reuse current SnapshotCache/project topology instead of creating parallel caches;
- avoid recomputing stable Git/worktree topology multiple times inside one logical request when a version/sequence can prove it unchanged;
- use `herdr_since` / state sequence where it can replace a second full inspect;
- fix utility-pane readiness/reaping if a completed wrapper unnecessarily keeps the pane unavailable; never bypass a genuinely active interactive foreground child;
- preserve explicit target/pane/workspace safety checks.

### Acceptance

Define targets only after recording the baseline. The goal is measurable lower p50/p95 planning latency without weakening freshness or mutation safety.

## 6. P1 — Agent inventory refresh and dispatch quality

v0.4.1 records installed/startable Agent capability evidence. v0.4.2 should make that evidence useful without turning every inspect into an expensive scan.

### Authority hierarchy must remain

1. **Live instance state:** Herdr `agent.list` / snapshot.
2. **Detection support:** Herdr `server.agent_manifests`.
3. **Startable kinds:** the installed Herdr CLI's own declaration.
4. **Local executable/version/headless evidence:** herdr-mcp bounded probe.

Do not copy a static list of Agent kinds into herdr-mcp.

### Refresh policy

Audit current inventory staleness semantics and add a bounded policy such as:

- if inventory missing: recommend or perform one lightweight refresh at an appropriate lifecycle point;
- if fresh: read persisted inventory without spawning probes;
- if stale: refresh in a bounded/background-safe way;
- deep/version/headless probes remain explicit or TTL-controlled;
- do not full-scan on every `herdr_inspect`.

Consider install/update/first-use refresh only after measuring cost and failure behavior.

### Dispatch inputs

Any automatic recommendation/dispatch should consider:

- explicit user target first;
- current Agent visibility policy;
- live status (`idle/working/blocked/done`);
- workspace/project locality;
- recorded executable/startability evidence;
- task type and mutation risk;
- expected latency/cost;
- available parallelism.

Do not silently replace an explicit target with a cheaper/lower-quality Agent.

### Acceptance

Add benchmark scenarios proving that:

- trivial deterministic tasks stay direct;
- an appropriate idle worker is preferred for a genuinely delegatable task;
- busy/unavailable/hidden workers are not selected;
- capability evidence enriches dispatch but live Herdr state remains authoritative;
- stale inventory cannot create a false "available" claim.

## 7. P1 — Progressive Skill disclosure: measure, then decide default

Do not redesign the Skill architecture from scratch. v0.4.2 should evaluate the existing progressive implementation with real multi-Agent evidence.

### Measure

Compare progressive vs compatibility/legacy path for representative tasks:

- bootstrap bytes/tokens;
- skill bodies loaded per task;
- first-use latency;
- immutable skill-cache hits;
- capability refresh behavior;
- dispatch correctness;
- fallback behavior when network skill source is unavailable.

### Desired disclosure model

Initial disclosure should contain only the minimal planner policy, catalog/pointers and current capability summary. Load detailed skill bodies only when the selected task/tool path needs them.

Keep these invariants:

- immutable identity by URI + digest;
- live capability refresh does not change skill text identity;
- unknown/digest mismatch fails closed;
- public MCP tool catalog remains 18 tools.

### Default-on decision

Run real multi-Agent UAT before changing the default of `HERDR_MCP_PROGRESSIVE_SKILLS`.

If progressive mode is consistently better and no compatibility blocker remains:

- make it default in v0.4.2;
- retain a bounded rollback/compatibility escape hatch for at least the migration window;
- update docs/AGENTS/SKILL wording.

If evidence is mixed, keep the flag and record the blocker instead of forcing the migration.

## 8. P1 — safe resource lifecycle / cleanup planning

The current conservative behavior (do not auto-delete uncertain resources) is correct. Optimize only the accumulation of resources that are provably dead.

### Inventory before implementation

Audit:

- Herdr workspaces/panes with no active Agent;
- done/idle Agents and whether the upstream Herdr lifecycle already owns their cleanup;
- closed `herdr_exec_start` session metadata retention;
- local worktrees;
- local/remote merged branches;
- temporary UAT directories/processes;
- stale release staging/download assets.

Prefer upstream Herdr cleanup APIs when they exist.

### Safe cleanup predicate

A worktree/branch must never be proposed for destructive cleanup unless all applicable conditions are true:

- clean working tree;
- no unpushed/unmerged commit;
- branch merged into the intended base or explicitly marked obsolete;
- no open PR;
- no working Agent/process;
- no active Herdr workspace dependency;
- not main/current release/recovery state;
- not referenced by runtime/update/rollback evidence.

### Product shape

Do **not** add a new public MCP tool just for cleanup. Prefer a maintainer CLI/dry-run planner or existing Herdr APIs. Default behavior must be inventory/dry-run; destructive apply requires explicit intent.

### Acceptance

- repeated cleanup is idempotent;
- dirty/unmerged/active resources are always retained with a reason;
- completed resources can be reclaimed without manual forensic work;
- no process is killed by broad name matching;
- exec child process groups are reaped and no orphan accumulation appears in soak tests.

## 9. P1 — stability and bounded observability

The Link/Native IPC/browser connection stack is already mature; do not rewrite it without evidence.

Run targeted soak/UAT for:

- Link reconnect/backoff/silence;
- runtime restart and generation change;
- Chrome MV3 service-worker restart;
- one shared extension SSE/native stream with multiple workspace bindings;
- Native Host runtime sync after updater apply/rollback;
- long exec start/read/kill/reap;
- browser handoff/Auto over a long-lived tab;
- process count, FD count and bounded state-store growth.

Record only bounded operational evidence. Keep Core always on, Recent Activity bounded/default-on, Analytics explicit opt-in. Do not introduce always-on telemetry to solve a development observability problem.

Only promote a stability optimization if the soak/user evidence identifies a real failure mode.

Define one job per page:

Avoid hard-coded patch versions in ordinary instructions unless the exact version matters historically. Prefer "current stable" / stable channel and derive machine facts at build/test time where practical.

At minimum ensure current docs do not remain stuck on `v0.4.0` after `v0.4.1` becomes stable.

Do not rewrite historical evidence to new versions.

## 11. P0/P1 — documentation-site wording and information architecture

The site currently has **no real docs landing page**: `/docs/` chooses a locale and forwards directly to the first document, while each locale entry also forwards into the document sequence. v0.4.2 should replace this with a real product-oriented landing page.

### Site user model

The primary audience is a user who already has a Coding Agent and wants Herdr/herdr-mcp working with minimal conceptual overhead.

The first screen should answer only:

1. What is herdr-mcp?
2. What should I copy to my Coding Agent?
3. At which two points will I need to take over?
4. What can I do after installation?

Do not lead with GA gates, UAT, Runtime A/B, contract internals or maintainer history.

### Homepage redesign

Create real locale homepages (for example `/docs/en/` and `/docs/zh-CN/`) instead of redirecting immediately to `quick-agent-install`.

Recommended structure:

1. **Hero**
   - one-sentence product value;
   - one primary CTA: "Install with my Coding Agent" / "让 Coding Agent 帮我安装";
   - copyable install prompt;
   - secondary links only: Manual install / Learn how it works.
2. **What the Agent will do**
   - install/check Herdr;
   - install stable herdr-mcp from GitHub Releases;
   - deploy/configure Edge + Link;
   - verify runtime/doctor;
   - explicitly show the two user handoff points: Cloudflare login/token and ChatGPT Connector setup.
3. **Choose your path**
   - Agent-assisted install (recommended);
   - Manual install;
