# Herdr MCP v0.4.6

v0.4.6 is a focused authentication and onboarding security hotfix. It does not add new public workstation tools and does not include the separate 1.0/WebChat work.

## Upgrade

From v0.4.5:

```bash
herdr-mcp update
```

Then verify:

```bash
herdr-mcp version
herdr-mcp status
herdr-mcp service status
herdr-mcp link status
```

The expected runtime version is v0.4.6.

## Main changes

- New MCP/OAuth Connectors no longer receive an authorization grant merely by completing client registration and PKCE. A new Connector enters a short-lived pending state and must be explicitly approved by the Worker fleet control plane. Herdr does not have an owner/member device hierarchy: any currently enrolled device can approve locally with `herdr-mcp connector approve <approval-request-id>`, and an explicitly approved Connector or Worker operator credential can perform the same fleet administration through the existing private `herdr_call` surface. Pre-v0.4.6 OAuth tokens that never went through explicit approval retain ordinary MCP compatibility but do not silently gain fleet-admin authority. [PR #303](https://github.com/whshang/herdr-mcp/pull/303) [PR #304](https://github.com/whshang/herdr-mcp/pull/304)
- Connector approval is bound to the request, client, redirect URI, resource, scope, and PKCE challenge; the six-digit approval code is attempt-bounded and its durable verifier is protected with the deployment secret rather than a snapshot-brute-forceable plain digest. The code is entered interactively and is never accepted on CLI argv. [PR #303](https://github.com/whshang/herdr-mcp/pull/303)
- Connector grants can be explicitly revoked. Revocation leaves a durable grant tombstone, fences already-issued v0.4.6 access/refresh credentials, and deletes matching stored token records. The same revoke path can create a tombstone for a pre-v0.4.6 client, so an operator can actually terminate an old Connector instead of leaving it permanently grandfathered. [PR #303](https://github.com/whshang/herdr-mcp/pull/303) [PR #304](https://github.com/whshang/herdr-mcp/pull/304)
- GitLab CI and other unattended MCP callers now have a first-class Automation Client credential instead of relying on one fleet-wide static bearer. Each project/environment can have its own named `svc_...` client, one-time `client_secret`, short-lived `client_credentials` access tokens (maximum one hour, no refresh token), bounded issuance metadata, independent rotation, and immediate revocation. Automation Clients have ordinary MCP access but never fleet-admin authority. Long-lived secrets are created/rotated from an enrolled-device CLI and are not returned by WebChat inventory. [PR #304](https://github.com/whshang/herdr-mcp/pull/304)
- `herdr-mcp worker pair` now fails closed with a semantic enrollment error on a genuinely fresh machine instead of leaking a missing `dev.herdr-mcp.link-prod.plist` / `Io(NotFound)` failure. Pairing creation is a Worker fleet-admin action: run it from any already-enrolled device or an explicitly approved WebChat. A fresh machine joining an existing fleet uses `worker connect`; the first machine follows the first-Worker Cloudflare bootstrap path. Existing config-based enrollment and legacy Link-plist installs remain compatible. This fixes the low-level failure reported in Issue #302, while the broader one-command first-Worker bootstrap request remains open. [PR #303](https://github.com/whshang/herdr-mcp/pull/303) [PR #304](https://github.com/whshang/herdr-mcp/pull/304) [Issue #302](https://github.com/whshang/herdr-mcp/issues/302)
- Local authentication boundaries are now documented explicitly: the loopback TCP endpoint `http://127.0.0.1:8772/mcp` remains bearer-authenticated, while the official browser extension never receives that bearer and uses the origin-checked Native Messaging → mode-`0600` Unix socket trusted IPC path instead. [PR #304](https://github.com/whshang/herdr-mcp/pull/304)

## Known issues

- [Issue #302](https://github.com/whshang/herdr-mcp/issues/302) remains open for the broader first-Worker onboarding goal: v0.4.6 prevents a fresh machine from incorrectly entering `worker pair` and leaking a missing-Link implementation error, but it does not yet collapse first-Worker Cloudflare bootstrap/readiness into one fully automatic command.

## Compatibility

- Workstation Runtime Execution Contract remains epoch 2 / 18 public tools.
- Public ChatGPT contract remains epoch 3 / 19 actions; Connector administration uses private methods under the existing `herdr_call` surface.
- Existing v0.4.5 Worker/device credentials, Link configuration, Custom Domain, Native Messaging integration, browser extension installation, and local runtime configuration remain compatible.
- Browser extension versioning remains independent; v0.4.6 does not require an extension update.
