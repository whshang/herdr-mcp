# Herdr MCP v0.4.9

v0.4.9 is a bounded migration bridge for existing v0.4.8 installations. It remains on the v0.4.x Runtime Execution Contract and durable state schema so the immutable v0.4.8 updater can verify and launch it. It is not a new long-lived product baseline and does not introduce 1.0 features into the 0.4.x service.

## Upgrade from v0.4.8

The ordinary user action is exactly:

```bash
herdr-mcp update
```

Do not download or run v0.4.9 manually. The v0.4.8 foreground updater verifies the v0.4.9 release manifest and artifact, then launches v0.4.9 only as the detached worker of that same durable update job. On the successful path the bridge is never installed as the production service.

The bridge discovers the highest attested stable Runtime release that is explicitly compatible with the qualified v0.4.8 → 1.0 boundary: durable state schema 15 and Runtime Execution Contract epoch 4 / 18 tools with the frozen v4 contract hash. It downloads and probes that final Runtime before any service mutation, then invokes the final Runtime's existing `update major-apply`. At that moment the active source is still the exact v0.4.8 service, so the major-upgrade rollback set contains the exact v0.4.8 executable and a final consistent schema-5 SQLite snapshot rather than the bridge.

After the Runtime migration succeeds, the same update job invokes the newly active Runtime's `worker update`. Cloudflare authorization uses the normal browser device flow and updates the health-proven existing Worker in place. Worker name/public origin, Durable Objects, secrets, known optional bindings, enrolled devices, OAuth issuer and Connector records are preserved. The user does not run first-Worker bootstrap, re-pair the device, or re-add ChatGPT.

If Cloudflare authorization takes longer than the v0.4.8 foreground updater's bounded watch, the detached bridge continues the same durable update job; a second update command is not required. If Runtime migration commits but Edge reconciliation fails, the job records the exact recovery action `herdr-mcp worker update` and keeps `herdr-mcp update major-rollback` available.

After the job completes, verify the active final Runtime rather than expecting v0.4.9 to be installed:

```bash
herdr-mcp version
herdr-mcp status
herdr-mcp service status
herdr-mcp link status
herdr-mcp doctor
```

## Main changes

- Add the one-time 0.4.x migration worker that delegates schema migration to the verified final 1.0 Runtime instead of installing v0.4.9 as a service. [PR #534](https://github.com/whshang/herdr-mcp/pull/534)
- Pin the bridge to the qualified schema-15 / Runtime epoch-4 / 18-tool contract identity. Future incompatible contract or schema releases are not silently crossed. [PR #534](https://github.com/whshang/herdr-mcp/pull/534)
- Preserve the v0.4.8 updater's existing manifest, artifact SHA-256 and GitHub/Sigstore attestation checks for the bridge itself; the bridge independently verifies the final Runtime manifest and binary before mutation. [PR #534](https://github.com/whshang/herdr-mcp/pull/534)
- Keep the original v0.4.8 update job as the sole durable user-visible update transaction and report migration / Cloudflare reconciliation progress through that job. [PR #534](https://github.com/whshang/herdr-mcp/pull/534)

## Known issues

- The one-command path is supported only on platforms where the qualified major migration exists (macOS and Linux). Windows remains outside this schema-5 major migration bridge.
- Real end-to-end publication acceptance requires both the immutable v0.4.9 release and a stable 1.0 Runtime release with `runtime-manifest.json`; source/unit qualification alone does not substitute for that published-artifact UAT.

## Compatibility

- Workstation Runtime Execution Contract remains **epoch 2 / 18 public tools** for the bridge binary itself.
- Public Edge contract and user Worker are not changed by installing the bridge because the bridge is not activated as the production service.
- Durable state remains **schema 5** until the verified final 1.0 Runtime performs `major-apply`.
- The successful final state preserves the existing Worker/OAuth/Connector/device identities and moves Runtime state to schema 15.
