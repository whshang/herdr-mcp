# Herdr MCP v1.0.3

v1.0.3 是 1.0 稳定线的 major-upgrade hotfix，修复早期 v0.4.x 安装（用 wrangler 模板部署自有 Cloudflare Worker、未登记 device id 的单设备安装）经 v0.4.9 migration bridge 升级到 1.0.x 时无法完成、以及失败回滚后丢失本机配置的问题。Runtime state schema、执行契约、Edge contract、provider 范围和 Browser Extension 版本均不变。 [PR #566](https://github.com/whshang/herdr-mcp/pull/566)

## 升级

所有受支持的旧版本继续只使用标准命令：

```bash
herdr-mcp update
```

- v0.4.3 / v0.4.8 等 schema 5 安装不需要逐版本升级；updater 会先进入 v0.4.9 migration bridge，再选择当前 stable v1.0.3 Runtime。 [PR #566](https://github.com/whshang/herdr-mcp/pull/566)
- 已安装 v1.0.0 / v1.0.1 / v1.0.2 的用户走正常同 schema verified update。 [PR #566](https://github.com/whshang/herdr-mcp/pull/566)
- 升级过程中若浏览器弹出 Cloudflare 授权页面，请本人批准；该步骤原地更新已有 Worker，不需要重新 pair device、重建 Worker 或重新添加 ChatGPT Connector。 [PR #566](https://github.com/whshang/herdr-mcp/pull/566)

升级后验证：

```bash
herdr-mcp version
herdr-mcp status
herdr-mcp doctor
```

成功后应看到 v1.0.3、schema 15、健康的 service / local MCP，且 Link 在线。

如果之前用 v1.0.1 / v1.0.2 升级失败并被回滚：先确认 `~/.config/herdr-mcp/config.toml` 是否仍存在。若只剩 `config.toml.migrated`，说明旧版 1.x 已把 0.4.x 配置改名，当前 0.4.x 正以默认配置运行；v1.0.3 在大版本回滚时会自动恢复它，也可以在升级前手动执行 `cp -p ~/.config/herdr-mcp/config.toml.migrated ~/.config/herdr-mcp/config.toml`。

若 v1.0.3 升级仍然失败，完整失败原因会保存在 `~/.config/herdr-mcp/major-upgrade-last-failure.log`，请附上该文件内容反馈。

## 主要变更

- `worker update` 可以原地更新早期 wrangler 模板部署的 Worker：`/health` 返回通用 `service: "herdr-edge"` 时，仅在 workers.dev 域名下由域名解析真实脚本名，自定义域名继续拒绝；未登记 device id 的单设备机器，只有当本机 production Link 的 `HERDR_WORKSTATION_ID` 与该 Worker 的 `DEFAULT_WORKSTATION_ID` 完全一致、并经 Cloudflare 实时配置复核后才允许更新；`DEFAULT_WORKSTATION_ID` 原值保留，`EDGE_PROJECT` 收敛为脚本名。普通 1.x Worker 的严格身份与配置校验不变。 [PR #566](https://github.com/whshang/herdr-mcp/pull/566)
- 修复静默成功：Worker 地址只记录在 production Link `HERDR_EDGE_URL` 中时，`worker update` 以前会返回 `worker_update_skipped` 并被 migration bridge 视为成功，导致本机已升到 1.x 而旧 Worker 未更新、Link 无法连接；现在会回退读取该地址并执行真实更新。 [PR #566](https://github.com/whshang/herdr-mcp/pull/566)
- 1.x 迁移配置到 `config.json` 时不再改名或改写 0.4.x 的 `config.toml`；大版本回滚在恢复旧 Runtime 前，会从 `config.toml.migrated` 恢复被 v1.0.0–v1.0.2 改名的配置（不覆盖已有文件、拒绝符号链接、0600 原子写入）。 [PR #566](https://github.com/whshang/herdr-mcp/pull/566)
- `update major-apply` 失败时把完整原因写入 `~/.config/herdr-mcp/major-upgrade-last-failure.log`（0600，仅保留最近一次），弥补 v0.4.8 updater 只保留 512 字节 job detail、bridge 会删除临时日志的问题；install 报告成功但 state 未迁移时不再误报为 `ExitCode(0)`。 [PR #566](https://github.com/whshang/herdr-mcp/pull/566)
- major migration 在核心 Runtime/schema/service 已提交后，Herdr supervisor、production Link generation reconcile、native-host 同步等可修复 sidecar 失败改为可恢复警告，不再错误整体回滚；普通 `service install` 继续严格。 [PR #561](https://github.com/whshang/herdr-mcp/pull/561)

## 已知限制

- 未登记 device id 的旧单设备安装，其 Worker 身份识别目前只覆盖 macOS production Link；Linux 上此类安装的 `worker update` 行为与 v1.0.2 相同。 [PR #566](https://github.com/whshang/herdr-mcp/pull/566)
- 使用自定义域名、且 `/health` 仍返回通用 `herdr-edge` 的旧 Worker 无法安全确定 Cloudflare 脚本名，`worker update` 会拒绝并且不做任何修改。 [PR #566](https://github.com/whshang/herdr-mcp/pull/566)
- 已处于 v0.4.9 运行态的机器，前台 `herdr-mcp update` 只读取 legacy manifest，无法自行发现 1.x；此类机器需要按支持指引恢复。 [PR #566](https://github.com/whshang/herdr-mcp/pull/566)
- Windows x86_64 / ARM64 仍属于 Candidate 支持；Browser Extension 继续独立版本化，本次 Runtime patch 不升级扩展，仍为 **0.1.133**。

## 兼容性

- Workstation Runtime Execution Contract：epoch **4 / 18 tools**。 [PR #566](https://github.com/whshang/herdr-mcp/pull/566)
- Durable Runtime state：schema **15**。 [PR #566](https://github.com/whshang/herdr-mcp/pull/566)
- First-party DEV/PROD Public Edge contract：epoch **7 / 19 actions**。 [PR #566](https://github.com/whshang/herdr-mcp/pull/566)
- 发布目标继续为 macOS Apple Silicon、Linux x86_64/ARM64 musl、Windows x86_64/ARM64。 [PR #566](https://github.com/whshang/herdr-mcp/pull/566)
- Worker public origin、设备身份、OAuth/Connector identity、rollback material 与 v0.4.9 migration bridge 选择语义保持不变。 [PR #566](https://github.com/whshang/herdr-mcp/pull/566)
