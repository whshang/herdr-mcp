# Release model — runtime, extension, and contract compatibility

This document is the long-lived contributor SSOT for Herdr release boundaries. It defines what is released, how each release plane is versioned, and what must remain compatible. Version-specific qualification records and UAT evidence do not belong here.

## Release planes

| Plane | Ships | Version source | Update path |
| --- | --- | --- | --- |
| Runtime | `herdr-mcp` native binaries, release manifest and checksums | `crates/herdr-mcp/Cargo.toml` + `v*` Git tag | `herdr-mcp update check/apply` |
| Browser extension | STORE and STANDALONE packages; DEV is source-only | `extension/manifest.json` plus channel-specific packaging identity | Store update or standalone distribution |
| Contract compatibility | MCP epoch/tool catalog, state schema, Edge OAuth/MCP behavior | source contracts + release manifest fields | coordinated compatibility, not a shared package version |

Runtime and browser-extension semver are independent. An extension-only change does not require a runtime version bump, and runtime GitHub Releases do not silently own or bundle the browser-extension lifecycle.

### Runtime DEV / PROD channels

Runtime installation has exactly two persistent planes:

- **PROD** — the ordinary installed runtime originating from a published/verified release artifact.
- **DEV** — an explicit source-dogfood runtime built from a repository/worktree and activated as a managed generation for maintainer testing.

`herdr-mcp dev sync` is the only normal source-development path that may deliberately move the default workstation from PROD to a repo-built DEV generation. It embeds DEV build provenance, pins the pre-existing PROD binary and checksum before activation, and reuses the same transactional service/Link generation lifecycle as PROD. The existing channel state also persists the latest DEV-sync transaction from `building` through activation/reconciliation to a terminal `succeeded`, `rolled_back`, or `failed` result, so a caller can recover the exact outcome after the runtime generation replaces itself. `herdr-mcp dev rollback` returns to the pinned PROD binary; repeated DEV builds do not redefine PROD as "the previous DEV". `herdr-mcp dev status` is read-only and exposes channel/generation/provenance plus that latest durable transaction; it is not a second updater or scheduler.

DEV/PROD are runtime planes, not browser-extension identities. Browser extension DEV/STANDALONE/STORE remains a separate release plane. Candidate/UAT processes are disposable validation resources, not a third installed runtime channel.

## Runtime publication

- `.github/workflows/rust-release.yml` is the runtime release workflow.
- `workflow_dispatch` is qualification only; it must not publish or overwrite a GitHub Release.
- only an immutable `v*` tag push may publish a Runtime Release.
- every runtime tag carries authored `docs/releases/<tag>.md` release notes in the exact tagged source; GitHub's autogenerated PR list is not the release log.
- release notes must state the exact upgrade command/version boundary, post-upgrade verification, user-facing `Main changes` with implementation PR links, `Known issue(s)`, and compatibility boundaries. `scripts/validate-release-notes.mjs` is a publish gate.
- release manifests describe the runtime binary set and compatibility metadata.
- stable releases use plain semantic versions; prereleases use normal semver prerelease identifiers.
- installed generations are content-addressed; rollback reactivates an existing installed generation rather than rebuilding source.

### Retention

Stable Releases and stable Git tags are retained long term. After the corresponding stable release is published, superseded prerelease Releases and tags may be removed unless an active compatibility or rollback requirement explicitly depends on them. Historical qualification evidence should not be retained merely to justify keeping obsolete prerelease distribution artifacts.

## Browser extension distribution

Herdr uses three extension identities:

- **STORE** — ordinary-user default, installed and updated through the browser store.
- **STANDALONE** — fixed non-Store identity for auditable manual/GitHub distribution.
- **DEV** — developer-mode source checkout; path-derived and never treated as a release channel.

Native Messaging ownership must resolve to one supported extension owner at a time. Packaging for STORE or STANDALONE must not mutate the DEV source manifest into a fixed release identity. Runtime self-update does not update the extension.

## Contract compatibility

The runtime, Link and Edge surfaces must agree on the active contract epoch and compatibility-sensitive fields, including:

- MCP tool catalog / contract epoch;
- runtime state schema;
- OAuth issuer and public MCP endpoint behavior;
- Link production readiness and runtime ownership invariants.

Edge and Runtime remain separate release/rollback planes: publishing or deploying one never silently publishes the other, and an Edge deployment never switches the local runtime generation. For an already-enrolled ordinary user, however, interactive `herdr-mcp update` may reconcile the user's existing Worker **after** the Runtime update has committed when the release manifest is contract-compatible. That reconciliation uses temporary Cloudflare authorization, updates the proven existing Worker in place, preserves its Durable Objects, secrets, public OAuth origin, devices, Connectors and known optional R2 binding, and never changes DNS. `herdr-mcp worker update` exposes the same reconciliation directly. Unknown/custom Worker bindings fail closed rather than being dropped. Non-interactive `update auto` never opens Cloudflare authorization and instead reports `herdr-mcp worker update` as the next action when Edge is stale. Incompatible runtime-contract, state-schema, OAuth-identity or DNS changes remain explicit coordinated migrations and must not be hidden inside ordinary update.

The public [platform and compatibility support matrix](i18n/en/platform-support-matrix.md) is the release-claim boundary for tested MCP versions, N/N-1/N+1 behavior, and macOS/Linux/Windows/WSL security status. A release must not broaden a platform or compatibility claim unless that matrix and its contract test are updated with the qualifying evidence.

### Major state-schema upgrades

The ordinary `update apply` path remains fail-closed across incompatible runtime state schemas. A release that changes the durable state schema must provide an explicit qualified migration path instead of weakening the updater's manifest/candidate checks.

For the v0.4.8 (schema 5) → v1.0 (schema 15) boundary, the **ordinary user path is one command: `herdr-mcp update`**. The immutable v0.4.8 updater can only admit schema-5 / epoch-2 candidates, so publication uses one bounded migration bridge, v0.4.9. Stable v1.0+ releases publish `runtime-manifest.json` rather than the legacy `release-manifest.json`; therefore an old v0.4.8 updater continues to discover the compatible v0.4.9 bridge instead of selecting an incompatible schema-15 release. The bridge is executed only as the detached worker of the original v0.4.8 update job and is never installed as the production service on the successful path. It discovers an attested schema-15 / Runtime Contract epoch-4 target, downloads and probes the final Runtime, then invokes that final Runtime's existing `update major-apply`. The live source service is still the exact v0.4.8 binary at that point, so the major migration records the real schema-5 database snapshot and the exact v0.4.8 executable for N-1 rollback rather than backing up the bridge.

After the Runtime migration commits, the same bridge job invokes the newly active Runtime's `worker update`. Cloudflare authorization uses the normal browser device flow; the updater resolves the health-proven existing Worker to a unique accessible Cloudflare account (or the non-secret `CLOUDFLARE_ACCOUNT_ID` disambiguator) and updates that Worker in place. Durable Objects, secrets, known optional bindings, public OAuth origin, devices and Connector identities are preserved; the successful path never runs first-Worker bootstrap and never asks the user to re-add ChatGPT. The original foreground v0.4.8 command observes the same durable update job; if authorization takes longer than its bounded foreground watch, the detached bridge continues without requiring a second command.

The underlying `update major-apply` and `update major-rollback` commands remain the authoritative migration/recovery primitives. `major-apply` is an operator/recovery entrypoint, not the normal 0.4.8 user instruction. It verifies schema 5, stops the source service only after the target has been verified, takes the final consistent SQLite snapshot plus exact v0.4.8 binary, hashes both artifacts, and reuses transactional service installation to migrate to schema 15. Snapshot failure restarts the source service; preexisting rollback material is rejected before service stop. `major-rollback` verifies the recorded artifacts, stops the active service, restores the exact schema-5 snapshot and v0.4.8 binary, accepts an interrupted migration at schemas 5–14, and then retires consumed backup material. Rollback intentionally discards durable state created after migration and is N-1 recovery only. Service-changing major lifecycle commands still refuse managed `herdr_exec` execution.

The schema-5 backup and rollback record remain until the operator completes or explicitly rolls back the major upgrade. Normal same-schema 1.0 updates continue through the regular verified updater.

## Ownership boundaries

| Identity | Location | Do not confuse with |
| --- | --- | --- |
| Source checkout | Git worktree | active runtime |
| Build artifact | `target/*/herdr-mcp` | installed generation |
| Installed generation | `~/.config/herdr-mcp/runtime/generations/rust-*` | repository build output |
| Active runtime | `~/.config/herdr-mcp/runtime/current/herdr-mcp` | Git `HEAD` |
| Pinned PROD recovery binary | `~/.config/herdr-mcp/runtime/channels/prod/herdr-mcp` | previous DEV generation |
| User CLI | `~/.local/bin/herdr-mcp` → `runtime/current` | repository wrapper scripts |

## Release discipline

For each stable runtime release:

1. write and validate `docs/releases/vX.Y.Z.md` against the exact intended source, including the previous-version upgrade path and PR-linked `Main changes`;
2. qualify the exact final source without publishing;
3. create an immutable stable tag pointing to that exact qualified source;
4. let the tag-push workflow rebuild, attest and publish the authored notes with the assets;
5. verify stable-channel update, service ownership, Native Messaging and rollback invariants;
6. remove superseded prerelease distribution artifacts once they no longer serve an active compatibility requirement.

Architecture and operating rules live in `docs/i18n/*/architecture.md`, `docs/herdr-architecture-roadmap.md`, browser-extension architecture docs, and `AGENTS.md`. Active implementation plans live in `docs/_wip/`; completed execution evidence is intentionally not kept as normal product documentation.
