# Herdr-MCP 1.0 Architecture Plan

> Status: D1-D5 settled; phased 1.0 implementation baseline
> Scope: multi-controller WebChat, multi-device development, Work Memory, browser control / external conversation dispatch, plugin seams, workstation portability, authentication
> Supersedes the roadmap formerly named `v0.5-v1.0-plugin-kernel-and-workstation-portability.md`.
> Related design: [`v0.4.6-work-memory-and-webchat-control.md`](v0.4.6-work-memory-and-webchat-control.md)
> Related interface: [`v0.4.6-webchat-control-interface.md`](v0.4.6-webchat-control-interface.md)

## 0. Product decision

Treat the next architecture line as the **Herdr-MCP 1.0 program**, not as an ordinary v0.4.6 feature bundle.

1.0 changes the product from a remote MCP bridge into a provider-neutral development control plane:

```text
controllers
  ├─ ChatGPT / Claude / Grok / Gemini / z.ai / DeepSeek
  ├─ Cursor / Claude Code / compatible local MCP clients
  ├─ Herdr-managed coding agents
  └─ GitLab / GitHub / external workflows
        ↓
trusted Herdr control kernel
        ↓
Work Memory + fleet scheduler + typed capabilities
        ↓
multiple devices / repos / worktrees / agents / WebChat sessions
```

`1.0.0` is the compatibility commitment. Development may use preview tags/releases before GA, but the architecture, naming, migration and UAT are designed against the 1.0 target rather than pretending this is a small 0.4.x feature.

Settled user decisions as of 2026-09-04:

```text
D1 = C  hybrid fleet checkpoint + local detailed evidence
D2 = A  transferable exclusive planner lease
D3 = A  keep the frozen epoch-2 public MCP tool surface; use CLI/private methods
D4 = A  official browser extension only for browser-only WebChat actuation
D5 = 1.0 owns the provider-neutral browser control / external conversation dispatch product; 0.4.6 remains hotfix-only
```

Operational preference: whenever a provider exposes a supported API/CLI path and a valid user token can be used safely, prefer that deterministic API/CLI path. Use browser actuation only for operations that genuinely require the provider UI, and then only through the official Herdr browser extension path. Do not add third-party browser automation as a runtime dependency.

## 1. Architecture review record

Review performed 2026-09-04 using the current WIP architecture plus the historical v0.4.3 multi-device design.

- Grok 4.6: completed a full architecture review.
- Antigravity / Gemini 3.8 Flash (`agy`): completed an independent review.
- Droid: launch succeeded, but its weekly usage limit prevented an actual review; no Droid opinion is attributed below.
- Web planner: reconciled the two completed reviews with current repository/runtime constraints.

Areas of agreement:

1. controller-neutral WebChat and no privileged vendor are correct;
2. typed WebChat operations are preferable to general browser RPA;
3. provider control and Tool Bridge must remain separate, local-user, default-deny permissions;
4. Git remotes remain source of truth for code; worktrees are machine-local execution state;
5. Workstation Profile is desired state, not a `$HOME` backup;
6. trusted kernel must own authorization, identity, state transactions, idempotency/fencing and runtime lifecycle;
7. internal adapters may use plugin-style registration, but 1.0 should not freeze a third-party native plugin ABI;
8. the current design is missing an explicit Work Memory locality/replication model and a work-chain concurrency model.

## 2. First principle: no fixed vendor master does not mean no writer ownership

These statements are both required:

```text
No fixed master provider:
  ChatGPT, Claude, Cursor, GitLab, etc. may all become the active planner.

Single-writer consistency:
  one work chain cannot have multiple independent planners changing recovery state concurrently without a defined merge protocol.
```

Therefore `controller` and `planner lease` are separate concepts.

A controller is authenticated provenance. A planner lease is durable authority to change the current plan/checkpoint and issue dependent dispatch/wake operations.

The 1.0 model must never infer planner authority from provider name, focused tab, newest conversation, current device, or default ChatGPT routing.

## 3. Trusted kernel

The Rust kernel owns the invariants that must not be replaceable by an untrusted provider adapter.

```text
protocol / contract negotiation
device identity, enrollment and revocation
request-scoped device routing
authentication, authorization and caller provenance
local consent intersection
StateStore transactions and migrations
Work Memory evidence append and checkpoint projection
planner/execution leases and generation fencing
idempotency and delivery-state ledger
stable refs and locality metadata
secret / credential handles
audit primitives
runtime generation, update and rollback
native-host protocol negotiation
```

The kernel does **not** need to freeze a general Cordis-style event/plugin ABI for 1.0. Typed events and reversible registration are implementation techniques until an external extension contract is deliberately published.

## 4. Plugin architecture: borrow the seams, not the trust model

DeepSeek Harness is a useful architectural reference because it models a capability as service definition + provider + consumer, uses typed events, reversible effects and configuration composition.

Herdr should borrow:

- explicit capability definitions;
- replaceable provider implementations;
- dependency/capability discovery;
- reversible registration/disposal;
- durable event -> projection separation;
- profile-style composition where permissions can only be narrowed by lower-trust layers.

Herdr should **not** copy "everything is a plugin" literally. Herdr is a privileged workstation control plane; the security/consistency kernel above remains privileged.

### 4.1 Plugin classes

Use three different terms/trust classes instead of calling all of them the same thing:

1. **built-in capability module** — compiled Rust/extension implementation behind internal interfaces;
2. **provider adapter** — browser/provider or agent adapter that implements a typed semantic capability;
3. **external extension** — an out-of-process third-party component, when/if Herdr later publishes that contract.

Only class 3 is an actual sandbox/trust boundary.

### 4.2 1.0 plugin promise — recommended

For 1.0:

- built-in modules and provider adapters use internal typed registries;
- WebChat adapters remain extension-hosted where browser session identity requires it;
- external tools use MCP where MCP fits;
- coding-agent interoperability uses ACP where ACP fits;
- no Rust dylib ABI;
- no custom third-party Unix-socket plugin host required for GA;
- no marketplace/signing program required for GA.

A public external plugin ABI can be a 1.x feature after real seams are proven.

## 5. WebChat resource and control model

Canonical hierarchy:

```text
device
  └─ browser_endpoint
       └─ provider_account
            └─ space?        # only when the provider has a native grouping object
                 └─ session
                      └─ view*
```

`space` is optional. Never invent a fake Project/Notebook for providers that do not have one.

Typed operations remain semantic:

```text
identity.inspect
space.list / inspect / create / rename / archive / delete
session.list / inspect / create / open / rename / archive / delete
session.move_to_space / remove_from_space
message.read / append
composer.inspect / select_model / select_tool / set_reasoning / set_message / submit
generation.status / stop
```

Do not expose arbitrary CSS/XPath, JS execution, CDP, cookie/token access, arbitrary external navigation or keyboard/mouse macro as the WebChat contract.

### 5.1 Capability snapshots are fenced state

A provider capability probe is not timeless truth.

Each capability snapshot needs at least:

```text
endpoint_ref
provider
adapter_protocol_version
page_generation / observation_generation
observed_at
capabilities
```

A mutation planned against snapshot generation N must not silently run against an incompatible N+1 page/adapter state. Re-probe or fail with stale/capability-unknown rather than emulate an operation that was not verified.

### 5.2 WebChat Control and Tool Bridge stay separate

```text
WebChat Control:
  trusted controller -> Herdr -> browser adapter -> WebChat

WebChat Tool Bridge:
  WebChat model -> browser adapter -> Herdr -> scoped tools -> bounded result
```

Both default OFF. Tool Bridge workstation mutation permission is a third, narrower gate and also defaults OFF.

No remote controller may enable these local permissions.

## 6. Dispatch model

Cross-WebChat dispatch is an asynchronous job, not a transparent model-to-model stream.

```text
submit
  -> dispatch_id
  -> target session/endpoint reservation
  -> actuation
  -> generation observation
  -> settled | failed | uncertain | stopped
  -> bounded result + evidence refs
```

Universal return path is pull/status. `webchat_wake` is only an optimization for a locally observed source WebChat session whose identity can actually be proven. A generic remote OAuth MCP call is not automatically a trusted ChatGPT/Claude conversation identity.

`dispatch.stop` stops the WebChat generation owned by that dispatch. If the target conversation launched a local coding agent, that agent is a separate resource and must have its own ownership/cancel semantics.

### 6.1 Decision D5 — browser control and external conversation dispatch belong to 1.0

The generic browser endpoint and external conversation-dispatch product is a **Herdr-MCP 1.0** capability. It is not a new 0.4.6 product surface.

The version boundary is normative:

```text
0.4.6
  security, reliability, compatibility and regression fixes for existing behavior
  repair experimental code only when it causes a current-version bug or security risk
  keep unfinished browser/dispatch surfaces internal, disabled, experimental or non-contractual

1.0
  provider-neutral browser endpoint and provider-account registry
  stable space/session resource identity
  typed external append/dispatch/status semantics
  browser resource reservation, multi-device/account fencing and recovery
  formal permission, authorization, postcondition and compatibility contracts
```

0.4.6 must not:

- publish a complete external conversation-dispatch product;
- freeze experimental `chat.*` methods into the public MCP contract;
- add the multi-device/multi-account browser scheduling model;
- broaden legacy OAuth grants merely to operate an experimental surface;
- introduce Playwright, external CDP, OpenCLI or another browser controller as a runtime dependency;
- embed GitLab Issue/MR/label/assignee policy in Herdr core.

If 0.4.6 already contains useful experimental code, 1.0 may preserve its endpoint identity, idempotency, delivery-state, lifecycle-recovery, postcondition and test lessons. The 1.0 contract is nevertheless respecified from the provider-neutral model rather than treating the prototype as the compatibility source of truth.

`gitlab-ai-workflow` is the first intended real consumer, not the owner of the core model. GitHub, Feishu, an IDE, a local MCP client and another external workflow must be able to use the same contract without GitLab-specific fields. OpenCLI remains research, UAT and bounded fallback tooling; it is not an installation or runtime dependency.

### 6.2 Stable provider resources and bindings

The generic resource vocabulary remains `browser_endpoint`, `provider_account`, optional `space`, `session` and local `view`. Provider adapters map native product concepts into that vocabulary:

```text
ChatGPT Project      -> space
ChatGPT Conversation -> session
browser tab/view     -> local view observation
```

A provider without a native project/notebook object does not receive a fabricated `space`.

Stable provider-resource identity is opaque and adapter-owned. It must not depend on display title, tab order, focused page, DOM selector, current URL alone, workspace name or an absolute checkout path. The durable binding model is:

```text
provider resource
  <-> provider account
  <-> browser endpoint
  <-> enrolled device

work chain / repo / execution lane
  <-> provider-resource binding
```

`workspace_ref`, `pane_ref`, `worktree_ref` and absolute paths are locality observations only. Recreating or closing a workspace must not change the identity of a Project/Conversation. A canonical conversation URL may be returned as clickable postcondition evidence, but it is not accepted as the sole mutation target and is never the cross-device resource identity.

### 6.3 Three ownership layers must not be conflated

1.0 has three related but distinct ownership mechanisms:

| Mechanism | Owns | Does not own |
| --- | --- | --- |
| planner lease | the right to mutate a work chain checkpoint/task graph and dependent dispatch plan | a browser tab, provider generation or development process |
| execution-lane ownership | the device/branch/base/file/runtime scope responsible for an engineering subtask | planner authority or a provider conversation |
| browser resource reservation | the dispatch allowed to actuate a selected endpoint/account/session and observe or stop its generation | work-chain planning authority or a local coding agent |

They may reuse generation fencing, CAS, idempotency and audit primitives, but they have separate records, expiry/reclaim rules and cancellation semantics. Taking over a planner lease does not silently seize a running browser generation. Stopping a WebChat dispatch does not implicitly kill a local coding agent started by that conversation.

### 6.4 Typed external contract and forbidden inputs

The external caller supplies semantic intent and stable refs, not browser implementation details. The initial private-method vocabulary may include provider-neutral equivalents of:

```text
endpoint/account/resource inspect
space/session create, open and inspect
message append
dispatch submit, status and stop
composer reasoning/app intent
```

Exact private method names and schemas are frozen only in the corresponding implementation-phase specification. Under D3, they remain behind the existing `herdr_call` gateway until usage and compatibility evidence justify a public-tool change.

External callers may provide stable endpoint/account/space/session/binding refs, a bounded message, semantic reasoning effort, semantic required capabilities/apps such as `required_apps:["herdr"]`, an idempotency key and expected generations. They may not provide:

- CSS selectors, XPath or DOM traversal instructions;
- arbitrary JavaScript, CDP commands or keyboard/mouse macros;
- arbitrary navigation or raw URL mutation targets;
- shell commands or workstation filesystem paths as browser actions;
- cookies, bearer tokens, refresh tokens or provider credentials.

Unsupported provider operations return explicit `unsupported` or capability-unknown results. An adapter must not emulate an unverified lifecycle action merely to present a uniform surface.

### 6.5 Permission and business-authorization intersection

WebChat Control, WebChat Tool Bridge and workstation mutation remain three separate grants, all default OFF. A business application grant and an Extension permission card intersect by least privilege:

```text
effective permission
  = authenticated caller grant
  ∩ fleet/business policy
  ∩ local Extension global consent
  ∩ local provider/account capability allowlist
  ∩ current capability snapshot
```

Remote policy may narrow local consent but cannot enable or widen it. Permission-card `Auto` means that an already locally authorized semantic operation may proceed without another repetitive page confirmation; it is not blanket browser automation and does not grant Tool Bridge or workstation mutation. Destructive lifecycle operations such as delete remain separately capability-gated and should not be used as ordinary cleanup.

### 6.6 Authoritative postconditions, recovery and uncertain delivery

A successful browser mutation requires authoritative postconditions appropriate to the operation, not only a successful extension message send. Depending on the operation, evidence includes:

- stable endpoint/account/resource ref resolution;
- requested Project/Conversation create/open/lifecycle state;
- reasoning effort read-back confirmation;
- required app/capability selection read-back;
- accepted message identity or a provider-observed message baseline advance;
- generation ownership/status;
- canonical conversation URL as output evidence.

Reload, stale-view, detached-tab and provisioning recovery re-resolve the stable resource and re-probe a capability snapshot before mutation. A request planned against observation generation N must not silently execute against an incompatible generation N+1.

Delivery states distinguish at least `not_applied`, `applied`, `uncertain`, `rejected`, `browser_offline`, `resource_unavailable` and `stopped` (final exact enums belong to the implementation specification). An `uncertain` request is inspected or reconciled before retry; it is never blindly replayed. Late confirmation may settle the exact fenced dispatch, but it cannot confirm a newer request or overwrite a later generation.

## 7. Work Memory: durable evidence and checkpoint

The durable conceptual model remains:

```text
append-oriented evidence
  -> deterministic projection
       -> rolling checkpoint
       -> FTS/search views
       -> controller-specific context
```

Core evidence/checkpoint semantics are kernel-owned. Optional search indexes or summarizers may be replaceable projections, but they cannot rewrite authoritative requirements, corrections, decisions or idempotency history without provenance.

### 7.1 Portable evidence identity

Do not use a device-local absolute path or pane/workspace id as cross-device recovery identity.

Portable source evidence should prefer:

```text
repo_id / remote identity
commit_sha or base_sha
repo_relative_path
optional line/range/hash
```

Device-local observations may additionally contain:

```text
device_id
workspace_ref
worktree_ref
absolute_path
pane_ref
runtime generation
```

but those fields are locality hints/evidence, not something another device may replay blindly.

## 8. Decision D1 — Work Memory uses hybrid fleet checkpoint + local detailed evidence

### D1-A — device-local authority + explicit transfer

```text
one chain has a home_device_id
home StateStore owns evidence/checkpoint
cross-device handoff uses versioned export/import or explicit home transfer
```

Advantages:

- matches current StateStore and v0.4.3 locality/privacy model;
- no distributed database or conflict resolver;
- deterministic ownership;
- low Cloudflare write/storage cost.

Costs:

- a device that dies before a recent export can lose untransferred work state;
- remote controllers need the home device reachable for current memory;
- A -> B handoff is an explicit operation, not magic replication.

Grok recommendation: D1-A.

### D1-B — fleet-replicated Work Memory

```text
fleet/Edge owns or replicates chain evidence/checkpoint
all enrolled devices/controllers can recover the same chain
```

Advantages:

- survives loss of home device;
- native multi-device resume;
- remote planners can inspect memory while devices are offline.

Costs:

- new distributed consistency/privacy/retention contract;
- Edge becomes a second durable state plane;
- higher write/storage budget;
- must define offline conflicts and reconciliation.

AGY considers this defensible; Grok argues it should be a separate later program.

### D1-C — hybrid fleet checkpoint + local detailed evidence

A third option from the reconciliation review:

```text
fleet stores:
  chain revision
  active planner/execution leases
  compact accepted requirements/decisions/task graph
  portable evidence refs + latest portable checkpoint

local StateStore stores:
  full local observations
  detailed execution evidence
  logs/artifact refs
  cache/replica of fleet checkpoint
```

Only state transitions are synchronized; tool streams and raw logs are not. Writes are batched/bounded to protect Cloudflare Durable Object quotas.

Advantages:

- fleet can coordinate multi-device work and recover the current plan;
- avoids replicating all local runtime detail;
- supports A dying better than D1-A;
- lower Edge cost than full event replication.

Costs:

- still creates two state planes and a sync protocol;
- must precisely define which fields are authoritative fleet state vs local evidence;
- offline planner semantics become more complex.

**Decision: D1-C.** Fleet state is intentionally compact and coordination-oriented; detailed execution evidence remains device-local. This does not authorize full log replication, arbitrary artifact replication or a fleet-wide filesystem abstraction.

## 9. Decision D2 — transferable exclusive planner lease

### D2-A — transferable exclusive planner lease

Any authorized controller can acquire the lease; only its holder may change the current checkpoint/task graph or emit dependent dispatch/wake actions.

```text
work_chain
  planner_lease:
    holder_principal
    lease_generation
    expires_at / reclaim policy
```

Execution can still be parallelized into independent lanes. A planner lease is not a ban on parallel work; it prevents multiple planners from independently redefining the same plan.

Explicit takeover increments generation and fences old wake/retry paths.

Grok and AGY recommend this class of single-writer model.

### D2-B — cooperative multi-writer checkpoint

Multiple controllers append/advance concurrently. This requires an authoritative event log, parent revisions and a deterministic merge/reconciliation model for requirements, assumptions and task completion.

This is substantially more complex and changes the meaning of checkpoint as recovery state.

**Decision: D2-A.** Multiple controllers may inspect and contribute evidence, but only the current lease holder may mutate checkpoint/task-graph state or issue dependent wake/dispatch transitions. Parallelism happens in execution lanes, not through competing planners.

## 10. Multi-device parallel development is a first-class 1.0 scenario

The user requirement is explicit: multiple devices may develop the same project in parallel.

Therefore 1.0 should support:

```text
repo_identity: github.com/org/repo or GitLab project identity

Device A
  canonical clone
  branch A
  worktree/lane A

Device B
  canonical clone
  branch B
  worktree/lane B

shared:
  upstream Git
  work_chain/task graph

never shared:
  absolute checkout path
  Git worktree directory
  dirty filesystem
  process/agent identity
```

### 10.1 Lane model

A planner can split one work chain into execution lanes:

```text
lane_id
work_chain_id
device_id
repo_id
base_commit
branch_ref
optional worktree_ref
file_scope / subsystem_scope
runtime_scope
owner / agent ref
lane_generation
status
validation
```

Independent lanes may run simultaneously on A and B only when file/runtime ownership does not overlap.

Shared files, branch tip, deployment/runtime or state owner serialize unless ownership is explicitly transferred.

### 10.2 Branch policy

Never have two devices independently mutate/push the same branch as the normal parallel workflow.

Default planner-generated branch identity should include a stable lane/task suffix rather than relying on a local path. The exact human-readable naming format is advisory; branch ref + repo + device/lane binding is authoritative.

### 10.3 Integration

Integration is a separate lane/action:

1. verify each lane's commit/ref and tests;
2. fetch authoritative remote refs;
3. cross-audit the combined diff;
4. merge/rebase according to repo policy;
5. run integration validation;
6. only then reclaim per-device worktrees/branches.

No device is selected merely because it has a matching filesystem path.

## 11. Workstation Profile and device desired state

Workstation Profile answers what a machine should be capable of executing. It does not own a work chain or active worktree.

Recommended 1.0 scope:

```yaml
profile: dev-main
schema_version: 1
projects:
  - id: herdr-mcp
    remote: github:whshang/herdr-mcp
    path: ~/Documents/herdr-mcp
    bootstrap: project-defined
  - id: plm
    remote: <authoritative remote>
    path: ~/Documents/libernovo-plm
    bootstrap: project-defined
agents:
  requirements:
    - capability: code_edit
      min_count: 1
checks:
  - herdr
  - herdr-mcp
  - git_auth
secrets:
  policy: reauthorize
```

`path` is a device-local desired mapping, never cross-device project identity. Durable state addresses the project by `repo_id` / authoritative remote identity and stores absolute paths only as local observations.

Default layout should be consistent where practical without pretending every OS has the same filesystem:

```text
macOS:          ~/Documents/<repo>
Linux desktop:  ~/Documents/<repo> when that user directory exists
Linux headless: ~/src/<repo> by default, overridable by profile
Windows:        %USERPROFILE%\Documents\<repo>
```

The profile may override a per-device `workspace_root`; sibling devices with the same OS should normally use the same relative repository layout. Herdr must never route or recover a project by comparing absolute path strings across devices.

Do not make Herdr a package manager. Toolchain truth should come from project files / documented bootstrap (`mise`, `rust-toolchain`, package manager metadata, project scripts, etc.). The profile can declare/check prerequisites and invoke project bootstrap; it should not invent another universal dependency DSL.

### 11.1 Profile storage

A profile must survive Device A being offline/dead. Therefore it cannot exist only as "ask A to export it".

Acceptable authoritative locations:

- a tracked non-secret Git manifest in an operator-owned repo;
- a fleet-level non-secret profile object;
- both, with one explicitly declared source of truth.

Profile desired state never overrides local security consent. A profile may say a WebChat capability is desired; bootstrap must report `needs_user_auth` / `needs_local_consent` rather than flipping Extension Options.

### 11.2 Actual state

`herdr-mcp scan --probe`, doctor checks and project Git/runtime inspection are actual state. Profile is desired state. Reconciliation must show drift rather than pretending YAML means a capability exists.

### 12.1 Historical B migration observation

The following was observed during the 2026-09-04 architecture pass. It is migration evidence, not a live runtime assertion; current Git/runtime/device state must always be re-inspected before mutation.

At that observation point, `yitaidiannao` had:

- an enrolled online Herdr device;
- herdr-mcp `0.4.4-dev` candidate runtime at the last inspection;
- canonical source checkout at `~/Documents/herdr-mcp`;
- its previous `~/Documents/coding/herdr-mcp` clone moved in place, with the linked UAT worktree repaired and verified;

This demonstrates the safe move path: move the clean common checkout, run Git worktree repair, then verify both the canonical checkout and every retained linked worktree before fetching/updating.

### 12.2 Migration rule

For future migrations:

1. finish/push all useful A work, including any still-dirty prototype lane;
2. verify GitHub contains the exact 1.0 architecture plan and any code intended to survive;
3. on the target device, prefer its platform-default/profile-selected canonical workspace root and either clone cleanly or safely rebuild/move an existing clone topology;
4. verify origin/main, local status and project instructions;
5. install/upgrade B's managed runtime separately from source;
6. recreate required worktrees from Git refs, never copy `~/.herdr/worktrees`;
7. only then retire A's project checkouts/worktrees.

A deletion of A's repository must not destroy the active runtime: `runtime/current` and installed generations are separate from the source checkout by design.

### 12.3 New Device C

C bootstrap remains:

```text
install Herdr
install stable herdr-mcp Release
permissions/FDA
pair into existing fleet
resolve Workstation Profile
reauthorize Git/provider secrets
clone authoritative repos
run project-defined bootstrap
install/probe desired agents
verify projects/runtime
optionally enable WebChat controls locally
```

No new Worker/Connector is created merely because project bootstrap fails.

Current ignored non-build candidates on A were inspected.

### `docs/_wip`

`docs/_wip/*.md` is intentionally tracked by the current `.gitignore` exceptions and therefore **does migrate through Git**. It should contain active design only.

Before A retirement:

- archive reusable historical design under `docs/history`;
- delete one-off raw execution evidence rather than moving it to B;
- do not use `.gitignore` as a substitute for deciding whether a WIP document is durable architecture.

## 14. Authentication boundary: Gemini Spark exposed a real OAuth flaw

Google Gemini Spark added custom MCP Connected Apps in beta. Google's current documentation says a user may add an MCP server URL and that Spark supports Dynamic Client Registration; when DCR is unsupported it asks for credentials. Google also warns that third-party MCP servers are outside Google's security control and currently applies manual confirmation to write actions.

Herdr's current OAuth implementation has a more fundamental problem:

1. public DCR accepts a client registration;
2. the authorization endpoint validates client, redirect URI, resource and PKCE;
3. it then creates an authorization code and redirects immediately;
4. there is no Herdr human login/owner approval/consent gate in that flow;
5. current scope is a single broad `mcp` scope.

Therefore a DCR-capable client can potentially obtain Herdr MCP authorization without a visible Herdr consent step. Spark merely made the flaw visible; this is **not Gemini-specific**.

Treat this as a security blocker independent of the 1.0 plugin work.

### 14.1 Required v0.4.6 hotfix flow

The authorization server must authenticate/authorize the resource owner before issuing a code.

The approval interaction should deliberately resemble secure new-device pairing:

```text
new Connector/WebChat
  -> DCR registers metadata only
  -> /authorize creates pending approval request
  -> client shows request id + one-time short approval code + expiry

already enrolled owner device
  OR a WebChat grant previously approved by this mechanism
  -> inspect pending request
  -> approve exact request/code

authorization server
  -> marks that exact request approved
  -> original client completes authorization-code + PKCE flow
```

Minimum requirements:

- DCR creates client metadata, not resource-owner authority;
- `/authorize` requires an equivalent one-time owner approval before an OAuth authorization code can be issued;
- approval binds exact client id, redirect URI, PKCE challenge, resource, scope and request state/nonce so parameters cannot be swapped after approval;
- the pending request exposes a bounded request id, one-time short approval code and exact expiry, with rate/attempt limits and single-use semantics;
- an enrolled owner device is the secure bootstrap authority;
- a WebChat may approve another Connector only when its own grant was explicitly approved by this mechanism and includes approval authority;
- pre-hotfix OAuth tokens are never silently promoted into connector-approval authority;
- show client identity, requested resource/scope and capability class before approval;
- deny by default for unknown/unapproved clients;
- issue/rotate/revoke grants separately per client;
- support grant/token revocation;
- do not rely on a client UI's write-confirmation behavior as the Herdr authorization boundary;
- consider finer scopes/capability grants rather than one undifferentiated `mcp` permission before 1.0.

Existing connected clients must have a migration/re-consent plan rather than silently inheriting new broad authority.

### 14.2 Immediate operator posture

Until the server-side authorization flaw is fixed, custom DCR clients should be considered capable of receiving more authority than intended. Disconnecting an app in a client UI is prudent but is not sufficient evidence that a previously issued Herdr refresh/access grant was revoked, because the current Herdr OAuth surface does not expose a revocation path in the inspected implementation.

## 15. Decision D3 — keep the epoch-2 public MCP surface frozen

### D3-A — keep epoch 2 public tools and use private methods/CLI

Pros: minimal compatibility churn while semantics settle.

Cons: local controllers see a generic `herdr_call` instead of typed Work/WebChat schemas.

### D3-B — deliberately introduce a 1.0 contract epoch

Expose a small number of stable high-level typed operations after the semantics are proven; retain explicit compatibility for older epoch-2 clients.

Pros: 1.0 becomes a clean public API boundary.

Cons: every promoted tool/schema becomes a long-lived compatibility promise.

The user's priority is deterministic CLI/API operation rather than adding public MCP tools. Therefore **D3-A is selected for 1.0**:

- keep the current public tool count/contract epoch stable unless a later independently justified contract change is approved;
- expose 1.0 orchestration through CLI and versioned private `herdr_call` methods first;
- let MCP/WebChat planners use the existing generic private-method gateway;
- promote a method into a first-class public MCP tool only after real usage proves that the generic route materially harms safety/usability and the schema is ready for a long compatibility promise.

This is a public API choice, not a UI setting.

## 16. Decision D4 — official extension for browser-only WebChat execution

### D4-A — user browser/extension only for 1.0

CI/external workflows may dispatch work to an enrolled desktop browser endpoint but do not create headless logged-in provider sessions.

Advantages: reuses user session, no cookie credential vault, narrower security surface, lower anti-bot fragility.

### D4-B — hybrid extension + Playwright/CDP headless provider sessions

Advantages: true server/CI autonomous WebChat.

Costs: browser credential lifecycle, CAPTCHA/anti-bot fragility, broader RPA surface, a second actuation implementation and substantially larger security scope.

AGY identified this fork; current Herdr principles strongly favor D4-A for 1.0.

**Decision: D4-A.** Prefer provider-supported token/API/CLI operations first. Operations that genuinely require an authenticated browser UI use the official Herdr extension on an enrolled workstation. 1.0 does not depend on third-party browser automation, external CDP controllers or a separately managed headless provider-login profile.

### 16.1 Phase 1 implementation boundary — Fleet Control Kernel Foundation

The first implementation slice is deliberately narrower than the full 1.0 program:

```text
authenticated controller
  -> create/inspect work chain
  -> acquire exclusive planner lease
  -> create explicit execution lane
  -> renew/release/take over planner lease
  -> stale generation is fenced
  -> compact fleet state survives authority restart
```

Authority for the compact cross-device coordination state lives at Edge in the existing fleet Durable Object boundary. The workstation `StateStore` remains authoritative for detailed local observations/evidence and may cache fleet checkpoints, but it does not own the fleet planner lease, chain revision, or lane assignment. Phase 1 must extend an existing Edge state owner rather than introduce a second long-lived database/daemon or a second authoritative lease store.

The remote entry stays inside the frozen epoch-2 `herdr_call` tool through versioned, typed private `herdr_mcp.work_chain.*`, `herdr_mcp.planner_lease.*`, and `herdr_mcp.execution_lane.*` operations (or an equivalently typed discriminated command if implementation evidence proves fewer methods safer). Caller principal is derived from authenticated Edge/kernel context; request payload text is never authorization identity.

Phase 1 does not implement full Work Memory replication, a task-graph scheduler, automatic Agent dispatch, WebChat adapters/control, Extension DOM work, provider-specific workflows, a plugin ABI, or a public MCP epoch change. Acceptance requires persistent authoritative chain/lease/lane state, atomic CAS/idempotency/fencing behavior, a real private-method boundary test, backward-compatible state migration, and unchanged public epoch-2 / 18-tool evidence.

## 17. 1.0 compatibility gates

Do not tag 1.0.0 until these observable gates pass.

### Security and identity

- OAuth DCR cannot self-authorize a resource owner.
- Client grants are inspectable/revocable and migration is defined.
- Provider control, Tool Bridge and workstation mutations remain separately default-deny.
- Device identity/enrollment/revocation and request-scoped routing preserve the v0.4.3 fail-closed rules.
- Secrets never appear in portable profile/Work Memory export.

### Work Memory and controller handoff

- Work Memory locality/replication follows the selected D1 contract.
- one chain has explicit revision/lease semantics;
- checkpoint is reproducible from authoritative evidence;
- controller handoff on one device works without losing accepted requirements/corrections/validation evidence;
- machine handoff A -> B is tested separately from controller handoff;
- portable evidence does not depend on A's absolute paths.

### Multi-device parallel development

- two devices can have the same repo without ambiguous path routing;
- one planner splits at least two non-overlapping lanes to different devices;
- each lane has explicit device/repo/branch/base ownership;
- no two devices implicitly share a branch/worktree;
- integration fetches refs and validates the combined result;
- stale device/workspace refs fail closed rather than silently retargeting.

### WebChat

- at least two providers prove the semantic adapter seam;
- browser endpoint, provider account and provider resources have stable opaque refs that survive view/workspace recreation;
- capability snapshots are generation-fenced;
- ambiguous target/account/session fails closed;
- planner lease, execution-lane ownership and browser resource reservation remain distinct and independently fenced;
- dispatch retry/idempotency handles `uncertain` without blind replay;
- semantic reasoning and required-app intent are read back or reported unsupported rather than assumed;
- accepted-message evidence and canonical conversation URL postconditions are independently observable;
- external callers cannot submit selectors, XPath, arbitrary JS/CDP, keyboard macros, shell, credentials or arbitrary raw-URL mutation targets;
- local Extension consent cannot be enabled or widened by a remote business caller;
- extension/runtime N-1/N+1 compatible protocol window is defined or fails explicitly on unsupported skew;
- local MCP controller proves no WebChat provider is privileged.
- `gitlab-ai-workflow` and at least one non-GitLab consumer prove that core schemas contain no GitLab-specific policy.

### Runtime and workstation portability

- B/C bootstrap uses authoritative Git + project bootstrap, not copied home directories;
- runtime source/build/installed/active identities remain separate;
- update/rollback preserves device identity, TCC broker and selected Work Memory contract;
- Workstation Profile contains no secrets and reports desired-vs-actual drift;
- A may be unavailable without preventing C from resolving the authoritative profile.

## 18. Explicit non-goals for 1.0

- general browser RPA;
- arbitrary JS/CDP/cookie/token browser API;
- external selector/XPath/keyboard-macro or raw-URL mutation contracts;
- treating URL, title, tab order, workspace or absolute path as durable provider-resource identity;
- embedding GitLab, GitHub, Feishu, Jira or another consumer's business policy in Herdr core;
- conflating planner lease, execution-lane ownership and browser resource reservation;
- Rust dylib plugin ABI;
- third-party plugin marketplace;
- mandatory native WebMCP support;
- full provider feature parity;
- vector DB before measured retrieval need;
- syncing browser cookies/Keychain/SSH private keys;
- copying `~/.herdr/worktrees` between devices;
- treating matching filesystem paths as device selection;
- making Herdr a universal OS/toolchain package manager;
- automatic concurrent planner merge unless D2-B is explicitly selected.

## 19. Settled decisions and implementation entry

Implementation proceeds with the decisions recorded at the top of this document:

1. **D1-C:** hybrid fleet checkpoint + local detailed evidence.
2. **D2-A:** transferable exclusive planner lease with generation fencing.
3. **D3-A:** frozen epoch-2 public MCP surface; 1.0 semantics begin as CLI/private methods.
4. **D4-A:** provider API/CLI first; browser-only operations use the official Herdr Extension.
5. **D5:** provider-neutral Browser Control and External Conversation Dispatch are a 1.0 product; 0.4.6 remains limited to current-surface security, reliability and compatibility fixes.
6. **Multi-device parallel development:** in scope, with explicit device/repo/branch/base execution lanes and no implicit shared branch/worktree.
7. **Consumer neutrality:** `gitlab-ai-workflow` is an initial UAT consumer, OpenCLI is research/UAT/fallback tooling, and neither is a runtime or core-schema dependency.
