# Herdr-MCP 1.0 beta.1 — Browser Reliability and Postcondition

Status: implementation in progress on `feat/v1.0-beta1-reliability-postcondition-20260907`.

## Purpose

Beta.1 makes an already-authorized Browser/WebChat mutation reliable enough to become the substrate for beta.2 orchestration. It does not add scheduling, fan-out, reservation, failover, or another task-state owner.

The durable task, memory, delegation, and handoff state remains in Herdr-MCP. A browser tab is only a disposable view of a provider session.

## Invariants

1. A caller plans against one positive Browser Registry `observation_generation`. A mutation planned against generation N must never silently execute against N+1.
2. A successful browser command acknowledgement is not sufficient proof of application. Delivery becomes `applied` only when the operation-specific postcondition is observed.
3. `uncertain` is durable and non-retryable by default. The same idempotency key must never cause a second browser submit merely because the acknowledgement was lost.
4. Late evidence may settle only the original durable dispatch row and its original generation. It must not update a sibling dispatch or replace the current provider generation.
5. Service-worker suspension may discard in-memory tab routing, but it must not discard the stable Browser Registry session identity. Recovery may rebuild an in-memory target; it may not replay the mutation.
6. Physical Chrome tab/window ids are local views, not durable identities. Duplicate views of the same logical session are ambiguous for actuation and fail closed.
7. Browser actuation protocol skew fails closed. An unsupported adapter protocol is not represented as an ordinary 12-second timeout.
8. Public Workstation epoch 2 / 18 tools, public Edge epoch 3 / 19 actions, and SQLite schema v8 remain unchanged.

## Delivery versus execution

`BrowserDeliveryState` answers only whether one browser mutation was proven to have applied:

```text
not_applied
applied
uncertain
rejected
browser_offline
resource_unavailable
stopped
```

Beta.1 does not reinterpret `applied` as "the delegated task finished". Task execution/result state belongs to the beta.2 Work Chain / execution-lane projection and Work Memory evidence.

## Late settlement

A submit reserves one durable `browser_dispatches` row before browser actuation. The row is marked `uncertain` before the command may cross the browser boundary.

If the synchronous evidence deadline expires after the command may have crossed that boundary:

- the dispatch remains `uncertain`;
- the exact actuation correlation is retained in bounded runtime memory for a short late-completion TTL;
- the same idempotency key reopens the existing dispatch and never actuates again;
- `browser_dispatch.status` may consume one exact late completion and settle the durable row;
- late evidence is checked through the same postcondition and generation-owner rules as synchronous evidence;
- correlation expires boundedly and does not create a resident reconciliation daemon.

The StateStore late-settlement operation deliberately checks the durable dispatch row's original generation rather than requiring the provider's current observation generation to remain unchanged. This permits valid evidence for generation N to settle dispatch N even after the browser has observed generation N+1, while leaving N+1 authoritative for all new mutations.

## Service-worker target recovery

The page content script caches only:

```text
browserSessionRef
browserGeneration
```

These are Herdr opaque identity/fencing values already returned by Browser Registry registration. Raw account native identity is not exposed through the recovery handshake.

If the MV3 service worker loses its in-memory `browserSessionTargets` map, one incoming actuation may perform one bounded read-only scan across supported complete tabs:

1. query the already permitted supported WebChat origins;
2. ask each existing content script for `h2w_get_convkey`;
3. require exact `browserSessionRef` and exact expected generation;
4. reconstruct provider/conversation identity from the bounded supported URL parser;
5. accept exactly one matching physical tab;
6. repopulate only the in-memory target map.

Recovery never calls `tabs.reload`, `tabs.update`, `scripting.executeScript`, or a browser mutation. A duplicate physical view is ambiguous and fails closed. A matching session at a newer generation reports that newer generation so the caller receives the stale-generation fence rather than reusing stale state.

## Protocol fencing

The runtime currently accepts Browser adapter protocol version `1` for actuation. Ordering is intentional:

1. caller grant and local consent;
2. expected/resource generation fence;
3. adapter protocol compatibility;
4. advertised capability;
5. browser actuation.

Therefore an old planned request still reports `stale_capability_generation` even if the newly observed provider generation also changes protocol. When generation is current but protocol is unsupported, actuation fails with `browser_adapter_protocol_unsupported` before a command is queued.

At the Extension boundary, an unknown `herdr-browser-actuation/*` protocol receives explicit rejected evidence for a syntactically valid actuation id instead of being silently dropped into a timeout.

## Verification requirements

Required focused evidence:

- late completion can settle only the exact dispatch and original generation;
- sibling uncertain dispatch remains untouched;
- already settled dispatch cannot be rewritten;
- timed-out dispatch correlation accepts an exact late completion inside TTL;
- expired correlation rejects late completion;
- adapter protocol mismatch fails before actuation while stale generation remains the primary fence;
- service-worker target recovery succeeds for exactly one stable session view;
- duplicate views fail closed;
- newer-generation views are not reused;
- page recovery handshake exposes no raw account identifier;
- existing provider adapters, background binding, and extension smoke do not regress.

```text
cargo fmt --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace

```

## Explicit non-goals

Beta.1 does not implement:

- `browser_session.create/open` provider actuation;
- multiple WebChat worker fan-out;
- execution-lane reservation;
- multi-device / multi-endpoint / multi-account scheduling or failover;
- worker result aggregation or planner wake;
- recursive worker delegation;
- Page Assist integration;
- production Edge deployment or caller-grant widening.

Those orchestration capabilities belong to beta.2 after this reliability boundary is qualified.
