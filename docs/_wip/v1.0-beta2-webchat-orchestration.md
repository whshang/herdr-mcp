# Herdr-MCP 1.0 beta.2 — WebChat Orchestration, Reservation, and Failover

Status: active on `integ/v1.0-v048-final-unified-20260908` after beta.1 local qualification at `a2de4e1`.

Implementation guardrails for the v0.4.8 unified line:

- reuse the existing `work_chain`, `planner_lease`, `execution_lane`, Browser Registry, `browser_dispatch`, continuity journal, and Work Memory state owners;
- do not duplicate v0.4.8 device enrollment/CRUD/revoke/admin or generic exec/route/retry infrastructure;
- do not directly port the old `ce25fa1` schema-v9 locator/reservation DDL; add a migration only when a real reservation consumer cannot be represented safely by schema 8;
- first prove one ChatGPT Planner controlling multiple ChatGPT worker sessions on one endpoint/account before adding cross-account/device/provider failover.

## Product goal

Herdr-MCP, not an individual browser conversation, owns durable task identity, memory, delegation, handoff, and worker topology.

The first acceptance target is deliberately homogeneous:

```text
main ChatGPT planner
  -> multiple ChatGPT worker sessions
  -> independent bounded assignments
  -> worker results written to the same Herdr Work Chain
  -> main ChatGPT planner observes and aggregates those results
```

Only after that path is proven do we validate mixed ChatGPT / Claude / Grok / Gemini workers using the same provider-neutral contracts.

## Canonical vocabulary

Do not introduce duplicate `WebChatAgent`, `WebChatTask`, `Topic`, or browser-owned memory entities.

| Term | Authority / meaning |
| --- | --- |
| `work_chain` | Durable unit of coordinated work and memory. Comparable to an orchestration topic, but owned by Herdr-MCP. |
| `planner_lease` | The single current planning authority for a Work Chain. First beta.2 validation keeps this on the main ChatGPT conversation. |
| `execution_lane` | Durable bounded subtask/participant identity. Provider-neutral and stable even if its WebChat session is replaced. |
| `browser_endpoint_ref` | Local browser/profile endpoint capable of hosting supported WebChat resources. |
| `account_ref` | Opaque provider account identity under one endpoint. |
| `space_ref` | Optional provider-native project/space identity. |
| `session_ref` | Replaceable provider WebChat conversation resource bound to an execution lane. It is not an Agent identity. |
| `browser_dispatch` | One idempotent delivery attempt to a concrete session. Its `delivery_state` does not mean task completion. |
| Work Memory evidence | Durable result/evidence channel back to the Work Chain and planner. |

Physical Chrome window/tab ids are always disposable local view state and never become durable task or worker identity.

## Relationship model

The topology is intentionally flat at first:

```text
Work Chain
  planner_lease -> main ChatGPT session

  execution_lane A -> ChatGPT worker session A
  execution_lane B -> ChatGPT worker session B
  execution_lane C -> ChatGPT worker session C
```

A worker does not become a second planner merely because it can call Herdr-MCP. If a worker believes another delegation is useful, it may write a bounded delegation request/result into the Work Chain; the current planner decides whether to create another lane.

Recursive worker fan-out is therefore disabled by default in beta.2 first-stage validation.

## Session lifecycle

Beta.2 completes the provider actuation behind the already frozen private methods:

```text
herdr_mcp.browser_session.create
herdr_mcp.browser_session.open
herdr_mcp.browser_session.inspect
```

`browser_session.create` creates a new provider conversation under an exact endpoint/provider/account/optional-space scope. It returns only after a stable Browser Registry `session_ref` and canonical URL are observed.

`browser_session.open` creates or selects a disposable physical view for an existing stable session. Closing a Chrome tab must not delete the session binding, execution lane, Work Chain, or result evidence.

Session creation/opening uses the same expected-generation, idempotency, caller-grant, local-consent, adapter-protocol, and postcondition rules established by Alpha 4 and beta.1.

## Reservation and scheduling

Reservation chooses an execution resource for a lane. It does not create a second policy authority.

The candidate tuple is:

```text
device_id
endpoint_ref
provider
account_ref
space_ref?
```

Selection must be based on explicit capability/consent/freshness and the Work Chain's bounded assignment requirements. No resource may be selected solely because a browser tab happens to be open or recently active.

First-stage ChatGPT-only validation should use one device and one signed-in ChatGPT account where possible so orchestration semantics are proven before failover complexity is introduced.

Then expand in this order:

1. multiple ChatGPT sessions on one endpoint/account;
2. multiple eligible endpoints/accounts on one device;
3. multiple devices with exact resource reservation and bounded failover;
4. mixed Claude/Grok/Gemini provider workers using the same lane/result contract.

## Dispatch and execution state are separate

`BrowserDeliveryState` remains the transport/postcondition state for one submit:

```text
not_applied | applied | uncertain | rejected |
browser_offline | resource_unavailable | stopped
```

Execution state describes the delegated assignment after delivery. The canonical beta.2 projection is:

```text
queued
submitted
generating
settled
stopped
failed
```

This projection must not become a second browser-owned database. It is derived from the execution lane, durable dispatch records, provider observations, and Work Memory evidence.

A dispatch being `applied` means only that the prompt submit was proven. It never means the worker assignment is complete.

## Result return

Worker results return to Herdr-MCP first, not directly into the planner's composer.

When a worker session settles:

1. Extension/provider observation proves the assistant turn is settled for the expected session/generation;
2. Herdr-MCP records bounded result metadata and content/evidence under the execution lane and same `work_chain_id`;
3. result content is indexed in Work Memory with provider/session provenance;
4. the lane projection becomes `settled` only after durable result evidence exists;
5. the planner reads the lane/result through Herdr-MCP and performs synthesis.

The worker must not paste its full answer into the main ChatGPT conversation as the authoritative return path.

## Planner notification

If the planner WebChat is live and idle, Extension may send a small wake pointer such as:

```text
work_chain_id
lane_id
dispatch_id
result_evidence_ref
```

The pointer asks the planner to read authoritative Herdr state. It must not copy the full worker answer, and loss of this notification must not lose the result. Closing or reloading the planner tab therefore does not break orchestration.

## Herdr-like WebChat management projection

The UI may present a `WebChat Workspace`-style projection for familiarity, but it is explicitly a projection and not a new Herdr workspace identity.

Recommended hierarchy:

```text
WebChat Work Chain View
  Planner
    provider / account / session

  Lane: research
    provider / session
    execution state
    latest result evidence

  Lane: implementation
    provider / session
    execution state

  Lane: review
    provider / session
    execution state
```

Supported management actions should map to existing/frozen browser and Work Chain operations:

```text
create
open
inspect
dispatch
status
stop
reassign
failover
```

The authoritative objects remain Work Chain, Planner Lease, execution lanes, Browser Registry resources, dispatch records, and Work Memory evidence.

## First acceptance scenario — ChatGPT controls ChatGPT

The first beta.2 real-browser UAT is mandatory before mixed providers:

1. Bind the current signed-in ChatGPT conversation as the Work Chain planner.
2. Create at least two independent execution lanes.
3. Through Herdr-MCP + Extension, create two new ChatGPT sessions under the exact same authorized browser endpoint/account.
4. Bind one session to each lane.
5. Dispatch distinct harmless bounded assignments with independent idempotency keys.
6. Prove each dispatch delivery and generation ownership through beta.1 semantics.
7. Observe each worker generation to a settled assistant result without relying on physical tab focus.
8. Persist each result into Work Memory with lane/provider/session provenance.
9. From the main ChatGPT session, inspect the Work Chain and retrieve both results through Herdr-MCP.
10. Prove planner aggregation can complete even if one worker tab was closed and reopened before result retrieval.
11. Prove replay of a dispatch idempotency key never creates a duplicate worker message.
12. Prove a worker cannot acquire the Planner Lease or recursively create another worker unless the planner explicitly authorizes a future delegation policy.

## Second acceptance scenario — provider-neutral workers

After the ChatGPT-only scenario passes, reuse the same Work Chain/lane contracts with a bounded mixture of Claude, Grok, and Gemini sessions. Provider-specific differences are limited to adapter capability/identity/session lifecycle; task memory, result return, lane state, planner ownership, reservation, and failover semantics remain Herdr-MCP-owned and provider-neutral.

## Failover

Failover is allowed only before delivery is proven or after a lane is explicitly reassigned from a settled/failed resource state. An `uncertain` browser mutation from beta.1 must not automatically fail over to another session, because that can duplicate the task.

Any takeover/reassignment records the old and new session bindings in the execution lane history and preserves prior evidence in Work Memory.

## Compatibility and authority

### Owner-approved Planner capability

Ordinary OAuth remains denied for Fleet Control, including workers sharing the
same Connector token. WebChat Control alone grants no Fleet authority. The
stateless ChatGPT MCP surface issues no `Mcp-Session-Id`. Runtime retains epoch
2 / 18 tools; Edge retains its existing epoch 3 / 19 tools including
`herdr_devices`. Planner adds no public tool.

Use `herdr_call` with these private Edge-local methods:

1. `herdr_mcp.planner_control.request`: pass `device_id`, `endpoint_ref`,
   `provider`, `account_ref`, `space_ref` (null when absent), `session_ref`, and
   positive `observation_generation` in `params`. The authenticated OAuth
   Connector generation must already have the exact WebChat Control grant.
   Save the one-time `claim_secret` privately. The request expires in 10 minutes.
2. The configured owner device reviews `herdr-mcp connector planner-control list`
   and the exact tuple, then runs
   `herdr-mcp connector planner-control approve <request-id> --confirm`.
   REST equivalent: `POST /connectors/planner-control` with
   `{"action":"approve","request_id":"<request-id>"}`. `list` and `revoke`
   use the same route. Authentication requires the existing owner workstation
   and credential boundary used by `/connectors/webchat-control`.
3. The requesting OAuth caller invokes `herdr_mcp.planner_control.claim` with
   `request_id` and `claim_secret`. Only this one-time response returns
   `controller_capability`; it expires after 30 minutes, with no renewal API.
4. Supply `params._controller_capability` on existing Fleet Control methods.
   Edge removes it before ordinary method validation and passes it separately
   to authorization. Never put either secret in worker assignments, evidence,
   idempotency keys, logs, or Git.
5. Revoke with `herdr-mcp connector planner-control revoke <request-id> --confirm`.

The capability identifies an opaque controller principal with
`can_force_takeover=false`. Every use rechecks the active Connector generation,
the exact WebChat grant, expiry, and revocation. It grants only the existing
`FLEET_CONTROL_METHODS`; takeover and administrative operations remain denied.
OAuth Store persists only secret digests; owner responses omit those digests.
The session tuple is owner-reviewed request provenance. Possession supplies the
per-conversation authority because the shared OAuth token cannot identify an
individual ChatGPT conversation. Sharing the capability shares that authority.

Air UAT limitation: the CLI retains the existing `resolve_fleet_link_identity`
path. An Air installation missing its `devsec` cannot use this CLI until owner
identity resolution is fixed separately. The Edge owner boundary is unchanged;
an arbitrary enrolled device credential does not qualify as owner authority.

Beta.2 must preserve:

- public Workstation epoch 2 / 18 tools;
- public Edge epoch 3 / 19 actions unless a separately authorized contract epoch intentionally changes them;
- existing OAuth Connector caller authority as the remote source of truth;
- local Extension consent as an independent required factor;
- provider/account/session identities as opaque refs outside their local adapter boundary;
- SQLite schema changes only when a durable state requirement cannot be represented safely in the existing store, with explicit migration proof if needed.

## Non-goals for first beta.2 slice

- arbitrary recursive agent trees;
- autonomous budget/policy optimization across providers;
- browser tabs as durable worker identities;
- browser-local memory as the delegation source of truth;
- copying worker answers directly into planner chat as the authoritative result path;
- hidden fallback from one WebChat to another after an uncertain submit;
- a second task database outside the existing StateStore / Work Memory model.
