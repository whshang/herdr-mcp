# v0.5 → v1.0 Roadmap: Plugin Kernel and Workstation Portability

> Status: WIP / roadmap
> Scope: versioning, plugin architecture, controller interoperability, workstation migration/bootstrap
> Related architecture: [`v0.4.6-work-memory-and-webchat-control.md`](v0.4.6-work-memory-and-webchat-control.md)
> Related interface: [`v0.4.6-webchat-control-interface.md`](v0.4.6-webchat-control-interface.md)

## 0. Decision summary

The Work Memory + controller-neutral WebChat design is a **1.0-scale product architecture change**, but the first implementation should not be tagged `1.0.0` merely because the diff is large.

Recommended release strategy:

```text
0.4.x
  current stable control/runtime foundation

0.5.x
  architectural preview:
  plugin kernel + Work Memory + controller-neutral WebChat + portable workstation bootstrap

0.6.x if needed
  external-plugin hardening, migration/compatibility cleanup, broad provider/device UAT

1.0.0
  compatibility commitment / GA contract
```

The redesigned work should therefore stop being mentally constrained as a small `0.4.6` feature. Existing `v0.4.6-*` documents remain useful design history/SSOT while planning is being consolidated, but the implementation/release line should be treated as the candidate `0.5.0` architecture preview unless a later release decision says otherwise.

`1.0.0` means the public and durable contracts are ready to be depended on, not that the implementation contains many changes.

## 1. What makes this 1.0-scale

The change is larger than adding another MCP tool or another provider adapter. It changes the product model from:

```text
Web AI
  -> Herdr tools
  -> one workstation
```

into:

```text
many controllers
  ├─ ChatGPT / Claude / Grok / Gemini / z.ai / DeepSeek
  ├─ Cursor / Claude Code / Codex / other local MCP clients
  ├─ Herdr-managed coding agents
  └─ GitLab / other external workflows
        ↓
small trusted Herdr kernel
        ↓
capability plugins + Work Memory + fleet routing
        ↓
many devices / projects / WebChat surfaces / execution runtimes
```

The durable unit of work becomes the Herdr `work_chain`, not a ChatGPT conversation, browser tab, coding-agent session, or one workstation checkout.

This introduces three long-lived contracts that should be stable before `1.0.0`:

1. plugin/capability contract;
2. Work Memory / resource identity contract;
3. workstation/fleet portability contract.

## 2. Versioning gates

### 2.1 Why not jump directly to `1.0.0`

The first pluginized implementation will almost certainly reveal better names, capability boundaries, migration rules, and provider adapter contracts. A direct `1.0.0` would force compatibility work before real multi-controller/multi-device usage has validated those choices.

Pre-1.0 minor versions are the correct place to make deliberate architecture corrections.

### 2.2 Proposed `0.5.0` scope

`0.5.0` should prove the architecture, not maximize plugin count.

Required:

- one trusted runtime kernel and one durable state owner;
- internal plugin registry/lifecycle;
- Work Memory evidence + rolling work state;
- provider-neutral WebChat resource model;
- at least two independent WebChat provider adapters proving the seam;
- local `127.0.0.1` MCP controller path proving ChatGPT is not privileged;
- existing fleet/device routing preserved;
- portable workstation bootstrap design and at least a minimal assisted flow;
- upgrade/rollback from the last `0.4.x` stable line.

Not required:

- public third-party plugin marketplace;
- dynamic Rust ABI plugins;
- every WebChat provider at full feature parity;
- generic browser RPA;
- native WebMCP support;
- automatic migration of arbitrary secrets/dotfiles.

### 2.3 `1.0.0` GA gates

Do not tag `1.0.0` until all are true:

1. plugin manifest/API versioning and capability negotiation are documented and tested;
2. internal and supported external plugins cannot bypass authorization/fencing;
3. Work Memory schema has forward migration + rollback/recovery policy;
4. one work chain can move between at least one Web controller and one local controller without losing exact requirement/change/test evidence;
5. workstation A → B handoff is documented and reproducible without copying a home directory;
6. a new workstation C can join an existing fleet, restore the requested development profile, clone projects from authoritative remotes, and pass end-to-end verification;
7. provider/site enablement remains local-user opt-in and default-deny;
8. `0.x` → `1.0` configuration migration is explicit and tested;
9. release/update/rollback does not invalidate device identity, TCC ownership, Work Memory, or stable local/public MCP identities;
10. contract epoch/version negotiation gives older clients an explicit compatibility result instead of silent partial behavior.

## 3. DeepSeek Harness: what to borrow

DeepSeek Harness is the strongest current reference for plugin composition. Its architecture uses Cordis: plugins contribute services, typed events, and reversible effects to a shared context. Model adapters, tools, session log, and the agent loop are all replaceable plugins. Runtime composition is expressed as profiles + bundles + ordered patches.

Reference:

- <https://github.com/deepseek-ai/deepseek-harness>
- <https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md>

Useful ideas for Herdr:

### 3.1 Capability seams

A capability should have three explicit roles:

```text
contract / service definition
provider implementation
consumer
```

This maps directly to Herdr:

```text
webchat.session
  contract: create/list/read/append/stop
  provider: ChatGPT adapter / Claude adapter / ...
  consumer: local MCP client / Web controller / workflow dispatcher
```

### 3.2 Typed events

Use typed domain events instead of cross-module callbacks:

```text
device.*
workspace.*
agent.*
work.*
memory.*
webchat.*
plugin.*
```

Durable facts and transient lifecycle events must remain distinct.

### 3.3 Reversible registrations

Plugin registration must return a disposable lifecycle handle. Unloading or disabling a plugin must unregister its capabilities/listeners deterministically instead of leaving stale global state.

### 3.4 Composition layers

Borrow the profile/bundle idea conceptually, but do not copy DSH's exact configuration syntax.

Herdr should resolve configuration in explicit layers such as:

```text
built-in safe defaults
  ↓
installed capability pack defaults
  ↓
machine/user configuration
  ↓
project/work-chain policy where allowed
  ↓
one-shot operator override
```

Higher layers may narrow permissions. A lower-trust project/WebChat layer must never enable a machine-level capability that the local user disabled.

### 3.5 Durable event projection

DSH's append-oriented session log + projections is a useful analogue for Work Memory:

```text
durable evidence events
  -> deterministic projections
       -> rolling work checkpoint
       -> search/index views
       -> controller-specific context
```

Herdr should not copy full provider transcripts as the source of truth.

## 4. Do not copy “everything is a plugin” literally

Herdr is a remote workstation control plane. Some behavior must remain a small trusted kernel because it defines the security and consistency boundary.

### 4.1 Trusted kernel

The kernel owns:

```text
protocol/version negotiation
device identity and enrollment
authorization + capability checks
StateStore transactions and schema migration
idempotency / delivery state / fencing
stable Herdr refs and device routing
plugin discovery + lifecycle + dependency graph
typed event bus semantics
secret boundary / credential handles
audit/provenance primitives
runtime generation/update/rollback ownership
```

A plugin may consume these services but may not replace their invariants inside the same trust class.

### 4.2 Plugin domains

Most product capability belongs outside the kernel:

```text
agent adapters
  pi / codex / claude / grok / opencode / ACP-compatible agents / ...

webchat adapters
  chatgpt / claude / grok / gemini / zai / deepseek / ...

workflow adapters
  gitlab / github / future issue trackers / event consumers

memory projections/indexers
  FTS / future semantic index / summaries / domain projections

transport extensions
  optional relay/provider implementations behind a stable transport seam

browser-extension adapters
  provider DOM/API semantics and capability probes

artifact adapters
  optional import/export backends behind the existing safe artifact boundary
```

### 4.3 Built-in first, external later

Do not start `0.5.0` by designing a public binary plugin ABI.

Recommended evolution:

```text
Phase 1
  Rust traits/interfaces + internal registry
  built-in plugins compiled with the runtime

Phase 2
  versioned manifest + out-of-process plugin host
  stdio/Unix-socket transport
  explicit capability/permission negotiation

Phase 3
  optional registry/distribution/signing policy
```

Avoid Rust `dylib`/`cdylib` as the public extension boundary: Rust ABI stability and in-process trust are poor fits for third-party plugins.

Where standards already exist, reuse them instead of inventing another protocol:

- MCP for tool/resource servers;
- ACP where coding-agent client/agent interoperability fits;
- WebMCP only for page-native browser tools;
- Herdr private JSON-RPC/socket methods for trusted local runtime operations that do not deserve a public MCP tool.

## 5. Proposed plugin manifest

Conceptual shape only:

```yaml
id: webchat.claude
version: 0.1.0
api_version: 1
kind: webchat_provider
runtime: browser_extension
provides:
  - webchat.identity.inspect
  - webchat.session.list
  - webchat.session.create
  - webchat.session.read
  - webchat.session.append
requires:
  - browser.native_host
permissions:
  - provider: claude
  - browser_origin: https://claude.ai/*
default_enabled: false
```

A local Agent adapter might be:

```yaml
id: agent.acp
api_version: 1
kind: agent_provider
runtime: process
provides:
  - agent.discover
  - agent.start
  - agent.prompt
  - agent.cancel
requires:
  - process.spawn
permissions:
  - executable_probe
```

The manifest describes capabilities, dependencies, runtime class, and requested permissions. It does not itself grant permission.

## 6. Plugin configuration and enablement

Keep enablement explicit and observable.

Example conceptual configuration:

```yaml
plugins:
  webchat.chatgpt:
    enabled: false
  webchat.claude:
    enabled: false
  webchat.grok:
    enabled: false
  webchat.gemini:
    enabled: false
  webchat.zai:
    enabled: false
  webchat.deepseek:
    enabled: false
```

For browser providers, local Extension Options remain the user-consent source of truth. Runtime configuration can narrow the effective capability set but cannot remotely override a local browser opt-out.

`plugin list`, `plugin inspect`, and `plugin doctor` are better long-term primitives than many provider-specific status commands, while user-facing `webchat ...` remains the semantic product CLI.

## 7. Other GitHub projects worth borrowing from

### 7.1 OpenCode

<https://github.com/anomalyco/opencode>

Useful ideas:

- global + project plugin scopes;
- ordered hook registration;
- internal/external plugin API convergence;
- disposable registrations;
- small typed core services with provider/auth/model/generation behavior moved outward.

Do not copy its JavaScript package-loading mechanism directly into the Rust runtime.

### 7.2 goose

<https://github.com/aaif-goose/goose>

Useful ideas:

- extensions are explicit, toggleable capabilities;
- MCP servers are reusable outside the host application;
- provider choice is independent from extensions;
- ACP can pass extension capabilities through to compatible agents.

This reinforces the Herdr direction: Herdr should be usable by ChatGPT, Claude, Cursor, Claude Code, or another controller without making any one of them the product core.

### 7.3 Agent Client Protocol

<https://github.com/agentclientprotocol/agent-client-protocol>

Useful ideas:

- protocol version negotiated independently of package version;
- capabilities negotiated at connection time;
- standardized session new/resume/prompt/cancel/update flow between clients/editors and coding agents.

Herdr should prefer ACP adapters where they eliminate per-agent hard-coded drivers, while preserving native adapters where Herdr-specific lifecycle control is stronger.

### 7.4 Playwright MCP

<https://github.com/microsoft/playwright-mcp>

Useful ideas:

- structured browser semantics instead of screenshot-only control;
- separation between MCP and CLI/skill usage;
- coding agents may benefit from concise CLI/skills rather than loading a very large MCP browser schema.

For Herdr this supports a narrow `webchat` semantic CLI/private API rather than exposing a generic browser action catalog to every planner.

### 7.5 Browser Use / Browser Harness

<https://github.com/browser-use/browser-use>
<https://github.com/browser-use/browser-harness>

Useful ideas:

- persistent browser state;
- domain/site-specific skills around a protected browser core;
- coding-agent-friendly browser CLI.

Use as browser-adapter/UAT inspiration, not as justification to turn Herdr into general RPA.

### 7.6 OpenHands

<https://github.com/All-Hands-AI/OpenHands>

Useful ideas:

- explicit runtime/action/observation separation;
- event-stream-based execution state;
- sandbox/runtime provider abstraction.

The implementation is heavier than Herdr needs, but the boundary between planner, action, observation, and execution runtime is worth preserving.

### 7.7 MCP Registry

<https://github.com/modelcontextprotocol/registry>

Useful later for:

- manifest/version/discovery concepts;
- registry metadata and publication lifecycle;
- avoiding a proprietary plugin discovery format when an MCP server is the actual extension artifact.

A Herdr plugin registry is not a `0.5.0` requirement.

## 8. Workstation portability is a first-class architecture concern

Multi-device enrollment only answers:

```text
Can Herdr route a request to this computer?
```

A development workstation also needs:

```text
Which repositories should exist?
Where should they live?
Which toolchains/agents should be present?
Which project bootstrap commands are required?
Which optional plugins/capabilities should be enabled?
Which credentials must the user re-authorize?
```

Therefore fleet enrollment and development-environment bootstrap are separate layers.

## 9. Device A → Device B: current recommended migration

Current observed state on 2026-09-04:

- device A `qingxian-macbookair` is online with the current `0.4.5-dev` runtime and the active development repositories;
- device B `yitaidiannao` is already enrolled and online;
- B currently runs a `0.4.4-dev` candidate runtime;
- B currently exposes one managed herdr-mcp UAT worktree, not a canonical `~/Documents/herdr-mcp` development checkout;
- common `~/Documents/herdr-mcp`, `libernovo-plm`, `apihub`, and `novo` roots were not present on B in this inspection.

### 9.1 Default: clone/fetch from the authoritative Git remote

For a clean committed project, prefer:

```text
GitHub/GitLab authoritative remote
        ↓
fresh canonical clone on B
        ↓
fetch desired branches
        ↓
project bootstrap/tests
```

Reasons:

- remote remains the source of truth;
- no stale absolute worktree paths;
- no copied build outputs/caches;
- no accidental secret transfer;
- easier verification and future recovery.

For herdr-mcp specifically, create a normal canonical development checkout on B instead of promoting the existing UAT worktree into the primary checkout.

### 9.2 Preserve unpushed work explicitly

Before moving an active lane from A:

1. inspect dirty state;
2. commit/push useful work to a branch when appropriate;
3. or create a `git bundle` when work must remain private/offline;
4. recreate worktrees on B from refs/branches.

Do **not** copy `~/.herdr/worktrees/**` between machines. Git worktree metadata contains machine-specific paths and shared repository relationships.

### 9.3 When LAN/SSH transfer is useful

LAN transfer is an optimization, not the source-of-truth workflow.

Use it for:

- a very large Git repository when upstream cloning is slow;
- Git LFS/object caches that are expensive to redownload;
- large non-Git test data/artifacts;
- a `git bundle` containing unpushed refs.

If cloning directly from A over SSH, reset the canonical `origin` to GitHub/GitLab afterward. Do not leave A as the permanent upstream by accident.

Avoid raw `rsync` of an entire live checkout as the normal migration mechanism. It can copy stale build products, absolute worktree links, sockets, ignored secrets, permissions, and machine-specific state.

### 9.4 Runtime and source remain separate

Migrating development to B does not mean pointing B's service at the checkout.

Correct order:

```text
install/upgrade managed herdr-mcp runtime on B
  ↓
verify fleet/link/runtime
  ↓
clone source checkout separately
  ↓
use `herdr-mcp dev sync` only when deliberately dogfooding B from that source
```

The active runtime remains an immutable generation under `~/.config/herdr-mcp/runtime/`.

## 10. New Device C: current bootstrap flow

For a new macOS computer with nothing installed:

### 10.1 Base machine

1. install Herdr stable;
2. install herdr-mcp stable from GitHub Release, not from a source clone;
3. fix PATH once;
4. complete `permissions status/verify` and Full Disk Access;
5. run `doctor`.

### 10.2 Join the existing fleet

From an already authorized owner conversation:

```text
create short-lived pairing
  ↓
C runs `herdr-mcp worker connect <pairing-address>`
  ↓
user enters the one-time code
  ↓
service + Link start
  ↓
verify C appears online
```

Do not deploy another Cloudflare Worker or create another Connector.

### 10.3 Development prerequisites

Install only what the selected projects require, for example:

- Git + GitHub/GitLab client/authentication;
- Xcode Command Line Tools/Homebrew where required;
- Node/pnpm, Python/uv, Rust, Java, Docker, etc. based on repo bootstrap contracts;
- desired coding agents.

Run `herdr-mcp scan --probe` after installing agents instead of assuming vendor availability.

### 10.4 Project reconstruction

For each selected project:

```text
authoritative Git remote
  ↓
canonical clone to configured path
  ↓
read AGENTS/CLAUDE/README
  ↓
install project dependencies
  ↓
restore only documented non-secret configuration
  ↓
run project validation
```

Secrets and personal credentials are re-authorized through Keychain/SSH/OAuth/secret manager. They are not copied from A's home directory.

### 10.5 Optional WebChat/browser layer

If C will drive or be driven by WebChat:

- install/select the supported extension channel;
- verify Native Messaging;
- explicitly enable only desired provider integrations/control targets;
- keep WebChat Control and WebChat Tool Bridge default-off.

### 10.6 Local controller layer

Cursor, Claude Code, or another local MCP client may connect directly to:

```text
http://127.0.0.1:8772/mcp
```

with the local credential path. Cloudflare is unnecessary for this same-machine controller path.

## 11. Target: portable workstation profile

The current manual/Agent-assisted process should evolve into a non-secret, inspectable workstation profile rather than copying machines byte-for-byte.

Conceptual model:

```yaml
profile: dev-main
version: 1
projects:
  - id: herdr-mcp
    remote: github:whshang/herdr-mcp
    path: ~/Documents/herdr-mcp
  - id: plm
    remote: <authoritative remote ref>
    path: ~/Documents/libernovo-plm
  - id: apihub
    remote: <authoritative remote ref>
    path: ~/Documents/apihub
agents:
  required: [one-capable-worker]
  optional: [auditor]
plugins:
  webchat.chatgpt: false
  webchat.claude: false
toolchains:
  derive_from_projects: true
secrets:
  policy: reauthorize
```

The profile records desired state and references. It never contains:

- API keys;
- OAuth refresh tokens;
- SSH private keys;
- Keychain exports;
- browser cookies;
- provider session tokens.

### 11.1 Future CLI direction

Possible interface:

```bash
herdr-mcp workstation profile inspect
herdr-mcp workstation profile export --portable
herdr-mcp workstation bootstrap --profile dev-main
herdr-mcp workstation doctor --profile dev-main
```

A later multi-device convenience path may allow an enrolled C to request an owner-approved portable profile derived from A:

```text
C -> Herdr fleet -> request profile from A
A/owner approves -> bounded non-secret manifest
C -> clone/install/verify
```

This must copy desired-state metadata, not A's live home directory or worktrees.

## 12. Bootstrap semantics

A bootstrap operation should be resumable and idempotent.

Each item reports:

```text
already_satisfied
installed
cloned
configured
needs_user_auth
blocked
failed
skipped
```

Example plan:

```text
Herdr                already_satisfied
herdr-mcp runtime    installed
fleet enrollment     already_satisfied
GitLab auth          needs_user_auth
herdr-mcp repo       cloned
PLM repo             cloned
PLM dependencies     installed
Claude Code          installed
WebChat control      skipped (default off)
final doctor         passed
```

A failed project should not corrupt already-complete projects or cause another Worker/Connector to be created.

## 13. Relationship to Work Memory

Workstation portability and Work Memory solve different problems:

```text
Work Memory
  moves task knowledge between controllers/sessions/devices

Workstation Profile
  reconstructs the tools/repos/capabilities needed to execute that task
```

Together they allow:

```text
A fails or is retired
  ↓
C joins fleet
  ↓
C bootstraps development profile
  ↓
Work Chain resumes on C
  ↓
controller continues with prior evidence/decisions/tests
```

This is the desired `1.0` portability story.

## 14. Implementation order

Do not implement all plugin/distribution ideas at once.

Recommended sequence:

### Phase A — architecture extraction

- define trusted-kernel invariants;
- define capability/plugin vocabulary;
- map current hard-coded providers/agents/transports to candidate plugin seams;
- keep current behavior unchanged.

### Phase B — internal plugin registry

- built-in plugin manifests;
- dependency/capability graph;
- deterministic enable/disable lifecycle;
- typed events + disposal;
- no public third-party loader yet.

### Phase C — migrate high-value adapters

First prove two different domains:

1. WebChat provider adapters;
2. local Agent adapter(s).

Do not migrate every subsystem simply for architectural purity.

### Phase D — workstation profile/bootstrap

- portable non-secret manifest;
- clone/install/doctor planner;
- existing-fleet pairing integration;
- current A → B and fresh C UAT.

### Phase E — external plugin boundary

Only after internal seams are stable:

- out-of-process manifest/handshake;
- permissions;
- version negotiation;
- crash isolation;
- signing/distribution policy if needed.

### Phase F — `1.0.0` compatibility freeze

- migrate configs/state;
- publish plugin/API compatibility policy;
- full multi-controller + multi-device UAT;
- release/rollback evidence;
- freeze stable contract epoch/version.

## 15. Non-goals

- cloning a whole developer home directory as onboarding;
- syncing browser cookies or Keychain secrets between machines;
- copying active Herdr/Git worktree directories between devices;
- making every Rust internal type a public plugin API;
- loading arbitrary unsigned native code into the trusted runtime;
- introducing a plugin marketplace before the plugin contract is proven;
- replacing GitHub/GitLab as repository source of truth;
- making Cloudflare mandatory for local MCP clients.
