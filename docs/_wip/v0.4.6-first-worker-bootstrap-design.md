# v0.4.6 first-Worker bootstrap design (#302)

Status: **accepted for v0.4.6 implementation on 2026-09-05**. The four architectural consequences in the decision section are the implementation contract for #302.

## Goal

Add one guided command:

```text
herdr-mcp worker bootstrap
```

that takes an already-installed v0.4.6 runtime from “no Herdr fleet exists” to one canonical enrolled device with an operational production Link and a verified public MCP/OAuth origin. The command may pause only for Cloudflare authorization/account choice that cannot be inferred safely. ChatGPT Connector creation/OAuth remains the final human/Web-UI step after the command succeeds.

This closes the remaining #302 gap rather than merely wrapping the current manual document.

## 1. Command boundary

The command **does include creation/configuration of the Cloudflare Worker**. If the user still had to create the Worker, provision secrets, create the first pairing, reconcile the canonical device id, and install the Link manually, #302 would remain materially unresolved.

The state machine is:

```text
local preflight
-> classify first fleet vs existing fleet
-> Cloudflare read-only account/Worker discovery
-> acquire temporary Cloudflare authorization (device flow preferred; API token fallback)
-> deploy the exact release-matched Edge bundle
-> provision bootstrap secrets
-> create + consume the first pairing
-> persist the canonical dev_<ULID> device credential locally
-> remove the temporary bootstrap operator credential
-> install/reconcile the production Link to runtime/current
-> verify Edge/OAuth/device/Link/runtime-generation alignment
-> operational_ready=true
-> print the canonical /mcp URL for ChatGPT
```

It does **not** automate ChatGPT Developer Mode or the ChatGPT Connector/OAuth browser consent. Those are external account/UI authorization steps and remain the final instruction after a successful bootstrap.

### Automate the existing Cloudflare/Wrangler path; do not invent a second installer

`worker bootstrap` is the executable form of `docs/i18n/en/agent-install.md`, not a replacement deployment architecture. It must preserve the current manual-flow invariants and artifacts:

- obtain the release-matched Edge sources/config template used by the manual guide;
- generate a non-secret `wrangler.user.toml` from the published user example;
- set the chosen Worker name and bootstrap workstation value through the same config fields;
- keep `workers_dev = true`;
- keep `[[r2_buckets]]` commented out unless the user explicitly enables R2;
- verify the token/device-flow credential and account before deploy;
- list existing Worker scripts before any deploy mutation;
- use the same Worker deploy and Worker-secret semantics as the manual flow;
- verify workers.dev `/health` before optional Custom Domain finalization.

Do not use `wrangler@latest`. The release must pin a Wrangler version known to pass the 0.4.6 Edge tests, and the bootstrap should invoke that pinned version when a Wrangler operation is required. The generated `wrangler.user.toml` contains no credential and may be retained as non-secret local recovery metadata; the Cloudflare credential itself is never written into it or any Wrangler auth profile.

The device-flow exception is intentional: do **not** literally call `wrangler login --device`, because Wrangler persists the returned OAuth credential. `herdr-mcp` performs the same Cloudflare device authorization protocol in memory, then supplies the resulting bearer only to the current pinned-Wrangler/API process environment. API-token fallback likewise uses temporary process environment/stdin. This keeps the deployment behavior aligned with the existing guide while satisfying #302's stronger no-credential-on-disk invariant.

### Cloudflare authorization: device flow first, API token fallback

The default beginner path is Cloudflare's OAuth 2.0 Device Authorization Grant, compatible with the current `wrangler login --device` flow. Cloudflare currently presents a short user code at `dash.cloudflare.com/oauth2/device`, normally gives about five minutes to approve it, and the CLI polls until Cloudflare returns an access token.

`herdr-mcp` should implement the device-flow exchange directly instead of invoking `wrangler login --device`: Wrangler intentionally persists OAuth credentials, while #302 requires the bootstrap Cloudflare credential to **never be written to disk**. Herdr may reuse Cloudflare's supported device-flow protocol/client metadata and scopes, but the resulting access/refresh credential exists only in the bootstrap process memory and is discarded when the command ends. It is never printed.

Beginner interaction:

1. print `Open Cloudflare to authorize Herdr` and open the verification URL when possible;
2. show only the non-secret short user code and expiry;
3. poll with Cloudflare's instructed interval without busy-looping;
4. on `authorization_pending`, keep waiting and show quiet progress;
5. on expiry/denial/network failure, stop with a plain-language next action: `Run the same command again to get a new Cloudflare authorization code.`

Fallback path: if device flow is unavailable or the user explicitly chooses an API token, accept `CLOUDFLARE_API_TOKEN` from the current process environment or a no-echo interactive stdin prompt. Never accept the token as an argv value. Before the prompt, state the minimum core permissions exactly:

- Account → **Workers Scripts → Edit**
- Account → **Account Settings → Read**
- only when the user explicitly enables optional R2: Account → **Workers R2 Storage → Edit**

Recommend a short token expiry. Custom-domain discovery/routing may require extra Zone read/route permission only when that optional path is selected; do not inflate the core Worker bootstrap token pre-emptively. Validate an API token with `/user/tokens/verify`, then map each 403 to the missing permission instead of reporting only an HTTP status.

### Credential lifetime and redaction

Cloudflare credentials are ephemeral bootstrap inputs, not Herdr state:

- never write them to config, `state.db`, the bootstrap journal, temp files, Wrangler config, Keychain, logs, telemetry, crash summaries, shell history, or command arguments;
- never pass them as a literal argument to Wrangler or another child process;
- keep them only in process memory and zero/drop the owned buffer as soon as Cloudflare work is complete;
- a credential pasted by the user into an Agent conversation is the user's input, but **herdr-mcp must never echo or reproduce it in any output**.

All bootstrap output/error/status paths use one shared sanitizer. Reuse the existing `status.rs::sanitize_probe_token` and `runtime_meta.rs::redact_command_summary` rules rather than creating a parallel redaction policy, and extend them with Cloudflare credential shapes before the bootstrap code can emit errors. Tests must inject representative API/OAuth token forms and assert the literal never appears in stdout, stderr, structured errors, persisted state, or command summaries.

At command completion, always print the Cloudflare API-token management/revocation dashboard link and: `If a Cloudflare credential appeared in any conversation or terminal, revoke it now.` For API tokens, if the current token can identify and revoke itself without requesting broader permissions, attempt self-revocation after all Cloudflare API work, then report only `Cloudflare bootstrap token revoked` or `Could not revoke automatically; use the link above`. A 403 on self-revoke does not turn an otherwise successful bootstrap into failure. OAuth device-flow credentials are discarded locally; do not persist a refresh token merely to revoke later.

## 2. Idempotency and failure recovery

Bootstrap is a resumable state machine, not a shell script that assumes every previous mutation succeeded.

“Safe to rerun” means bootstrap never leaves an **unknown or untracked half-configured state**. A remote Worker or other resource may intentionally remain after a failure only when the mutation outcome has been read back, ownership is proven, and the exact incomplete phase is durably journaled; the next run must adopt and continue that verified state instead of creating a duplicate. If outcome or ownership is uncertain, the command stops before any compensating/destructive mutation and resolves the ambiguity by read-back on the next run.

Persist a non-secret journal at:

```text
~/.config/herdr-mcp/bootstrap/first-worker-v1.json
```

mode `0600`, updated atomically. It may contain only facts needed to resume, for example:

- schema/version and bootstrap phase;
- installed release/source identity and Edge bundle digest;
- Cloudflare account id, Worker name, bootstrap/final origin;
- mutation receipts/observed resource identifiers;
- canonical device id after enrollment;
- runtime generation/source commit expected at completion.

It must never contain the Cloudflare API token, device secret, `LINK_SHARED_SECRET`, raw pairing code, OAuth secrets, or static bearer values.

Long-lived local secrets use the existing credential/Keychain boundary. A secret that must survive a retry is generated once, stored there first, and only a non-secret reference/fingerprint is journaled.

Every remote phase follows the same protocol:

```text
read current state
-> compare with journal + expected ownership
-> if already correct, adopt it
-> otherwise perform one bounded mutation
-> read back and verify
-> atomically advance the journal
```

Rules for the required failure cases:

- **Network loss / ambiguous response:** never blind-replay a Worker, secret, pairing, or route mutation. Read Cloudflare/Edge state first; retry only when the read proves the mutation did not land.
- **Invalid/under-scoped token:** no Cloudflare mutation is attempted. Preserve the current phase and accept a new token on rerun.
- **Worker already exists:** never silently treat existence as success. Read it back and classify it. If its Herdr ownership marker and release identity match the journal, print `Existing Herdr Worker verified; resuming configuration` and continue from the first incomplete phase. If it belongs to an existing Herdr installation, switch to the existing-Worker flow. If ownership is unrelated or ambiguous, stop and explain that the name is occupied; only an explicitly confirmed first-Worker install may choose another name after proving the existing Worker is unrelated.
- **No workers.dev subdomain:** read the account subdomain first. If none exists, create one once, read it back, and journal the verified value. If creation fails, report `Cloudflare account has no workers.dev subdomain yet; configuration was not completed` and preserve a resumable phase. Do not deploy a Worker with a fabricated origin.
- **R2 unavailable/not enabled:** the core path never requests, provisions, or binds R2. R2 absence and lack of a payment method are therefore not errors. If the user explicitly enabled the optional artifact relay, fail that optional phase with an actionable R2 message while leaving the core Worker state resumable; never silently remove an expected binding or pretend R2 was configured.
- **Failure after Worker deploy but before enrollment:** retain the verified Worker and journal; rerun continues from the first incomplete phase instead of deploying another Worker.
- **Failure after enrollment:** the canonical device identity is authoritative; rerun reuses it and completes Link/runtime reconciliation.

Rollback means restoring a known verified phase, not deleting resources after an uncertain network result. Temporary files are always removed; remote resources are deleted only when ownership and mutation outcome are both certain. A failed bootstrap therefore remains safely resumable rather than “clean-looking but unknown”.

## 3. Fleet classification and device equality

This ordering is a hard invariant:

```text
classify fleet intent
-> perform read-only Cloudflare discovery
-> establish first-fleet certainty
-> only then permit Cloudflare mutation
```

Before any Cloudflare mutation, the command checks local enrolled identity and, once temporary Cloudflare authorization/account context is available, lists the account’s Worker scripts for an existing Herdr Worker. The existing `tests/agent-install-doc.test.mjs` assertion that fleet classification precedes Cloudflare authorization/mutation is a hard ordering invariant and must not be weakened; implementation adds a command-level regression that records Cloudflare calls and proves zero mutations occur before classification completes.

If an existing fleet is found, `worker bootstrap` stops the first-Worker mutation path and directs the user to obtain a pairing from **any enrolled device**, then use `worker connect` on this computer.

The first enrolled device is not an “owner”. It is a normal `DeviceRecord` with the same fleet-admin capability model as every other active enrolled device. No owner/member hierarchy or permanent bootstrap role is introduced.

The core path targets **Workers Free**: `workers_dev=true`, no R2 binding, no card requirement, and no Custom Domain requirement. A suitable existing Cloudflare zone can still be offered as a convenience after the Worker is healthy on workers.dev, but declining or lacking a zone is a normal successful path.

### First enrollment without the old two-deploy identity dance

The current compatibility path can authorize fleet administration with a configured legacy/default workstation plus shared secret. The new bootstrap must not make a fake hostname/default workstation into the canonical device id.

For a genuinely empty fleet, bootstrap uses a **temporary operator bearer only for first enrollment**, reusing the existing Worker operator-auth boundary rather than adding a privileged device class:

1. generate/store the bootstrap bearer locally as secret material;
2. provision it as the Worker’s temporary static operator secret;
3. use it to create the first pairing while the registry is empty;
4. consume that pairing locally, letting `DeviceRegistryDO` generate the canonical `dev_<ULID>` and per-device credential;
5. verify that the new device credential independently authenticates as fleet-admin;
6. delete the temporary static operator secret and verify it no longer authenticates.

The Worker is therefore deployed once. `DEFAULT_WORKSTATION_ID` is not rewritten from a bootstrap placeholder to the canonical device id, and no second deployment is required for identity reconciliation.

If the registry is non-empty at step 3, first-enrollment bootstrap fails closed and switches to the existing-fleet path.

## 4. Relationship to #306 and #307

Bootstrap is not complete merely because `/health` is 200 or the device appears online.

After first enrollment, the command must use the existing exact-generation reconciliation path so that:

```text
runtime/current generation
== local runtime health generation
== runtime-control desired/active generation
== loaded production Link generation
== Edge device heartbeat generation
```

A stale `local-mcp-active` bootstrap alias is never an accepted terminal state.

The authoritative final check should report at least:

```text
Local runtime       PASS
macOS permissions   PASS
Production Link     PASS
Runtime generation  PASS
Edge/OAuth          PASS
Canonical device    PASS
Device online       PASS
Operational ready   TRUE
ChatGPT MCP URL      https://.../mcp
```

`operational_ready=true` is the ordinary-user completion signal. Maintainer-only cutover sealing remains separate and must not make a successful install look incomplete.

Bootstrap does not synthesize a second readiness calculation. Its terminal readiness gate is the existing `herdr-mcp link status` path itself: after all reconciliation is complete, bootstrap must run/read that status and require its returned `operational_ready` field to be exactly `true`. Any other value is a bootstrap failure with the `link status` diagnostic preserved in sanitized output.

Before returning success, bootstrap performs an authenticated read-only E2E probe through the same public Edge/device route. The regression must start from the historical stale-alias shape and prove the first remote call does **not** return `runtime_generation_superseded_before_dispatch`.

## 5. Beginner interaction: what each screen says

Internal words such as `fleet`, `principal`, and `generation` are not primary UI text. When they are unavoidable in diagnostics, pair them with plain language (`your Herdr setup`, `authorized app`, `running Herdr version`). The normal path is intentionally short:

| Screen | User-facing message | Normal wait | Failure next step |
| --- | --- | --- | --- |
| 1. Check | `Checking whether this computer is already connected to Herdr…` | seconds | Existing setup → explain that no new Worker will be created and switch to connect/repair guidance. |
| 2. Cloudflare | `Authorize Herdr in Cloudflare. Your Cloudflare credential will not be saved.` Open device URL + show short code. | usually under 5 minutes; code expires | Expired/denied/offline → `Run the same command again; nothing has been changed yet` when no mutation occurred. |
| 3. Account | `Using Cloudflare account <name>.` Auto-select one account; ask once only when several accounts are materially possible. | seconds | Explain which account permission/read failed. |
| 4. Worker | `Creating or resuming your Herdr Worker…` Show Worker name, never credential. | tens of seconds | Distinguish `name already used`, `created but configuration incomplete; rerun will resume`, and permission/network failures. |
| 5. Computer | `Connecting this computer to your Worker…` | seconds | Preserve canonical device identity if already created; rerun resumes rather than pairs again. |
| 6. Connection | `Starting the background Herdr connection and checking it can reach Cloudflare…` | seconds to bounded network fallback | Report the hostname/transport problem in plain language; do not create a second Worker. |
| 7. Done | `Herdr is ready on this computer.` Print public `/mcp` URL and the next ChatGPT action. | immediate | Never claim success unless `operational_ready=true` and the authenticated read-only probe passed. |

API-token fallback inserts one extra screen before step 3. It lists the minimum permissions, recommends a short expiry, accepts the token with no echo, and never prints the token back in success or failure output.

Acceptance measures the **actual** human work, not just command count. Target for a normal single-account, no-R2, workers.dev install is: one bootstrap invocation, one Cloudflare browser approval, then the existing ChatGPT Connector creation + Herdr approval needed for the first ChatGPT request. Account/zone questions appear only when genuinely ambiguous. Real UAT records the exact number of user interventions and elapsed wall time; if the result still resembles the current ten-plus-step manual flow, #302 is not complete.

## 6. Uninstall: local cleanup only, no Cloudflare deletion

`herdr-mcp uninstall` never retains/reacquires a Cloudflare credential and never queries Cloudflare to decide what to delete. Before local state is removed, it reads only locally known non-secret facts: Worker name/public origin and whether this installation has ever recorded Connector activity. If no suitable local Connector-history fact exists today, implementation should add the smallest non-secret local marker/timestamp at successful Connector-management time; do not create remote dependency for uninstall.

After local uninstall succeeds, print:

```text
Herdr has been removed from this computer.
Your Cloudflare account still contains Worker <worker-name>.
Open Cloudflare Workers dashboard: <direct Worker/dashboard link>
```

Then choose wording solely from local history:

- **No local Connector history:** explain that the remaining Worker has no known client attached from this installation and may be left in place; do not perform a remote check merely to strengthen that statement.
- **Connector history exists:** recommend manually deleting the Worker when the user is finished with it, because its Durable Objects can retain device records, Connector authorization records, and revocation tombstones.

Do not add remote cleanup, token retention, delete-on-uninstall, or a new failure mode where local uninstall depends on Cloudflare availability.

## 7. Required implementation tests after design approval

Implementation should add:

1. state-machine unit tests for resume after each mutation boundary;
2. a mock-Cloudflare/Edge E2E happy path covering device authorization -> first Worker creation -> first pairing -> canonical device -> Link/runtime reconciliation -> `operational_ready`;
3. API-token permission failure proving a valid-but-under-scoped credential produces the exact missing-permission guidance and **zero mutation after the failing preflight**;
4. Worker-same-name tests: resume an owned incomplete Worker, redirect an existing Herdr setup, and refuse unrelated/ambiguous ownership rather than silently skipping;
5. ambiguous/mid-mutation network interruption followed by rerun, proving read-before-retry and no duplicate Worker, secret, or pairing;
6. workers.dev-subdomain absence/create/read-back recovery and R2-disabled core success on the Free path;
7. redaction tests with representative Cloudflare API/OAuth token shapes asserting the literal credential never appears in stdout, stderr, structured errors, telemetry/command summaries, bootstrap journal, config, or `state.db`;
8. device-flow expiry/denial tests with a human-readable rerun action and no persisted OAuth credential;
9. first-enrollment test proving the temporary Herdr bootstrap operator bearer is removed after canonical device auth works;
10. `tests/agent-install-doc.test.mjs` plus a command-level call-order regression proving existing-setup classification completes before **any** Cloudflare mutation;
11. #306/#307 regression proving exact runtime-generation alignment and a successful first authenticated read-only remote call;
12. uninstall tests proving zero Cloudflare calls, correct Worker-name/dashboard guidance, and distinct no-Connector-history vs Connector-history text.

After those are green, run one real UAT on a genuinely unenrolled environment and retain sanitized command/output evidence. The real UAT must not reuse or destroy an existing production fleet.

The implementation acceptance gate is exactly the requested release gate: `cargo fmt --check`, clippy with warnings denied, `cargo test -p herdr-mcp`, and `npm run test:edge`, plus the mock E2E/redaction tests above. The real UAT report records the exact command, sanitized output, number of user actions, and elapsed time from invocation to the first successful remote tool call.

## Accepted implementation contract

The product-owner decisions settle Worker creation and device-flow preference. The accepted implementation must preserve these architectural consequences:

1. **`worker bootstrap` automates the existing `agent-install.md` Cloudflare/Wrangler flow** with a pinned Wrangler version; it does not create a second deployment system.
2. **Cloudflare device flow is implemented in-memory by herdr-mcp** rather than invoking credential-persisting `wrangler login`; API token is fallback only.
3. **First enrollment uses a temporary existing Herdr operator-bearer boundary**, removed immediately after the canonical device credential is proven, rather than a fake default workstation or a new owner role.
4. **Uninstall remains local-only** and uses local Connector-history evidence solely to choose guidance; it never queries or deletes Cloudflare resources.
