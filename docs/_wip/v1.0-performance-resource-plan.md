# Herdr-MCP 1.0 Compile and Memory Efficiency Plan

Status: active cross-cutting 1.0 engineering plan.

This plan is subordinate to the 1.0 milestone sequence and frozen architecture decisions. It does not introduce a new product stage, state authority, daemon, scheduler, public MCP tool, or contract epoch. It defines performance/resource constraints and measurement gates that each 1.0 stage must satisfy where applicable.

## 1. Objective

Herdr-MCP is a remote control plane for durable work on real developer machines. Its resource target is therefore different from a standalone coding-agent CLI:

- the workstation Runtime is long-lived and must stay cheap while idle;
- Link and Supervisor remain independent reliability/lifecycle boundaries;
- many WebChat resources, projects, work chains, devices, and Agent sessions may exist while only a small subset is active;
- Work Memory and continuity must survive controller changes without requiring full historical payloads to stay resident;
- multi-device scheduling already belongs to Fleet Control and beta.2 reservation/failover, so resource awareness must extend that authority rather than create a second scheduler;
- browser-extension memory pressure is a browser lifecycle problem and must not be solved by moving browser state into the Rust Runtime.

The goal is predictable scaling: low idle cost, bounded active-set growth, controlled peak memory under concurrent work, and faster Rust iteration/CI without weakening release validation.

## 2. Architectural invariants

The following are non-goals even if another harness obtains lower benchmark numbers with them:

1. **Do not merge Runtime, production Link, or Supervisor solely to reduce RSS.** Their independent restart/update/failure boundaries are product reliability features.
2. **Do not create per-provider, per-account, per-project, or per-conversation daemons by default.** ChatGPT/Gemini/other adapters should remain lightweight resources/capabilities on existing Runtime/Extension boundaries unless an isolation requirement is proven.
3. **Do not make a local embedding/model runtime part of the idle Herdr baseline.** If a future Work Memory retrieval design needs local inference, it must be optional, lazy-loaded, and unloadable after idle; external/model-assisted retrieval remains preferable when it preserves correctness and privacy requirements.
4. **Do not add a second resource scheduler.** Device memory/CPU pressure becomes evidence consumed by the existing Fleet Control reservation/admission path in beta.2.
5. **Do not trade away validation coverage for compile-time numbers.** Release CI semantics change only when an equivalent or stronger gate is demonstrated.
6. **Do not use browser/OS memory pressure as correctness authority.** Resource signals may delay, queue, compact, unload, or route optional work; they must not silently alter authorization, mutation delivery, generation fencing, or evidence truth.

## 3. Existing Herdr properties to preserve

The current Rust Runtime already uses bounded structures and payload limits extensively. Examples include:

- EventCache digest history capped at 2048 entries;
- MCP HTTP session registry capped at 1024 sessions;
- bounded text transfer, Git output, prompt replay, event frames, relay payloads, artifact import, and web-artifact cache;
- result compaction before model context;
- bounded long-exec output and persisted completion evidence;
- shared local SQLite/WAL state rather than one state service per feature.

Therefore 1.0 should not respond by scattering more per-object limits. The missing layer is **aggregate admission and lifecycle control** across many individually valid objects.

## 4. Measurement contract

Optimization work starts with repeatable measurements. A change without a comparable before/after workload is not a performance change.

### 4.1 Runtime memory measurements

Record at minimum:

- process RSS on all supported workstation platforms;
- Linux PSS / anonymous PSS when `/proc/<pid>/smaps_rollup` is available;
- peak resident memory for burst workloads;
- idle memory after a burst and after a bounded settle interval;
- process/thread count;
- active object counts: MCP sessions, Work Memory chains, browser resources/endpoints, exec sessions, Agent reservations, cache entries;
- when allocator diagnostics are available, live allocator bytes versus resident anonymous memory.

Canonical workload families:

1. idle installed Runtime + Link + Supervisor;
2. one active controller/session;
3. 10 lightweight concurrent controller/session resources;
4. Work Memory append/checkpoint/resume/search over small and large histories;
5. many Browser Endpoint/Resource Registry entries with a small active subset;
6. concurrent `exec_start`/result consumption with bounded outputs;
7. large Git/diff/tool-result bursts followed by idle recovery;
8. beta.2 multi-device reservation with several candidate Agents/resources.

Measure **incremental cost per additional active resource**, not only total RSS. Herdr's 1.0 design should keep inactive historical objects predominantly in SQLite/on-disk state and make per-active-session state small.

### 4.2 Compile measurements

Keep separate baselines for:

- GitHub release/CI verification wall time;
- `cargo fmt`, Clippy, tests, docs/schema generation phase time;
- `sccache` hit/miss/error statistics;
- cold build;
- warm no-op build;
- warm touched-file build for representative high-fanout and low-fanout Rust files;
- peak build-process RSS on constrained developer machines.

No-op cache timings alone are insufficient for crate-boundary decisions. Touched-file rebuilds are the relevant measure of invalidation fan-out.

## 5. Compile acceleration strategy

### 5.1 First: expose where time is spent

The 0.4.x release gate already concentrates most elapsed time in the Rust authoritative gate. Keep phase timing and `sccache --show-stats` available so 1.0 decisions use measured data rather than assumptions.

### 5.2 Remove accidental rebuild/invalidation before structural refactors

Audit for inputs that cause broad recompilation without changing runtime semantics, including generated build metadata, environment-driven build scripts, broad feature unification, and high-fanout modules that change frequently.

The preferred order is:

1. eliminate accidental invalidation;
2. narrow developer build target/feature surface where the task allows it;
3. split a crate/module boundary only when touched-file timing proves that boundary materially reduces rebuild fan-out;
4. preserve the full release build/gate independently.

Do not copy another project's crate decomposition. Herdr's natural boundaries are its existing ownership domains: Runtime execution/core state, Link/relay transport, Edge/contract compatibility, browser Extension, and optional feature modules. A split that makes those ownership boundaries less clear is a regression even if a benchmark improves.

### 5.3 CI cache policy

- Keep one primary Rust compilation cache strategy. Do not stack target-directory caches on top of `sccache` without measured need.
- Keep `CARGO_INCREMENTAL=0` for ephemeral release CI while `sccache` remains effective; revisit only with CI evidence.
- Cache Cargo registry/git downloads only if download time is material and the cache has a clear invalidation policy.
- Evaluate `sccache` by actual hit rate and saved compile time, not by whether the action itself adds setup seconds.

### 5.4 Linker and profile experiments

`lld`/`mold`, codegen-unit changes, incremental builds, or a dedicated fast local profile are A/B experiments, not defaults.

Keep two concerns separate:

- **release/CI profile:** reproducible, full validation, stable artifact behavior;
- **developer constrained-memory/fast-iteration profile:** may use incremental compilation, different codegen units, or a faster linker if local measurements prove a benefit.

A low-memory local profile must never silently weaken the release gate or become a CI workaround for a real compilation regression.

### 5.5 Clippy/test overlap

Do not remove `--all-targets` or otherwise reduce lint coverage merely because Clippy and tests compile overlapping code. First measure phase-level compilation reuse. Any future gate restructuring must demonstrate equivalent target coverage and total runner/resource impact, not just lower wall-clock time in one job.

## 6. Runtime memory strategy

### 6.1 Keep the resident control plane small

The Runtime should retain only data required for low-latency control and correctness. Durable detailed history belongs in the existing local state store; compact current projections belong in memory.

Provider/WebChat adapters should store stable identifiers, fencing/revision state, active request state, and bounded recent observations. They should not retain full page histories, DOM snapshots, or duplicated Work Memory transcripts.

### 6.2 Work Memory: projection before full deserialization

Alpha 2 correctly made the local Shared State Store authoritative and `resume` return a verified checkpoint plus a bounded recent raw tail. Extend that principle to 1.0 search/retrieval:

- index/search lightweight searchable projections and metadata first;
- load full evidence bodies only for the selected bounded result set;
- avoid materializing images, large tool payloads, environment snapshots, or unrelated replay fields during search when the query does not need them;
- preserve exact evidence refs so a later targeted read can recover the original body.

This is preferable to keeping an embedding/model service resident merely to make full-session search convenient.

### 6.3 Aggregate byte-budgeted admission

Counts alone are not a safe concurrency limit when object sizes vary. For operations that may deserialize/load several histories, artifacts, tool results, or evidence blobs concurrently, admission should consider estimated source bytes plus bounded worker concurrency.

Target pattern:

```text
candidate metadata
    -> estimate/load-size class
    -> bounded aggregate byte batch
    -> deserialize/process selected batch
    -> release temporary bodies
```

One oversized/unknown object may be isolated rather than dropped. A byte estimate is an admission heuristic, not an RSS guarantee; validation must include serde/decoded expansion.

This policy should be implemented at the actual high-memory operation, not as a generic global semaphore that serializes unrelated lightweight calls.

### 6.4 Cache lifecycle

Every new 1.0 cache must answer:

- what is the authoritative source;
- maximum entries and/or maximum bytes;
- active versus inactive retention policy;
- invalidation/freshness rule;
- whether eviction affects only latency or could affect correctness;
- how memory is released after a burst.

Prefer compact projections and bounded LRU/TTL behavior. Do not cache entire Work Memory chains or browser page bodies merely because individual payloads already pass a per-request limit.

### 6.5 Heavy optional components

If future functionality introduces a materially heavy component (local embedding model, parser/indexer, language server, browser analysis engine):

1. measure its cold-start and resident cost;
2. keep it outside the idle baseline unless it is genuinely latency-critical;
3. share one instance across eligible sessions when correctness allows;
4. unload/close it after idle if reload cost is acceptable;
5. after unload, verify resident memory actually returns toward baseline.

Do not implement an idle-unload framework before such a component exists.

### 6.6 Allocator/retained-memory policy

Herdr currently has no evidence that allocator retention is a dominant problem. Therefore jemalloc, arena tuning, `malloc_trim`, decay tuning, and retained-heap watchdogs remain **measurement-triggered experiments**.

Only start this lane when burst-to-idle tests show a repeatable gap between live application state and resident anonymous memory. Then compare system allocator versus candidate tuning on the same workload, including latency and CPU cost. A purge/watchdog is acceptable only if it addresses measured retained pages and does not become periodic background churn.

## 7. Multi-device and Agent resource awareness

Beta.2 already owns reservation/failover. Extend its candidate evidence with coarse resource pressure instead of adding a new scheduler.

Candidate resource evidence may include:

- available/total memory where safely obtainable;
- current Herdr-controlled active Agent/exec reservation counts;
- coarse build/test pressure;
- recent resource admission rejection.

The first version should use conservative bands (`healthy`, `pressured`, `critical`/unavailable) rather than pretend RSS predictions are exact. The scheduler may prefer another eligible device or queue optional parallel work when pressured. It must not reroute a mutation whose device/workspace affinity is already fenced.

Hard safety limits remain explicit; dynamic resource evidence refines admission inside those limits rather than replacing them.

## 8. Browser Extension boundary

Long WebChat conversations can consume far more memory in the browser than the Rust Runtime. The correct mitigation remains continuity/checkpoint/rollover and bounded extension caches:

- compact old conversation context into verified checkpoints + bounded raw tail;
- avoid retaining full DOM/history bodies in Extension state;
- keep page-health memory signals advisory;
- when a page is unhealthy, preserve Herdr Work Memory/evidence before rollover rather than making browser memory state authoritative.

Do not move browser transcript/DOM retention into the workstation Runtime to make Chrome look lighter.

## 9. Stage integration

This plan does not add another milestone. Apply it at existing boundaries:

| Stage | Resource/performance obligation |
| --- | --- |
| alpha.1 Fleet Control | Preserve one authority for leases/reservations; no resource scheduler fork. |
| alpha.2 Work Memory | Preserve checkpoint + bounded raw-tail design; add measured projection/byte-budget work only when search/history scale requires it. |
| alpha.3 Browser Registry | Keep registry entries lightweight/bounded; resource identity must not retain page bodies. |
| alpha.4 ChatGPT adapter | Prove adapter adds lightweight per-resource state and no provider daemon/full-history duplication. |
| alpha.5 Gemini adapter | Prove the same shared adapter seam with a second provider; compare incremental memory per endpoint/provider. |
| beta.1 reliability/postcondition | Add resource diagnostics needed to distinguish leaks/retention/runaway active objects; ensure recovery loops themselves are bounded. |
| beta.2 reservation/failover | Consume coarse device pressure in existing Fleet Control admission/routing; add aggregate workload budgets where measured. |
| rc.1 | Run compile and runtime scaling gates on supported OSes; verify burst-to-idle recovery, N-1/N+1 behavior, rollback, and no contract/reliability regression. |

## 10. Acceptance gates

Before 1.0 RC:

1. A repeatable compile benchmark report exists for CI and representative local touched-file builds.
2. CI phase timing and cache effectiveness are observable; any semantic gate change has explicit equivalent-coverage evidence.
3. Runtime memory baselines exist for idle, one active session, multi-session, Work Memory search/resume, browser registry scaling, and burst-to-idle recovery.
4. New 1.0 caches/state projections have explicit entry/byte/lifecycle bounds.
5. Work Memory/history operations that load variable-size payloads do not rely on item-count-only parallelism when measured payload variance can create unsafe peaks.
6. ChatGPT and Gemini adapter verticals demonstrate small incremental memory rather than duplicated runtime/provider baselines.
7. Beta.2 resource-aware admission extends Fleet Control rather than adding a second scheduler or weakening affinity/fencing.
8. No optional heavy component is permanently resident without measured latency justification.
9. Allocator changes, linker changes, Cargo profile changes, and crate splits are accepted only on measured Herdr workloads.

## 11. External-project lessons deliberately not copied

External harnesses such as jcode are useful evidence that shared-server baselines, PSS measurement, lazy heavy-component lifecycle, allocator-retention diagnostics, byte-based admission, and constrained-memory build profiles can matter. Herdr should internalize only the underlying failure modes:

- duplicated long-lived baselines;
- freed-but-resident allocator memory;
- heavy optional components pinned while idle;
- count-bounded but byte-unbounded concurrent deserialization;
- build invalidation fan-out;
- resource-unaware parallel Agent spawning.

Their process topology, allocator constants, Agent limits, embedding architecture, crate graph, and build profiles are not Herdr defaults. Each mechanism above requires Herdr-specific measurement and must preserve Herdr's existing reliability, Fleet Control, Work Memory, Extension, and contract boundaries.
