Status: **planned after v0.4.1 stable**
Target: **v0.4.2 stable quality/consolidation release**
Scope: execution-context correctness, local/CI parity, delegation quality, progressive-skill disclosure, safe resource lifecycle, documentation taxonomy, documentation-site information architecture, and homepage redesign.

## 1. Baseline inherited from v0.4.1

v0.4.1 establishes the baseline this plan must preserve:

- Rust runtime owns production MCP/service/updater/Link/Native Messaging paths;
- public MCP contract remains epoch 2 / 18 tools;
- `herdr-mcp scan` records evidence-backed client Agent capabilities without replacing Herdr's live-agent authority;
- Herdr remains authoritative for live agents (`agent.list` / snapshot), loaded detection manifests and supported agent start behavior;
- `herdr_inspect.capability_inventory.available_agents` exposes locally startable Agent kinds only after current visibility-policy filtering;
- Chrome Web Store identity has one machine-readable SSOT in `contracts/browser-extension-store.json`; the Store ID is not duplicated as a Rust source literal;
- normal Native Messaging install is Store-first; unpacked/dev identity requires an explicit maintainer override;
- Runtime GitHub Releases no longer distribute the browser extension;
- `bin/herdr-extension-host` is compatibility delegation to the Rust owner, not a second installer/broker;
- browser extension has its own release cadence and automatic Store update path;
- end-user browser docs are Store-first; historical unpacked installation is history/maintainer-only evidence.

Do not regress any of these boundaries in v0.4.2.

## 2. Release thesis

v0.4.2 is **not** a feature-accumulation release. It should make the system cheaper to operate, easier to reason about and much easier for a new user/contributor to understand.

### In scope

1. Local release-gate / GitHub CI parity and execution-environment isolation.
2. Direct-tool vs Agent-delegation efficiency.
3. Bounded Agent capability refresh and better dispatch evidence.
4. Progressive Skill disclosure measurement and migration decision.
5. Safe, explicit resource cleanup planning for panes/worktrees/closed exec state.
6. Stability/soak evidence without broad protocol rewrites.
7. `docs/` taxonomy and historical-evidence cleanup.
8. User-facing wording/version-drift cleanup.
9. Real documentation-site homepage and navigation redesign.
10. Release-engineering maintenance found during v0.4.1, including GitHub Actions runtime deprecation warnings.

### Explicitly out of scope unless a measured blocker appears

- adding a 19th public MCP tool;
- changing contract epoch 2 solely for convenience;
- broad Link/WebSocket protocol rewrite;
- new browser mutation/terminal/true-steer features;
- aggressive browser DOM manipulation or speculative memory hacks;
- always-on analytics/telemetry;
- automatic destructive cleanup of dirty/unmerged/active resources;
- coupling browser-extension semver to Rust runtime semver;
- duplicating Herdr's Agent detector or hard-coding Herdr Agent kinds in herdr-mcp.

## 3. P0 — one authoritative release/test execution profile

### Problem observed during v0.4.1

The local pre-PR gate and GitHub CI were not initially identical. GitHub runs:

```text
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace
```

while a narrower local package-only gate initially passed. Managed Herdr execution also injects values such as `HERDR_MCP_PORT=8772`; a HOME-only Native Host UAT inherited a real `HERDR_MCP_CONFIG_DIR`, proving that test/release commands must not silently inherit production-scoped overrides.

### Required implementation

Create one maintainer-facing gate entrypoint (for example `scripts/release-gate.sh`; exact name may change after audit) and make both local release validation and CI consume the same command sequence.

It must cover at least:

- `cargo fmt --check`;
- `cargo clippy --workspace --all-targets --all-features -- -D warnings`;
- `cargo test --workspace`;
- Node build/tests;
- docs-site build;
- Edge tests;
- browser-extension smoke;
- package/shell/diff hygiene;
- release-surface / Store-identity contracts.

Define an explicit **release/test environment profile**. At minimum audit and deliberately scrub or set:

- `HERDR_MCP_PORT`;
- `HERDR_MCP_CONFIG_DIR`;
- `HERDR_MCP_INSTANCE`;
- `HERDR_EXTENSION_PATH`;
- `HERDR_EXTENSION_ORIGIN`;
- `HERDR_MCP_ROOT`;
- production contract/runtime overrides.

Do not globally remove production environment behavior from the runtime. The gate must isolate tests; runtime semantics remain explicit and backwards compatible.

### Parallel-test hardening

Audit tests that mutate process-global environment (`HOME`, `HERDR_MCP_*`). Prefer, in order:

1. dependency/path injection;
2. explicit fixture parameters;
3. a shared process-global test guard only when injection is impossible.

Do not hide flaky parallel behavior by globally forcing `--test-threads=1` unless a specific external dependency genuinely requires serialization.

### GitHub Actions maintenance

The v0.4.1 Release run emits GitHub's warning that `actions/checkout@v4` / `actions/setup-node@v4` still target deprecated Node.js 20 and are being forced onto Node 24. Audit the current recommended action versions and repository supply-chain policy, then upgrade/pin deliberately. Do not blindly float security-sensitive release actions.

### Acceptance

- one command reproduces CI locally;
- CI calls the same maintained gate or an exact shared script fragment;
- no release-only lint surprise after local PASS;
- environment-sensitive tests pass repeatedly under parallel execution;
- production config/native-host files are SHA-identical before/after isolated test/UAT runs;
- no new release workflow warning that is already actionable in the repository.

## 4. P1 — direct execution vs Agent delegation efficiency

The desired default is:

- deterministic filesystem/Git/status/build/test work -> direct `herdr_fs_*`, `herdr_git`, `herdr_exec*`;
- independent, reasoning-heavy or long-running work -> Agent delegation;
- never launch an Agent merely to run a trivial `git status`, `rg`, one-file edit or short test.

### Audit first

Measure before changing behavior:

- `herdr_inspect` latency and payload size;
- `herdr_git` status/diff/log latency;
- `herdr_exec` short-command latency;
- `herdr_exec_start/read` startup/reap latency;
- command-size / shell-delivery behavior: oversized or malformed command payloads must fail fast with an explicit error rather than leave a zero-output session running with no useful child process;
- repeated project-topology derivation cost;
- repeated full snapshot vs incremental/since cost;
- time from Agent prompt -> useful first result;
- duplicate work caused by unnecessary delegation.

Store bounded benchmark evidence under `docs/benchmarks/`.

### Optimization principles

- reuse current SnapshotCache/project topology instead of creating parallel caches;
- avoid recomputing stable Git/worktree topology multiple times inside one logical request when a version/sequence can prove it unchanged;
- use `herdr_since` / state sequence where it can replace a second full inspect;
- fix utility-pane readiness/reaping if a completed wrapper unnecessarily keeps the pane unavailable; never bypass a genuinely active interactive foreground child;
- preserve explicit target/pane/workspace safety checks.

### Acceptance

Define targets only after recording the baseline. The goal is measurable lower p50/p95 planning latency without weakening freshness or mutation safety.

## 5. P1 — Agent inventory refresh and dispatch quality

v0.4.1 records installed/startable Agent capability evidence. v0.4.2 should make that evidence useful without turning every inspect into an expensive scan.

### Authority hierarchy must remain

1. **Live instance state:** Herdr `agent.list` / snapshot.
2. **Detection support:** Herdr `server.agent_manifests`.
3. **Startable kinds:** the installed Herdr CLI's own declaration.
4. **Local executable/version/headless evidence:** herdr-mcp bounded probe.

Do not copy a static list of Agent kinds into herdr-mcp.

### Refresh policy

Audit current inventory staleness semantics and add a bounded policy such as:

- if inventory missing: recommend or perform one lightweight refresh at an appropriate lifecycle point;
- if fresh: read persisted inventory without spawning probes;
- if stale: refresh in a bounded/background-safe way;
- deep/version/headless probes remain explicit or TTL-controlled;
- do not full-scan on every `herdr_inspect`.

Consider install/update/first-use refresh only after measuring cost and failure behavior.

### Dispatch inputs

Any automatic recommendation/dispatch should consider:

- explicit user target first;
- current Agent visibility policy;
- live status (`idle/working/blocked/done`);
- workspace/project locality;
- recorded executable/startability evidence;
- task type and mutation risk;
- expected latency/cost;
- available parallelism.

Do not silently replace an explicit target with a cheaper/lower-quality Agent.

### Acceptance

Add benchmark scenarios proving that:

- trivial deterministic tasks stay direct;
- an appropriate idle worker is preferred for a genuinely delegatable task;
- busy/unavailable/hidden workers are not selected;
- capability evidence enriches dispatch but live Herdr state remains authoritative;
- stale inventory cannot create a false "available" claim.

## 6. P1 — Progressive Skill disclosure: measure, then decide default

Do not redesign the Skill architecture from scratch. v0.4.2 should evaluate the existing progressive implementation with real multi-Agent evidence.

### Measure

Compare progressive vs compatibility/legacy path for representative tasks:

- bootstrap bytes/tokens;
- skill bodies loaded per task;
- first-use latency;
- immutable skill-cache hits;
- capability refresh behavior;
- dispatch correctness;
- fallback behavior when network skill source is unavailable.

### Desired disclosure model

Initial disclosure should contain only the minimal planner policy, catalog/pointers and current capability summary. Load detailed skill bodies only when the selected task/tool path needs them.

Keep these invariants:

- immutable identity by URI + digest;
- live capability refresh does not change skill text identity;
- unknown/digest mismatch fails closed;
- public MCP tool catalog remains 18 tools.

### Default-on decision

Run real multi-Agent UAT before changing the default of `HERDR_MCP_PROGRESSIVE_SKILLS`.

If progressive mode is consistently better and no compatibility blocker remains:

- make it default in v0.4.2;
- retain a bounded rollback/compatibility escape hatch for at least the migration window;
- update docs/AGENTS/SKILL wording.

If evidence is mixed, keep the flag and record the blocker instead of forcing the migration.

## 7. P1 — safe resource lifecycle / cleanup planning

The current conservative behavior (do not auto-delete uncertain resources) is correct. Optimize only the accumulation of resources that are provably dead.

### Inventory before implementation

Audit:

- Herdr workspaces/panes with no active Agent;
- done/idle Agents and whether the upstream Herdr lifecycle already owns their cleanup;
- closed `herdr_exec_start` session metadata retention;
- local worktrees;
- local/remote merged branches;
- temporary UAT directories/processes;
- stale release staging/download assets.

Prefer upstream Herdr cleanup APIs when they exist.

### Safe cleanup predicate

A worktree/branch must never be proposed for destructive cleanup unless all applicable conditions are true:

- clean working tree;
- no unpushed/unmerged commit;
- branch merged into the intended base or explicitly marked obsolete;
- no open PR;
- no working Agent/process;
- no active Herdr workspace dependency;
- not main/current release/recovery state;
- not referenced by runtime/update/rollback evidence.

### Product shape

Do **not** add a new public MCP tool just for cleanup. Prefer a maintainer CLI/dry-run planner or existing Herdr APIs. Default behavior must be inventory/dry-run; destructive apply requires explicit intent.

### Acceptance

- repeated cleanup is idempotent;
- dirty/unmerged/active resources are always retained with a reason;
- completed resources can be reclaimed without manual forensic work;
- no process is killed by broad name matching;
- exec child process groups are reaped and no orphan accumulation appears in soak tests.

## 8. P1 — stability and bounded observability

The Link/Native IPC/browser connection stack is already mature; do not rewrite it without evidence.

Run targeted soak/UAT for:

- Link reconnect/backoff/silence;
- runtime restart and generation change;
- Chrome MV3 service-worker restart;
- one shared extension SSE/native stream with multiple workspace bindings;
- Native Host runtime sync after updater apply/rollback;
- long exec start/read/kill/reap;
- browser handoff/Auto over a long-lived tab;
- process count, FD count and bounded state-store growth.

Record only bounded operational evidence. Keep Core always on, Recent Activity bounded/default-on, Analytics explicit opt-in. Do not introduce always-on telemetry to solve a development observability problem.

Only promote a stability optimization if the soak/user evidence identifies a real failure mode.

## 9. P0/P1 — documentation taxonomy cleanup

The repository currently mixes active user docs, current contributor SSOT, completed GA evidence and active WIP. v0.4.2 should make the directory structure express lifecycle explicitly.

### Target lifecycle model

- `docs/i18n/<locale>/` — current published user/contributor articles only;
- `docs/history/` — completed release/GA/migration evidence;
- `docs/benchmarks/` — bounded benchmark records + an index/retention rule;
- `docs/_wip/` — **active plans/designs only**;
- top-level `docs/*.md` — only current cross-locale SSOT documents that really need to live outside the site article set.

### Immediate inventory to review

Current `_wip` contains both active designs and completed evidence. Reclassify, do not bulk delete:

- `browser-control-plane.md` — keep if still active;
- `browser-extension-development-and-store-release.md` — keep until Store publication/review is actually closed, then archive;
- `modular-progressive-skills.md` — keep through progressive-skill migration decision, then turn the final architecture into current docs/ADR and archive the plan;
- `g67-dogfood-public-uat-20260828.*` — completed evidence; move to history if no active test imports require the old path;
- `g910-rc1-*.json` — completed release evidence; move to history if references are updated;
- `.contract-epoch1-baseline.json` — determine whether it is a live test fixture or historical evidence; move to the appropriate fixtures/history location instead of leaving it as WIP metadata.

Remove tracked `.DS_Store` files and ensure ignore rules prevent recurrence.

### GA / alpha documents

Do not simply delete evidence.

- `exit-alpha-checklist.md` is a completed lifecycle runbook and should become historical once no active automation depends on it;
- `ga-candidate-status.md` / `ga-release-gate.md` should stop appearing as normal current-product reading once the final G25/Store position is explicitly frozen; preserve the final snapshot under `docs/history/ga/`;
- do not archive the sole GA SSOT prematurely if a real unresolved veto still uses it.

### Architecture roadmap

`docs/herdr-architecture-roadmap.md` currently contains a large chronological migration diary plus current roadmap statements. Split responsibilities:

1. a concise current architecture/roadmap with present tense, priorities and remaining work;
2. historical migration/release chronology under `docs/history/architecture/` or `docs/history/releases/`.

Old test counts, alpha generations and now-completed cutover steps should not dominate the current roadmap.

### Installation-doc de-duplication

Define one job per page:

- `quick-agent-install` — authoritative "give this to a Coding Agent" install protocol;
- `install` — human/manual installation reference;
- `quick-start` — what to do **after** installation to prove the first useful remote task, not another installation tutorial;
- `agent-install` — either merge unique low-level Agent automation details into `quick-agent-install`/maintainer docs or clearly demote it to an implementation reference;
- `overview` — product explanation only, no competing install flow.

For browser docs:

- `extension` — Store installation + user-facing extension overview;
- `browser-continuity` — conceptual handoff/Auto behavior;
- `browser-control-center` — Side Panel/HUD user reference;
- `privacy` — public policy;
- `extension-wake` / `extension-bridge` — evaluate whether they belong in advanced/maintainer navigation rather than the ordinary user's six-page browser path.

### Version/support wording

Avoid hard-coded patch versions in ordinary instructions unless the exact version matters historically. Prefer "current stable" / stable channel and derive machine facts at build/test time where practical.

At minimum ensure current docs do not remain stuck on `v0.4.0` after `v0.4.1` becomes stable.

Do not rewrite historical evidence to new versions.

## 10. P0/P1 — documentation-site wording and information architecture

The site currently has **no real docs landing page**: `/docs/` chooses a locale and forwards directly to the first document, while each locale entry also forwards into the document sequence. v0.4.2 should replace this with a real product-oriented landing page.

### Site user model

The primary audience is a user who already has a Coding Agent and wants Herdr/herdr-mcp working with minimal conceptual overhead.

The first screen should answer only:

1. What is herdr-mcp?
2. What should I copy to my Coding Agent?
3. At which two points will I need to take over?
4. What can I do after installation?

Do not lead with GA gates, UAT, Runtime A/B, contract internals or maintainer history.

### Homepage redesign

Create real locale homepages (for example `/docs/en/` and `/docs/zh-CN/`) instead of redirecting immediately to `quick-agent-install`.

Recommended structure:

1. **Hero**
   - one-sentence product value;
   - one primary CTA: "Install with my Coding Agent" / "让 Coding Agent 帮我安装";
   - copyable install prompt;
   - secondary links only: Manual install / Learn how it works.
2. **What the Agent will do**
   - install/check Herdr;
   - install stable herdr-mcp from GitHub Releases;
   - deploy/configure Edge + Link;
   - verify runtime/doctor;
   - explicitly show the two user handoff points: Cloudflare login/token and ChatGPT Connector setup.
3. **Choose your path**
   - Agent-assisted install (recommended);
   - Manual install;
   - Browser extension (optional, Chrome Web Store only).
4. **What you get**
   - local Herdr workspaces/Agents through the remote MCP bridge;
   - stable ChatGPT Connector path;
   - evidence-backed local Agent capability awareness;
   - optional browser continuity/control surfaces;
   - safe update/rollback.
5. **Safety boundary**
   - browser page never needs the long-lived local bearer;
   - Native Messaging is local and Store identity is explicit;
   - runtime and extension update independently;
   - mutations remain target- and delivery-aware.
6. **Support / deeper docs**
   - Troubleshooting;
   - Architecture;
   - Maintainer reference as a deliberately secondary/collapsed area.

### Navigation redesign

Current groups are useful but still expose too much maintainer material in the main reading sequence. Re-evaluate order after doc de-duplication.

Desired high-level hierarchy:

- Start;
- Use herdr-mcp;
- Browser (optional);
- Operate / troubleshoot;
- Architecture / advanced;
- Maintainer reference (secondary/collapsible, not part of ordinary next/previous reading flow where possible).

`clean-machine-uat` must not look like an end-user getting-started article.

### Locale routing

Preserve current automatic zh browser routing, explicit language pinning, hreflang/canonical metadata and language switcher, but route users to the new locale homepage instead of the first article.

### Wording rules

Above the fold and first-install path should avoid internal terms unless required:

- alpha / candidate / G1-G25 / GA scorecard;
- UAT;
- Runtime A/B;
- Node compatibility history;
- exact tool-count trivia;
- worktree/release-engineering terminology.

Those concepts remain available in advanced/maintainer docs.

### Design / UX acceptance

- mobile and desktop layouts both work;
- primary install CTA is obvious without scrolling through architecture copy;
- copyable Agent prompt is keyboard-accessible;
- English/zh-CN parity is enforced by build/tests;
- search still indexes articles correctly;
- canonical/hreflang remains correct;
- dark/light behavior remains intact;
- no new large JS framework is introduced solely for the landing page;
- build remains deterministic/offline;
- homepage links resolve under GitHub Pages base path.

Add tests proving that `/docs/` routes by locale to real homepages and that locale homepages contain the intended primary CTA instead of being meta-refresh wrappers to the first document.

## 11. README vs docs-site contract

README should remain a short repository entrance, not a second documentation site.

Keep README focused on:

- one-sentence purpose;
- one copyable Coding-Agent installation prompt;
- first useful smoke/example;
- support boundary;
- links to docs/browser/privacy/troubleshooting.

Do not copy long architecture, release-gate or UAT sections back into README.

Where facts are shared (Store identity, current repo runtime version, extension version), prefer deriving/testing against existing machine-readable sources rather than maintaining contradictory prose copies.

## 12. Sequencing / branch strategy

Do not implement all of v0.4.2 in one huge branch.

Recommended sequence:

### Wave A — engineering baseline

1. release/test execution-profile parity;
2. environment-test hardening;
3. GitHub Actions runtime maintenance;
4. performance baseline capture.

### Wave B — execution quality

1. scan staleness/refresh policy;
2. direct-vs-Agent dispatch benchmarks and small fixes;
3. progressive-skill A/B and default decision;
4. resource-lifecycle audit / safe cleanup planner if evidence justifies implementation.

### Wave C — docs taxonomy

1. inventory links/imports before moves;
2. move completed WIP/GA evidence to history;
3. trim/split architecture roadmap;
4. de-duplicate installation/browser docs;
5. remove stale version/product wording.

### Wave D — site redesign

Only after doc slugs/roles stabilize:

1. real localized homepage;
2. navigation/order changes;
3. wording/CTA polish;
4. accessibility/responsive/search/link tests;
5. visual browser smoke.

Each mutation line should use its own branch/worktree when parallel work would otherwise collide. Do not touch another task's dirty worktree.

## 14. Definition of Done

v0.4.2 is done when:

1. local and CI release gates share one authoritative execution profile;
2. production-scoped environment variables cannot silently contaminate isolated release/UAT tests;
3. direct deterministic work is not unnecessarily delegated to Agents;
4. Agent inventory has bounded freshness semantics without duplicating Herdr authority;
5. progressive Skill behavior has an evidence-backed default decision;
6. no meaningful orphan/process/worktree accumulation remains without a safe explicit cleanup story;
7. `docs/_wip` contains active work only;
8. completed GA/alpha/UAT evidence is preserved under history rather than mixed into current user reading;
9. the architecture roadmap is current and concise, with chronology separated;
10. install/browser docs have one clear responsibility each;
11. docs-site `/docs/` lands on a real bilingual product homepage instead of forwarding into a manual;
12. the homepage presents one primary Agent-assisted install path, two user handoff points, and optional Store extension without maintainer jargon;
13. README remains short and consistent with the site;
14. full release/dogfood validation is green;
15. no new public MCP tool or browser/runtime release coupling was introduced just to implement this cleanup.
