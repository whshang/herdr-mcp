# Herdr-MCP 1.0 Alpha 5 — Gemini Second-Provider Vertical

Status: implementation specification for `docs/v1.0-alpha5-gemini-spec-20260906`.

Planning SSOT: [`docs/history/architecture/v1.0-architecture-plan.md`](../history/architecture/v1.0-architecture-plan.md).

Milestone SSOT: [`docs/herdr-architecture-roadmap.md`](../herdr-architecture-roadmap.md).

## Goal

Alpha 5 proves that the Alpha 4 WebChat seam is actually provider-neutral by adding one minimum Gemini vertical and then running a real ChatGPT -> Gemini Planner Handoff against the same Herdr Work Memory.

The milestone has two inseparable correctness goals:

1. **Second-provider actuation proof.** Gemini maps into the existing provider-neutral `browser_endpoint -> provider_account -> space? -> session` model and uses the already-frozen private browser operation seam. Alpha 5 does not build a generic provider framework or add a second dispatch architecture.
2. **Cross-provider evidence proof.** Before the formal dual-provider UAT, Work Memory gains the minimum evidence semantics needed to keep a bounded result truthful while evidence grows: dimension-specific coverage and a stable evidence cursor fixed to one accepted append-only boundary.

Provider-native Memory is never project authority. Herdr's verified checkpoint, Work Memory evidence, Fleet lease state, Git objects, and live Herdr/runtime state remain the authorities defined by Alpha 1-4.

## Existing boundaries reused unchanged

Alpha 5 reuses rather than duplicates:

- Alpha 1 work-chain revision, Planner Lease, and execution-lane authority;
- Alpha 2 `state.db` Work Memory partition `project_ref + repo_id + work_chain_id`, append-only turns/evidence, verified checkpoint CAS, FTS5 index, portable Git refs, and bounded resume;
- Alpha 3 opaque browser endpoint/account/space/session identity and capability generations;
- Alpha 4 caller-grant intersection, trusted Extension IPC, browser mutation gate, expected-generation fencing, dispatch idempotency, immediate delivery states, authoritative postconditions, and Work Memory dispatch write-back;
- public Edge epoch 3 / 19 actions and workstation Runtime Execution epoch 2 / 18 tools.

Alpha 5 adds no new public MCP tool/action and no contract epoch change.

## Explicit non-goals

Alpha 5 does **not** add:

- a generic provider plugin framework, provider DSL, adapter registry rewrite, or provider feature-parity project;
- Claude/Grok/z.ai/DeepSeek implementation work merely because adjacent extension adapters exist;
- browser resource reservation, scheduling, takeover, multi-endpoint failover, or fleet/business dispatch policy (beta.2);
- late settlement of `uncertain`, reload/stale-view recovery, detached-tab reconciliation, or retry-after-reconciliation policy (beta.1);
- `browser_delivery_events` or another delivery ledger;
- a SnapshotStore, cursor table, second database, daemon, timer, or raw-evidence replication plane;
- provider-native Memory as checkpoint/evidence authority;
- `work_memory.evidence.inspect` / `resolve` in the initial implementation;
- context-adaptive Work Memory projection unless the current Extension pressure signal can enter the request through an existing small trusted request-scoped path without a new state owner or complex IPC;
- production deployment, runtime activation, tag, or release.

## Provider-neutral identity and Gemini mapping

The core hierarchy stays unchanged:

```text
device
  -> browser_endpoint
       -> provider_account
            -> space?
                 -> session
                      -> view*
```

Gemini-native concepts are adapter vocabulary only. Alpha 5 must discover the minimum stable mapping from the live Gemini Web UI before freezing provider-specific observations. The core must never persist or expose a raw Gemini account id, DOM selector, tab id, browser profile seed, or provider-native conversation id as a portable identity.

If Gemini has no native grouping object that satisfies the existing `space` contract, `space` stays absent. The adapter must not fabricate one for symmetry with ChatGPT Projects.

A canonical Gemini conversation URL may be returned as clickable postcondition evidence, but it is not accepted as a mutation target and is never the durable cross-device session identity.

## Minimum Gemini capability vertical

Alpha 5 is intentionally narrower than provider parity.

The minimum real mutation is the same semantic operation that Alpha 4 proved for ChatGPT:

```text
herdr_mcp.browser_dispatch.submit
```

Required behavior:

- exact endpoint/provider/account/session resolution;
- authenticated caller grant for the exact `(endpoint, "gemini", account)` tuple;
- local WebChat Control consent;
- current capability generation and `expected_generation` match before dispatch;
- one idempotent dispatch reservation before browser actuation;
- accepted-message evidence or provider-observed message baseline advance;
- generation ownership/status observation before `applied`;
- send-only evidence is never sufficient for `applied`;
- repeated idempotency key cannot create a second Gemini browser mutation after runtime restart.

Other frozen Alpha 4 mutations remain available through the same private method names but may return explicit `unsupported` until the Gemini adapter can prove the operation-specific authoritative postcondition. Alpha 5 must not add guessed lifecycle automation merely to claim parity.

### Semantic reasoning and required apps

Alpha 5 re-evaluates Alpha 4's provider-neutral intent rather than copying Gemini-native labels into core state:

```text
reasoning_effort = economy | balanced | thorough
required_apps    = semantic capability list
```

For each value/capability, the Gemini adapter must do one of two things:

1. map it exactly and read the selected state back; or
2. return `unsupported`.

No approximation or silent downgrade is allowed. If Gemini proves that the three-value reasoning enum itself is not provider-neutral, the enum changes only through an explicit spec/compatibility revision; the adapter must not hide the mismatch.

## Evidence Semantics P0

Alpha 5 absorbs the two P0 requirements from Evidence Semantics commit `0713464` before the formal ChatGPT -> Gemini UAT.

### 1. Dimension-specific coverage

Every bounded Work Memory `resume` or `search` result exposes compact coverage derived only from facts the kernel actually knows.

Normative dimensions:

```text
result_completeness:
  complete | partial

source_verification:
  verified | mixed | unverified | stale | not_applicable
```

These dimensions are independent. Execution facts remain typed and independent as well:

```text
test candidate discovered != test executed
test executed != test passed
browser message accepted != generation settled
postcondition observed != whole work-chain task complete
```

A bounded presentation must also state whether the current response is only a page/excerpt of a complete retained result. Presentation truncation must never be encoded as result incompleteness.

The minimum response shape is conceptually:

```json
{
  "coverage": {
    "boundary": {
      "checkpoint_revision": 17,
      "through_evidence_id": "ev_..."
    },
    "result_completeness": "complete",
    "source_verification": "unverified",
    "display_truncated": true,
    "limitations": ["display_page_truncated"]
  }
}
```

Exact field placement may be adjusted during implementation review, but the semantics above are frozen.

Under Alpha 2's current `retain_all` policy, a result that remains fully queryable through cursor continuation is `complete` even when the current response displays one page. `partial` is reserved for a kernel-observed loss/retention/budget condition that makes part of the accepted result unavailable. Do not mark a normal paginated page `partial`.

`limitations` is a bounded list of stable reason codes, not free-form warning text. Add only states Herdr can actually observe. Candidate Alpha 5 codes are:

```text
display_page_truncated
display_excerpt_truncated
result_retention_partial
source_revision_unverified
source_revision_stale
source_unavailable
```

### Source verification truthfulness

A structurally valid portable Git ref is **not** automatically `verified`.

Current Alpha 2 append validation proves only that the ref has a canonical repo id, full object-id syntax, relative path/range, and a deterministic evidence digest. It does not read the referenced Git object. Therefore Alpha 5 Work Memory must report such source claims as `unverified` unless the exact referenced source has actually been checked.

A fixed Git source is `verified` only after the exact `repo_id + full commit object + repo-relative path/range + evidence digest` is checked against that referenced object. A later dirty/current worktree may be reported separately, but its bytes must never be combined with the old fixed-object evidence and labeled verified.

The initial Alpha 5 UAT performs exact-object verification with existing Git/fs primitives. It does **not** add `work_memory.evidence.inspect`. If repeated UAT boilerplate causes a concrete correctness failure, a later narrowly-scoped private resolver may be proposed as an adapter over the same StateStore/Git authority.

### 2. Stable evidence cursor

A Work Memory search starts one immutable logical view. Appending evidence after the first page must not change later pages of that view.

No durable cursor/snapshot table is added. Alpha 5 reuses:

- append-only `continuity_evidence`;
- existing FTS5 `continuity_memory_fts` in the same StateStore;
- stable FTS rowids under the current append-only/retain-all contract;
- checkpoint revision and `through_evidence_id` authority already present in Alpha 2.

At the first search, StateStore captures a bounded accepted search boundary:

```text
continuity_id / project_ref / repo_id / work_chain_id
checkpoint_revision
accepted FTS max rowid
accepted latest evidence_id (if any)
query digest
page size
continuation offset
cursor kind + version
```

The cursor is opaque transport metadata, not an authorization capability and not a new authority. It may use a versioned encoded payload plus integrity checksum; every continuation is revalidated against the current Work Memory partition before querying.

Fresh-query mode and continuation mode are distinct:

```text
fresh:
  project_ref + repo_id + work_chain_id + query + optional limit

continue:
  cursor
```

Supplying a cursor together with conflicting fresh-query selection fields fails explicitly rather than silently starting a new query.

Continuation queries are constrained to the captured FTS boundary and use a deterministic order over the frozen candidate set. New rows with a later FTS rowid are excluded. The same valid cursor replay is idempotent.

Required failures are explicit and never downgrade to a fresh search:

```text
work_memory_cursor_invalid
work_memory_cursor_conflict
work_memory_cursor_partition_mismatch
work_memory_cursor_boundary_unavailable
work_memory_cursor_version_unsupported
```

No cursor-expiry policy is invented in Alpha 5 because Alpha 2 retains all evidence and has no prune path. Future prune/retention work must define the corresponding boundary-unavailable behavior before deleting source rows.

### Cursor acceptance scenario

```text
E1-E100 exist
  -> fresh query
  -> cursor/view boundary fixed through E100
  -> append E101-E120
  -> old cursor page 2 still ranges only over E1-E100
  -> replay old cursor gives the same page
  -> fresh query can observe E101-E120
```

PASS requires no silent rerun, no duplicated row caused by append growth, and no omission caused by the new rows changing ranking.

## Why Evidence Semantics requires no StateStore migration

Alpha 5 P0 is a query/response semantic change, not a new durable-state owner.

The current schema already contains every durable primitive needed:

- append-only evidence identity/content/digest/provider provenance;
- portable Git object/path/range fields;
- checkpoint revision + `through_evidence_id`;
- FTS5 source kind/source id/text in the same database;
- stable row identity usable to cap a frozen query candidate set;
- `retain_all` with no prune path.

Therefore Alpha 5 **must not bump schema v8** for coverage or stable cursors. A migration is allowed only if implementation finds a concrete invariant that cannot be represented or safely derived from these existing primitives and documents that contradiction before code is merged.

## Context-adaptive projection — deferred P1

The Evidence Semantics addendum proposes mapping Extension conversation pressure to `full / tight / critical` Work Memory presentation tiers.

Current code keeps the pressure record in the ChatGPT content-script/Extension path. It is not already attached to remote `work_memory.resume/search` requests through a trusted request-scoped field. Wiring it into Work Memory today would require new cross-component state/IPC rather than reusing an existing small hint.

Per Alpha 5 scope policy, context-adaptive projection is therefore **deferred** and does not block Alpha 5. The implementation must not add a second tokenizer, pressure store, daemon, or resident synchronization path merely to satisfy this P1.

If a later code inspection exposes an already-trusted request-scoped pressure hint that can be consumed with a very small change, it may be reconsidered separately; the checkpoint/evidence authority must remain identical across projection tiers.

## Gemini Extension boundary

Gemini is implemented as one provider-specific vertical on the existing Extension architecture, not as a provider-framework rewrite.

Expected minimum files:

- one Gemini content adapter under `extension/content/injector/`;
- bounded Gemini URL/session/account observation in `extension/background.js`;
- provider-specific target resolution and plain `browser_dispatch.submit` actuation;
- targeted tests for observation, capability generation, submit/postcondition evidence, and fail-closed unsupported behavior.

The current extension already has an optional-origin/dynamic-content-script mechanism for experimental sites. Alpha 5 should reuse that mechanism rather than adding broad static host permissions.

Any commit that changes Extension permission-request behavior for the Gemini origin remains subject to the separate explicit permission-change approval gate. Until that approval exists, implementation may proceed on Work Memory and non-permission Gemini code, but the permission-change commit must not be created.

## Planner Handoff and Work Memory authority

Alpha 5's formal cross-provider proof is Planner Handoff:

```text
ChatGPT Planner
  -> append evidence
  -> write verified checkpoint
  -> obtain bounded evidence view + stable cursor
  -> project/transfer Planner authority
  -> Gemini resumes same work_chain_id
  -> Gemini receives the same verified checkpoint authority
  -> Gemini may continue the frozen evidence cursor
     OR explicitly issue a fresh Work Memory query
  -> Gemini re-checks live Git/runtime before mutation
```

Provider-native ChatGPT or Gemini Memory is supplementary UI context only. It cannot override the Herdr checkpoint, accepted requirements/decisions, evidence boundary, Git object, Planner Lease, or live runtime state.

Cross-WebChat Delegation remains a second acceptance mode from the roadmap, but Alpha 5 implements only the minimum bounded Gemini execution lane needed to prove the same provider-neutral dispatch/evidence seam. It must not expand into general multi-provider scheduling.

## Required real UAT

### A. ChatGPT -> Gemini Planner Handoff

ChatGPT:

1. binds/writes to one Work Memory partition;
2. appends evidence;
3. writes a verified checkpoint with a real evidence boundary;
4. performs a bounded Work Memory search and records the stable cursor;
5. transfers/releases Planner authority according to the existing Fleet contract.

Gemini:

1. binds its provider-qualified session to the same `work_chain_id`;
2. resumes the same partition;
3. receives the exact same checkpoint revision/body/digest as authority;
4. can continue the old frozen evidence cursor;
5. can alternatively issue an explicit fresh query;
6. re-checks live Git/runtime before mutation.

PASS requires no use of provider-native Memory as project authority.

### B. Evidence growth

1. append E1-E100;
2. fresh query returns page 1 and a cursor frozen through that accepted boundary;
3. append E101-E120;
4. old cursor page 2 contains only results from E1-E100;
5. replay old cursor is identical;
6. fresh query may see E101-E120.

### C. Source truthfulness

1. append evidence carrying a portable ref to a fixed Git object;
2. verify the exact referenced object/path/range using existing Git/fs primitives;
3. mutate the current worktree afterward;
4. resume/search the old evidence;
5. confirm the fixed-object ref still names the original object;
6. report current worktree state separately;
7. never combine current bytes with the fixed object and call the combination verified.

### D. Result completeness vs display truncation

Force a result with more matches than one response page. PASS requires:

- `result_completeness=complete` while the full frozen result remains cursor-queryable under `retain_all`;
- `display_truncated=true` (or equivalent presentation limitation) for the current page/excerpt;
- no implication that the displayed page is the complete result set.

### E. Gemini dispatch

A real Gemini session receives one bounded plain `browser_dispatch.submit`. PASS requires the same Alpha 4 safety properties: exact target/grant/consent/generation, durable idempotency, accepted-message evidence plus generation ownership/status before `applied`, and no second actuation on replay/restart.

## Minimum implementation file scope

The expected implementation should stay close to:

### Work Memory P0

- `crates/herdr-mcp/src/state_store.rs`
  - frozen FTS boundary query/page logic;
  - coverage facts derivable from retained evidence and portable refs;
  - stable cursor-boundary tests.
- `crates/herdr-mcp/src/mcp.rs`
  - private `work_memory.search/resume` request/response semantics;
  - cursor encode/decode/validation and stable error codes;
  - coverage rendering and regression tests.
- `crates/herdr-mcp/src/progressive_skills.rs`
  - private method schema metadata for the optional cursor/coverage response contract.

No StateStore migration is expected.

### Gemini vertical

- `extension/background.js`
  - Gemini observation/opaque registry integration, target resolution, and actuation routing.
- `extension/content/injector/gemini.js`
  - Gemini-specific page observations and minimum submit/postcondition behavior.
- narrowly scoped extension tests, preferably extending existing browser-control-plane test infrastructure.
- `extension/options.js` and/or related option/localization files only if the optional Gemini origin enablement needs them; that permission behavior is a separately gated commit.

Edge changes are not expected: Alpha 4 caller grants and routing are already provider-neutral and bind a string provider as part of the exact tuple. Any proposed Edge mutation requires evidence of a real missing invariant rather than provider-name plumbing.

## Acceptance matrix

### Work Memory

- no schema version bump and no new durable state owner;
- stable cursor excludes rows appended after its accepted FTS boundary;
- cursor replay is idempotent;
- malformed/conflicting/unsupported-version/unavailable-boundary cursor fails explicitly;
- cursor failure never falls back to a fresh query;
- response exposes result completeness separately from display truncation;
- source-verification aggregate never claims `verified` from portable-ref syntax alone;
- fixed Git object and current worktree are never merged into one verified claim;
- existing Alpha 2 checkpoint authority/CAS semantics remain unchanged.

### Gemini provider

- opaque provider/account/session identity; no raw native id becomes portable evidence;
- exact caller grant + consent + capability generation required;
- plain dispatch submit proves accepted-message and generation postconditions;
- idempotency/restart cannot produce a second mutation;
- semantic reasoning/apps are read back exactly or explicit `unsupported`;
- unsupported lifecycle operations are not emulated;
- no public MCP contract drift.

### Cross-provider UAT

- ChatGPT and Gemini bind different provider-qualified sessions to one Work Memory partition;
- same verified checkpoint authority on both providers;
- same frozen cursor can be continued after handoff;
- explicit fresh query sees later evidence;
- Provider-native Memory is not used as authority;
- live Git/runtime is rechecked after resume before mutation.

### Gates

- targeted Work Memory Rust tests;
- targeted Gemini Extension tests;
- `cargo fmt --check`;
- `cargo clippy --workspace --all-targets --all-features -- -D warnings`;
- `cargo test --workspace`;
- `npm run build`;
- relevant extension smoke/browser-control tests;
- `npm run test:edge` / public-contract identity gate when shared contract code is touched;
- `git diff --check`;
- independent final security/architecture audit;
- exact-head GitHub required CI green before merge.

## Merge boundary

Alpha 5 may merge only when the second-provider vertical and the required dual-provider UAT are evidenced on the final implementation HEAD. Alpha 5 does not need beta.1 late settlement or beta.2 reservation/failover to pass, and those features must not be pulled forward to make the UAT convenient.
