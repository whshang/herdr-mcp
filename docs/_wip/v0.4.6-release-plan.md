# v0.4.6 release plan — pre-1.0 stabilization

Status: active plan. Remove or archive under `docs/history/` once v0.4.6 is published and its qualification record is complete.

## Positioning

v0.4.6 is the **last stable release before 1.0**. There is no planned `0.5.0`: after v0.4.6 the version line moves directly to 1.0. Its scope is deliberately wider than the original auth/onboarding patch that opened [PR #304](https://github.com/whshang/herdr-mcp/pull/304).

The release goal is that the ordinary **one conversation + one project** workflow is already dependable before 1.0: a new user can install and configure Herdr without avoidable setup friction; authentication and authorization boundaries are explicit and revocable; Connector, device and credential lifecycle state is inspectable; and the resident runtime remains healthy and efficient through restarts and long-lived use. 1.0 feature work (fleet control kernel, WebChat dispatch, browser control) then starts from this stable base.

Consequences of that positioning:

- The v1.0 fleet control kernel merged into `main` as [PR #305](https://github.com/whshang/herdr-mcp/pull/305) is **out of scope**. It is 1.0 feature work; v0.4.6 stabilizes what precedes it. The tag is therefore cut from `release/v0.4.6-auth-hotfix-20260904`, whose base `e9281b4` predates #305, and the release branch merges back into `main` after publication.
- Correctness and resource defects found while preparing the release are in scope even when they were not part of the original patch, provided each one lands as an independently revertable commit with its own regression test.
- Feature requests remain out of scope. [Issue #57](https://github.com/whshang/herdr-mcp/issues/57) (browser steer bridge) is 1.0 line work.

## Scope by class

### 1. Authentication and connector authority

Connector approval, request/PKCE/redirect/resource binding, deployment-secret-protected six-digit verifiers, grant revoke with durable tombstones and legacy fences, device-bound Automation Clients, unified fleet principals.

Lands as: `98ca437`, `2e813fc`, `4267e2e`, `eeb4f51`, `8701016`, `c0b72ed` on the release branch.
References: [PR #303](https://github.com/whshang/herdr-mcp/pull/303), [PR #304](https://github.com/whshang/herdr-mcp/pull/304).

### 2. First-owner onboarding and readiness

Semantic enrollment error from `worker pair` on a fresh machine, fresh-install Link generation reconcile, `operational_ready` separated from maintainer-only cutover sealing, actionable managed-root hint, converged install guidance in four locales.

Lands as: `b2aafdd`, `0902414`, `713b068`, `3e890ed`.
Closes: [#306](https://github.com/whshang/herdr-mcp/issues/306), [#307](https://github.com/whshang/herdr-mcp/issues/307). Partially addresses [#302](https://github.com/whshang/herdr-mcp/issues/302) — the low-level `Io(NotFound)` leak is fixed; one-command first-Worker bootstrap remains open.

### 3. Connector, device and credential lifecycle management

The pre-1.0 stable line must have an owner-visible management path for everything that can continue to access a Worker:

- Connector inventory includes current `conn_*` instances and legacy OAuth clients that predate Connector-instance records, without exposing secrets.
- Current Connector instances can be revoked independently; legacy client grants have an explicit operator revoke path that invalidates their issued access/refresh credentials.
- Enrolled devices have a CLI inventory path in addition to rename/revoke, using immutable `device_id` for destructive actions.
- Automation credentials remain device-bound and support list/rotate/revoke. Lists expose lifecycle metadata only; plaintext secrets are returned only at create/rotate time and are never recoverable later.
- Token management is grant/principal based: operators can see non-secret token/grant counts and revoke the owning Connector/client/automation principal. The product does not add a raw bearer-token browser or persist plaintext tokens for convenience.

No new public MCP tool is required for this management surface; it stays on the enrolled-device/operator control plane.

### 4. Runtime CPU and resident behavior

[#308](https://github.com/whshang/herdr-mcp/issues/308) — a Herdr server restart leaves both EventCache streams at EOF, and because EOF is indistinguishable from a poll timeout the loop spins on closed sockets at ~100% CPU while `doctor` still reports `mode=healthy`.

Lane: `fix/v046-eventcache-eof-spin-20260904` (based on `origin/main`; `events.rs`/`state_cache.rs` do not overlap #305, so it cherry-picks cleanly onto the release branch).

Follow-on, same subsystem, deliberately **serialized after** #308 rather than parallel: the always-on polling cost — two 250 ms `poll_event` calls per loop iteration, an unconditional full `session.snapshot` every 30 s regardless of activity or client presence, and a per-SSE-client 250 ms `digest_since` that deep-clones all agents and all workspaces with no unchanged fast path. Serialized because #308 establishes the EOF/backoff invariant that idle backoff must not weaken.

Hard constraint for the polling work: **idle backoff must not change the freshness semantics of `herdr_inspect` / `herdr_since` results while a client is active.** Reduced polling must not become stale data.

### 5. Planner-facing tool integrity

- [#309](https://github.com/whshang/herdr-mcp/issues/309) — `herdr_fs_grep` returns a successful empty result for patterns that exist on disk.
- [#310](https://github.com/whshang/herdr-mcp/issues/310) — an unknown param on a mutating `herdr_call` method only warns, and the mutation then lands in the focused workspace.
- [#311](https://github.com/whshang/herdr-mcp/issues/311) — disposable named validation instances stay resident with no inventory and no reap path, and orphan plists accumulate.

Lane: `fix/v046-planner-tool-integrity-20260904` (based on the release branch tip; no cherry-pick needed).

#309 and #310 are both silent-wrongness defects: a successful response carrying a wrong result. They are in scope for a stabilization release precisely because no error surfaces and every downstream consumer acts on the false answer.

Agent supervision is also part of this stabilization surface. If a working Agent emits the same/near-identical block repeatedly with no new command result, Git diff, or task evidence, the planner must confirm from a bounded recent output tail, interrupt immediately, verify Git/task state, and restart unfinished work in a fresh Agent session from the current verified state. Already-integrated work must not be replayed. A second loop is reassigned or taken back by the main planner. This is a planner-discipline fix and does not add a public tool or autonomous resident monitor.

## UAT groups

Static audit does not satisfy any of these. Each group needs a real built runtime and, where noted, a real Edge deployment.

### A. Authentication (from the independent release-candidate audit)

1. Enrolled device: `herdr-mcp connector list` lists `conn_*`.
2. New Connector completes DCR and PKCE through the browser and stops at the approval page with no code issued; only after `connector approve <request-id>` with the interactively entered six-digit code does `/oauth/token` return a JWT.
3. `connector revoke <conn_A> --confirm` invalidates A immediately while `conn_B` of the same client still works.
4. Operator revoke of a pre-v0.4.6 `client_id` with no stored record invalidates the old JWT immediately.
5. Automation: `create --name … --device <dev_*>`; omitting the device routes to the bound machine; a different device selector or ref is not delivered.
6. The copyable approval command never carries the code; a code passed on argv must fail.

### B. Onboarding

7. A genuinely unenrolled machine running `worker pair` gets a semantic enrollment error, not `Io(NotFound)`.
8. A fresh install's first remote tool call does not fail with `runtime_generation_superseded_before_dispatch`.
9. `link status` reports `operational_ready` true without sealing, and cutover gates are categorized as maintainer-only.
10. An older browser extension build shows no regression under the new inventory rule.

### C. Lifecycle management

11. `connector list` shows both current Connector instances and any legacy OAuth client registrations in non-secret form; a legacy client can be revoked explicitly and its old credentials stop working.
12. `device list` / the compatible Worker alias shows enrolled device IDs and status; rename/revoke continue to use the immutable device identity and never revoke by display name.
13. Automation list/rotate/revoke remains device-bound; rotate invalidates the previous secret immediately and list never returns plaintext credentials.
14. Management output includes only non-secret token/grant lifecycle metadata or counts. No access token, refresh token, bearer, client secret or verification code is emitted by inventory commands.

### D. Runtime CPU

15. Restart the Herdr server while the herdr-mcp candidate keeps running; sample CPU for at least 60 s and confirm no sustained spin.
16. Confirm both topology and status subscriptions re-establish automatically after the server returns.
17. Confirm `doctor` does not report `mode=healthy` while streams are at EOF.
18. Idle power comparison against v0.4.5 once the polling work lands.

### E. Tool integrity

19. `herdr_fs_grep` returns the known matches for a fixture symbol; an unscannable root errors instead of returning empty.
20. A mutating `herdr_call` with a misspelled target param is rejected before the socket call and creates nothing.
21. Instance inventory lists default and named instances; reaping a named validation instance removes its job, plist and config root without touching the default install or `~/.config/herdr-mcp/releases/**`.
