# herdr-mcp v0.4.3 plan

Status: active implementation plan
Baseline: `origin/main` at multi-device branch creation (`1f8f9cf`)
Stable release remains immutable: `v0.4.2`

## Release goal

v0.4.3 is the first multi-device release and a compatibility/product-boundary release.

Primary product outcome:

```text
one Herdr Worker
one ChatGPT Connector
N authenticated devices
request-scoped deterministic routing
```

The release must preserve the post-v0.4.2 reliability and browser-control improvements already on `main` while introducing multi-device support without expanding the Rust runtime tool surface unnecessarily.

Frozen environment model:

```text
Runtime:           DEV / PROD
Browser extension: DEV / STANDALONE / STORE
Worker binding:    none / create / connect
```

CI/UAT/candidate resources remain temporary resources, not another installed environment.

## Current multi-device implementation status

Implemented on `feat/v0.4.3-multi-device-core-20260831`:

- [x] P0-A contract split: Public epoch 3 is independent from Runtime epoch 2; `/health` publishes both identities and Rust Link prefers the runtime identity with v0.4.2 fallback.
- [x] P0-A/P0-B identity foundation: canonical `device_id`, Worker-side `DeviceRegistryDO`, legacy `device_id -> workstation_id` mapping.
- [x] P0-B read-only fleet: Edge-local `herdr_devices` joins Registry state with `WorkstationDO` realtime status.
- [x] Legacy v0.4.2 default workstation self-registers once during authenticated Link connect; reconnect does not rewrite the registry and heartbeat remains outside the registry.
- [x] P0-D explicit routing foundation: common public `device` selector, deterministic ID/unique-name resolution, single-routable-device selection, ambiguity fail-closed, Edge-only selector removal before Runtime v2 forwarding.
- [x] Existing custom-domain probe accepts a larger Public contract while still verifying Runtime v2 compatibility.
- [ ] P0-C secure enrollment/per-device credential remains the next blocking slice before formal two-device support.
- [ ] Device-aware opaque refs and trusted browser project binding integration remain after secure enrollment.

Current verification: Edge/public-contract tests, custom-domain tests, targeted Rust Link contract tests, and the repository Node test suite are green on the implementation branch.

## P0 — Multi-device core feature

Canonical design: `docs/_wip/multi-device-worker-control-plane.md`.

### P0-A — Protocol foundation

Required:

- split Public Edge Contract from Runtime Execution Contract;
- keep existing Rust/runtime 18-tool epoch-2 execution contract stable;
- allow the public contract to evolve to a device-aware epoch without forcing the Link runtime to implement Edge-local tools;
- freeze immutable Worker-scoped `device_id = dev_<ULID>` identity;
- preserve `workstation_id` as a relay/internal execution identity during migration;
- model legacy `device_id -> workstation_id` mapping;
- introduce request-scoped selected-device context;
- ensure retries/recovery retain selected-device affinity;
- map public errors to stable `device_*` semantics without discarding existing delivery/retry metadata.

Hard invariant:

```text
one logical operation selects one device exactly once;
retry/recovery never moves that operation to another device.
```

### P0-B — Read-only fleet

Required:

- add persistent Worker-side `DeviceRegistryDO`;
- keep realtime presence/health in existing `WorkstationDO`;
- bootstrap the existing v0.4.2 single device into the registry without breaking its current Link identity;
- add Edge-local `herdr_devices`;
- aggregate:
  - immutable device id;
  - name;
  - workstation mapping;
  - authorization;
  - scheduling;
  - connection/presence;
  - health;
  - runtime version/generation;
  - compatibility;
- retain current single-device behavior when only one routable device exists.

The Device Registry must not become a heartbeat hot path.

### P0-C — Secure enrollment

Required before a second device is considered formally supported:

- one-time enrollment flow;
- per-device credential bound to one immutable `device_id`;
- high-entropy device credential is sufficient for the first implementation; public-key identity can follow later;
- joining a second device must not require a Cloudflare deployment token;
- credential A must not authenticate as device B;
- revoke must block future reconnect with the old credential;
- legacy `LINK_SHARED_SECRET` remains a compatibility path for existing deployments, not the normal second-device enrollment path.

Target CLI surface:

```text
herdr-mcp worker setup
herdr-mcp worker create
herdr-mcp worker connect
herdr-mcp worker status
herdr-mcp devices list
herdr-mcp device status <device>
```

### P0-D — Explicit device routing

Public workstation-bound tools gain one common Edge routing extension. Do not modify the canonical 18 runtime schemas individually.

Routing order:

1. explicit device selector;
2. device-aware opaque ref;
3. trusted conversation/project binding containing `device_id`;
4. exactly one routable device;
5. otherwise `device_ambiguous`.

Deferred:

- probing all devices for project matches;
- model/path-string guesses;
- capability scoring/load balancing;
- automatic mutation failover.

Device-aware refs must preserve device identity across workspace/pane follow-up calls.

## P0 — Post-v0.4.2 Link reliability baseline

Already on `main`; do not recreate as multi-device work:

- oversized outbound result containment;
- prolonged workstation-offline recovery;
- public workstation retry policy;
- existing WorkstationDO mutation/delivery correctness.

Verification/acceptance status:

- oversized-result containment has a real incident root cause (`payload_too_large`) plus regression coverage that converts an oversized ToolResult into bounded `response_too_large` instead of terminating Link;
- the 2026-08-31 live outage exposed a second failure mode after DEV generation activation: `runtime/current` and runtime-control had advanced while the running Link still held its startup generation identity, producing repeated `GenerationMismatch { expected: old, observed: new }` and a launchd restart loop. The 0.4.3 acceptance baseline therefore requires one request-ownership fence: request leases come from `RuntimeGenerationManager`, dispatch consumes that exact lease, shared-loopback supersession is a bounded per-request error, and a stale startup generation cannot terminate the persistent Link;
- outbound oversize containment covers both ToolResult and ToolError and all bounded validation-budget classes used by relay encoding (`frame_too_large`, `payload_too_large`, string/depth/key/item limits); an individual oversized response must never terminate the Link process;
- Edge reconnect grace is 2 seconds by default, stays process-local, and is covered by zero-DO-write/alarm tests;
- `workstation_offline` / `workstation_reconnecting` expose `retryable=true`, `delivery_state=not_delivered`, `retry_after_ms=5000`, and a bounded read-only `herdr_inspect` recovery policy with 5s / 10s / 20s backoff;
- prolonged local Link offline is bounded at 300 seconds before diagnostic process recycle lets launchd `KeepAlive` rebuild `dev.herdr-mcp.link-prod`;
- mutation replay remains fail-closed unless delivery is explicitly `not_delivered` or independent evidence proves the mutation was not applied;
- production Edge deployment and automated Edge/Link regression gates passed for the implemented recovery chain. Do not claim browser-extension involvement in the `workstation_offline` decision path.
- live ChatGPT recovery UAT on 2026-08-31 first demonstrated the structured retry contract, then a later real outage proved that launchd/process health alone was insufficient when generation ownership diverged. Manual plist alignment restored the workstation and supplied the regression evidence above; 0.4.3 must pass generation-switch + prolonged-offline + oversized-response UAT together before this baseline is considered closed.

Multi-device routing must call into these mechanisms after target selection.

## P0 — Manual Continue composer-busy false positive

Extension `0.1.83` tightens the manual HUD Continue path after a real-user report on current ChatGPT UI.

Target contract:

- composer busy detection must inspect explicit Stop controls in the active composer, not every visible `button` / `[role=button]` on the page;
- unrelated page controls whose accessible text contains `Stop` must never block Continue;
- an actually streaming assistant remains busy through the existing streaming marker / composer Stop evidence;
- manual Continue waits only a short bounded interval for a genuinely busy composer before returning `composer-busy`; automatic wake/recovery retains the longer bounded wait;
- `composer-busy` carries a structured `busy_reason` so future UI drift can distinguish Stop-control evidence from assistant-streaming evidence.

Extension `0.1.84` audits the neighboring manual controls for the same latency and false-state failure class:

- a successful `h2w_wake` responds as soon as submission is accepted; the up-to-30-second reply-start confirmation runs asynchronously and remains health evidence rather than button latency;
- manual `LLM decide` never judges a still-streaming assistant turn, uses one bounded 15-second attempt, and keeps the longer retry policy only for automation;
- manual `Check Herdr` performs one explicit 4-second fresh-state request instead of immediately repeating the same failed request for another 4 seconds;
- manual Continue and handoff background handlers convert unexpected exceptions into structured responses instead of leaving a message port unresolved;
- a concurrent HUD action is reported as `action-busy`, not mislabelled as automation being enabled or handoff being unavailable.
- Control Center `Read tail` is read-only and therefore uses a 10-second bound instead of inheriting the generic 90-second JSON bridge timeout; write controls keep their uncertainty-aware delivery contract.

## P0 — Runtime DEV / PROD provenance

Current 0.4.2 commands can be executed from a repo-built binary and mutate global Native Host/service state. v0.4.3 should make this provenance explicit and prevent accidental cross-plane pollution.

Target behavior:

- PROD runtime = immutable installed generation originating from a published/verified release artifact.
- DEV runtime = repo/worktree build (`target/debug`, `target/release`, or an explicit development process).
- `herdr-mcp dev sync` is the explicit DEV entry: it builds Rust from the current checkout as `0.4.3-dev`, embeds `channel=dev`, source commit and dirty provenance, then hands the binary to the existing transactional `service install` path so server, Native Host and `dev.herdr-mcp.link-prod` converge on the same managed generation.
- DEV entry first pins the current PROD binary under `runtime/channels/prod/` with SHA-256 evidence. Repeated DEV syncs preserve that fixed PROD recovery source instead of redefining PROD as the previous DEV generation.
- `herdr-mcp dev rollback` verifies the pinned PROD snapshot and re-enters the existing transactional service lifecycle from that binary; it never rebuilds source as a rollback mechanism.
- `herdr-mcp dev status` reports DEV/PROD channel state, source commit/dirty status, active/dev/prod generations and snapshot validation. `herdr-mcp dev` without a subcommand is the read-only status alias.
- DEV sync refuses dirty source by default; `--allow-dirty` is an explicit provenance override. `--dry-run` is mutation-free.
- `status`/`doctor` expose runtime plane/source/commit or equivalent trustworthy provenance.
- PROD `runtime/current` must not silently become a repo-local build; only the explicit DEV transaction may switch the default workstation onto a repo-built generation.
- Global Native Host/service lifecycle mutations should use the active installed runtime or explicitly acknowledge a DEV override.
- `runtime_matches_current=true` is the normal healthy Native Host invariant.
- DEV/PROD switching never deploys Edge, changes DNS/OAuth, or creates a third persistent test environment. Candidate/UAT resources stay temporary.

This is not a third `test` environment. Candidate/UAT instances remain bounded and disposable.

Implementation/acceptance status: **complete on `main`**. A real workstation round-trip UAT passed `PROD 0.4.2 → DEV 0.4.3-dev → PROD 0.4.2 → DEV 0.4.3-dev`, including fixed PROD snapshot validation, `runtime/current` / Link desired / Link active generation agreement, clean source provenance, and the DEV Link generation-reconcile fix. The development workstation is expected to remain on the latest validated DEV generation while v0.4.3 is under active development.

## P0 — Cross-schema update / rollback compatibility

Integrate the existing cross-schema updater independently from multi-device Worker storage.

Required narrow contract:

- support the audited additive state-schema rollback path required by v0.4.2 <-> v0.4.3;
- preserve continuity data;
- reject unsupported destructive downgrades;
- allow the upgraded runtime to restore the current schema idempotently after a rollback-compatible older open.

Multi-device Device Registry authority belongs to the Worker. Local state stores only the minimal Worker/device binding and secure credential reference required by the local runtime.

Do not couple fleet registry evolution to the local SQLite rollback mechanism.

## P1 — Agent-first installation and Worker onboarding

Installation remains an execution protocol for an Agent.

Required behavior:

1. install/verify local PROD runtime;
2. select extension channel from explicit intent/capability;
3. independently determine Worker binding:
   - create a new Worker;
   - connect to an existing Worker;
   - local only;
4. never create a second Worker merely because Cloudflare credentials are available;
5. joining an existing Worker uses enrollment authorization, not deployment credentials;
6. report only non-sensitive identifiers/status.

The Agent must not print enrollment secrets, device credentials, Cloudflare tokens, owner credentials, or local MCP tokens.

## P1 — Local project auto-bind compatibility

Local project auto-bind is already on `main` via `208bca0` and becomes part of the v0.4.3 baseline:

- Herdr exposes an explicit `local_project_key` instead of making the extension infer Git identity;
- Git checkouts/worktrees share a key derived from common-dir metadata; non-Git workspaces use the canonical local folder path;
- newly opened Herdr workspaces with the same local project key inherit the current browser scope;
- a ChatGPT Project keeps project scope, while ordinary chats remain conversation-scoped;
- workspace removal and authoritative reconciliation remove stale bindings without treating a transient empty catalog as proof that all workspaces closed.

Multi-device compatibility adds one requirement: local project identity is not globally unique across devices. The routing hierarchy is therefore:

```text
browser conversation/project
  -> device_id
  -> local_project_key
  -> workspace_id
  -> pane_id
```

The current auto-bind implementation remains local-device behavior. Device-aware binding integration must compose with it rather than replace or duplicate its reconciliation rules.

## P1 — Autonomous planning advice and resource-aware orchestration

v0.4.3 adds a planning-advice layer for the Web ChatGPT planner without adding a 19th public MCP tool or turning herdr-mcp into a hard-coded scheduler.

Frozen behavior:

1. `herdr_skill` progressive bootstrap exposes compact live planning context plus the existing-call local method `herdr_mcp.planning.advise`;
2. the method accepts task requirements and returns deterministic direct options, compatible/rejected live workers, scan-proven startable-but-inactive Agent kinds, parallelism opportunity, and current workspace/pane/worktree resource facts;
3. delegation and parallelism remain advisory; only the Web planner chooses whether to delegate, create a lane, or stay direct;
4. user-explicit targets are preserved and never silently replaced;
5. required capabilities fail closed when unverified, while optional provider/model/quality/cost/latency traits remain unknown instead of being inferred from an Agent name;
6. default visibility is runtime self-discovery; `HERDR_MCP_AGENT_ALLOW` is an explicit operator restriction rather than a built-in worker-role list;
7. reuse of existing Agent panes, utility panes, and worktrees is preferred; there is no autonomous cleanup daemon;
8. live status remains Herdr/EventCache authority and static capability evidence remains the bounded scan inventory.

Dogfood acceptance must include adaptive behavior, not only unit tests: stop an ineffective worker rather than spawning duplicates, observe uncertain delivery before retry, reuse existing panes, and parallelize validation/review only when those lanes are independent.

## Integration order

1. Create and keep multi-device development in its own branch/worktree.
2. Land the Public/Runtime contract separation with tests before changing the public tool set.
3. Add device-id validation/model + Device Registry storage contract.
4. Add legacy single-device registry bootstrap and read-only aggregation.
5. Add Edge-local `herdr_devices` and public-contract epoch evolution.

10. Integrate independent standalone, provenance and cross-schema branches after rebasing each on current `main` and resolving contract conflicts deliberately.
11. Finish Agent/install docs against the actual implemented CLI.
12. Qualify exact final source and publish immutable `v0.4.3` only after all release gates pass.

## Multi-device core release gates

At minimum:

- Public contract identity and Runtime contract identity are distinct concepts in code/tests;
- runtime Link compatibility still accepts the intended epoch-2/current and epoch-1 rollback contracts;
- `herdr_devices` is Edge-local and is never forwarded to a workstation;
- two devices can remain online simultaneously behind one Worker;
- device aliases do not substitute for immutable identity after resolution;
- explicit call to A never executes on B;
- explicit call to B never executes on A;
- multi-candidate unqualified mutation returns `device_ambiguous`;
- opaque ref preserves its originating device;
- retry/recovery remains on the originally selected device;
- per-device credential cannot claim another device id;
- revoked credential cannot reconnect;
- existing v0.4.2 single-device deployment upgrades without losing Link availability;
- heartbeat/status/UI observation does not introduce Device Registry write churn;
- extension channel switching does not alter device identity;
- local schema rollback work remains independent of Worker Registry evolution.
