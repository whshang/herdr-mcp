# herdr-mcp v0.4.3 plan

Status: active planning / integration document
Baseline: `main` after PR #214 (`30e5031` after planning rebase)
Stable release remains immutable: `v0.4.2`

## Goal

v0.4.3 is a compatibility and product-boundary release. It should make the installed workstation easy to reason about without adding a third persistent runtime environment.

The product model is frozen as follows:

- Runtime: **DEV / PROD** only.
- Browser extension: **DEV / STANDALONE / STORE**.
- CI/UAT/candidate resources are temporary execution resources, not a third installed environment.
- `v0.4.2` is not re-tagged, rebuilt in place, or overwritten. All new contracts ship forward in v0.4.3 or in the independently versioned extension release plane.

## P0 — Browser extension distribution identities

### DEV

- Loaded unpacked directly from a repo/worktree `extension/` directory.
- Chromium identity remains path-derived; the DEV manifest must not gain a fixed `key`.
- Intended for source development and local debugging.
- Moving the unpacked directory can change its extension ID; re-register the DEV origin when that happens.

### STANDALONE

- Fixed, non-Store Chromium identity derived from a public manifest key.
- Distributed as a deterministic extension package through GitHub/manual download.
- The same fixed-identity package can be exported/generated by a DEV or PROD herdr-mcp build; the resulting browser identity must be identical regardless of source path or workstation.
- Must not share the Store ID and must not fall back to a path-derived DEV identity.
- No private signing key is required in the repository: only the public manifest key used by Chromium to derive the extension ID is stored in the contract/package.

### STORE

- Chrome Web Store-managed identity and update path.
- Existing official Store ID remains authoritative.
- Store publication remains independent from the Rust runtime tag lifecycle.

### Native Host ownership

- Add explicit `store | standalone | dev` ownership/status.
- One exact active `allowed_origins` owner at a time; inactive installed siblings stay in standby.
- Add `native-host use standalone` while preserving `use store`, `use dev`, DEV enable/disable and rollback semantics.
- Existing v0.4.2 Store/DEV installations must migrate additively; unknown/tampered origins fail closed.
- Status/doctor should show the active extension channel, ID, identity source and whether the Native Host binary matches the active runtime generation.

### Packaging and release

- Keep DEV source manifest unkeyed.
- `scripts/pack-extension.mjs` gains an explicit standalone build mode that injects the fixed public manifest key into the packaged manifest without mutating source `extension/manifest.json`.
- Standalone package output is deterministic and carries a SHA-256 sidecar/attestation.
- Do not make the Rust runtime release workflow silently own the extension lifecycle. Use an independent extension release surface or explicit release attachment policy whose provenance is auditable.
- GitHub/manual download means **STANDALONE**, never DEV.

## P0 — Runtime DEV / PROD provenance

Current 0.4.2 commands can be executed from a repo-built binary and mutate global Native Host/service state. v0.4.3 should make this provenance explicit and prevent accidental cross-plane pollution.

Target behavior:

- PROD runtime = immutable installed generation originating from a published/verified release artifact.
- DEV runtime = repo/worktree build (`target/debug`, `target/release`, or an explicit development process).
- `herdr-mcp dev sync` is the explicit DEV entry: it builds Rust from the current checkout as `0.4.3-dev`, embeds `channel=dev`, source commit and dirty provenance, then hands the binary to the existing transactional `service install` path so server, Native Host and `dev.herdr-mcp.link-prod` converge on the same managed generation.
- DEV entry first pins the current PROD binary under `runtime/channels/prod/` with SHA-256 evidence. Repeated DEV syncs preserve that fixed PROD recovery source instead of redefining PROD as the previous DEV generation.
- `herdr-mcp dev rollback` verifies the pinned PROD snapshot and re-enters the existing transactional service lifecycle from that binary; it never rebuilds source as a rollback mechanism.
- `herdr-mcp dev status` reports DEV/PROD channel state, source commit/dirty status, active/dev/prod generations and snapshot validation. `herdr-mcp dev` without a subcommand is the read-only status alias.
- DEV sync refuses dirty source by default; `--allow-dirty` is an explicit provenance override. `--dry-run` is mutation-free.
- `status`/`doctor` expose runtime plane/source/commit or equivalent trustworthy provenance.
- PROD `runtime/current` must not silently become a repo-local build; only the explicit DEV transaction may switch the default workstation onto a repo-built generation.
- Global Native Host/service lifecycle mutations should use the active installed runtime or explicitly acknowledge a DEV override.
- `runtime_matches_current=true` is the normal healthy Native Host invariant.
- DEV/PROD switching never deploys Edge, changes DNS/OAuth, or creates a third persistent test environment. Candidate/UAT resources stay temporary.

This is not a third `test` environment. Candidate/UAT instances remain bounded and disposable.

## P0 — Cross-schema update / rollback compatibility

Integrate the existing `fix/v0.4.3-cross-schema-updater-20260831` work only after rebasing it on current `main` and re-running the release gates.

The intended contract is narrow:

- support the audited additive state-schema rollback path needed by v0.4.2 ↔ v0.4.3 generation rollback;
- preserve continuity data across the compatibility transition;
- reject unsupported schema downgrades instead of attempting generic destructive migration;
- ensure an upgraded runtime can idempotently restore the current schema after a rollback-compatible older open.

No general-purpose arbitrary schema downgrade mechanism should be introduced.

## P0 — Manual Continue composer-busy false positive

Extension `0.1.83` tightens the manual HUD Continue path after a real-user report on current ChatGPT UI.

Target contract:

- composer busy detection must inspect explicit Stop controls in the active composer, not every visible `button` / `[role=button]` on the page;
- unrelated page controls whose accessible text contains `Stop` must never block Continue;
- an actually streaming assistant remains busy through the existing streaming marker / composer Stop evidence;
- manual Continue waits only a short bounded interval for a genuinely busy composer before returning `composer-busy`; automatic wake/recovery retains the longer bounded wait;
- `composer-busy` carries a structured `busy_reason` so future UI drift can distinguish Stop-control evidence from assistant-streaming evidence.

## P0 — Local project workspace auto-binding

Keep the existing per-workspace binding model; do not introduce a separate persistent ProjectBinding layer.

Target contract:

- each live Herdr workspace exposes a derived `local_project_key`, independent from the ChatGPT Project/conversation key;
- Git checkouts and linked worktrees share one key derived from Git common-dir metadata, without spawning Git on `/push/state` reads;
- non-Git workspaces fall back to the canonical local folder path;
- after one workspace is bound, newly opened Herdr workspaces with the same `local_project_key` inherit the same current browser scope automatically;
- a ChatGPT Project keeps its existing project scope, while an ordinary chat inherits only inside that conversation;
- `workspace_removed` immediately removes bindings for the closed workspace, and non-empty authoritative catalogs compensate for missed lifecycle events;
- an empty/transient workspace catalog is not treated as proof that every workspace closed;
- unbinding a member of an auto-bound local-project group removes that group from the current browser scope so it does not immediately inherit again;
- stale closed workspaces are not synthesized as offline rows in the Control Center.

This is a small binding reconciliation rule, not a new project registry or persistence model.

## P0 — Link oversized-result containment

The current `fix/v0.4.3-link-offline-self-healing-20260831` worktree contains one narrow reliability fix: an outbound result that exceeds the Relay result-payload budget currently raises `payload_too_large`, while the compact `response_too_large` fallback only handles `frame_too_large`. That encoding failure must not become a Link outage.

Target contract:

- treat outbound `payload_too_large` and `frame_too_large` as the same bounded-result condition for `ToolResult`;
- replace the oversized result with the existing compact, correlated `response_too_large` `ToolError`;
- mark the original request delivered/non-retryable so an unsafe operation is never replayed just because its result was too large;
- keep the Link online and available for later requests;
- retain the existing fail-closed behavior if even the compact fallback cannot be encoded.

This containment fix is already part of the v0.4.3 baseline after PR #216. It does not by itself cover a Link process that remains alive while its Edge connection stays unavailable.

## P0 — Link prolonged-offline self-healing

v0.4.3 must also contain transient Edge ↔ workstation outages before they become sustained ChatGPT-visible `workstation_offline` failures.

Target contract:

- keep the normal Link WebSocket reconnect/backoff path as the first recovery mechanism;
- if the Link process cannot reach `Online` for a bounded prolonged interval (default 5 minutes), terminate that Link process with a diagnostic non-zero outcome so the existing `dev.herdr-mcp.link-prod` launchd `KeepAlive` policy starts a fresh process;
- cancel the prolonged-offline recycle timer immediately after a successful validated Link handshake;
- do not restart the healthy `dev.herdr-mcp.server` merely because the Edge Link is offline;
- when a workstation was connected moments ago and its active Link is briefly absent, Edge waits a short bounded reconnect grace (default 2 seconds, never beyond the original request deadline) before returning `workstation_offline`;
- a validated `hello` wakes those request-local waiters immediately;
- the reconnect grace stays process-local and consumes zero Durable Object storage/alarm writes;
- never-connected or already-prolonged-offline workstations fail fast instead of paying the reconnect-grace latency;
- no mutation is sent or blindly replayed during the reconnect grace; existing delivery-state, idempotency, pending-capacity, and fail-closed semantics remain authoritative.
- if Edge still returns `workstation_offline` / `workstation_reconnecting`, the MCP tool error must be self-describing: `retryable=true`, `delivery_state=not_delivered`, `retry_after_ms=5000`, and `recovery={action:"retry_read_only_probe",probe_tool:"herdr_inspect",max_attempts:3,backoff_ms:[5000,10000,20000],...}`;
- the Agent follows the tool-provided bounded read-only recovery policy rather than guessing from the error code or prose; a failed mutation is replay-safe only after an explicit `not_delivered` result, while `delivery_unknown`, `delivered`, or missing delivery state still requires evidence before any replay.

The Edge grace is request-local recovery, not a new heartbeat/polling mechanism. It must not increase steady-state Durable Object wakeups or daily write consumption.

## P1 — Agent-first installation and documentation

The installation documentation is an **execution protocol for an Agent**, not a prompt template for a human to copy into a named coding product.

Required documentation model:

- `agent-install.md`: authoritative executable protocol addressed directly to the Agent.
- `agent-install.md`: detailed execution contract and security/network decisions for the Agent.
- `install.md`: operator/manual/reference path; it may explain human-only pauses but must not make "copy this whole prompt to Codex/Claude/Cursor/Pi/Cline" the primary UX.
- README: link directly to the Agent protocol and explain what the Agent should do; no vendor laundry-list prompt block.
- English and Simplified Chinese stay semantically aligned; Japanese README follows the same product model and links to the canonical Agent protocol until a full Japanese protocol exists.

Agent behavior:

- execute deterministic checks/mutations directly;
- pause only for genuinely interactive human authorization/choice;
- if network/login/third-party availability blocks the requested path, stop and report the blocker rather than inventing proxy or bypass infrastructure;
- never expose secrets in command output, logs, docs or final reports;
- install ordinary workstation PROD runtime from published releases, not from a git checkout.

## P1 — Extension installation decision for Agents

After the Connector/runtime path is healthy, the Agent selects an extension channel from explicit user intent and runtime capability:

1. **STORE** — default ordinary-user path when the Chrome Web Store item is available.
2. **STANDALONE** — supported v0.4.3+ manual/GitHub path when Store installation is unavailable or the user explicitly chooses independent distribution.
3. **DEV** — only when the user is developing herdr-mcp/extension source or explicitly asks for a development build.

The Agent must never call a path-derived DEV build "standalone" and must never label a GitHub/manual fixed-identity package "dev".

For a machine still running v0.4.2, the Agent must not pretend `standalone` exists in the runtime Native Host contract. Upgrade to a release that advertises standalone support first, or use the supported v0.4.2 Store/DEV paths.

## Release integration order

1. Land already-independent fixes that are reviewed and green; never rewrite v0.4.2.
2. Rebase each dirty v0.4.3 worktree on current `main` before integration; preserve unrelated worktree ownership.
3. Treat PR #213 image-only capture and PR #214 HUD/Control Center settlement as baseline; do not recreate their old worktrees as new feature work.
4. Land the narrow Link oversized-result containment fix after rebasing and Rust transport tests.
5. Land standalone identity/Native Host/package contract.
6. Land runtime provenance and cross-schema rollback compatibility.
7. Land/finalize Agent-first documentation against the actual implemented command surface; future-tense standalone commands remain version-gated until implementation lands.
8. Run Rust + Node/docs + extension smoke + release-surface tests, then real DEV/STANDALONE/STORE browser identity UAT in isolated browser profiles.
9. Qualify the exact final v0.4.3 source through the existing release gate; only then create the immutable `v0.4.3` tag and publish.

## v0.4.3 release gates

At minimum:

- `cargo fmt --check`
- `cargo clippy --workspace --all-targets --all-features -- -D warnings`
- `cargo test --workspace`
- Node/docs/Edge release gate
- package/diff hygiene
- extension smoke and Native Host ownership tests
- standalone package determinism + fixed-ID derivation test
- Store ID unchanged
- DEV source manifest remains unkeyed/path-derived
- `store -> standalone -> dev -> store` owner switching with stale-connection fencing
- v0.4.2 installed state -> v0.4.3 update -> rollback -> re-apply, including state-schema compatibility
- PROD runtime/Native Host binary provenance is visible and consistent

## Explicit non-goals

- no persistent TEST installation plane;
- no retagging/rebuilding `v0.4.2` in place;
- no Store identity/key change;
- no generic browser-file relay expansion;
- no automatic network/proxy reconfiguration as an installation workaround;
- no arbitrary state-schema downgrade framework;
- no duplication of Herdr workspace/agent/runtime responsibilities inside the extension.
