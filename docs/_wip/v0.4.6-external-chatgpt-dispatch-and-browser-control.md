# v0.4.6 开发计划：外部任务注入 ChatGPT Project 与浏览器控制面

> 状态：WIP / architecture plan
> 目标版本：v0.4.6
> 范围：herdr-mcp Browser Extension + 本地可信控制路径 + 必要的 runtime/Edge 路由契约
> 非目标：为任何单一公司的 GitLab、Jira、飞书或其他业务系统做专用逻辑

## 0. 结论先行

v0.4.6 的核心能力不是“GitLab 自动开发”，也不是“把 OpenCLI 集成进 herdr-mcp”。

目标应该定义为：

> **允许一个经过授权的外部应用，把一条任务或后续消息可靠、幂等地注入到指定 ChatGPT Project / Conversation，并由现有 Herdr 浏览器连续性、Auto、权限卡处理、handoff 和多设备执行能力继续完成后续工作。**

因此职责边界是：

```text
External workflow / CLI / ticket system
            │
            │ typed dispatch intent
            ▼
Herdr authenticated routing layer
            │
            │ select explicit browser endpoint/device
            ▼
herdr-mcp Browser Extension
            │
            ├─ own ChatGPT DOM / Project / Conversation semantics
            ├─ own composer reasoning/app selection
            ├─ own postcondition + stale-view recovery
            └─ own Project Auto / permission-card / continuity integration
            │
            ▼
ChatGPT Project conversation
            │
            ▼
Web planner
            │ MCP
            ▼
Herdr fleet → files / Git / commands / Pi / Cline / Codex / other agents
```

OpenCLI 在本计划中仅是：

1. 浏览器行为研究工具；
2. 首次 bootstrap / UAT 工具；
3. extension 主路径失效时可选的外部兼容 fallback。

**OpenCLI 不是 herdr-mcp 的运行时依赖，也不进入 public contract。**

GitLab 在本文后半部分作为一个完整参考消费者：`gitlab-ai-workflow`。GitLab 相关业务规则不进入 herdr-mcp 核心代码。

## 1. 命名与概念边界

### 1.1 外部 GitLab 项目建议命名 `gitlab-ai-workflow`

相比 `gitlab-ai-orchestrator`，`gitlab-ai-workflow` 更准确：它拥有的是 GitLab 事件、策略、幂等、任务状态和回写 workflow，不是整个 Herdr / ChatGPT 控制平面的唯一 orchestrator。

推荐独立项目：

```text
root/gitlab-ai-workflow
```

现有 `root/gitlab-mr-review` 可以逐步迁入，兼容模板保持一段时间。

### 1.2 GitLab 中的非人类 assignee 建议叫 `herdr-worker`

`ChatGPT Worker` 太窄，因为真正承担工作的是：

```text
ChatGPT planner identity
+ browser endpoint
+ Herdr fleet
+ coding agents
+ project policy
```

在外部 workflow 中，可以定义逻辑 worker：

```text
hw:qingxian-main
hw:alice-main
hw:platform-pool
```

GitLab Service Account 的人类可读名称建议：

```text
Herdr Worker · Qingxian
Herdr Worker · Alice
Herdr Worker · Platform
```

username：

```text
herdr-worker-qingxian
herdr-worker-alice
herdr-worker-platform
```

不要按 GitLab 项目或设备创建大量账号，例如不要使用：

```text
herdr-worker-plm-macbook-01
herdr-worker-oms-macbook-02
```

worker 应按**开发者 / ChatGPT 账号 / 信任边界**划分，而设备是 worker 可以调度的运行资源。

### 1.3 `herdr-worker` 不是 herdr-mcp 核心协议实体

这是重要边界。

herdr-mcp 核心只需要理解：

```text
browser_endpoint_id
browser/account identity
project binding
conversation identity
Herdr device identity
workspace/runtime state
```

`herdr-worker` 是 GitLab 或其他外部 workflow 用来表达“由谁负责”的业务调度概念。

## 2. 为什么不把 GitLab 或 OpenCLI 做进 herdr-mcp

### 2.1 GitLab 是消费者，不是浏览器自动化事实源

未来调用方可能包括：

- GitLab Issue / MR；
- Jira；
- 飞书项目 / 多维表格；
- 邮件工单；
- 本地 CLI；
- 定时任务；
- 自研审批系统；
- 其他 Agent 平台。

核心接口如果接受的是：

```text
“把这条消息可靠地交给 project X 的 conversation Y”
```

所有系统都能复用。

如果核心接口接受的是：

```text
“处理 GitLab Issue #42 的待开发标签”
```

就已经发生错误分层。

### 2.2 OpenCLI 是外挂，不是依赖

本轮 OpenCLI 的价值很高：它证明了 ChatGPT Web 上一批动作可自动化，并暴露了缓存、controlled input、click-no-effect 等真实问题。

但生产架构不能要求：

```text
herdr-mcp runtime -> shell -> opencli -> Chrome
```

作为唯一主路径。

主路径应是 extension 自己拥有网页适配语义；OpenCLI 可以继续独立发展，并通过命令行反向调用同一个通用 dispatch 能力，或在主路径故障时作为 operator fallback。

## 3. v0.4.6 目标架构

```text
                         ┌──────────────────────────────┐
                         │ External applications        │
                         │ GitLab/Jira/Feishu/CLI/etc. │
                         └──────────────┬───────────────┘
                                        │
                              typed authenticated intent
                                        │
                         ┌──────────────▼───────────────┐
                         │ Herdr routing / capability   │
                         │ - auth                       │
                         │ - device routing             │
                         │ - idempotency envelope       │
                         └──────────────┬───────────────┘
                                        │
                         explicit browser endpoint/device
                                        │
                 ┌──────────────────────▼──────────────────────┐
                 │ herdr-mcp Browser Extension                │
                 │ External Chat Dispatch Gateway             │
                 │                                             │
                 │ Project Registry / Conversation Ledger      │
                 │ Composer App + Reasoning Controller         │
                 │ Mutation Reliability Kernel                 │
                 │ Auto / Permission / Continuity integration │
                 └──────────────────────┬──────────────────────┘
                                        │
                                    ChatGPT Web
                                        │
                         ┌──────────────▼───────────────┐
                         │ Project / Conversation       │
                         │ Web planner                  │
                         └──────────────┬───────────────┘
                                        │ MCP
                         ┌──────────────▼───────────────┐
                         │ Herdr fleet                  │
                         │ device A / B / C             │
                         │ repo/worktree/agents         │
                         └──────────────────────────────┘
```

关键点：

1. **浏览器所在设备和代码执行设备不是一个概念。**
2. 一个 ChatGPT 浏览器账号可以规划多个项目，并把实际任务分散到多个 Herdr device。
3. external application 不获得 Chrome cookie，也不获得任意 DOM / shell 权限。
4. extension 承担 ChatGPT 页面语义，而 runtime/Edge 只负责认证、路由和 typed intent transport。

## 4. Browser Endpoint：多设备时代必须先定义的身份

### 4.1 为什么不能只保存 device_id

同一台机器上可能有：

- Chrome Profile A：开发者 A 的 ChatGPT；
- Chrome Profile B：开发者 B 的 ChatGPT；
- 两个不同 ChatGPT 账号；
- stable / beta 浏览器；
- 同一个 ChatGPT 账号在不同机器上登录。

因此新增稳定本地身份：

```text
browser_endpoint_id
```

建议逻辑结构：

```json
{
  "browser_endpoint_id": "be:q-macbookair-chatgpt-main",
  "device_id": "dev_...",
  "browser": "chrome",
  "profile_id": "local-generated-stable-id",
  "site": "chatgpt.com",
  "account_fingerprint": "opaque-stable-fingerprint",
  "extension_install_id": "ext-install-...",
  "status": "online"
}
```

不要把真实账号邮箱、cookie、OAuth token 当 identity 存在中央系统。

### 4.2 Account fingerprint

只需要回答：

> 当前浏览器端点是不是预期的 ChatGPT 身份？

可以由 extension 从页面可见稳定账户元数据生成 opaque fingerprint，并只在本地/受限控制面使用。

不上传密码、cookie 或完整个人资料。

### 4.3 同一账号多端登录

允许多个 browser endpoint 指向同一个 account fingerprint，但同一个 Project/Work Unit 的 planner lease 同一时刻只允许一个 active endpoint。

否则可能出现：

```text
Mac A 自动 wake conversation C42
Mac B 同时自动 wake conversation C42
→ 两端重复提交下一回合
```

必须使用 lease generation / fencing token。

## 5. Project Binding Registry

### 5.1 不按名称猜

不要求外部项目名、ChatGPT Project 名、Herdr workspace 名一致。

例如：

```text
GitLab:          bo.yang/libernovo-plm
ChatGPT Project: plm-物料协同平台
Herdr workspace: plm-grid-optimization
repo root:       /Users/.../libernovo-plm
```

显示名服务人类，机器使用 stable IDs。

### 5.2 本地 binding

extension / local runtime 保存：

```yaml
bindings:
  plm:
    browser_endpoint_id: be:q-macbookair-chatgpt-main
    chatgpt_project_id: g-p-6a97bfd57b448191b3d9d7e25f6ab27c
    chatgpt_project_url: https://chatgpt.com/g/g-p-.../project
    default_reasoning: extremely_high
    required_apps:
      - keyword: herdr
        plugin_id: plugin:asdk_app_...
    project_auto: true
    execution_affinity:
      repo_roots:
        - /Users/qingxian/Documents/libernovo-plm
      eligible_devices:
        - dev_...
```

`plugin_id` 在绑定/探测时发现，不应该在核心源码中硬编码企业实例 ID。

### 5.3 不永久绑定 workspace/pane

workspace、pane、agent 是运行时资源。

长期保存：

```text
binding_key
browser_endpoint_id
chatgpt_project_id
repo root affinity
eligible device IDs
```

任务开始时再通过 Herdr 实时解析合适 workspace。

## 6. 通用 External Chat Dispatch Contract

### 6.1 高层接口优先

外部应用最常用的接口应该只有：

```text
chat.dispatch
chat.append
chat.status
```

而不是把 DOM primitive 暴露出去。

示例：

```json
{
  "request_id": "opaque-unique-id",
  "idempotency_key": "source/work-unit/event-id",
  "binding_key": "plm",
  "work_unit_key": "opaque:issue:42",
  "mode": "new_or_resume",
  "message": {
    "text": "..."
  },
  "composer": {
    "reasoning_effort": "extremely_high",
    "required_apps": ["herdr"]
  },
  "automation": {
    "enable_project_auto": true
  },
  "postconditions": {
    "require_conversation_id": true,
    "require_message_accepted": true,
    "require_apps_selected": true
  }
}
```

### 6.2 返回值

```json
{
  "status": "confirmed",
  "dispatch_id": "dp_...",
  "replayed": false,
  "browser_endpoint_id": "be:...",
  "project_id": "g-p-...",
  "conversation_id": "...",
  "conversation_url": "https://chatgpt.com/g/.../c/...",
  "evidence": {
    "required_apps": ["herdr"],
    "reasoning_effort": "extremely_high",
    "server_accepted": true,
    "view_reload_used": false
  }
}
```

### 6.3 结果状态

至少区分：

```text
confirmed          authoritative postcondition passed
replayed           same idempotency key, prior confirmed result reused
queued             browser busy, accepted into local bounded queue
rejected           policy/auth/binding/capability rejection
not_applied        mutation definitely did not apply
uncertain          delivery may have happened; do not blindly retry
browser_offline    selected browser endpoint unavailable
project_unready    Project exists but provisioning/readiness not established
```

不要只返回：

```text
clicked=true
```

## 7. External API 不允许什么

远端 dispatch 请求**禁止**包含：

- CSS selector；
- OpenCLI ref；
- DOM XPath；
- 任意 JavaScript；
- 任意网页 URL；
- 任意 keyboard sequence；
- raw Chrome DevTools command；
- 任意 shell command；
- ChatGPT cookie；
- 浏览器 local storage token。

远端只能表达高层意图，例如：

```text
project=plm
conversation=new_or_resume
message=...
reasoning=extremely_high
required_apps=[herdr]
```

DOM 适配完全留在 extension。


## 9. ChatGPT Project / Conversation 生命周期 UAT（2026-09-03）

以下结果来自当前 Pro 账号 + 当前 ChatGPT Web + OpenCLI 浏览器自动化实测。OpenCLI 只作为 UAT 工具；这些结果用于定义 extension 的正确 contract。

### 9.1 Project 操作

| 动作 | 当前实测 | 稳定锚点 / 后验 | v0.4.6 要求 |
| --- | --- | --- | --- |
| 列出项目 | PASS | `/projects`、Project rows / stable `g-p-*` | binding bootstrap 可用 |
| 创建项目 | PASS | `data-testid=modal-new-project-enhanced`，创建后得到 stable `g-p-*` Project URL | create 后进入 readiness barrier |
| 打开项目 | PASS | `/g/g-p-.../project` | 后续运行直接用 project ID/URL，不扫侧栏 |
| 置顶项目 | PASS | menu `置顶项目`，再次打开变 `取消置顶项目` | action + state verification |
| 取消置顶 | PASS（由状态可逆路径确认） | `取消置顶项目` | 同上 |
| 重命名项目 | UI 存在；generic OpenCLI path 未完成持久化资格 | `#project-name` 存在，但本轮 controlled input 未观察到 authoritative save | extension 实现专用路径；强刷/server state 后验，不把旧 DOM 判失败 |
| 删除项目 | PASS | `modal-delete-project`，确认按钮“从‘聊天’和‘工作’中删除”；删除后 `/projects` 不再存在 | destructive capability 单独授权 |

临时 Project `AUTOMATION-UAT-v046` 已在 UAT 后删除。

### 9.2 Conversation 操作

| 动作 | 当前实测 | 关键证据 |
| --- | --- | --- |
| 在已稳定 Project 创建新对话 | PASS | send 后得到 `/g/<project>/c/<conversation-id>` |
| 重命名对话 | PASS | 侧栏 options → `重命名` → `aria-label=聊天标题` → Enter；标题/侧栏同步 |
| 归档 | PASS | 归档后从普通历史入口消失；direct URL 仍可读取，符合 archive 而非 delete 语义 |
| 删除 | PASS | `delete-conversation-confirm-button`；删除后 direct URL 不再返回原内容 |
| 移至项目 | PASS，但鼠标 click 曾出现 no-effect | keyboard focus + Enter 后 Project chat list 出现 `/g/<target-project>/c/<id>` |
| 从项目移除 | PASS | target Project chat list 不再包含 conversation；一般 `/c/<id>` 保留 |

### 9.3 Reasoning effort

当前账号实际显示 5 档 slider：

```text
aria-valuemin=0
aria-valuemax=4
```

实测：

```text
2 = 高
3 = 极高
4 = Pro
```

当前页面显示共 5 项。

extension 对外不要暴露本地化中文字符串，而是语义枚举：

```text
instant
medium
high
extremely_high
pro
```

启动时根据页面能力探测映射；不支持时默认 fail closed，除非调用方明确允许 downgrade。

### 9.4 `herdr` app 显式选择

实测 `@` 是 ChatGPT composer 自己暴露的插件/文件/技能 picker 快捷入口；它和左侧 `+` 的目标语义相同。

通过 picker 选择 `herdr` 后，composer 会创建正式 inline selection pill：

```html
data-inline-selection-pill
 data-keyword="herdr"
 data-id="plugin:asdk_app_..."
 data-system-hint-type="plugin:asdk_app_..."
```

这是可以依赖的 selected-app 后验。

本轮进一步验证：

1. 选择 `herdr` app pill；
2. 创建新 Project conversation；
3. ChatGPT 页面出现“已调用工具”；
4. read-only Herdr 探针完成并返回 `HERDR_READY_`。

因此 `required_apps:["herdr"]` 是可实现的。

实现策略：

```text
preferred: native + menu flow
fallback: ChatGPT 自带 @ picker shortcut
postcondition: inline selection pill exists with expected discovered plugin identity
```

不能把“点击 + 成功”当后验；最终只看正式 app pill。

## 10. 缓存、网络波动和 stale view：不能把旧 DOM 当事实

ChatGPT Web 会出现：

- mutation 已经被 server 接收，但 DOM 仍旧；
- Project/Conversation 刚创建后局部数据还未收敛；
- browser cache 显示旧标题；
- click 返回成功但没有真正触发业务 handler；
- 页面 URL 延迟更新；
- DOM 与 server snapshot 暂时不同步。

v0.4.6 必须复用现有 browser continuity 的 evidence-first 思路。

### 10.1 正确验证顺序

```text
perform typed action
      │
      ▼
local DOM immediate evidence
      │
      ▼
authoritative same-origin/server evidence when available
      │
      ├─ server confirms → SUCCESS
      │
      ├─ server ahead, DOM stale → one bounded reload → SUCCESS if converged
      │
      ├─ definitely not applied → NOT_APPLIED
      │
      └─ cannot tell → UNCERTAIN
```

### 10.2 不允许

```text
clicked=true -> success
```

也不允许：

```text
DOM still old -> immediately retry mutation
```

### 10.3 Project readiness barrier

刚创建 Project 后，不能立刻假设 composer/backend 全部可用。

`project.create` 完成后进入：

```text
created -> provisioning -> ready
```

`ready` 至少要求：

- exact Project URL 可加载；
- project ID 一致；
- composer 可用；
- Project chat/source tabs 初始化；
- 必要时一次 refresh 后仍一致。

这样可以吸收“新建 Project 后立即 send 无效果”的网络/缓存/后端收敛窗口，而不是误判成产品不支持。

## 11. 幂等与 delivery semantics

### 11.1 每个外部请求必须有 idempotency key

```text
source/work-unit/event-id
```

extension/runtime 保存短期 durable dispatch ledger：

```text
idempotency_key
status
browser_endpoint_id
project_id
conversation_id
message fingerprint
started_at
confirmed_at
outcome evidence
```

### 11.2 发送不确定时不重放

如果 submit 后：

- DOM 卡死；
- network timeout；
- browser worker 重启；
- conversation URL 尚未更新；

但无法证明 server 没收到，则返回：

```text
uncertain
```

调用方不得自动再发同样消息。

恢复后先用 idempotency key / conversation server state 判断。

### 11.3 追加消息也必须幂等

一个 GitLab webhook、Jira callback 或定时任务重放 3 次，不能产生 3 条用户消息。

## 12. 权限卡和 Project Auto

现有 extension 已有保守 auto-Allow：

- 仅 ChatGPT automation enabled；
- 显式 Allow；
- 同一最小 card 有 permission 文本；
- 存在显式 deny action；
- visible / enabled；
- WeakSet 防重复。

v0.4.6 直接复用，不另造“自动点所有确认按钮”。

需要区分两层授权：

```text
ChatGPT UI 工具权限卡
→ 可以按 Project Auto policy 自动处理

业务/生产高风险批准
→ 仍由项目自己的安全 policy 控制
```

例如数据库 destructive migration 的人工审批不能因为浏览器能 auto-Allow 就被绕过。

## 13. 外部应用接入方式

### 13.1 本地应用

可以提供 CLI / local IPC：

```text
herdr-mcp chat dispatch --binding plm --message-file ...
```

CLI 只是 typed contract client，不直接操作 DOM。

### 13.2 远端应用

通过现有 Herdr authenticated routing：

```text
external service
  -> Herdr Edge/private capability
  -> explicit device/browser endpoint
  -> local runtime
  -> extension native messaging path
```

不新增入站 Mac HTTP server。

### 13.3 public MCP tool contract

v0.4.6 默认不需要新增 ChatGPT-visible public MCP tool。

优先使用：

- private Herdr method；或
- native/local dispatch API；或
- 已存在的私有 extension route。

这样避免为了“让外部程序唤醒 ChatGPT”扩大 Web planner 自己可见的 public tool ABI。

## 14. Dispatch Capability Security

远端 external app 应获得最小 capability，例如：

```yaml
subject: gitlab-ai-workflow-prod
allowed_actions:
  - chat.dispatch
  - chat.append
  - chat.status
allowed_bindings:
  - plm
  - oms
expires: ...
```

默认不允许：

- `project.delete`；
- `conversation.delete`；
- arbitrary URL；
- arbitrary DOM；
- arbitrary terminal；
- arbitrary Herdr method。

Project/Conversation destructive lifecycle 需要更高等级 local/admin capability。

## 15. 多机器：Planner Device 与 Execution Device 分离

这是 herdr-mcp 现有群控能力在 v0.4.6 的核心优势。

### 15.1 一个 ChatGPT 账号负责多个项目

例如：

```text
ChatGPT account q-main
Browser endpoint be:q-macbookair
    │
    ├─ Project PLM
    ├─ Project OMS
    ├─ Project Data Platform
    └─ Project Timesheet

Herdr fleet
    ├─ dev_macbookair
    ├─ dev_macstudio
    └─ dev_server
```

外部事件只需要唤醒 `be:q-macbookair` 上正确 Project。

进入 ChatGPT 后，Web planner 可以通过 Herdr 把具体工作派到：

```text
PLM -> macbookair
OMS backend -> macstudio
integration test -> dev_server
```

因此不应把 ChatGPT Project 永久绑定到某一台“代码执行机器”。

### 15.2 Browser endpoint 是 planner ingress

任务注入必须路由到：

> 哪台设备的哪个浏览器 Profile 正登录目标 ChatGPT 账号。

之后的工程执行可以跨整个 fleet。

## 16. 多 ChatGPT 账号 / 多开发者

### 16.1 每个信任边界一个逻辑 worker

例如：

```text
hw:qingxian-main
  browser endpoint: be:q-macbookair
  ChatGPT account: q-main
  Herdr fleet: company-dev-fleet

hw:alice-main
  browser endpoint: be:alice-macbook
  ChatGPT account: alice-main
  Herdr fleet: company-dev-fleet or alice-owned subset
```

一个开发者如果有两个完全独立的 ChatGPT 账号/浏览器权限边界，可以有：

```text
hw:qingxian-main
hw:qingxian-secondary
```

### 16.2 同一个外部项目可以有多个 worker

例如：

```yaml
project: plm
workers:
  primary:
    - hw:qingxian-main
  fallback:
    - hw:alice-main
  reviewers:
    - hw:platform-review
```

### 16.3 Work Unit sticky lease

一旦 Issue/Task 创建了 conversation：

```text
work_unit_key
→ worker_id
→ browser_endpoint_id
→ chatgpt_project_id
→ conversation_id
→ lease_generation
```

后续 MR、pipeline、deployment、补充评论都优先追加到这一条 conversation。

不要每个事件重新做 worker 负载均衡。

### 16.4 Failover

只有在安全边界做：

1. 原 worker 明确不可用；
2. 没有 delivery-unknown mutation；
3. Continuity Journal / handoff packet 已就绪；
4. 新 worker 有目标 Project 访问权，或配置了自己的对应 Project；
5. 新 conversation seed 验证成功；
6. lease generation 原子切换；
7. 原 endpoint 被 fencing token 阻止继续 wake。

跨 ChatGPT 账号不能假设原 conversation 可直接转移；默认使用 continuity/handoff 新建目标 conversation。

## 17. 多账号下 Project 映射不能只存一份

不同 ChatGPT 账号可能：

- 访问同一个 shared Project；
- 各自有独立同名 Project；
- 一个账号有访问权、另一个没有。

所以外部 workflow registry 建议：

```yaml
bindings:
  plm:
    external_project: gitlab:123
    workers:
      hw:qingxian-main:
        chatgpt_binding_key: plm-q
      hw:alice-main:
        chatgpt_binding_key: plm-alice
```

worker 本地：

```yaml
plm-q:
  project_id: g-p-aaa

plm-alice:
  project_id: g-p-bbb
```

如果确实是 shared Project，两者可以解析到同一个 stable Project ID，但调度模型不应依赖这个假设。

## 22. MR Workflow：四级分流

MR 不应全部创建 ChatGPT conversation。

```text
MR pipeline
   │
   ▼
deterministic preflight
   │
   ├─ Tier 0: skip
   │    docs/format/generated/no-risk
   │
   ├─ Tier 1: cheap review
   │    small remote LLM narrow judgement
   │
   ├─ Tier 2: deep agent review
   │    Herdr -> Pi/Codex/Grok/Droid
   │
   └─ Tier 3: ChatGPT escalation
        auth / migration / production / cross-system /
        P1 / semantic conflict / linked complex Issue
```

### 22.1 保留 cheap LLM 的合理位置

cheap LLM 只回答窄问题，例如：

```text
是否存在明显风险？
是否需要 deep review？
```

它不是项目 planner。

### 22.2 deep agent path

普通深审直接：

```text
workflow -> Herdr -> review agent -> structured conclusion
```

不污染 ChatGPT Project 历史。

### 22.3 ChatGPT escalation

如果 MR 关联 Issue #42：

```text
append to Issue #42 existing conversation
```

不要新建第二条 MR conversation。

只有没有 Work Unit 且确实需要高级 planner 时才新建 MR conversation。

## 41. 关键决策摘要

1. **herdr-mcp v0.4.6 做通用 External Chat Dispatch，不做 GitLab 定制。**
2. **Browser Extension 拥有 ChatGPT Project/Conversation/Composer 页面语义。**
3. runtime/Edge 只做认证、设备路由和 typed intent transport，不理解 GitLab 标签或业务规则。
4. OpenCLI 是外挂研究/bootstrap/fallback，不是 herdr-mcp 依赖。
5. `gitlab-ai-workflow` 是推荐的 GitLab 消费者项目名。
6. GitLab 非人类 assignee 使用 `herdr-worker-*` 家族；按开发者/ChatGPT 信任边界拆，不按设备/项目拆。
7. 一个 worker 可以服务多个外部项目并控制多个 Herdr device；planner browser endpoint 与 execution device 分离。
8. 一个项目可以有 primary/fallback/reviewer 多 worker；Work Unit 启动后 sticky lease。
9. GitLab/ChatGPT/Herdr 名称不需要对齐；机器用 stable IDs + binding key。
10. 外部应用只调用 `chat.dispatch/append/status` 这类高层接口，不拿 DOM/shell 权限。
11. 所有 browser mutation 都必须 `action + authoritative postcondition`。
12. stale DOM / cache 不能直接判失败；server ahead 时允许一次 bounded refresh。
13. 新建 Project 有 readiness/provisioning barrier。
14. required app 在最终 prompt 组装后选择，发送前验证正式 inline pill。
15. `herdr` app 已实测能形成正式 plugin pill，并能触发真实 Herdr tool call。
16. pipeline/外部调用方只等待 dispatch 确认，不等待 Web planner 长任务结束。
17. 跨账号/跨 endpoint failover 必须 continuity + lease fencing，不重放 delivery-unknown mutation。

## 42. v0.4.6 完成定义

只有以下全部满足，才算本方向完成：

- 任意经过授权的外部应用可以通过通用 typed contract 唤醒指定 ChatGPT Project；
- 可以 new/resume/append，并返回 stable conversation evidence；
- 可以配置 reasoning effort；
- 可以声明 `required_apps=[herdr]`，并验证正式 app pill；
- 已证明带 herdr app 的真实对话产生 Herdr tool call；
- Project create/readiness/pin/delete 可自动验收；
- Project rename 有 extension 专用可靠实现和强刷/server 后验；
- Conversation rename/archive/delete/move/remove 均有后验；
- duplicate dispatch 不产生重复 user turn；
- delivery unknown 不盲重试；
- stale DOM/cache 能 evidence-first 恢复；
- 单 ChatGPT 账号 + 多 Herdr device 可以安全工作；
- 多账号/多开发者可以通过 browser endpoint + worker mapping 分配；
- external workflow 无法获得 ChatGPT cookie 或 arbitrary shell；
- GitLab PoC 可以完整跑通，但删除 GitLab consumer 后核心能力依然成立；
- extension/runtime/public contract/release ownership boundary 不被破坏。
