## 0. Decision

v0.4.6 is not a ChatGPT automation release and is not a GitLab automation release.

The release establishes four reusable capabilities:

1. **Herdr Work Memory** — durable, provider-neutral work memory that survives context-window changes and can be inherited by ChatGPT, Claude, Grok, Gemini, local coding agents, and future MCP clients.
2. **WebChat Inventory and Control** — discover and manage Web AI sessions through the browser with a resource model comparable to Herdr workspace/window/pane management.
3. **Cross-WebChat Dispatch** — an authorized planner on one surface can create or resume work on another WebChat provider, observe progress, stop generation, collect bounded result evidence, and reclaim the task.
4. **Pending Work Scheduler** — when a planner needs user input, it can continue independent work and stop only when the unresolved question blocks the remaining useful work.

GitLab Issue/MR automation remains an important reference consumer. A GitLab workflow may dispatch an Issue to a WebChat session for implementation or an MR for review, but GitLab-specific policy does not define the herdr-mcp core.

## 1. Design principles

### 1.1 Herdr owns durable work continuity; providers are adapters

Provider-native memory is useful but cannot be the only recovery path. Herdr must be able to reconstruct the engineering state even when:

- the source WebChat loses context;
- a conversation is handed off to a new conversation;
- the planner moves from ChatGPT to Claude, Grok, or Gemini;
- a local Agent takes over the task;
- a browser or runtime restarts;
- a provider changes its UI or product-level memory behavior.

ChatGPT, Claude, Grok, Gemini, and future sites are therefore **surfaces**, not owners of Herdr work identity.

### 1.2 One durable state owner

The existing Rust `StateStore` is the durable state owner. v0.4.6 extends it rather than creating a second browser-dispatch database.

Current schema-v5 continuity tables already provide the base:

- `continuity_chains`;
- `continuity_bindings`;
- `continuity_turns`;
- `continuity_checkpoints`;
- `continuity_transfers`.

The implementation may migrate/extend these tables, but should not leave a second long-term state kernel for `chat_requests`, browser bindings, or reliability state unless there is a proven ownership boundary that requires it.

### 1.3 Capability-driven, not lowest-common-denominator

Providers expose different product concepts. The core defines semantic capabilities; each adapter reports which are currently supported.

A missing capability returns `unsupported`. The adapter must not silently emulate a different operation and claim equivalence.

### 1.4 Typed intent, not remote browser automation

The trusted control boundary accepts operations such as:

```text
space.list
session.create
session.move_to_space
message.append
generation.stop
dispatch.submit
```

It does not expose arbitrary:

```text
URL navigation
CSS / XPath selectors
JavaScript
CDP commands
cookies or tokens
keyboard/mouse macros
shell commands
```

Selectors and site-specific navigation remain private implementation details of the Browser Extension adapter.

### 1.5 Mutation success requires a postcondition

`click()` or an HTTP 2xx is not a success condition.

Every browser mutation must produce one of the common delivery states and verify an authoritative postcondition where feasible. DOM state can be stale; bounded refresh/reload is part of the reliability kernel, not provider business logic.

### 1.6 Logical session and browser view are different resources

A WebChat conversation can exist without an open tab. Closing a browser tab must not delete or archive the logical conversation.

The core therefore models `session` and `view` separately.

### 1.7 There is no fixed master planner

ChatGPT is a convenient default surface, not the architecture root.

Any authorized controller may own the current planning turn for a work chain:

```text
remote WebChat with Herdr MCP access
local MCP client (Cursor / Claude Code / other Agent)
Herdr-managed coding Agent
external workflow such as GitLab automation
WebChat page using the explicit Herdr Tool Bridge
```

The durable owner remains Herdr `work_chain`, not whichever controller happens to be active. A controller can therefore delegate to WebChat sessions, local Agents, or another controller without converting the whole task into a ChatGPT-owned session tree.

Controller identity is an authorization/provenance concept, not a new durable state kernel. The runtime derives it from the authenticated channel and records source evidence/bindings where useful.

## 2. Core resource model

```text
Herdr device
  └─ browser endpoint
       └─ provider account
            └─ space (optional provider-native container)
                 └─ session
                      └─ zero or more views

work chain
  ├─ binds to one or more sessions across providers
  ├─ binds to Herdr workspaces / panes / agents as work executes
  ├─ owns rolling work state
  └─ owns durable evidence references
```

### 2.1 `work_chain`

A stable identity for one long-lived unit of work. It may span multiple conversations and execution surfaces.

Example:

```text
ChatGPT conversation A
  -> Claude conversation B
  -> Codex local session
  -> Grok review conversation C
  -> ChatGPT conversation D
```

All may belong to one `work_chain_id`.

Existing `continuity_id` values remain valid. The implementation should evolve continuity chains into this broader work-chain model rather than invalidate prior chains.

### 2.2 `browser_endpoint`

A stable addressable Browser Extension installation/profile endpoint. It records:

- Herdr device affinity;
- browser/profile identity;
- extension installation identity;
- opaque account observations per provider;
- connection/lease state;
- supported provider adapters and capability snapshots.

It must not store provider cookies or browser bearer tokens in ordinary state.

### 2.3 `provider_account`

A provider plus an opaque account fingerprint observed by the adapter.

Examples of `provider`:

```text
chatgpt
claude
grok
gemini
deepseek
zai
```

A human email/name may be displayed locally when available, but durable routing should use an opaque stable identity rather than mutable display text.

### 2.4 `space`

A generic provider-native grouping container.

The neutral API uses `space`; adapters expose the native label:

| Provider | Native space observed | Mapping |
| --- | --- | --- |
| ChatGPT | Project | `space(native_kind=project)` |
| Claude | Project | `space(native_kind=project)` |
| Grok | Project | `space(native_kind=project)` |
| Gemini | Notebook | `space(native_kind=notebook)` |

A provider that has no useful grouping concept reports `space.*` as unsupported. Herdr must not invent a fake Project.

### 2.5 `session`

A provider-native conversation-like resource. `native_kind` can distinguish concepts when necessary, for example:

```text
chat
conversation
task
cowork_task
temporary_chat
```

P0 normalizes the ordinary durable text conversation. Provider-specific session types remain capability extensions.

### 2.6 `view`

An actual browser tab/page displaying a session or provider home surface.

`view.close` is browser-resource reclamation only. Destructive logical operations remain `session.delete`, `space.delete`, etc.

## 3. Herdr Work Memory

### 3.1 Two-layer memory

Work Memory is split into:

```text
immutable / append-oriented evidence
+
rolling compact work state
```

This avoids both extremes: storing only an unreliable summary or repeatedly replaying the full transcript.

### 3.2 Evidence

Evidence records preserve bounded facts with provenance. Initial kinds:

```text
user_requirement
user_correction
decision
constraint
assumption
pending_question
assistant_note
tool_result
test_result
git_change
commit
file_change
runtime_observation
agent_result
external_event
```

Each record should support at least:

```text
evidence_ref
work_chain_id
kind
summary
source_surface
source_provider
source_session_ref
source_message_id / source_tool_call_id
Herdr device/workspace/pane refs when relevant
observed_at
content_hash
bounded_excerpt
structured metadata
```

Large stdout, full diffs, binary payloads, and repeated transcripts are not copied into the memory database by default. Store a bounded sanitized excerpt plus stable hashes/paths/source references when enough to retrieve or re-verify the fact.

Secrets and credential-like material must be redacted or rejected before durable evidence storage.

### 3.3 Rolling work state

The latest checkpoint is a compact recovery state, including:

```text
goal
accepted_requirements
user_corrections
decisions
constraints
explicit_assumptions
completed_items
ready_tasks
blocked_tasks
pending_questions
active_devices/workspaces
active_branches/worktrees
important_files
commits
latest_validation
next_actions
literal anchors
```

The checkpoint is not evidence by itself. It references evidence records for important claims such as “test passed”, “commit merged”, or “user required X”.

### 3.4 Search

v0.4.6 starts with deterministic local search:

- SQLite FTS / substring matching;
- structured filters by chain, provider, session, evidence kind, device/workspace, and time;
- bounded ranked results;
- explicit provenance and `evidence_ref`;
- a separate inspect/get operation for details.

No vector database or embedding service is required for v0.4.6. Semantic retrieval may be added later only if measured recall is insufficient.

### 3.5 Compatibility with Continuity 1.x

Existing methods stay valid:

```text
continuity.resume
continuity.search
continuity.resolve
continuity.list
```

They remain the compatibility surface for conversation continuity. New Work Memory methods operate on the same durable state and allow finer-grained evidence retrieval. No duplicate memory subsystem is introduced.

## 4. Pending Work Scheduler

### 4.1 Planner-owned impact classification

The model/planner, not the Browser Extension, classifies a pending user question as:

- `blocking` — affects final acceptance, irreversible action, data/security/permission boundary, public behavior, destructive operation, or major implementation direction;
- `non_blocking` — reversible/local/low-cost choice that can safely proceed under an explicit assumption.

Do not add a complex numerical risk-scoring framework in v0.4.6.

### 4.2 Blocking question behavior

When a blocking question exists:

1. persist the question and the tasks that depend on it;
2. keep independent tasks in `ready_tasks`;
3. continue useful ready work through bounded wake/continuation turns;
4. never resolve the question by inference;
5. when no useful independent task remains, transition the chain to `awaiting_user` and stop self-waking.

### 4.3 Non-blocking assumption behavior

For a low-impact choice:

1. persist an explicit assumption and rationale;
2. continue the task;
3. make later correction local/reversible when the user supplies a different preference.

### 4.4 No hidden background agent loop

The Web model cannot continue executing after its turn ends by itself. Continuation is implemented by the existing Browser Extension reverse/wake channel:

```text
work checkpoint has ready tasks
  -> extension sees settled/no active generation
  -> fenced, idempotent wake
  -> planner resumes work chain
  -> execute ready work
  -> checkpoint again
```

Cooldown, generation fencing, endpoint lease, and idempotency prevent wake loops and duplicate mutations.

## 5. WebChat Control Plane

### 5.1 Discovery

Existing:

```bash
herdr-mcp scan --probe
```

continues to discover local CLI/coding agents.

New:

```bash
herdr-mcp webchat scan
```

discovers Browser Extension endpoints, provider accounts, spaces/sessions, and live capabilities.

`herdr_inspect` may later expose both:

```text
capability_inventory   # local agents
webchat_inventory      # browser Web AI
```

This does not require adding another public MCP tool in contract epoch 2; the existing generic/private method path can carry the new local operations.

### 5.2 Browser Extension adapter shape

The current `BaseAdapter` is the correct starting direction but must grow from composer-only behavior into a capability adapter.

Conceptual interface:

```text
identity.inspect
space.list / inspect / create / rename / pin / unpin / archive / delete
session.list / inspect / create / open / rename / pin / unpin / archive / delete
session.move_to_space / session.remove_from_space
message.read / message.append
composer.inspect_capabilities / set_reasoning / select_tool / set_message / submit
generation.status / generation.stop
```

Only capabilities actually verified for the current provider/account/UI are advertised.

### 5.3 User-facing namespace is `webchat`

Use `webchat` for the CLI and private semantic control methods.

- `extension` is an implementation detail and would incorrectly bind the interface to Chrome/MV3;
- `browser` is too broad and implies general RPA, arbitrary navigation, selectors, and page automation that Herdr intentionally does not expose;
- `webchat` accurately describes the managed resource domain: provider accounts, spaces, sessions, generation state, messages, and views for Web AI products.

Reserve `webmcp` as a separate future namespace for standards-based page tools because WebMCP applies to arbitrary websites, not only WebChat providers.

### 5.4 Runtime ownership

The runtime owns:

- resource refs and routing;
- durable state;
- work memory/evidence;
- idempotency ledger;
- dispatch lifecycle;
- capability snapshots;
- scheduling and dependency state;
- security/authorization decisions.

The extension owns:

- provider/page detection;
- DOM/same-origin browser semantics;
- provider-native IDs and navigation details;
- composer control;
- local browser postcondition evidence;
- stale-view recovery;
- browser tab/view lifecycle.

### 5.5 Provider enablement is local, explicit, and default-deny

WebChat control is a higher-trust experimental capability and must not be enabled merely because an adapter or host permission exists.

The Extension Options page is the local consent boundary. Recommended settings model:

```text
WebChat control (experimental)                 default OFF
  ChatGPT                                      default OFF
  Claude                                       default OFF
  Grok                                         default OFF
  Gemini                                       default OFF
  z.ai                                         default OFF
  DeepSeek                                     default OFF

WebChat Tool Bridge (page model -> Herdr)      default OFF
  provider allowlist                           default empty
  workstation mutations                        default OFF
```

This control permission is distinct from ordinary provider integration such as HUD/continuity. Existing ChatGPT/Claude integration can remain available without granting external WebChat control. Existing z.ai/DeepSeek experimental integration remains independently gated; enabling its HUD/continuity must not silently enable remote control or workstation tool execution.

Rules:

1. runtime/remote MCP callers may inspect effective policy but cannot turn a provider on;
2. disabled providers are omitted from actionable inventory or reported as `disabled_by_user`;
3. a provider must be enabled before any create/append/rename/move/stop/delete dispatch reaches its page adapter;
4. Tool Bridge permission is separate from “this site may be controlled”; a controlled WebChat must not automatically gain permission to call Herdr tools;
5. provider control policy applies equally to local MCP callers and remote OAuth callers, so a local Agent cannot bypass a local user choice.

### 5.6 Controller-neutral topology

The same WebChat control plane should work from three primary controller paths:

```text
Local Agent / IDE
  -> http://127.0.0.1:8772/mcp + local bearer
  -> existing Herdr MCP tools / herdr_call
  -> webchat private methods
  -> Native Messaging -> Extension -> target WebChat

Remote WebChat / MCP client
  -> OAuth / Cloudflare Edge
  -> Herdr Link -> runtime
  -> webchat private methods
  -> Native Messaging -> Extension -> target WebChat

WebChat without native MCP connector
  -> explicit per-provider Tool Bridge
  -> Extension -> Native Messaging -> runtime
  -> scoped Herdr tools
```

This means Cursor or Claude Code can be the planner and use Claude/Grok/Gemini/ChatGPT as workers; Claude Web can be the planner and use DeepSeek as a discussion/review worker; ChatGPT does not need to sit at the top of either topology.

The existing local MCP endpoint is already intentionally usable by local clients such as Cursor/curl with `HERDR_MCP_TOKEN`. v0.4.6 should reuse that endpoint and the frozen public tool surface; WebChat operations remain reachable through the existing generic/private method path instead of adding a second local API server.

Arbitrary third-party MCP clients do not necessarily have a reverse wake channel. Dispatch therefore supports a durable result that can be pulled later. When the source is a known WebChat session, the Extension wake path may additionally push a compact settle event back to that session.

### 5.7 Two browser directions, two permissions

The Extension may participate in both directions, but they must never be conflated:

```text
CONTROL
controller -> Herdr runtime -> Extension -> WebChat

TOOL BRIDGE
WebChat model -> Extension -> Herdr runtime -> Herdr tools
```

Control lets a trusted caller manipulate a WebChat session through typed intents. Tool Bridge lets the model inside a specifically enabled WebChat call a scoped Herdr tool catalog. The latter has a larger prompt-injection blast radius and therefore requires a separate default-off switch and mutation permission.

The current z.ai/DeepSeek JSON bridge is an early implementation of the Tool Bridge direction: it injects a compact tool protocol into the conversation, parses structured model tool calls, executes them through the background/native path, and feeds bounded results back. It should be generalized behind provider capability adapters rather than made the definition of WebChat control.

### 5.8 Native WebMCP is adjacent, not the same thing

As of the 26 August 2026 WebMCP Community Group draft, a webpage can register structured tools through `document.modelContext`; in-page agents can discover/execute registered tools through the corresponding WebMCP API. The draft is page/browser scoped and does not define Herdr's remote MCP transport.

References:

- https://webmachinelearning.github.io/webmcp/
- https://developer.chrome.com/docs/ai/webmcp

Therefore:

- Herdr's JSON conversation Tool Bridge must not be branded as standards WebMCP;
- `webchat.*` manages Web AI sessions;
- a future `webmcp.*` adapter may discover and execute page-registered WebMCP tools through the Extension without exposing raw DOM/CDP;
- WebMCP results remain untrusted page content and pass through the same authorization/evidence boundaries as other browser-derived results.

Do not assume that registering Herdr tools into `document.modelContext` would automatically make the model inside ChatGPT/Claude/Grok/etc. able to call them. WebMCP defines a page/browser agent tool surface; whether a hosted WebChat model consumes that surface is a separate browser/provider integration question. The JSON conversation Tool Bridge remains the provider-compatible fallback for models that do not natively consume browser WebMCP tools.

Native WebMCP passthrough is architecture-compatible but not required for the v0.4.6 P0 WebChat control gate.

### 5.9 Postcondition hierarchy

For mutations, prefer evidence in this order where available:

1. provider-native same-origin/API response or refreshed provider resource state;
2. stable provider-native URL/ID plus refreshed UI state;
3. bounded DOM postcondition after refresh;
4. otherwise return `uncertain`, never `confirmed` merely because a click fired.

## 7. Cross-WebChat Dispatch

### 7.1 Purpose

Any authorized planner using herdr-mcp can delegate work to a supported WebChat provider.

Example:

```text
ChatGPT planner
  -> webchat.dispatch(provider=claude, task=implementation)
  -> Herdr runtime selects explicit browser endpoint/account
  -> Claude adapter creates/resumes target session
  -> task is submitted with work_chain reference
  -> Herdr observes generation/session progress
  -> bounded result + evidence refs are persisted
  -> source planner is woken with dispatch completion
```

The source planner does not need the target provider's entire transcript copied back into its context. It receives a compact result plus evidence references and can query details on demand.

### 7.2 Provider default

CLI and conversational convenience default to `chatgpt` when the provider is omitted, as long as endpoint/account selection is unambiguous.

A target `session_ref` always wins over the default because it already carries provider/account affinity.

### 7.3 Multi-endpoint ambiguity

If several eligible endpoints/accounts exist and no stable binding or explicit selector resolves them, mutating operations fail with an ambiguity result. Do not choose the most recently active browser or account by heuristic.

### 7.4 Source and target fencing

A dispatch/handoff records a runtime-derived source controller binding, optional source session ref, target session ref, and generation/lease fencing. A local MCP client may therefore be a source without inventing a WebChat session identity. Once a target is confirmed active, stale source tabs must not continue autonomous wake cycles for the same planner lease.

## 8. Security model

Cross-WebChat control is high-trust capability execution, not general RPA.

The authorization layer must be able to scope at least:

```text
source work chain / source binding
allowed target providers
allowed operations
allowed browser endpoint/device
destructive-operation permission
```

Safe defaults:

- list/inspect/status/read are read-only;
- create/rename/move/append/stop are typed mutations and require normal mutation authorization/idempotency;
- delete/bulk archive/provider settings are not implicit P0 automation rights;
- cookies, tokens, arbitrary browser scripting, and arbitrary navigation never cross the external control boundary.

Prompt-injected page content must not gain more browser authority than the caller's existing scoped capability.

## 9. GitLab Issue/MR integration remains a consumer

The original v0.4.6 motivation remains supported:

```text
GitLab Issue assigned/tagged for AI work
  -> external workflow creates a dispatch request
  -> default target provider ChatGPT unless policy specifies another provider
  -> create/resume a session in the mapped space
  -> bind it to a work chain
  -> work/review proceeds through Herdr
  -> result/status is written back by the external workflow
```

MR review follows the same generic dispatch contract with a review intent.

GitLab-specific concepts such as labels, assignees, pipeline state, comment templates, and service-account naming remain in `gitlab-ai-workflow`, not in the WebChat core.

## 10. Migration from the current v0.4.6 prototype

The dirty worktree `v046-external-chat-dispatch-core-20260904` is treated as a prototype, not the architecture source of truth.

Reusable concepts to preserve or extract:

- browser endpoint registration and routing;
- idempotency/request ledger behavior;
- delivery-state semantics;
- lifecycle/postcondition reliability code;
- native-host/extension transport work;
- tests that express provider-independent invariants.

Concepts to refactor before merging:

- ChatGPT-specific naming in durable/runtime contracts;
- a separate long-term durable state kernel that overlaps `StateStore`;
- direct `chat.*` core assumptions where `webchat.*` or work-memory semantics are required;
- provider UI assumptions that should live behind capability adapters.

Do not delete the prototype until its useful changes are either migrated or explicitly abandoned with destructive-operation authorization.

The previous ChatGPT-specific design document is retained because it contains useful ChatGPT lifecycle UAT, GitLab consumer design, and reliability analysis. It is no longer the v0.4.6 architecture SSOT.

## 11. Delivery plan

### P0-A — Work Memory

- extend the existing continuity/state-store model;
- first-class bounded evidence records;
- rolling checkpoint/work state;
- exact/FTS evidence search and provenance;
- backward-compatible continuity methods.

### P0-B — WebChat inventory/control kernel

- stable browser endpoint/account/resource refs;
- explicit local Extension Options consent gate, globally OFF by default;
- per-provider control allowlist for ChatGPT, Claude, Grok, Gemini, z.ai, and DeepSeek, all OFF by default;
- provider capability negotiation;
- `webchat scan` inventory;
- common space/session/view/generation operations;
- reliability/postcondition kernel;
- controller-neutral local/remote entry through the existing MCP tool surface;
- ChatGPT, Claude, Grok, and Gemini basic control adapters, while z.ai/DeepSeek keep their existing experimental integration path and adopt the same contract without schema changes.

### P0-C — Pending Work Scheduler

- persisted blocking questions and explicit assumptions;
- ready/blocked task dependency state;
- bounded auto-continuation through existing wake channel;
- deterministic `awaiting_user` stop condition.

### P0-D — Cross-WebChat dispatch

- source/target work-chain bindings;
- controller source may be a WebChat session, local MCP client/IDE Agent, Herdr-managed Agent, or external workflow;
- submit/status/settled lifecycle;
- target provider/endpoint selection;
- compact result/evidence return;
- pull result route for arbitrary MCP clients plus wake route when a known WebChat source supports it;
- generation stop and task reclamation.

### P1 — WebChat Tool Bridge, external workflow gateway, and advanced provider parity

- generalize the existing z.ai/DeepSeek JSON tool loop into a provider-capability Tool Bridge;
- keep Tool Bridge separately opt-in from WebChat control and keep workstation mutation separately gated;
- artifact upload uses a safe local `artifact_ref`/staged-file path, never raw remote bytes or arbitrary filesystem paths through the Extension;
- bounded text/JSON extraction may return inline; large/binary extraction becomes an artifact reference;
- GitLab Issue/MR external event integration;
- additional provider lifecycle operations;
- multi-account active/active endpoint leasing/failover;
- provider-specific advanced modes such as Deep Research, image generation, Cowork tasks, temporary chats, and rich project/notebook settings.

### P2 — Native WebMCP bridge (optional, draft-standard dependent)

- detect current `document.modelContext` support/capabilities in the page;
- discover and execute page-registered tools through typed `webmcp.*` semantics;
- never expose generic DOM selectors, arbitrary JavaScript, or CDP as a substitute;
- treat WebMCP tool definitions/results as untrusted page-origin content;
- keep this separate from WebChat Tool Bridge and do not make it a v0.4.6 P0 release blocker.

## 12. v0.4.6 acceptance

A release candidate is not complete until the following can be demonstrated without relying on one provider's native memory:

1. Conversation A receives a requirement, executes tools, records changes/tests, and creates a rolling checkpoint.
2. A fresh conversation on the same or another supported provider resumes the same work chain and can search the exact prior requirement, test result, and modification evidence.
3. A blocking user question prevents only dependent tasks; independent tasks continue through bounded wake turns.
4. Once only blocked work remains, the chain enters `awaiting_user` and stops autonomous continuation.
5. A later user answer reactivates the same work chain without replaying completed mutations.
6. CLI can discover WebChat providers/accounts/spaces/sessions and explicitly create a session on ChatGPT, Claude, Grok, or Gemini when that capability is supported.
7. One WebChat planner can dispatch a bounded task to another provider, observe status, stop generation when requested, and receive a compact settled result with evidence refs.
8. A local MCP client such as Cursor or Claude Code can use the existing `127.0.0.1:8772/mcp` endpoint to act as planner and dispatch work to an enabled WebChat provider without routing through ChatGPT or Cloudflare.
9. WebChat control is globally and per-provider OFF by default; a provider disabled in the Extension Options page cannot be controlled by either local or remote MCP callers.
10. Enabling WebChat control does not implicitly enable the page model to call Herdr tools; Tool Bridge remains a separate opt-in permission.
11. Browser/runtime restart preserves work-chain state and does not duplicate a prior uncertain dispatch or browser mutation.
12. Ambiguous multi-endpoint/account routing fails closed.
13. No public API exposes selectors, arbitrary JavaScript/CDP, cookies, provider tokens, or arbitrary browser navigation.

## 13. Explicit non-goals for v0.4.6

- making OpenCLI a runtime dependency;
- building a general browser-RPA platform;
- embedding GitLab/Jira/Feishu policy into herdr-mcp core;
- perfect feature parity across every WebChat provider;
- vector database / embedding infrastructure before deterministic search is measured insufficient;
- automatically deleting conversations/projects/notebooks as ordinary cleanup;
- treating provider-native memory as the Herdr durable state source;
- exposing provider credentials to remote planners.
- making ChatGPT, Claude, or any other provider the fixed architectural master;
- calling the JSON conversation Tool Bridge “WebMCP” when it does not use the WebMCP page API;
- making native WebMCP passthrough a v0.4.6 P0 blocker while the browser standard is still evolving.
