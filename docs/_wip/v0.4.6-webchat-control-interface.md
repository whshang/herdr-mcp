# v0.4.6 Interface Design: Work Memory and WebChat Control

> Status: WIP / interface SSOT
> Target: v0.4.6
> Architecture: [`v0.4.6-work-memory-and-webchat-control.md`](v0.4.6-work-memory-and-webchat-control.md)
> 1.0 architecture/decision plan: [`v1.0-architecture-plan.md`](v1.0-architecture-plan.md)
> Compatibility: keep public MCP contract epoch 2 stable unless a separate contract-epoch decision is made

## 0. Interface goals

The interface must let a planner answer these questions without knowing provider DOM details:

```text
Which WebChat providers/accounts are available in my browsers?
Which spaces and sessions exist on a selected provider?
Where will a new session be created?
Can this provider rename/move/pin/archive/stop this resource?
What is currently generating or waiting for the user?
How do I dispatch work from one WebChat to another?
How do I recover the requirements, tests, changes, and decisions from prior work?
```

The CLI and private runtime methods use provider-neutral nouns. Provider adapters translate them to native product labels.

## 1. Naming

### 1.1 Resource nouns

| Neutral noun | Meaning | ChatGPT | Claude | Grok | Gemini |
| --- | --- | --- | --- | --- | --- |
| `provider` | Web AI product | ChatGPT | Claude | Grok | Gemini |
| `endpoint` | browser/profile/extension endpoint | browser endpoint | browser endpoint | browser endpoint | browser endpoint |
| `account` | logged-in provider identity | account/workspace identity | account/org identity | account identity | Google account identity |
| `space` | optional session grouping container | Project | Project | Project | Notebook |
| `session` | conversation-like logical resource | Conversation | Chat | Chat | Chat |
| `view` | browser tab/page | tab | tab | tab | tab |
| `work_chain` | Herdr long-lived work identity | Herdr-owned | Herdr-owned | Herdr-owned | Herdr-owned |
| `evidence` | durable fact/provenance record | Herdr-owned | Herdr-owned | Herdr-owned | Herdr-owned |

The API must include `native_kind` / `native_label` when the provider term matters to users.

Example:

```json
{
  "kind": "space",
  "provider": "gemini",
  "native_kind": "notebook",
  "native_label": "Notebook"
}
```

### 1.2 Why not `project.*`

`project.*` would hard-code ChatGPT/Claude/Grok terminology and misdescribe Gemini Notebooks. The generic contract is therefore `space.*`.

### 1.3 Why `webchat`, not `browser`

`browser` suggests general RPA. The supported boundary is specifically Web AI session management. Use:

```text
webchat.*
```

for the control plane. General browser scripting is intentionally out of scope.

### 1.4 Why not `extension`, and where `webmcp` belongs

`extension` is a transport/adapter implementation detail. A caller should not need to know whether the target browser integration is MV3, another browser extension technology, or a future browser-native bridge.

Use these namespaces deliberately:

```text
webchat   Web AI provider/account/space/session/view control
webmcp    future standards-based page tool discovery/execution
browser   reserved; do not use in v0.4.6 unless Herdr intentionally becomes general browser automation
extension internal implementation only; not a public CLI noun
```

The existing z.ai/DeepSeek JSON tool loop is called **WebChat Tool Bridge**, not WebMCP, because it injects a Herdr tool protocol into a model conversation rather than consuming page-registered `document.modelContext` tools.

## 2. Stable references

Herdr-owned references are opaque, stable, and never parsed by callers.

Recommended resource reference classes:

```text
browser_endpoint_ref
provider_account_ref
space_ref
session_ref
view_ref
work_chain_id
evidence_ref
dispatch_id
```

Implementation prefixes are optional and must not become semantic encoding. If prefixes are used, a possible human-debug form is:

```text
wbe_...   browser endpoint
wac_...   provider account
wsp_...   space
wss_...   session
wvw_...   view
wc_...    work chain
ev_...    evidence
dp_...    dispatch
```

Provider-native IDs/URLs are stored as adapter metadata. A Herdr ref carries the stable routing relationship and may survive display-name changes.

Titles and names are never machine identity.

## 3. Provider and endpoint selection

### 3.1 CLI default

When no provider is specified, the CLI defaults to:

```text
provider=chatgpt
```

This is a convenience default, not a durable binding rule.

It is also not a fallback chain. If ChatGPT is disabled by local policy, an omitted `--provider` returns `webchat_provider_disabled_by_user`; Herdr must not silently choose Claude/Grok/Gemini instead.

### 3.2 Stable target precedence

Target resolution order:

1. explicit `session_ref` / `space_ref` / `view_ref`;
2. explicit `--provider` + `--endpoint` / account selector;
3. an existing unique work-chain/provider binding;
4. default provider `chatgpt` if exactly one eligible target exists;
5. otherwise fail `target_ambiguous`.

Never select a mutating target only because it was most recently active.

### 3.3 Device selection

The Herdr device remains an outer routing concern. A WebChat endpoint belongs to one enrolled device.

Conceptually:

```text
Herdr device selector
  -> browser_endpoint_ref
  -> provider_account_ref
  -> space/session/view
```

Existing `herdr_call` device routing should be reused rather than duplicating a second device selector inside every browser operation.

### 3.4 Provider-control policy

The Extension Options page owns the enable/disable decision. v0.4.6 control is default-off for every provider, even when the provider adapter is installed and ordinary HUD/continuity integration is active.

Conceptual effective policy:

```json
{
  "webchat_control": {
    "enabled": false,
    "providers": {
      "chatgpt": false,
      "claude": false,
      "grok": false,
      "gemini": false,
      "zai": false,
      "deepseek": false
    }
  },
  "webchat_tool_bridge": {
    "enabled": false,
    "providers": {},
    "allow_workstation_mutations": false
  }
}
```

API spelling uses `zai`; UI labels it `z.ai`.

CLI may accept `z.ai` as a human-friendly alias, but durable/provider enum normalization uses canonical `zai` so refs and stored policy do not depend on punctuation/display branding.

Remote methods and WebChat pages cannot enable these gates. Inventory/status may return `disabled_by_user`; authorization is local and fail-closed.

The effective gate is enforced twice: runtime policy rejects the request before dispatch, and the Extension adapter re-checks the provider gate before page actuation. Static content-script presence for existing HUD/continuity behavior is not equivalent to control permission.

## 4. CLI surface

### 4.1 Discovery

Local coding-agent inventory remains:

```bash
herdr-mcp scan [--json] [--refresh] [--probe]
```

Browser WebChat inventory becomes:

```bash
herdr-mcp webchat scan
herdr-mcp webchat scan --provider claude
herdr-mcp webchat scan --provider gemini --probe
herdr-mcp webchat scan --endpoint <endpoint-ref>
herdr-mcp webchat scan --json
```

`--probe` means refresh live provider/account/capability state instead of returning only the latest valid inventory snapshot.

The CLI may show the effective provider-control state, but P0 does not expose a remote/agent-callable command that turns a provider on. Enabling control remains an explicit local Extension Options action.

### 4.2 Endpoint/account commands

```bash
herdr-mcp webchat endpoints
herdr-mcp webchat endpoint inspect <endpoint-ref>
herdr-mcp webchat accounts [--provider <provider>]
herdr-mcp webchat account inspect <account-ref>
```

P0 does not expose credentials, cookies, or provider tokens.

### 4.3 Space commands

```bash
herdr-mcp webchat space list [--provider chatgpt]
herdr-mcp webchat space inspect <space-ref>
herdr-mcp webchat space create --name <name> [--provider <provider>]
herdr-mcp webchat space rename <space-ref> --name <name>
herdr-mcp webchat space open <space-ref>

# Capability-gated lifecycle operations
herdr-mcp webchat space pin <space-ref>
herdr-mcp webchat space unpin <space-ref>
herdr-mcp webchat space archive <space-ref>
herdr-mcp webchat space delete <space-ref> --confirm
```

Human output renders the provider-native label, for example:

```text
SPACE        PROVIDER  NATIVE     NAME
wsp_...      gemini    Notebook   kd100-数据资产地图
wsp_...      claude    Project    herdr-mcp
```

### 4.4 Session commands

```bash
herdr-mcp webchat session list [--provider <provider>] [--space <space-ref>]
herdr-mcp webchat session inspect <session-ref>
herdr-mcp webchat session create [--provider <provider>] [--space <space-ref>]
herdr-mcp webchat session open <session-ref>
herdr-mcp webchat session rename <session-ref> --title <title>
herdr-mcp webchat session move <session-ref> --space <space-ref>
herdr-mcp webchat session remove-from-space <session-ref>
herdr-mcp webchat session append <session-ref> --message <text>
herdr-mcp webchat session status <session-ref>
herdr-mcp webchat session stop <session-ref>
herdr-mcp webchat session handoff <session-ref> [--provider <provider>] [--space <space-ref>]

# Capability-gated/destructive operations
herdr-mcp webchat session pin <session-ref>
herdr-mcp webchat session unpin <session-ref>
herdr-mcp webchat session archive <session-ref>
herdr-mcp webchat session delete <session-ref> --confirm
```

If a provider cannot move a session between spaces, `session move` returns `unsupported`; it must not create a copy and claim success.

### 4.5 View commands

```bash
herdr-mcp webchat view list
herdr-mcp webchat view open <session-ref>
herdr-mcp webchat view focus <view-ref>
herdr-mcp webchat view close <view-ref>
```

`view close` closes a browser tab only. It never archives/deletes the logical session.

### 4.6 Dispatch commands

```bash
herdr-mcp webchat dispatch \
  --provider claude \
  --message "Review the current implementation and report concrete blockers." \
  [--space <space-ref>] \
  [--session <session-ref>] \
  [--work-chain <work-chain-id>]

herdr-mcp webchat dispatch status <dispatch-id>
herdr-mcp webchat dispatch stop <dispatch-id>
```

If `--provider` is omitted and neither `--space` nor `--session` supplies provider affinity, default to ChatGPT.

`dispatch stop` stops the target WebChat generation if one is active. It does not kill local Herdr processes or coding agents.

### 4.7 Work Memory commands

```bash
herdr-mcp memory search --query <text> [--work-chain <id>] [--kind <kind>]
herdr-mcp memory get <evidence-ref>
herdr-mcp memory note --work-chain <id> --text <text>

herdr-mcp work status <work-chain-id>
herdr-mcp work resume <work-chain-id>
herdr-mcp work checkpoint <work-chain-id>
```

The exact CLI surface can be reduced during implementation, but the underlying private methods should preserve these semantics.

### 7.1 Existing local MCP endpoint is a first-class controller path

Herdr already serves the local MCP endpoint:

```text
http://127.0.0.1:8772/mcp
```

Local MCP clients authenticate with the existing local bearer (`HERDR_MCP_TOKEN`). The bearer remains local and is never copied into provider pages or the Browser Extension.

Therefore Cursor, Claude Code, or any other compatible local MCP client can use the same frozen public tool surface and invoke the private WebChat methods through `herdr_call`. No additional localhost server, WebSocket API, or ChatGPT-specific bridge is required.

Conceptually:

```text
Cursor / Claude Code / local Agent
  -> local MCP
  -> herdr_call(herdr_mcp.webchat.*)
  -> runtime policy + idempotency
  -> Native Messaging
  -> Extension provider adapter
  -> WebChat session
```

This path still obeys the Extension's default-off per-provider control policy.

## 8. Common target selector

Operations that create a new resource accept a selector conceptually shaped as:

```json
{
  "provider": "claude",
  "endpoint_ref": "wbe_...",
  "account_ref": "wac_...",
  "space_ref": "wsp_..."
}
```

Rules:

- `provider` defaults to `chatgpt` only when no stronger ref gives provider affinity;
- `endpoint_ref` may be omitted only when exactly one eligible endpoint is resolved;
- `account_ref` may be omitted only when the endpoint has one eligible logged-in account for that provider;
- `space_ref` is optional for providers that allow ungrouped sessions;
- a `session_ref` already resolves provider/account/space affinity and must not be contradicted by separate selector fields.

Contradictory selectors fail `target_conflict`.


## 11. Mutation result envelope

All typed mutations should converge on a common result:

```json
{
  "ok": true,
  "operation": "session.rename",
  "delivery": "confirmed",
  "provider": "claude",
  "endpoint_ref": "wbe_...",
  "resource_ref": "wss_...",
  "idempotency_key": "...",
  "postcondition": {
    "verified": true,
    "source": "provider_state",
    "observed_at": "..."
  },
  "warnings": []
}
```

### 11.1 Delivery values

```text
confirmed       mutation and postcondition verified
replayed        identical idempotent request returned prior confirmed result
queued          accepted but not yet applied
rejected        refused before application
not_applied     verified not applied
uncertain       delivery/effect cannot be proven; caller must inspect before retry
browser_offline endpoint unavailable
provider_unready provider page/account not ready for this operation
unsupported     provider/account does not support the semantic capability
target_ambiguous multiple eligible targets and no deterministic binding
target_conflict contradictory selectors
```

`uncertain` is deliberately distinct from failure. It prohibits blind replay of non-idempotent mutations.

## 12. Idempotency

Mutating operations accept an `idempotency_key` generated by the caller or orchestration layer.

The durable ledger records:

```text
key
operation
normalized target
request hash
work_chain_id if present
created_at
latest state
confirmed result/postcondition
```

Rules:

1. same key + same request returns prior state/result;
2. same key + different normalized request is rejected;
3. a transport timeout with unknown delivery is inspected through status/postcondition before any resend;
4. a confirmed browser mutation is never repeated merely because the caller lost its first response.

## 13. Browser-extension request contract

The native/runtime-to-extension contract carries semantic operations only.

Conceptual request:

```json
{
  "request_id": "...",
  "operation": "session.move_to_space",
  "target": {
    "provider": "gemini",
    "session_native_id": "...",
    "space_native_id": "..."
  },
  "expected": {
    "session_space_native_id": "..."
  },
  "fence": {
    "endpoint_lease": 17,
    "generation": 4
  }
}
```

Conceptual result:

```json
{
  "request_id": "...",
  "status": "confirmed",
  "observed": {
    "session_native_id": "...",
    "space_native_id": "..."
  },
  "postcondition_source": "refreshed_provider_state"
}
```

The runtime maps native IDs to Herdr refs. Remote callers should normally never need native IDs.

### 13.1 WebChat Tool Bridge is the reverse direction

For explicitly enabled providers that do not expose Herdr through a native MCP connector, the Extension may run a bounded conversation-level tool loop:

```text
WebChat model emits structured Herdr tool call
  -> Extension parses/schema-validates it
  -> Native Messaging
  -> runtime authorizes and executes a scoped Herdr tool
  -> bounded TOOL_RESULT is fed back into the same WebChat session
```

The page never receives `HERDR_MCP_TOKEN`, OAuth credentials, native-host secrets, or a raw runtime socket.

Tool Bridge policy is independent of WebChat control. A provider may be a control target while its model is forbidden from calling Herdr tools.

For file/media movement:

- caller supplies a Herdr `artifact_ref`, not raw bytes/base64 and not an arbitrary local path;
- runtime/native host resolves a permitted local staged file when the provider adapter supports upload;
- bounded text/JSON extraction may return inline;
- large or binary extraction is imported into the existing artifact path and returned as an artifact reference;
- the Extension remains browser actuation, not binary transport.

### 13.2 Native WebMCP is a separate page-tool surface

The current WebMCP draft exposes page-owned structured tools through `document.modelContext`. If Herdr later bridges those tools, they are discovered/executed under `webmcp.*`, not `webchat.*` and not the conversation JSON Tool Bridge.

WebMCP tool descriptions and outputs are untrusted page-origin data. Authorization remains in Herdr; the existence of a page-registered tool is not permission to execute it.

## 14. Dispatch contract

### 14.1 Submit

Conceptual request:

```json
{
  "provider": "claude",
  "endpoint_ref": "wbe_...",
  "space_ref": "wsp_...",
  "session_ref": null,
  "work_chain_id": "wc_...",
  "message": "Review the implementation and report concrete correctness issues.",
  "intent": "review",
  "idempotency_key": "...",
  "return_policy": "summary_with_evidence_refs"
}
```

The caller does not self-assert a trusted controller identity. The runtime derives the authorization principal/source from the authenticated channel and may persist provenance such as:

```json
{
  "source": {
    "kind": "local_mcp_client | remote_mcp_client | webchat_session | herdr_agent | external_workflow",
    "source_session_ref": "wss_... or null",
    "principal_ref": "opaque-runtime-owned-ref"
  }
}
```

`source.kind` is evidence/routing metadata, not an authority chosen by request JSON.

`intent` is advisory metadata such as:

```text
work
review
research
follow_up
```

It does not grant extra permissions or hard-code GitLab semantics.

### 14.2 Dispatch lifecycle

```text
accepted
resolving_target
opening_or_creating_session
submitting
running
awaiting_user
settled
stopped
failed
uncertain
```

### 14.3 Settled result

```json
{
  "dispatch_id": "dp_...",
  "state": "settled",
  "target_session_ref": "wss_...",
  "work_chain_id": "wc_...",
  "summary": "Bounded provider result summary",
  "evidence_refs": ["ev_...", "ev_..."],
  "settled_at": "..."
}
```

The source planner queries evidence on demand rather than receiving the entire target transcript automatically.

Return delivery depends on source capabilities:

```text
pull             any MCP caller may query dispatch.status later
webchat_wake     known source WebChat session may receive a compact wake/settle event
herdr_event      a Herdr-managed source may observe the durable event stream
```

An arbitrary local MCP client is not assumed to support server-initiated wake. The durable dispatch record is sufficient for it to resume/poll in a later turn.

### 14.4 Stop/reclaim

`dispatch.stop`:

- requests `generation.stop` on the target WebChat session when supported;
- marks dispatch state only after the stop postcondition is observed;
- does not kill local coding agents launched by work inside the target conversation.

Local Agent lifecycle remains Herdr workspace/pane/agent control.

## 20. Authorization scopes

A future internal capability token/authorization record may express scopes such as:

```text
webchat.read
webchat.session.create
webchat.session.mutate
webchat.generation.stop
webchat.dispatch
webchat.destructive
memory.read
memory.write
```

Cross-provider dispatch should additionally constrain target provider/account/endpoint.

Two local user-consent gates sit outside ordinary capability scopes:

```text
provider control enabled in Extension Options
provider Tool Bridge enabled in Extension Options
```

An MCP scope cannot override either gate. `webchat.dispatch` authorization plus a disabled provider still returns `webchat_provider_disabled_by_user`.

Tool Bridge mutation authority is also separately gated. Enabling a provider's Tool Bridge without `allow_workstation_mutations` must not grant mutating Herdr commands merely because the model asks for them.

Example policy intent:

```text
A ChatGPT planner bound to work chain X may dispatch to Claude or Grok
on endpoint E, create/append/stop sessions, and read returned evidence,
but may not delete sessions/spaces or access provider credentials.
```

## 23. Implementation constraints

1. Do not add a second durable database owner for WebChat dispatch if `StateStore` can own the data.
2. Do not make OpenCLI or ego-browser production dependencies; they are research/UAT/reference tooling.
3. Do not add one MCP public tool per WebChat operation in contract epoch 2; use private methods/CLI until a deliberate public-contract revision is justified.
4. Do not expose CSS/XPath/JS/CDP/cookies/tokens through the WebChat control API.
5. Do not infer mutation success from click/submit alone.
6. Do not guess among multiple endpoints/accounts for mutations.
7. Do not treat `view.close` as `session.delete`.
8. Do not copy entire target-provider transcripts into source planner context by default.
9. Do not persist secrets in evidence excerpts.
10. Do not advertise provider capability solely because an old UAT or external adapter once supported it; live capability state is authoritative.
11. Do not let local/remote MCP scopes bypass the Extension's provider-control or Tool-Bridge consent gates.
12. Do not call the JSON conversation bridge “WebMCP”; reserve `webmcp.*` for actual page-registered WebMCP tools.

## 24. P0 interface acceptance

P0 interface implementation is acceptable when:

- `herdr-mcp scan` remains local-Agent discovery and `herdr-mcp webchat scan` independently discovers WebChat endpoints/providers;
- omitting provider defaults to ChatGPT only when target resolution is unambiguous and ChatGPT is locally enabled; it never silently falls through to another provider;
- CLI can explicitly select ChatGPT, Claude, Grok, Gemini, z.ai, or DeepSeek; where native containers exist it shows provider labels such as `Project`/`Notebook` while using neutral `space` semantics;
- all WebChat control providers are default-off in Extension Options and a disabled provider cannot be actuated from either local MCP or remote OAuth paths;
- all basic session mutations return common idempotency/delivery/postcondition envelopes;
- session and view lifecycles cannot be confused destructively;
- `memory.search` can retrieve exact previous requirements, tests, commits/changes, and tool evidence with provenance;
- continuity compatibility remains usable for existing chains;
- a source WebChat can dispatch to a target WebChat and get a compact settled result/evidence refs;
- a local MCP client can act as the planner through `127.0.0.1:8772/mcp` and dispatch to an enabled WebChat without ChatGPT being involved;
- WebChat Tool Bridge is independently disabled by default and does not gain workstation mutation authority merely because WebChat control is enabled;
- stop/handoff/recovery are fenced against duplicate wake or stale tabs;
- unsupported/provider-drift behavior is explicit rather than silently approximated.
