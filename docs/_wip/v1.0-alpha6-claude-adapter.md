# Herdr-MCP 1.0 Alpha 6 — Claude provider vertical

Status: implementation in progress on `feat/v1.0-claude-adapter-alpha6-20260907`.

Base: Alpha 5 implementation HEAD `8dee91a52785134beb49254664651873f161799d`.

## Goal

Add Claude as the next Browser Registry provider vertical by reusing the Browser Registry, Work Memory, consent, generation fencing, idempotency, and single-attempt browser actuation contracts already established by Alpha 4/5.

Alpha 6 is not a provider-framework rewrite. Provider-specific URL, DOM, and account details stay in the Claude adapter; browser authority and dispatch semantics stay provider-neutral.

## Scope

Alpha 6 includes:

- concrete Claude session identity for `https://claude.ai/chat/<uuid>` only;
- opaque Claude account identity derived in the page from the signed-in account and hashed before it reaches Browser Registry;
- Browser Registry topology `account -> session`;
- listener-less tab recovery through the existing bounded URL recovery path;
- the existing typed `herdr_mcp.browser_dispatch.submit` single-attempt actuation path;
- targeted adapter, Browser Registry, recovery, and regression tests;
- real signed-in Claude browser UAT after the local contract is green.

Alpha 6 does not include:

- Grok implementation;
- ChatGPT adapter or permission migration;
- a generic provider plugin framework;
- Claude Project resource creation without real provider evidence;
- provider-specific reasoning-effort or required-app exceptions;
- Edge deployment, caller-grant policy changes, reservation/failover, or beta.1/beta.2 work;
- changes to v0.4.8 Connector UAT.

## Session identity

The accepted session route is exactly:

```text
https://claude.ai/chat/<uuid>
```

The adapter and background URL fallback both reject non-chat roots, malformed IDs, and Project-only routes as sessions. Query parameters are not part of the canonical conversation key.

The canonical Browser Registry session native identity is the UUID only. The portable/opaque resource reference remains owned by Browser Registry.

Claude Project URLs are not converted into `space` resources in Alpha 6. A Project route is an entry/navigation surface, not sufficient evidence that a current chat has a stable Project parent. Alpha 6 therefore uses `project_id = null` and does not fabricate a space.

## Account identity and privacy

The Claude content adapter reads the signed-in current-account response from the Claude same-origin account endpoint. It accepts only a syntactically valid email candidate, normalizes it to lowercase, hashes it with SHA-256 inside the page context, and returns only:

```text
claude-account-sha256:<64 hex chars>
```

The raw email is never sent to `extension/background.js`, Browser Registry, Work Memory, Edge, or portable evidence.

If account identity cannot be obtained or hashed, Browser Registry observation fails closed rather than creating an account-less session topology.

## DOM boundary

The adapter uses bounded semantic selector families rather than unrestricted text scans. Current preferred observations are:

- composer: `[data-testid="chat-input"][contenteditable="true"]`;
- user message: `[data-testid="user-message"]`;
- assistant response: `.font-claude-response` with bounded semantic fallbacks;
- send: explicit `Send message` / send-button semantics;
- generation: explicit Stop control or bounded streaming/busy state.

Legacy ProseMirror/contenteditable fallbacks remain only where they preserve the existing Claude wake/HUD behavior. Generic visible `contenteditable` scanning is removed from the primary path.

## Browser Registry topology

For one signed-in Claude chat, the expected observation sequence is:

```text
provider.observe(provider=claude)
resource.observe(kind=account, parent=null)
resource.observe(kind=session, parent=<account_ref>)
```

No `space` is created in Alpha 6.

The provider shares the existing observation-generation owner. It must not add a second timer, endpoint owner, snapshot store, or provider-specific generation counter.

## Browser actuation

Claude joins the same strict typed actuation path already used by ChatGPT and Gemini:

```text
herdr_mcp.browser_dispatch.submit
```

The operation remains one attempt. Alpha 6 does not add reload/retry recovery to mutation dispatch. It preserves:

- expected observation-generation fencing;
- exact conversation-key fencing;
- empty-composer / no-generation preconditions;
- idempotency ownership in the existing runtime/Edge path;
- no `reasoning_effort` and no `required_apps` for the initial Claude vertical;
- provider-neutral postcondition evidence based on bounded DOM observations.

## Permission boundary

Claude already has the exact required host permission and static content-script registration in the current extension product. Alpha 6 intentionally does not migrate that installed-user permission model.

Future permission-registry unification must be handled separately so it does not silently remove an always-on permission relied on by existing users.

## Acceptance

Local acceptance requires:

1. adapter URL/session/account tests prove concrete identity and fail-closed unsupported routes;
2. account identity tests prove hashing before background registration;
3. listener-less Claude chat recovery uses the existing bounded page-reload path;
4. Browser Registry observes exactly `account -> session` with no fabricated space;
5. Claude reuses provider-neutral typed single-attempt actuation with no Claude-only dispatch branch;
6. existing Gemini/ChatGPT/extension smoke behavior remains green;
7. `scripts/release-gate.sh node` passes;
8. `scripts/release-gate.sh hygiene` passes;
9. `git diff --check` passes.

Real-browser acceptance then requires one signed-in Claude chat to prove the live URL/account/session selectors and one fenced/idempotent dispatch when the production Edge Browser Control route is available. Alpha 6 must not deploy or widen production Edge merely to manufacture this evidence.
