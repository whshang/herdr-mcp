# Herdr-MCP 1.0 Alpha 2 — Project Work Memory

状态：implementation / review

## 目标

Alpha 2 建立 Herdr 自己拥有的项目级 Work Memory。它独立于 ChatGPT、Gemini 或其他 Provider 的原生 Memory，并直接扩展现有 Rust `state.db` Continuity Journal；不新建第二个数据库、状态服务、daemon 或常驻 timer。

稳定逻辑分区为：

```text
project_ref + repo_id + work_chain_id
```

`continuity_id` 继续作为现有本机 Journal 的兼容 key。Provider 本地身份按 `provider + account_ref + space_ref + session_ref + message_ref` 完整限定，避免不同 Provider 复用相同 session/message ID 时碰撞。

## 非目标

Alpha 2 不实现：

- Gemini DOM adapter；
- Browser Endpoint Registry；
- External / Cross-WebChat Dispatch；
- ChatGPT/Gemini 页面选择器或扩展 DOM 自动化；
- 新 OAuth scope/grant；
- 新公开 MCP tool/action；
- Edge 保存完整对话、raw evidence 或设备本地路径；
- 物理删除历史 raw body。

公共 Edge 继续 epoch 3 / 19 actions；workstation Runtime Execution Contract 继续 epoch 2 / 18 tools。新增能力只通过现有 `herdr_call` private namespace 和现有 Fleet Control authority 暴露。

## 继承的 0.4.6 stabilization baseline

1.0 不重新实现 v0.4.6 已负责的可靠性/兼容性能力。Alpha 2 以及后续 alpha.3-alpha.5 直接消费这些边界：

- Connector 的 owner approval、`conn_*` instance identity、独立 revoke/legacy fence；
- device-bound Automation Client 与普通 MCP principal / fleet-admin authority 的分离；
- fresh-machine enrollment/readiness、active runtime generation reconcile 与 `operational_ready` 语义；
- EventCache/runtime resident liveness 与 planner-facing tool-result/parameter-integrity 修复；
- 现有 multi-device routing、Relay/onboarding、runtime generation fencing；
- 官方 Extension 的 tokenless Native Messaging → mode-`0600` Unix socket 本地信任边界；
- 现有 browser continuity/binding、target fencing、Control Center 和 browser-control runtime primitives；
- public Edge epoch 3 / 19 actions 与 workstation runtime epoch 2 / 18 tools 的合同分层。

这些是 1.0 的基础设施，不计作 Work Memory、Browser Endpoint Registry 或 Provider Adapter 的新增产品能力。若 v0.4.6 release branch 尚未回并 `main`，1.0 集成时吸收其已验证提交；不得把同一机制复制进 1.0 feature branch。

## 状态所有权

### 本机 `state.db`

本机 Shared Local State Store 是完整 Work Memory 的权威存储：

- provider-qualified account/space/session binding；
- append-only raw turns；
- append-only local evidence；
- verified rolling checkpoint；
- checkpoint revision/CAS；
- 最近 raw tail；
- FTS5 search index；
- retention policy metadata；
- 从本地 evidence 派生的 portable evidence refs。

FTS5 只是同一 SQLite 数据库的索引，不是第二事实源。

### Edge Fleet Control

Edge 只保存协调所需的紧凑投影：

- `work_chain_id` / chain revision；
- planner lease / generation；
- checkpoint revision；
- compact checkpoint；
- structured portable evidence refs。

Edge 不保存 raw turns、local evidence content、Provider 页面历史、本机绝对路径或 raw URL。

## Schema v6

Alpha 2 把 reliability `state.db` 从 schema v5 升到 v6。迁移是 append-only：

- `continuity_chains` 增加 project/repo/work-chain identity、checkpoint revision 与 retention policy；
- 新增 provider-qualified binding；
- legacy `continuity_turns` 保留原 PK，并增补 Provider identity；
- 新增 append-only evidence；
- checkpoint 增加 monotonic revision、JSON payload、digest、verified flag 与 through-evidence boundary；
- 新增同库 FTS5 index，并在 v5→v6 时回填已有 raw turns。

这是正式 durable-state compatibility boundary。schema v6 数据库不能由只理解 v5 的旧 binary 打开后继续写入；旧 binary 应按现有 `state_schema_too_new` 规则 fail closed。Alpha 2 PR 本身不部署、不切 runtime、不 bump/tag/release。未来投产必须把 binary upgrade 与 schema migration 作为同一 release gate，并在 migration 前保留可恢复的 v5 数据副本/升级路径。

## Private local API

通过现有 `herdr_call`：

```text
work_memory.bind
work_memory.append_turn
work_memory.append_evidence
work_memory.checkpoint.put
work_memory.resume
work_memory.search
```

`bind` 固定 `project_ref/repo_id/work_chain_id` 与 Provider session 关系；同一 `continuity_id` 不能静默改绑到另一个逻辑分区。

`append_turn` 使用 provider-qualified message identity。相同 `session_ref/message_ref` 可同时存在于 ChatGPT 与 Gemini。

`append_evidence` 始终保存本机 raw evidence，并返回本机 `evidence_id` + digest。只有调用方同时提供可验证的 Git source identity 时才生成 Fleet 可携带 ref：

```json
{
  "kind": "git_source",
  "repo_id": "github.com/org/repo",
  "commit_sha": "<full 40/64 hex object id>",
  "repo_relative_path": "src/example.rs",
  "line_start": 10,
  "line_end": 20,
  "evidence_sha256": "<64 hex>"
}
```

本机 `ev_*` ID 不是 portable identity，不进入 Fleet ref。portable ref 不接受绝对路径、raw URL、缩写 SHA、任意自由文本或 device/workspace/pane identity；另一台设备必须能从 repo + full commit + repo-relative path 重新解释该引用。

`checkpoint.put` 只写 verified checkpoint，并以 `expected_checkpoint_revision` 做 CAS。verified 表示 checkpoint JSON 为结构化对象、digest 可重算，且所声明的 `through_message_id` / `through_evidence_id` 确实属于同一 local Work Memory；没有任何 evidence boundary 的 checkpoint 不写入。`resume` 由稳定的 `project_ref + repo_id + work_chain_id` 解析本机 Continuity partition，而不是要求接手 Controller 知道本机内部 `continuity_id`；它只把最新 verified checkpoint 当作 checkpoint authority，同时返回有界 recent raw tail 与本机 evidence。`search` 使用同一精确 partition。

## Retention

Alpha 2 默认 `retention_policy=retain_all`：完整原始历史继续保留在本机 StateStore。恢复视图有界：raw turn tail 最多 64 条且约 64 KiB，recent evidence 同样有界。

本阶段不执行 raw prune。后续真正删除 raw body 前必须先验证 checkpoint 覆盖边界与 digest，并拥有可证明的 retention/recovery gate；不能把“有界 resume”误写成“历史已被删除”。

## Edge compact checkpoint mutation

现有 Fleet Control 增加 private `herdr_mcp.work_chain.checkpoint.update`。它要求：

- 当前有效 Planner Lease；
- expected chain revision；
- expected lease generation；
- expected checkpoint revision；
- idempotency key；
- compact checkpoint body + SHA-256；
- strict structured portable evidence refs。

checkpoint mutation 属于 routine control quota。它不能消耗为 lease release/takeover/lane terminal 等 critical recovery 保留的容量。chain 更新与 idempotency evidence 继续在同一个 Durable Object transaction 提交。

## 两种跨 WebChat 模式

### A. Planner Handoff

```text
ChatGPT Planner
  -> persist/verify local checkpoint
  -> project same compact checkpoint to Work Chain
  -> transfer/release Planner Lease
  -> Gemini obtains Planner Lease
  -> Gemini resumes same work_chain_id
     from verified checkpoint + recent raw tail + project evidence
```

目标是换 Provider 后继续同一个项目与 Work Chain。Provider 自己的 Memory 不是恢复依据；Herdr Work Memory 才是可移植项目上下文。

### B. Cross-WebChat Delegation

```text
ChatGPT keeps Planner Lease
  -> future bounded webchat dispatch
  -> Gemini session executes one bounded Execution Lane
  -> lane result/evidence returns to the same Work Chain
  -> ChatGPT remains Planner
```

Gemini 在此模式下是执行 lane，不成为第二 Planner。Alpha 2 只定义 Work Memory 与 Fleet Control 状态合同；实际 WebChat dispatch 留给后续阶段。

Alpha 2 的 Provider binding 只描述 Memory provenance，不授予 Fleet Control authority，也不改变 Alpha 1 的 principal 边界。当前 Planner Lease 仍以受信 credential principal 为身份粒度；stable per-controller principal、owner-mediated fleet grant/revoke 和真实多 Controller 隔离继续作为后续安全 gate。相同 credential 下的多个 WebChat caller 仍被视为同一 Planner principal，不能把 provider/session binding 当成可自报的授权身份。

## 1.0 正式验收场景

1. **ChatGPT → Gemini resume same project**：ChatGPT 形成 verified checkpoint 后转移 Planner Lease；Gemini 在不同 Provider session 中以同一 `work_chain_id` 恢复 checkpoint、recent turns 与 project evidence，并在重新核验 live Git/runtime 后继续。
2. **ChatGPT → Gemini delegated Web Chat task → same Work Chain**：ChatGPT 保持 Planner Lease，把有界任务交给 Gemini Web Chat execution lane；Gemini 结果以 evidence/lane state 回写同一 Work Chain，ChatGPT 继续持有规划权。

这两个场景在相应 adapter/dispatch 阶段完成真实 WebChat UAT 前都不能宣称 production complete。

## 后续边界

- alpha.3：Browser Endpoint / Resource Registry，建立稳定 WebChat endpoint/resource identity，不引入第二状态源；
- alpha.4：ChatGPT Web adapter / endpoint identity 的真实纵向阶段；
- **alpha.5：Gemini 第二 Provider 纵向阶段**，位于 ChatGPT adapter 后、reliability beta 前；完成 Planner Handoff 与 Delegation 的真实双 Provider UAT；
- beta：可靠性、恢复、故障注入和长期 retention/prune gate。

Alpha 2 不提前实现 alpha.3-alpha.5 的 DOM、Browser Endpoint Registry 或 External Dispatch。
