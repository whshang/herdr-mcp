# Herdr-MCP 1.1 — Browser Adapter Platform

> Status: WIP / 1.1 core architecture
>
> Date: 2026-09-26
>
> Roadmap authority: `docs/herdr-architecture-roadmap.md`
>
> Reference implementations studied: [OpenCLI](https://github.com/jackwener/OpenCLI) for its broad browser/site scenario catalog and adapter-author/autofix workflow, and [opencli-mcp](https://github.com/jackwener/opencli-mcp) for its MCP browser workflow, tab lifecycle, site Adapter authoring, and structured error model.

## 1. Product goal

Herdr-MCP 1.1 makes the browser a first-class execution surface.

The 1.0 browser work proved strong WebChat control for ChatGPT and bounded support for Grok / Claude, plus a deliberately narrow generic Page Assist vertical. 1.1 generalizes the proven reliability and identity model into a browser adapter platform that can:

- strengthen ChatGPT / Grok / Claude control without creating a second WebChat state machine;
- operate arbitrary user-approved web pages through a generic browser kernel;
- discover and run reusable site commands through built-in or locally installed Adapters;
- let users develop, verify, activate, replace, and remove local Adapters without rebuilding the Rust runtime or waiting for an extension release;
- reuse the user's existing signed-in Chrome session while keeping credentials, cookies, passwords, OTPs, and payment secrets out of model-visible results;
- fall back from a site Adapter to Generic Web only when the requested action can still be expressed safely and observably.

The target experience is goal-oriented:

```text
"Get the subtitles from this Bilibili video and summarize them."
        -> adapter search
        -> bilibili.video.transcript
        -> structured transcript
        -> model summary

"Ask Doubao to generate three poster concepts."
        -> adapter search
        -> doubao.image.generate
        -> submit once + return operation/dispatch identity
        -> observe completion through status/reconciliation
        -> return artifact refs / keep deliverable tab

"Search X for recent posts about Herdr and summarize the main themes."
        -> adapter search
        -> x.search.posts
        -> structured post rows + canonical URLs
        -> model summary

"Do this on a site for which no Adapter exists."
        -> Generic Web
        -> open/claim -> observe -> act -> verify -> finalize
```

This is a bounded browser execution platform, not an unrestricted desktop RPA system.

### 1.1 Capability-parity target from OpenCLI / opencli-mcp

The 1.1 target is **capability-pattern parity**, not a copy of OpenCLI's current 100+ site command inventory.

| Reference scenario class | OpenCLI / opencli-mcp examples | Herdr 1.1 target |
| --- | --- | --- |
| Generic Browser Use | navigate, structured state/read, click, type/fill, select, keys, wait, scroll, screenshot, multi-tab | Generic Web Browser Kernel using Herdr Extension, opaque refs, generation fencing, owned/claimed tab lifecycle |
| Logged-in content extraction | Bilibili subtitle/summary, Zhihu/Weixin article reads, Xiaoyuzhou transcript | read Adapters returning bounded structured data + canonical source + artifact evidence |
| Social search/read | X search/thread/timeline, Reddit search/read, Xiaohongshu search/feed | site Adapter search/read commands using the user's approved signed-in browser session |
| Social/write actions | post/reply/like/follow/save/publish | later write/external Adapter commands under one Runtime reservation and deterministic human-boundary policy |
| AI web applications | Claude/Gemini commands, image/deep-research flows, Midjourney-style generation | existing WebChat provider adapters plus generic AI-site UI Adapters such as Doubao image generation |
| Commerce/research | Amazon/1688 product research, Hacker News, scholar/content discovery | read-first site Adapters; add write actions only when a real workflow requires them |
| Downloads/artifacts | image/video/article/audio/transcript downloads | Browser Kernel download/artifact evidence, then hand durable file ownership to the existing artifact/download subsystem |
| Site API acceleration | browser-session authenticated API reads, network-informed adapters | exact page-origin fetch or reviewed builtin request builders; never expose cookies/tokens |
| Adapter discovery | site/command search then run | existing Progressive SkillService guides Adapter search/describe/run without inflating the permanent MCP schema |
| Adapter development/repair | adapter-author, browser recon/verify, autofix | Generic Web exploration -> local draft -> real try/assert -> atomic activate; repair creates a replacement draft against the current digest |

Reference examples are acceptance probes, not product hard-coding. Bilibili, X, and Doubao are the first three real-browser UAT sites because together they exercise authenticated structured reads, social search/read, pure UI mutation, long-running settlement, and artifacts.

A site without an Adapter remains usable through Generic Web. Repeated workflows with a stable result contract can later be promoted into a local Adapter.

### 1.2 Browser-extension-first product decision

As of 2026-09-26, 1.1 uses the **Herdr Browser Extension as the only Web/browser execution surface**.

The earlier isolated ChatGPT Desktop tweak spike is retired. It proved some useful observations around Chat-only mode gating and reversible preload experimentation, but it still created a separate client-injection/package path and did not help with arbitrary websites. The 1.1 goal now requires one browser bridge anyway, so maintaining both Desktop injection and Browser Extension paths would duplicate lifecycle, compatibility, release, and UAT work without expanding the core web capability.

Consequences:

- do not merge or continue the `desktop-tweak/**` implementation from the local spike branch;
- do not add macOS/Windows ChatGPT Desktop patch/install/update/restore work to the 1.1 release gate;
- do not build a hidden Desktop-to-browser fallback;
- ChatGPT, Grok, Claude, Doubao, Bilibili, X, and arbitrary approved sites all execute through Herdr's own browser extension path;
- desktop applications may still act as MCP/CLI clients of Herdr, but Herdr does not patch their renderer or preload runtime for 1.1;
- preserve the spike only as historical evidence: local branch `feat/chatgpt-desktop-tweak-1.1-20260921` ended at `52735a98` and is intentionally not part of main.

This decision removes one execution surface; it does not weaken the existing WebChat provider contracts.

## 2. Why this is a 1.1 core feature

1.0 already owns the hard reliability primitives:

- Browser Endpoint Registry;
- provider/account/space/session opaque identity;
- observation generation fencing;
- exact caller grants and local consent;
- idempotency and delivery-state semantics;
- `not_applied / applied / uncertain` mutation handling;
- fail-closed stale target behavior;
- canonical WebChat handoff and durable task settlement;
- bounded Page Assist with opaque generation-bound element refs.

The missing layer is reuse.

Today, a new website either needs dedicated extension code or falls into narrow Page Assist. 1.1 adds a reusable browser kernel and Adapter lifecycle around the existing authority model, so site-specific behavior becomes a thin integration rather than another control plane.

## 3. Design principles

### 3.1 One browser authority

The extension remains the browser-side execution, binding, observation, and lifecycle boundary.

The Rust runtime owns:

- authorization;
- browser operation reservations;
- idempotency;
- durable operation evidence;
- Adapter registry metadata;
- Adapter version/digest selection;
- human-boundary policy;
- uncertain-delivery reconciliation;
- one reserved operation for each intended Generic Web or Adapter mutation, including sequencing of its typed Browser Kernel steps.

The extension owns:

- tab/page observation;
- user-approved host access;
- DOM interaction;
- exact page-origin execution primitives;
- screenshot/artifact capture;
- browser-created resource cleanup;
- page generation invalidation.

An Adapter is never a second authority. The extension executes one typed browser operation and returns evidence; it does not interpret an Adapter workflow, own retries, or keep a second wait/delivery state machine. Runtime sequences Adapter steps under the existing operation/reservation authority.

### 3.2 Observe -> act -> verify -> finalize

Borrow the useful browser discipline from opencli-mcp and make it a Herdr invariant:

1. resolve an exact browser endpoint and page;
2. observe current page state and obtain generation-bound refs;
3. perform one bounded action;
4. verify the expected postcondition;
5. invalidate stale refs after page mutation;
6. finalize resources owned by the operation/session.

A successful click is not repeated merely because the expected result has not been observed yet. A mutation with uncertain outcome is reconciliation-only.

### 3.3 User tabs remain user-owned

Every controlled tab has an ownership class:

- `owned`: created by Herdr for the current browser operation/session;
- `claimed`: an existing user tab explicitly selected for Herdr control.

Finalize may close only `owned` tabs that were not marked deliverable/handoff.

Finalize releases `claimed` tabs without closing them.

Explicit close of a claimed user tab is a separate user-visible mutation and must never happen as cleanup.

### 3.4 Site-specific logic stays thin

Core vocabulary remains browser/provider-neutral.

A Bilibili Adapter may know Bilibili routes and transcript response shapes. A Doubao Adapter may know its generation UI. An X Adapter may know X search result semantics. These details do not enter Browser Kernel or StateStore schemas.

### 3.5 No arbitrary local JavaScript runtime in Rust

1.1 does not embed Node.js, QuickJS, or another general-purpose JavaScript engine into the Rust runtime merely to execute local Adapters.

Built-in Adapters may contain reviewed extension/runtime code.

Locally installed Adapters use a bounded declarative `adapter.json` format that composes typed Browser Kernel operations.

If real usage proves a bounded declarative command cannot express an important stable workflow, evolve the Adapter contract with the smallest missing typed primitive. Do not add arbitrary `eval` as an escape hatch.

## 4. Architecture

```text
ChatGPT / Claude / Grok / Local Agent / CLI
                    |
                    v
              herdr-mcp Rust
                    |
      +-------------+----------------+
      |                              |
      v                              v
Progressive browser skill      Adapter Registry
/private browser methods       builtin + local
      |                              |
      +-------------+----------------+
                    |
                    v
             Browser Kernel
      open / claim / observe / read
      act / expect / fetch / artifact
      release / close / finalize
                    |
                    v
             Herdr Extension
                    |
                    v
               User Chrome
```

WebChat providers use the same Browser Kernel, but keep their stronger provider-specific identity, dispatch, result-settlement, and Continuity contracts.

Generic sites use page identity and Adapter command postconditions rather than pretending every page is a WebChat session.

## 5. Browser Kernel

### 5.1 Minimum page identity

Add one internal browser resource for 1.1:

```text
BrowserPage {
  page_ref
  endpoint_ref
  tab_id              // extension-local only
  origin
  canonical_url?
  ownership           // owned | claimed
  observation_generation
  page_generation
  created_by_operation?
  last_seen_at
}
```

Only `page_ref` crosses the trusted browser boundary. Raw Chrome tab ids remain local diagnostic data unless an operator explicitly asks for them.

`BrowserPage` is an **ephemeral, generation-fenced view handle**, not a second durable browser identity catalog. Its live mapping and Herdr-created ownership survive MV3 Service Worker restart through extension session storage plus Runtime operation/reservation evidence; it is not persisted beside `browser_session_ref` as a new StateStore authority.

The page handle does not replace the existing WebChat `browser_session_ref`. A WebChat session may currently be observed through one BrowserPage while its durable session identity remains provider-owned.

### 5.2 Typed operations

Do not freeze a broad public method list before the first real vertical. The first Browser Kernel slice absorbs Alpha 8 Page Assist and adds only the missing lifecycle/postcondition operations:

- open / claim / list one exact page;
- observe visible state and generation-bound refs;
- click / fill;
- expect a bounded postcondition;
- screenshot;
- release / close / finalize.

`herdr_mcp.page_assist` must become a compatibility entry to this same kernel during migration, not remain a second generic-page implementation. Remote raw `tab_id` leaves the normal 1.1 contract in favor of the ephemeral `page_ref`.

Add `read`, `select`, `press`, `scroll`, `goto`, and bounded page-origin fetch only when a reference Adapter proves the missing primitive. `back` / `forward` are not part of the first slice.

The exact private-method names are frozen only when the Runtime contract/epoch change is reviewed. Do not expose arbitrary selector/XPath/JS/CDP/cookie/storage operations in the normal 1.1 Store path.

### 5.3 Opaque element refs

Continue the Alpha 8 Page Assist pattern.

`page.observe` returns a page generation plus short-lived opaque element refs:

```text
page_ref: bp_...
generation: pg_42

[e1] heading "Orders"
[e2] textbox "Search"
[e3] button "Filter"
[e4] link "Order #1024"
[e5] button "Next page"
```

An action must present both `ref` and `generation`.

Any action or navigation that may invalidate the DOM expires the old generation. The next dependent action must observe again.

Stable resource identity must never depend on `e4`, CSS, XPath, DOM position, or tab order.

### 5.4 Structured page state

The normal observation should remain bounded and semantic:

- URL/origin/title;
- headings/landmarks;
- visible text excerpt;
- actionable elements;
- role/type/label;
- selected/checked/expanded state where applicable;
- safe link target metadata;
- viewport/scroll summary;
- page-loading and dialog state;
- optional Adapter-provided state summary.

Exclude:

- password values;
- OTPs;
- credit-card numbers/CVC;
- cookie values;
- localStorage/sessionStorage values;
- hidden authentication tokens;
- arbitrary script source.

### 5.5 Page-origin fetch

A local Adapter often becomes much faster when it can use a verified JSON endpoint instead of replaying UI clicks.

Provide a bounded **page-origin fetch** primitive rather than raw browser secrets. The first generic contract is explicit:

- the request executes in the exact BrowserPage origin, using that origin's normal page/browser credential behavior;
- cross-origin fetch from an unrelated BrowserPage is rejected;
- if a site splits UI and API domains, Runtime may open a background `owned` BrowserPage on the separately authorized API origin and execute the request there;
- the normal local Adapter slice starts with bounded read methods; a write method is added only with one-reservation mutation semantics and a reference Adapter that proves the need;
- cookies/tokens are never returned separately or accepted as Adapter constants;
- request/response byte limits, redirect-origin checks, and a credential-header denylist are enforced.

Do not implement this as a generic extension-origin cross-site fetch and assume it has page credential/CORS semantics. Built-in Adapters may carry reviewed site-specific request/signing code when a site requires rotating signatures or CSRF behavior that a declarative local Adapter cannot express.

## 6. Adapter model

### 6.1 Adapter sources

1.1 supports two implementation sources:

1. **Built-in Adapter**
   - shipped with reviewed Herdr source / extension package;
   - may use site-specific code where a declarative workflow is insufficient;
   - used for core WebChat providers and selected high-value sites.

2. **Local Adapter**
   - installed from a local directory/package;
   - manifest + bounded declarative commands;
   - versioned and content-digested;
   - may use only Browser Kernel primitives exposed by its declared capabilities.

A local Adapter cannot add Chrome permissions, bypass a caller grant, read extension secrets, or execute arbitrary workstation shell code.

### 6.2 Local package shape

Initial 1.1 package:

```text
my-adapter/
  adapter.json
  README.md            # optional human documentation
  fixtures/            # optional authoring/verification fixtures
```

Do not require a new framework directory tree until real use needs it.

Illustrative `adapter.json` shape:

```json
{
  "schema_version": 1,
  "id": "example.catalog",
  "name": "Example Catalog",
  "version": "0.1.0",
  "origins": ["https://example.com"],
  "commands": [
    {
      "name": "search",
      "description": "Search the catalog and return the observed result page.",
      "access": "read",
      "input_schema": {
        "type": "object",
        "properties": {
          "query": { "type": "string" }
        },
        "required": ["query"]
      },
      "steps": [
        { "op": "open", "url": "https://example.com/search?q={{args.query}}", "save": "page" },
        { "op": "expect", "page": "{{page.page_ref}}", "state": "document_ready" },
        { "op": "observe", "page": "{{page.page_ref}}", "save": "result" }
      ],
      "result": "{{result}}"
    }
  ]
}
```

The operation names above are illustrative until the Browser Kernel private contract is frozen. The important boundary is that a local package composes already-proven typed Browser operations; it cannot introduce a new browser primitive or arbitrary executable code.

Bilibili/X/Doubao are **not** used to freeze this first local schema. Their 1.1 reference commands are reviewed builtin Adapters first, because signing/CSRF/long-running write behavior must prove the kernel before the local format is locked.

### 6.3 Minimal workflow constructs

Keep the first declarative engine smaller than a plugin VM.

Required:

- ordered `steps`;
- `save` named step results;
- input/result schema;
- bounded interpolation from `args` and prior saved JSON values;
- bounded `expect` assertions.

Do not add `when`, general `repeat`, recursive flow, dynamic imports, filesystem access, shell execution, arbitrary transforms, or unbounded loops in the first local format. Bounded waiting belongs in the kernel `expect` contract; pagination or site-specific decoding remains builtin code until a concrete local Adapter proves one additional primitive is necessary.

### 6.4 Access classification

Every command declares one access class:

- `read`: observation/fetch with no intended remote mutation;
- `write`: changes remote/site state;
- `external`: sends/publishes/commits externally or performs another high-impact action.

The declaration is not trusted as the only safety input. Runtime also derives effective risk from the Browser operations in the command.

Examples:

- Bilibili transcript: `read`;
- X search: `read`;
- Doubao image generation: `write` because it creates remote generated content and may consume quota;
- X publish post: `external`;
- delete account / payment / authorization changes: explicit human boundary regardless of Adapter declaration.

## 7. Adapter discovery and invocation

Do not expose every installed Adapter command as a permanent top-level MCP tool.

Use the existing Progressive SkillService as the model discovery policy. One browser domain Skill tells the planner how to discover and invoke the Runtime Adapter catalog; Adapter packages themselves are executable metadata, **not Skills** and not a second Skill registry.

The conceptual Runtime operations are search / describe / run (exact private-method names are frozen later with the Runtime contract):

```text
adapter.search(query, origin?, access?)
adapter.describe(adapter_id, command?)
adapter.run(adapter_id, command, args, idempotency_key?)
```

Web planners reach them through the existing `herdr_call` private-method boundary after loading the browser Skill.

Local agents receive equivalent CLI entrypoints:

```text
herdr-mcp browser adapter list
herdr-mcp browser adapter search ...
herdr-mcp browser adapter run ...
```

This keeps model context compact even when dozens of local Adapters are installed.

The returned metadata must include source and digest so the planner can distinguish:

- builtin;
- local user package;
- local project package, if project-scoped Adapters are later enabled.

1.1 should start with builtin + user-local scope. Add project-local scope only after a real repository use case requires it.

## 8. Adapter authoring lifecycle

Borrow the strongest part of opencli-mcp's authoring model only after the reviewed reference Adapters have proved the kernel primitives and the minimal local format can be frozen: a draft does not replace the active Adapter until it has passed a real trial.

### 8.1 Lifecycle

```text
discover
   -> draft
   -> validate
   -> try with real args + assertion
   -> activate atomically
   -> run
   -> replace / rollback / remove
```

Suggested CLI:

```text
herdr-mcp browser adapter draft ./my-adapter
herdr-mcp browser adapter try <draft_id> --command transcript --args ...
herdr-mcp browser adapter activate <draft_id>
herdr-mcp browser adapter remove <adapter_id>
```

### 8.2 Draft rules

- draft is immutable after its digest is calculated;
- validation checks schema, origins, command access, step bounds, and unavailable primitives;
- trial uses real browser state and returns actual result + assertion evidence;
- a failed trial leaves the active Adapter unchanged;
- activation is compare-and-swap against the Adapter version/digest observed when the draft was created;
- activation conflict returns a structured error rather than overwriting a newer version.

### 8.3 Verification assertions

Keep assertions intentionally small:

- `path_exists`;
- `equals`;
- `min_items`;
- `url_matches_origin`;
- `page_state`;
- command-specific result schema validation.

The Adapter author should validate authentication, arguments, pagination, error behavior, and write semantics before activation.

### 8.4 Agent-assisted authoring and repair

1.1 should ship one progressively loaded Browser Adapter authoring reference/Skill rather than permanent extra MCP schemas. It guides an Agent through:

- inspect the current site and Adapter source/digest;
- exercise Generic Web to understand the workflow;
- prefer an already-known stable endpoint or semantic UI action before adding new primitives;
- create a new local draft instead of editing the active Adapter in place;
- run one intended real trial with explicit assertions;
- compare result schema and postconditions;
- activate only after the trial passes;
- when a site changes, create a replacement draft against the current active digest and preserve rollback.

This is the Herdr equivalent of the useful OpenCLI adapter-author/autofix workflow, but the Skill is guidance only. Runtime validation, browser authority, activation CAS, and mutation safety remain deterministic.

## 9. Adapter registry and override policy

Adapter identity:

```text
(adapter_id, version, digest, source)
```

Do not silently shadow a reviewed builtin with a local package having the same id/command.

If a user intentionally wants a local replacement:

- activation must record `replaces: builtin:<id>@<version>` or the exact previous local digest;
- diagnostics and command results expose the active source;
- rollback can reactivate the previous version without rebuilding.

Adapter metadata belongs in a capability-style metadata store whose schema can evolve independently; do not raise the reliability `state.db` schema merely to add Adapter metadata. Browser live state stays in Extension/session observation, Browser Registry keeps WebChat identity, and delivery evidence stays in the existing operation/dispatch authority.

## 10. Built-in Adapter targets for 1.1

### 10.1 ChatGPT

Keep the frozen 1.0 `browser_session.*`, `browser_dispatch.*`, handoff, Continuity, account/Project/conversation identity, and durable settlement contracts. ChatGPT does **not** route through the generic local Adapter catalog.

1.1 shares lower-level Browser Kernel plumbing only. Concrete control improvements owned here are:

- one owned-tab lifecycle for create/open/failure cleanup, including the known `browser_session.open` registration-timeout orphan-tab path;
- MV3 Service Worker restart ownership reconciliation;
- common stale-view/generation checks and postcondition evidence;
- shared page actuation helpers where they preserve the existing provider acceptance/settlement semantics.

Exact App/reasoning capability mapping, canonical handoff, source-bound create/open, and no-uncertain-replay remain unchanged.

### 10.2 Grok

Grok keeps its frozen provider/session methods, project-route identity, stable result attribution, and provider-specific settlement. 1.1 may share:

- owned/claimed tab lifecycle;
- stale-view recovery;
- common observe/act/finalize plumbing;
- verified composer/stop postconditions when real Grok UAT proves them.

Do not route a Grok WebChat mutation through generic `adapter.run`.

### 10.3 Claude

Claude keeps its existing account/conversation identity and result-settlement path. 1.1 may share the same Browser Kernel lifecycle/observation helpers and add only control behavior backed by signed-in Claude UAT. It remains a WebChat provider adapter in the 1.0 sense, not a local `adapter.json` package.

### 10.4 Bilibili

The 1.1 reference implementation is a **reviewed builtin read Adapter**, not the first local declarative package:

```text
bilibili.video.inspect
bilibili.video.transcript
```

Acceptance:

- use an already signed-in/normal Chrome session;
- accept canonical video URL;
- return title + ordered subtitle segments + source URL;
- no cookies/tokens in output;
- explicitly handle the site's current video/subtitle identity and any rotating request-signature requirement in reviewed site code;
- use a separately authorized API-origin BrowserPage when structured retrieval needs another origin;
- provide a UI subtitle-panel fallback when the structured path is unavailable;
- summarize only after transcript retrieval completes.

This proves the page-origin fetch/site-code boundary before local Adapter JSON is frozen.

### 10.5 X

The first `x.search.posts` / `x.thread.read` commands are also **reviewed builtin read Adapters**. X request shapes, CSRF/bearer/feature flags and pagination are site-specific and must not be reconstructed by an untrusted local declarative package.

Acceptance:

- query recent posts using the current signed-in session;
- choose and document one verified strategy per command: reviewed page-origin request builder or semantic UI observation;
- return bounded structured rows with author/display handle, timestamp when available, text excerpt, canonical post URL;
- use bounded pagination and typed auth/rate-limit/empty-result errors;
- no publish/like/follow mutation in the first reference slice.

Publishing is a separate `external` command with explicit human-boundary policy.

### 10.6 Doubao

Reference **builtin UI/write Adapter**:

```text
doubao.image.generate
```

Acceptance:

- claim/open the exact Doubao image generation surface;
- fill a user prompt and supported controls;
- reserve one intended generation mutation and submit it exactly once;
- return stable operation/dispatch identity after provider acceptance instead of keeping one MCP call open for the full image-generation duration;
- observe completion through the existing dispatch/status/reconciliation authority, so a tool timeout never becomes permission to resubmit;
- return image artifact evidence through the existing artifact path and keep an `owned + deliverable` tab only when useful;
- never resubmit after an uncertain generation mutation.

This scenario proves long-running browser writes without adding an Adapter-owned wait daemon or second session identity.

## 11. Generic Web fallback

An Adapter is an optimization and reliability layer, not a prerequisite.

When no matching Adapter exists:

1. user intent resolves an exact site/origin;
2. Runtime checks caller permission;
3. Extension checks Chrome's live permission for the exact target origin; the required install/load-time `<all_urls>` grant normally satisfies it, while a user restriction in Chrome makes the call fail closed with `permission_required / host_permission_missing`;
4. after live permission is confirmed, open/claim one page;
5. observe;
6. perform bounded typed actions;
7. verify;
8. finalize.

Fallback after an Adapter failure is explicit:

- a read-only command may fall back to Generic Web when no remote mutation occurred;
- a `write` / `external` command never automatically switches execution paths after a mutation may have crossed the browser boundary;
- after explicit proof of `not_applied`, the caller may re-plan a separate Generic Web operation under the normal request-digest/idempotency rules;
- `uncertain` remains reconciliation-only.

The model may recommend authoring an Adapter only after a workflow is repeated or has a stable reusable result contract.

Never synthesize a permanent Adapter from one captured interaction trace.

## 12. Permissions and trust boundaries

### 12.1 Existing two-gate Page Assist model becomes the base

A generic browser operation requires both:

1. caller-side authorization for the selected device/browser endpoint;
2. live Chrome host access for the exact target origin.

Either missing gate fails closed. The second gate is normally satisfied by the required `<all_urls>` permission accepted when the extension is installed or loaded. If the user later restricts Herdr from Chrome's extension controls, the exact-origin permission check fails closed before page access.

Generic Web no longer keeps a second Herdr-owned approved-host list. An Adapter's `origins` field remains only a declared ceiling on where that Adapter may run; it is not a permission grant.

Caller classes are explicit:

- **Edge Connector caller**: must hold the existing owner-issued exact device + browser-endpoint grant; it cannot widen its own caller authority or Chrome host access;
- **trusted local CLI/agent**: authenticated through the local Runtime boundary and subject to the same live Chrome exact-origin check;
- **WebChat caller**: cannot self-grant Page Assist/Generic Web authority merely because it controls a conversation.

### 12.2 Store extension permission posture

On 2026-09-28 the Generic Web permission UX was changed to match OpenCLI's one-time browser-access model: the normal extension requests required `<all_urls>` host access at install/load time, with no per-site Herdr approval list and no runtime `chrome.permissions.request/remove` flow. BrowserPage still checks Chrome's live permission for the exact target origin immediately before access, so user restrictions in Chrome remain authoritative.

Do not add `debugger` to the normal 1.1 Store extension solely for Adapter authoring. `<all_urls>` is sufficient for the current content-script Browser Kernel; adding `debugger` would create another high-privilege execution path without evidence that current 1.1 scenarios require it.

2026-09-28 air validation used a fresh isolated Chrome for Testing profile with the worktree manifest unchanged. Live Chrome permission was already true for Bilibili and X while legacy `pageAssistOrigins` storage was absent. A task-private Native Messaging manifest, wrapper, HOME/config, socket, and candidate Runtime also exercised the normal macOS active-owner fence; `h2w_extension_owner_status` returned `active=true` for the isolated extension and Control Center received candidate Runtime state. The first real BrowserPage open exposed a separate Chrome timing bug: `tabs.create` returned only `pendingUrl`, while BrowserPage tried to persist the owned page immediately and misreported `browser_page_storage_unavailable`. Open now reuses the existing bounded `waitForTabComplete` fence before binding the record, with a regression test for the pending-URL path. The air CFT environment itself did not commit any tested external navigation (Example Domain, Bilibili, or X all remained `pendingUrl`), so that environment is not counted as a final live-site BrowserPage pass or failure. The earlier isolated yitaidiannao Ego acceptance remains the live Bilibili/X reference for the permission model.

The production Adapter runtime therefore relies first on:

- content-script Browser Kernel operations;
- exact page-origin browser fetch primitives;
- reviewed built-in Adapter code.

A future DEV/enterprise authoring companion may use `chrome.debugger` for network reconnaissance if the benefit justifies its separate permission boundary. It is not required for 1.1 Adapter execution.

### 12.3 Sensitive data

Never return or persist:

- passwords;
- OTPs;
- payment card secrets;
- raw cookies;
- bearer/session tokens;
- CSRF secrets as reusable Adapter constants;
- browser local/session storage values containing credentials.

A verified Adapter may recompute a transient request value at runtime from non-secret page/API evidence. It must not package a captured credential.

### 12.4 Human-boundary actions

Deterministic policy remains authoritative for:

- purchases/payments;
- public posting;
- external messages;
- destructive deletion;
- authorization/identity changes;
- security/privacy changes;
- irreversible account operations.

Semantic/Jev may classify context but cannot grant an action.

### 12.5 Semantic/Jev browser fast path

Jev is an optional **advisory action selector**, never a browser executor.

The deterministic authority chain stays:

```text
Planner / Adapter goal
  -> BrowserPage observe
  -> bounded Jev typed advice
  -> Runtime validates one allowed typed action
  -> Runtime reservation/idempotency gate
  -> Browser Kernel executes
  -> deterministic observation/evidence
```

The purpose is latency reduction. Without this fast path, a mechanical multi-step page flow pays one main-LLM round trip for every observe/act pair. With Jev configured, the Runtime may keep several low-risk DOM choices local and return to the main planner only when semantic judgment is actually needed.

Rules:

- Jev receives only the bounded BrowserPage observation already allowed to the caller: canonical URL/origin, DOM generation, visible text summary, and opaque interactable refs/types/labels. It never receives cookies, tokens, storage, raw CDP traffic, password/OTP/card fields, or hidden DOM.
- Jev may choose only from a deterministic candidate set created by Runtime. Initial vocabulary is `observe | click(ref) | fill(ref, value_slot) | expect(condition) | done | blocked | escalate`.
- Jev does **not** synthesize arbitrary fill values. `fill` may reference only a bounded value slot supplied by the planner/Adapter input or deterministically derived from that input. Sensitive values remain subject to the existing sensitive-field prohibition.
- Every chosen mutation still crosses the same Runtime permission, generation/ref, idempotency, delivery-state and human-boundary gates as a main-LLM chosen action.
- Jev cannot open a new origin, grant host permission, claim a user tab, finalize/close a resource, replay an uncertain mutation, approve a human-boundary action, or widen an Adapter origin/access declaration.
- `delivery_unknown`, stale page identity, cross-origin drift, bot challenge, login boundary, ambiguous candidate selection, sensitive-field interaction, or a human-boundary action immediately exits the fast loop to deterministic Runtime/main-planner handling.
- Missing semantic configuration, provider timeout/error, malformed output, or low/uncertain confidence exits to the existing planner path with the same BrowserPage state. Generic Web remains fully usable without Semantic/Jev.
- The Extension never stores Jev/provider credentials or runs a second semantic loop. It executes typed commands only. Runtime's existing `SemanticService` and route pool are the only semantic provider authority.

Initial bounded loop:

```text
full observe
  -> Jev choose one candidate
  -> validate + execute
  -> observe current page
  -> Jev choose next candidate
  -> ...
  -> done | blocked | escalate | budget exhausted
```

The first implementation deliberately prefers correctness over delta-observation complexity:

- maximum 8 Jev-selected action steps per local loop;
- maximum one Runtime semantic decision per step through the existing typed-evaluation route pool;
- no separate Browser retry loop after semantic/provider failure;
- the loop exits after one semantic failure and hands the current deterministic observation back to the planner;
- observation-delta compression may be added only after full-observation traces show it materially reduces latency/token cost without weakening stale-generation detection.

Do not expose a permanent top-level MCP tool for this loop during alpha. The first consumer should be Runtime-internal Generic Web / reviewed Adapter execution. A future private `browser_page.goal` method is allowed only after the typed action layer and the three reference Adapters prove a stable goal/result contract.

Acceptance for the fast path:

- configured Jev can complete at least one 3+ step non-sensitive DOM flow with fewer main-LLM round trips than single-step control;
- configured / not-configured / provider-error states produce the same permission, idempotency, delivery, cleanup and human-boundary outcomes;
- Jev advice never appears as browser mutation evidence; only the validated Runtime action and Browser Kernel result are authoritative;
- invalid/stale refs, unknown delivery, host-permission absence and sensitive fields exit without a semantic bypass;
- a deterministic single-step BrowserPage path remains available and behaviorally equivalent when Jev is disabled.

### 16.1 Contract and release-plane rule

Browser Kernel refactors that only change Extension internals can ship on the Extension release plane when the existing Runtime/private contract is unchanged.

Generic Web/Adapter work that adds Runtime reservations, new private methods, Adapter metadata, or long-running dispatch/status behavior is Runtime contract work. Before implementation freezes method names, write the minimal private-method list and compatibility/rollback boundary explicitly. Do not hide a new Runtime contract behind an extension-only release.

The first BrowserPage compatibility change is deliberately additive on the existing private `herdr_mcp.page_assist` method: add optional `page_ref` while retaining optional `tab_id` as the 1.0 compatibility input. `inspect` may mint or reuse one claimed BrowserPage and return `page_ref`; later `click` / `fill` prefer `page_ref` and must resolve it to the exact endpoint, origin, live tab and page generation. Supplying both identities requires them to resolve to the same tab. Rollback is extension/runtime-compatible because old callers continue using `tab_id`, old extension builds ignore no new method name, and no StateStore schema or durable Browser Registry resource is added. Removing `tab_id` is a later explicit contract cleanup after signed-in/browser UAT.

The first lifecycle Runtime contract is one private method, `herdr_mcp.browser_page.lifecycle`, instead of one method per verb. It reuses the existing Page Assist caller endpoint grant and Extension host-permission gate; it does not add a new authorization source or durable StateStore resource.

`herdr_mcp.browser_page.lifecycle` accepts:
- `endpoint_ref` — required and must match one trusted Page Assist caller grant;
- `action` — `open | claim | release | finalize`;
- `target_origin` + `url` — required for `open` / `claim`; both must be HTTP(S), exact-origin matched, and already covered by the Extension host permission;
- `page_ref` — required for `release` / `finalize`;
- `idempotency_key` — required for `open` / `claim`, optional for `release` / `finalize`, and used only as ephemeral creation/claim identity, never as a second durable browser registry.

Semantics:
- `open` creates at most one inactive Herdr-owned tab for one idempotency key, persists its owned `BrowserPage` record in `chrome.storage.session`, and closes the fresh tab if that ownership record cannot be persisted;
- owned records are never evicted to satisfy the bounded session-record cap; older claimed handles may be dropped first, and a new owned open fails/cleans up instead of losing ownership authority;
- `claim` requires exactly one already-open tab with the exact normalized URL, never focuses or navigates it, and creates a claimed handle only;
- `release` is allowed only for claimed pages and deletes the handle without closing the user's tab;
- `finalize` deletes claimed handles without closing their tab, while owned handles close the exact owned tab, verify absence, then delete the handle; close failure keeps the owned record retryable;
- every response returns only `page_ref`, ownership/origin/canonical URL and cleanup evidence; raw Chrome tab ids stay Extension-local.

Delivery/rollback boundary:
- the Extension makes `open` idempotent by `idempotency_key`, so a retried request cannot create a second owned tab;
- a Browser Actuation timeout after possible delivery remains `delivery_unknown` and must not invite blind replay; explicit not-delivered failures are retryable with the same key;
- old Runtime/Extension combinations keep using `herdr_mcp.page_assist`; no existing method is renamed or removed;
- rolling back the lifecycle method leaves only ephemeral `chrome.storage.session` records/tabs owned by the Extension; `finalize` is required before normal completion and Extension startup pruning may remove invalid records, but claimed user tabs are never cleanup targets.

The Store extension, Runtime, and Edge can still version independently; cross-plane capability negotiation must fail closed on unsupported Adapter/kernel protocol versions.

### Phase H — Release convergence

Before RC, freeze behavior and stop adding primitives.

Required convergence:

- Runtime/Extension capability negotiation and rollback boundary documented;
- old Runtime + new Extension and new Runtime + old Extension fail closed or retain the documented compatibility path;
- Page Assist compatibility remains during 1.1;
- semantic configured/unconfigured/provider-error parity is verified;
- MacBook Air DEV qualification passes before MacBook Pro PROD upgrade/rollback UAT;
- Windows/macOS/Linux installation/update changes are required only if the new Runtime contract actually changes their installed binaries/config; extension-only fixes must stay on the extension release plane;
- all temporary worktrees, branches, panes and test browser resources are reclaimed before release sign-off.

### 17.1 Critical path and freeze points

| Stage | 2026-09-26 state | May start now | Freeze point |
| --- | --- | --- | --- |
| Alpha 1 provider/kernel foundation | DONE on local `main` | maintenance/regression only | provider capability/hooks + BrowserPage identity/lifecycle authority |

Hard ordering rules:

1. Do not add a BrowserPage primitive because it is generally useful; add it only when Generic Web UAT or a reference Adapter has a concrete need.
2. Do not freeze local Adapter syntax before Bilibili/X/Doubao expose the common step/result requirements.

6. Do not start marketplace/remote distribution work while local install/digest/rollback semantics are still changing.

## 18. Testing and qualification strategy

Tests serve the 1.1 acceptance contract. Reuse existing coverage first; add only focused behavior tests for newly introduced contracts.

### 18.1 Deterministic BrowserPage matrix

Cover:

- owned vs claimed cleanup and MV3 restart reconciliation;
- page-ref endpoint/origin/navigation mismatch;
- stale DOM generation/ref rejection before mutation;
- legacy Page Assist -> Browser Kernel compatibility;
- remote permission-required vs HUD/Options user-grant path;
- exact origin permission recheck before every action;
- one-reservation mutation sequencing and same-key replay;
- same key + different request conflict;
- explicit not-applied reservation release and safe retry;
- delivery-unknown record/replay without second mutation;
- read-only observe/expect listener recovery;
- no inject-and-mutate recovery for click/fill;
- screenshot artifact boundary when added.

### 18.2 Semantic/Jev matrix

Every fast-path scenario has three mandatory modes:

| Mode | Expected behavior |
| --- | --- |
| semantic configured + healthy | Jev may select only deterministic candidates; Runtime evidence remains authoritative |
| semantic unconfigured | same Generic Web/Adapter task remains usable through deterministic/main-planner path |
| provider timeout/error/malformed/uncertain | exit the local loop and preserve the same permission/idempotency/delivery/cleanup facts |

Pin these failures:

- Jev suggests an action outside the candidate set -> reject/escalate, no browser mutation;
- Jev references stale/unknown ref -> deterministic validation fails, no semantic override;
- Jev suggests human-boundary/sensitive action -> deterministic policy blocks/escalates;
- mutation returns delivery-unknown -> fast loop terminates, never chooses/replays another equivalent mutation;
- semantic route fails after a successful browser action -> preserve action evidence, return current observation to planner;
- loop budget exhausted -> return deterministic current page state, not a synthesized success.

Performance evidence for the fast path is comparative, not a safety gate replacement:

- capture main-planner round trips, semantic decision count, wall time and BrowserPage action count for the same 3+ step flow with Jev on/off;
- accept the optimization only when it reduces planner round trips without increasing browser mutations or changing final deterministic evidence;
- do not hard-code provider-specific latency thresholds into product correctness.

### 18.3 Reference Adapter matrix

Bilibili:

- transcript available / unavailable;
- anonymous / signed-in where relevant;
- pagination/segment bound;
- signature/request failure;
- canonical evidence.

X:

- signed-in search;
- thread read;
- bounded pagination;
- login required / challenge / rate limit;
- no write side effect.

Doubao:

- submit accepted once;
- submit rejected before mutation;
- delivery unknown;
- long-running completion;
- failure/cancel;
- artifact evidence;
- owned deliverable cleanup.

### 18.4 Local Adapter lifecycle matrix

Cover:

- schema/origin/access rejection before browser use;
- digest immutability;
- install conflict;
- draft does not replace active;
- failed/blocked trial cannot activate;
- current-digest activation CAS conflict;
- active run during draft edit;

### 18.5 WebChat regression matrix

For ChatGPT/Grok/Claude, preserve existing signed-in acceptance:

- identity/account/space/session;

- submit/accepted-message evidence;

### 18.6 Platform/release gates

## 19. Explicit non-goals for 1.1

- desktop GUI automation outside supported browser surfaces;
- ChatGPT Desktop preload/renderer injection or desktop-client patch/update/restore packaging;

- automatically generated permanent Adapters from one captured trace;
- mandatory `chrome.debugger` permission in the normal Store extension;
- claiming feature parity across every website.

## 20. Success criteria

1. Unknown user-approved sites can be operated through Generic Web without installing an Adapter.
2. Alpha 8 Page Assist and Generic Web use one kernel/permission/ref authority rather than parallel generic-page paths.
3. Generic Web has a complete deterministic baseline: open/claim, observe, typed mutation, expect/screenshot and release/finalize with one Runtime idempotency/delivery authority.
4. Optional Jev can reduce main-planner round trips for bounded multi-step DOM work without changing permission, generation, idempotency, delivery, cleanup or human-boundary outcomes; disabling/failing Jev preserves full functionality.
5. Bilibili transcript, X search/read, and Doubao image generation pass real signed-in browser UAT as reviewed builtin reference Adapters.
6. Doubao proves submit-once + durable status/reconciliation without keeping the initial MCP call open until image generation completes or replaying uncertain delivery.
7. Stable workflows can be promoted to a local Adapter without rebuilding Herdr; draft/try/activate/repair/rollback are verified and atomic.
8. ChatGPT/Grok/Claude retain their existing 1.0 method, identity, delivery, Continuity and settlement guarantees while sharing only behaviorally equivalent lower-level Browser Kernel plumbing.
9. Extension restart and browser-operation failure do not leak Herdr-owned tabs; BrowserPage remains ephemeral and does not become a second durable identity catalog.
10. Claimed/user tabs are never closed by release/finalize/session cleanup.
11. Sensitive browser credentials remain outside model-visible Adapter/Jev observations and results.
12. Normal Store users do not need `chrome.debugger` to use 1.1 Generic Web or browser Adapters.
13. Adapter count can grow without permanently inflating the model-visible MCP schema or creating a second Skill registry.
14. Local Adapter execution remains available without a network registry, semantic provider or third-party package service.
15. Release qualification proves Runtime/Extension compatibility/rollback, DEV qualification on MacBook Air, PROD upgrade/rollback on MacBook Pro, and complete resource cleanup.

## 21. OpenCLI / opencli-mcp ideas deliberately adopted

Capability patterns and contracts worth borrowing:

- broad scenario coverage through one browser bridge: generic page interaction, signed-in reads, search/social workflows, AI web apps, downloads/artifacts, and reusable site commands;
- browser primitives plus a separate Adapter author/repair workflow, so every site does not need bespoke core code;
- explicit tab open/claim ownership;
- observe -> act -> verify -> finalize;
- fresh refs after page mutation;
- agent-created vs user-owned tab cleanup rules;
- site command discovery instead of exposing all commands permanently;
- draft -> real trial -> atomic activation;
- structured stable errors;
- use the user's already signed-in browser;
- verify API/auth/pagination/error behavior before turning a workflow into a permanent Adapter.

Herdr-specific differences:

- Browser Registry and endpoint/account/session identity remain Herdr-owned;
- generation/idempotency/delivery evidence remains stronger than a generic browser command runner;
- local Adapter execution is declarative in 1.1 rather than arbitrary host JavaScript;
- WebChat sessions keep Continuity/task/result semantics;
- normal Store deployment does not take a mandatory `debugger` permission;
- Adapter authoring and execution reuse Herdr caller grants, local consent, human-boundary policy, and resource cleanup rules.

If code is later adapted rather than merely reimplemented from concepts, preserve the upstream Apache-2.0 attribution/license obligations explicitly.
