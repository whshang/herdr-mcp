# herdr-mcp 0.4.4 Release Plan

Status: Draft  
Date: 2026-09-02

## 1. Version positioning

0.4.4 is a stability, workflow, and user-experience release.

Keep the current public execution surface stable:

- keep the epoch-2 18-tool execution contract;
- do not add a new public MCP execution tool;
- do not add a new required public parameter;
- do not change the public type of `herdr_prompt.target`;
- do not introduce a new agent registry, model registry, cleanup daemon, or orchestration layer;
- do not add provider-specific scheduling policy or hard-code agent roles from names;
- preserve explicit user/model choice and keep the Web model as planner.

0.4.4 should make existing 0.4.3 capabilities trustworthy and cheaper to operate: multi-device routing, agent identity, capability evidence, planning advice, runtime/update truth, and bounded context usage.

Already merged into `main` for 0.4.4 and treated as completed baseline work:

- `ed12bff` — preserve legacy/default workstation routing for selector-free calls;
- `2c05050` — wait for macOS launchd uninstall settle.

These changes remain part of the 0.4.4 release but are not reopened unless regression evidence appears.

---

## 2. Goal

After 0.4.4, a Web planner should be able to answer these questions from evidence without guessing:

1. Which device returned this state?
2. Which exact agent can I address?
3. What agent kind is it?
4. What model/provider is the agent actually using when that fact can be safely observed?
5. What model/provider will a new Pi instance use by default?
6. Can I start the same Pi agent kind with an explicit model override through the existing Herdr API?
7. Is a capability unknown because the device was never scanned, or because a scan could not verify it?
8. How fresh is a dirty/agent/workspace fact?
9. Which runtime generation is active, and which operation activated it?
10. When routing fails, what exact safe next action should the planner take?

---

## 3. Non-goals

The following are explicitly outside 0.4.4:

- new public MCP execution tools;
- a new contract epoch for the 18-tool execution surface;
- automatic failover of mutations to another device;
- runtime-side natural-language task decomposition;
- automatic model selection or benchmark-based model ranking;
- full cost/latency quality scoring;
- a herdr-mcp-owned model/provider credential store;
- copying or normalizing provider credentials from `~/.pi`, `~/.claude`, or other agent homes;
- broad scanning of user home directories;
- automatic worktree/pane cleanup;
- a resident cleanup/watch process;
- a third human-readable agent nickname/alias system;
- agent/provider-specific role assumptions such as "Pi is cheap" or "Claude is reviewer";
- cross-device filesystem probing from Edge to guess which machine owns a path;
- a new authorization meaning for device-aware refs;
- browser-extension feature expansion.

---

## 4. Unchanged boundaries

These areas must remain unchanged unless required by a regression fix in this plan:

- Cloudflare public hostname, OAuth identity, and Worker ownership;
- persistent Rust production Link architecture;
- runtime generation ownership and immutable installed generations;
- Keychain helper and TCC broker identity model;
- browser extension as optional continuity/control surface, never binary transport;
- Herdr as workspace/pane/agent lifecycle owner;
- Pi/Claude/Codex/etc. as owners of their own provider credentials and native model configuration;
- explicit device selectors remain valid and take precedence over legacy/default routing;
- default device unavailable means failure, not mutation failover.

## 5. Current evidence baseline

Verified on 2026-09-02 before writing this plan:

### Runtime / devices

- `qingxian-macbookair`: online, `0.4.3`, production-ready.
- `yitaidiannao`: online, `0.4.3`, phase `candidate`, `production_ready=false`.
- Device B capability inventory reports `source=not_scanned`, `record_count=0`, `available_agents=[]`.

Device B being candidate is operational/onboarding state, not itself proof of a 0.4.4 runtime regression. 0.4.4 must represent this state accurately; it must not auto-promote or silently scan/seal the device as a side effect.

### Agent identity

`herdr_inspect` currently projects a Pi worker roughly as:

```json
{
  "name": "pi",
  "kind": null,
  "pane": "w6X:p9"
}
```

while native `agent.get` returns the addressable identity:

```json
{
  "name": "pi-apihub-wms-label-contract",
  "agent": "pi",
  "pane_id": "w6X:p9",
  "workspace_id": "w6X"
}
```

and `planning.advise` exposes the same worker as an `agent_id` plus `kind=pi`.

This is a projection bug. `inspect`, `since`, native `agent.get`, and `planning.advise` need one identity vocabulary.

### Pi model evidence

The local Pi installation already provides enough safe evidence for a narrow 0.4.4 fix.

Current native Pi settings contain:

```text
defaultProvider=provider-a
defaultModel=model-a
defaultThinkingLevel=high
```

A live Pi session contains bounded metadata evidence:

```text
provider=provider-a
modelId=model-a
model=model-a
```

Pi itself confirms both models in its catalog:

```text
provider-a/model-a
zai-coding-cn/glm-5.3-flash
```

Pi also accepts the user-facing selector `zai/glm-5.3-flash`.

Herdr native `agent.start` already supports:

```json
{
  "name": "...",
  "kind": "pi",
  "pane_id": "...",
  "args": ["--model", "zai/glm-5.3-flash"]
}
```

Therefore 0.4.4 does not need a new public MCP argument or a herdr-mcp model profile system to support flexible Pi model launch.

### Runtime metadata drift

Current `herdr_skill` live context reports all of the following simultaneously:

```text
server_version=0.4.3
build_commit=dev
self_update.target_version=0.3.32
```

while the active runtime source commit is the v0.4.3 commit. This is stale/mixed provenance and must be fixed at the state-writing boundary rather than cosmetically rewritten in presentation code.

## 6. Decisions resolved for 0.4.4

### D1 — Device B candidate state

Decision: do not make Device B promotion a 0.4.4 release blocker.

Required behavior:

- represent `candidate`, `production_ready=false`, and `not_scanned` distinctly;
- do not interpret empty scan results as proof that no agents are installed;
- do not auto-run scan/seal/promotion from planner read calls.

Operational UAT can still finish Device B onboarding separately before release sign-off if the release test requires a symmetric two-production-device scenario.

### D2 — Cross-device error evidence source

Decision: do not add Edge cross-device filesystem/workspace probing.

Use only evidence already authoritative at the layer handling the failure:

- Edge routing errors may report registered/routable device candidates and the selected/default device;
- runtime target errors may report the current device and local target candidates;
- device-aware refs may carry existing device affinity;
- a runtime must not claim "this path is on device B" unless that fact is already known from trusted routing/reference state.

This keeps error messages actionable without creating a new distributed inventory/query mechanism.

### D3 — Bare pane/workspace IDs vs device-aware refs

Decision:

- bare `pane_id` / `workspace_id` remain local identifiers scoped to the selected device for backward compatibility;
- device-qualified opaque refs are the safe cross-device continuation handle;
- explicit `device` remains a valid selector;
- 0.4.4 does not replace existing ID fields or change the public target parameter type.

The current ref is routing metadata, not an authorization capability. Because an authenticated caller can already explicitly select another enrolled device, adding HMAC solely to prevent an authorized caller from constructing an equivalent same-Worker device ref does not materially improve authorization. Do not add signing in 0.4.4 unless a separate threat-model review proves that the ref will grant authority unavailable through existing selectors.

## 7. Workstream A — Identity and multi-device correctness (P0)

### A1. Fix agent identity projection

Make all planner-facing agent views use the same semantics:

```text
name / agent_id = unique addressable agent identity
kind            = agent implementation kind, e.g. pi
pane_id         = local pane identity
workspace_id    = local workspace identity
```

Requirements:

- `herdr_inspect` must stop putting the agent kind into `agents[].name`;
- `herdr_since` must use the same mapping;
- `planning.advise` must match the same unique identity;
- preserve existing native Herdr identity; do not invent another registry;
- prefer explicit `pane_id` as control target when ambiguity remains.

Acceptance:

1. Every addressable `agents[].name` returned by `herdr_inspect` resolves through native `agent.get`.
2. The same live worker has the same canonical identity in `inspect`, `since`, `agent.get`, and `planning.advise`.
3. Two Pi agents can coexist without either becoming addressable only as bare `pi`.

Regression coverage: extend the existing identity/projection tests only. Do not create a new test framework or broad matrix.

### A2. Return device identity with workstation results

Add trustworthy routing provenance to workstation-backed results:

```json
{
  "device_id": "dev_...",
  "device_name": "qingxian-macbookair"
}
```

Requirements:

- preserve existing payload fields;
- include device provenance in text-visible results as well as structured content;
- keep explicit selector semantics unchanged;
- do not make device name an authorization input.

Acceptance:

1. Repeating a selector-free read three times while both devices are online routes consistently to the proven legacy/default device and each result states which device answered.
2. An explicitly selected Device B result states Device B.
3. Old clients that omit `device` continue working through the already-merged `ed12bff` compatibility path.

### A3. Preserve device affinity in follow-up references

Repair the existing device-ref transport so clients that primarily consume MCP text do not lose affinity.

Requirements:

- keep current bare IDs for compatibility;
- expose a device-qualified ref as an additional field where the response contains a workspace/pane/agent target;
- reuse the existing Edge ref encoding/decoding path rather than inventing a second reference type;
- do not mutate unrelated text or image/audio blocks;
- a ref for Device B must still resolve to B when the conversation default is A.

Acceptance:

1. Obtain a Device B pane ref, then use that ref in a follow-up target field while the default workstation is A; routing must remain B.
2. A malformed ref is rejected.
3. A ref whose referenced device is no longer enrolled/routable fails closed; it never silently falls back to A.

### A4. Routing errors return exact evidence and next action

Normalize routing-class failures around evidence already available at the failing layer.

Minimum response material when applicable:

```text
failure_layer
selected_device / default_device
candidate_devices
requested_target
candidate_local_targets
retryable
delivery_state
next_action
```

Requirements:

- never recommend a selector-free retry after a device ambiguity;
- mutation failures must preserve delivery-state semantics;
- do not infer remote path/workspace ownership by probing other machines;
- align error usability with `herdr_exec` project-root errors: provide values the planner can directly reuse.

Acceptance:

1. Default device unavailable: fail and identify the unavailable default; do not use another device.
2. Device ambiguity: list candidates and require explicit selection.
3. Local target mismatch: show the selected device and bounded local candidates when known.
4. No error path advises replaying an uncertain mutation.

## 8. Workstream B — Runtime/update truth (P0/P1)

### B1. Separate active runtime truth from historical update state

Fix stale/mixed runtime metadata at the authority boundary without adding another state owner.

Implementation analysis found that active truth already has two authoritative sources: the running binary's compiled build metadata and the generation manager's active generation. `self-update-status.json` is a historical operation record from the updater path and must stay historical. Do not create a second activation-provenance file unless a later acceptance check proves these existing authorities cannot answer a required field.

Required concepts:

```text
active_version        <- running binary
active_generation     <- generation manager
active_source_commit  <- running binary compiled metadata
active_channel        <- running binary compiled metadata

last_update_state
last_update_target_version
last_update_at
```

Requirements:

- `last_update_target_version=0.3.32` may remain as historical evidence if that operation really happened;
- it must never be presented as the current target/active version;
- `build_commit=dev` must not overwrite a known active source commit for a published PROD generation;
- do not derive active runtime identity from Git HEAD or a checkout;
- label updater-derived state as historical/non-authoritative for current runtime identity;
- prefer the existing active binary + generation-manager authorities over a new activation state file.

Acceptance:

1. `update apply`, `dev sync`, install, and rollback each produce internally consistent active metadata.
2. `herdr_skill` and `herdr_inspect` agree on active version/generation/source commit.
3. Restart without activation does not fabricate a new activation event.
4. Historical updater state remains inspectable without masquerading as active truth.

## 9. Workstream C — Agent model/capability evidence (P1)

This is a narrow evidence fix, not a model-management feature.

### C1. Fix `not_scanned` semantics

Current ambiguous shape:

```json
{
  "source": "not_scanned",
  "available_agents": []
}
```

Required semantics:

```json
{
  "source": "not_scanned",
  "needs_scan": true,
  "available_agents": null
}
```

or an equivalent shape that unambiguously distinguishes:

- never scanned;
- scanned and agent absent;
- scanned but capability unverified;
- capability verified.

Acceptance: planner cannot interpret a never-scanned Device B as proof that it has zero agents.

### C2. Populate safe model/provider evidence when an adapter can prove it

Do not postpone all model/provider evidence to 0.4.5. Pi already exposes enough safe non-secret evidence.

For Pi, use bounded adapter-owned reads/probes only:

#### Configured default for a startable/inactive Pi

Read only allowlisted fields from Pi's native settings, for example:

```text
defaultProvider
defaultModel
defaultThinkingLevel
```

Do not return the rest of the file. Do not read/return auth material.

Optionally verify the configured selector against Pi's own model catalog command.

#### Effective model for a live Pi

When Herdr provides an `agent_session` path, parse only bounded model metadata from the Pi session record, for example:

```text
provider
model
modelId
responseModel
```

Do not return prompts, completions, environment values, API keys, bearer tokens, credentials, or arbitrary session content.

Semantics must distinguish:

```text
configured_default
active_session
unknown
```

A response model reported by a gateway is evidence about the backend response, not necessarily the requested model. Keep it separate from requested/effective agent model.

For agent kinds without a safe verified adapter, keep model/provider unknown. Never infer from binary name, agent name, or marketing defaults.

Acceptance:

1. Current Pi default is observable as `provider-a/model-a` without exposing credentials.
2. A live Pi started with the default shows active-session evidence for that model after Pi records it.
3. Unknown remains unknown for unsupported agent adapters.
4. No scan response contains secret values or arbitrary session text.

### C3. Flexible Pi launch uses existing `agent.start.args`

Do not add herdr-mcp model profiles or a new MCP field.

Default Pi launch:

```json
{
  "method": "agent.start",
  "params": {
    "name": "task-pi",
    "kind": "pi",
    "pane_id": "wX:pY"
  }
}
```

Explicit model override:

```json
{
  "method": "agent.start",
  "params": {
    "name": "task-pi-glm",
    "kind": "pi",
    "pane_id": "wX:pY",
    "args": ["--model", "zai/glm-5.3-flash"]
  }
}
```

Ownership rules:

- Pi owns the default provider/model and credentials;
- herdr-mcp observes safe evidence and forwards explicit launch args;
- Web planner/user owns the choice to override a model;
- herdr-mcp must not mutate the operator's Pi default settings just to run one task;
- after startup, trust live session evidence over assumed launch arguments when available.

This also generalizes cleanly: another Agent adapter may later expose its own safe default/effective model evidence without creating a central herdr-mcp model configuration system.

### C4. Capability evidence remains evidence-backed

Minimum useful fields continue to be:

```text
kind
binary_version
verified.headless
verified.code_edit
verified.shell
verified.vision
provider/model when proven
```

Do not synthesize cost/latency/reasoning tiers in 0.4.4 unless an authoritative source already exists.

## 10. Workstream D — Planning and local method usability (P1)

### D1. Local method discovery

`herdr_methods` currently reflects only native Herdr socket methods while `herdr_call` also accepts local `herdr_mcp.*` methods.

Fix discovery by unioning the existing local method registry into method discovery.

Requirements:

- keep local methods behind existing `herdr_call`;
- do not add a public MCP tool;
- report the method source (`herdr_socket` vs `herdr_mcp_local`);
- expose exact parameter schema for `herdr_mcp.planning.advise` and skill methods.

Acceptance: `herdr_methods(query="planning")` discovers `herdr_mcp.planning.advise` with its accepted parameters.

### D2. `herdr_call.params` dual-form compatibility

Where the Connector/tool runtime allows it, accept both the historical JSON string and a JSON object for local/native method params.

Compatibility order:

```text
object -> validate directly
string -> parse -> validate
```

Do not remove string support in 0.4.4.

If the frozen client schema makes object acceptance impossible without a public schema revision, keep the existing string schema and improve discovery/error guidance instead. Do not force an epoch change for this convenience item.

### D3. Keep planning advice narrow and task-aware

`planning.advise` should remain resource/capability advice. It must not become another planner.

Accept a small structured requirement set when provided, such as:

```text
project_root
intent = implement | audit | probe
must_not_busy
device
required_capabilities[]
independent_units
```

Requirements:

- no natural-language task interpretation inside runtime;
- no automatic agent start;
- no automatic model selection;
- no role assignment from agent kind/name;
- direct deterministic tools remain preferred when the planner already knows the operation.

`parallelism.reason` must not claim task decomposition facts when no task/independent-unit evidence was supplied.

### D4. `direct_tool` must be truthful or absent

Current `direct_tool=null` is not useful.

Either:

- populate it only when the structured request gives enough evidence for a deterministic `fs` / `git` / `exec` recommendation; or
- remove the implication that runtime can decide this without task evidence.

Do not create a runtime natural-language classifier for this field.

## 11. Workstream E — Context, freshness, and privacy (P1/P2)

These are valuable but may slide behind A-D if release size grows.

### E1. Snapshot freshness evidence

Add freshness/source evidence for state used in mutation gating, especially:

```text
project dirty / changed_files
agent status
workspace/project snapshot
```

Preferred concepts:

```text
observed_at
source = live | snapshot_cache | fallback
stale
```

Acceptance: planner can distinguish a cached dirty observation from a fresh Git fact before using `confirm_dirty`.

### E2. Exec-session command minimization/redaction

`inspect` currently exposes a long list of historical command strings. Even when no secret is present, this is excessive context and inconsistent with the tighter `fs_*` boundary.

Requirements:

- default output should prefer running sessions plus a bounded recent summary;
- truncate command display aggressively;
- redact obvious secret-bearing CLI argument forms;
- retain session ID, state, cwd, start time, and exit status needed for recovery;
- do not claim generic shell output is secret-safe.

### E3. Inspect payload reduction without breaking old clients

Do not remove fields from the default response merely to hit a token target unless compatibility tests prove old clients do not depend on them.

Preferred order:

1. remove duplicate material such as repeated `native_migration` blocks;
2. bound/redact `exec_sessions`;
3. compact deep capability tables;
4. only then consider optional `sections` / `detail` selectors.

An optional selector is an experience optimization, not a release blocker, because frozen Connector snapshots will not expose newly added optional args until refreshed.

### E4. `herdr_since` event noise

- ignore/debounce utility-pane pure scroll changes by default;
- bound utility scrollback/state retention where Herdr/runtime ownership permits;
- do not auto-close panes;
- preserve meaningful terminal/agent/workspace changes.

### E5. Read-only worktree reclaim evidence

Expose enough already-known facts for planner cleanup decisions:

```text
dirty
has_working_agent
branch_merged_or_gone
last_activity_at
safe_to_reclaim = true | false | unknown
```

No cleanup mutation is added. Planner remains owner of reclaim decisions.

### Phase 0 — Baseline

1. Preserve the already-merged implicit-route and uninstall-settle fixes.
2. Capture current failing regression evidence for A1, B1, C1/C2, and local discovery.
3. Keep `main` clean; use the minimum number of isolated mutation lanes.

### Phase 1 — P0 identity/truth

1. A1 agent identity projection.
2. A2 device identity provenance.
3. A3 device-affinity refs on text-visible results.

1. C1 `not_scanned` semantics.
2. C2 safe Pi model/provider evidence.
3. C3 existing `agent.start.args` model override path verification.
4. D1 local method discovery.
5. D3 task-aware narrow planning advice.
6. D4 truthful `direct_tool` behavior.

### Phase 3 — Context/experience

1. E1 freshness evidence.
2. E2 exec-session minimization/redaction.
3. E3 compact inspect cleanup.
4. E4 since noise.
5. E5 reclaim evidence.

If Phase 3 starts expanding into new APIs/state owners, stop and move the remaining items to 0.4.5.

## 13. Acceptance gates

### Gate G1 — Agent identity

- every planner-visible unique agent identity resolves natively;
- kind and unique identity are no longer conflated;
- multiple same-kind agents remain distinguishable.

### Gate G2 — Multi-device routing

- two online devices do not make legacy selector-free reads unusable;
- every workstation result identifies its device;
- device-affinity refs survive the text-visible client path;
- default device unavailable fails closed;
- no mutation silently fails over to another device.

### Gate G3 — Runtime truth

- active version/generation/source commit agree across inspect, skill, service/runtime status;
- activation source is accurate for update/install/dev-sync/rollback;
- old updater history is not presented as current runtime target.

### Gate G4 — Pi evidence and launch override

- scan/probe observes current configured default `provider-a/model-a` using allowlisted non-secret fields;
- live Pi session reports effective/requested provider/model when present;
- starting Pi with no model args uses Pi's configured default;
- starting Pi through existing native `agent.start.args=["--model","zai/glm-5.3-flash"]` works;
- the operator's global Pi default remains unchanged after the override task;
- no credentials/session text are exposed.

### Gate G5 — Discovery/planning

- local `herdr_mcp.*` methods are discoverable;
- `planning.advise` does not invent task decomposition when task constraints are absent;
- resource/capability rejections are evidence-based;
- no automatic agent/model choice is introduced.

### Gate G6 — Regression/compatibility

- Rust runtime gate passes for Rust changes;
- Edge/contract tests pass for Edge/ref/routing changes;
- existing epoch-2 18-tool execution catalog remains unchanged;
- old string-form `herdr_call.params` remains valid;
- old selector-free clients remain functional through the legacy/default route.

## 14. Testing scope

Tests only serve the accepted 0.4.4 behavior.

Prefer extending existing tests. Add a focused regression only when current coverage cannot detect the regression.

High-value additions/changes:

1. one agent identity projection regression;
2. existing device-ref/routing tests extended for text-visible device provenance and default-device failure;
3. one activation-provenance regression covering the shared writer rather than one test per command path when possible;
4. one Pi safe-evidence parser test with synthetic settings/session fixtures containing secret-like fields that must not be returned;
5. one `not_scanned` semantic regression;
6. existing method-discovery test extended for local method registry.

Do not add:

- a new test framework;
- a provider/model matrix;
- end-to-end tests for every coding agent;
- a broad benchmark suite;
- large snapshots solely to lock JSON formatting.

## 15. Release completion

0.4.4 is complete when:

- P0 workstreams A and B are implemented and verified on the real Connector path;
- C1-C3 and D1/D3 are complete unless a concrete compatibility blocker is documented;
- current runtime metadata is internally consistent;
- two-device routing UAT proves explicit routing, default routing, default-unavailable failure, and affinity preservation;
- Pi default/effective model evidence is visible without secrets;
- a Pi worker can be launched once with the configured default and once with `--model zai/glm-5.3-flash` without changing global Pi settings;
- release notes state that model/provider evidence is adapter-verified and may remain unknown for unsupported agents;
- no new public execution tool or automatic orchestration subsystem was added;
- final diff contains only files required for these accepted fixes and their focused regression coverage.

## 16. Planning rationale

The main 0.4.4 reliability issue is not lack of execution capability. 0.4.3 already has direct fs/Git/exec, multi-device routing, native agent control, capability scanning, and planning advice.

The remaining risk is ambiguous or stale evidence:

- agent identity projected incorrectly;
- device affinity lost on some client result paths;
- `not_scanned` looks like an empty scanned inventory;
- model/provider fields remain null despite safe local evidence being available for Pi;
- runtime activation history is mixed with active truth;
- planning advice can sound task-aware without task input;
- oversized inspect history increases context cost and hides the facts that matter.

0.4.4 should correct these evidence and workflow failures with the smallest possible changes. It should leave model ownership with the agents, device/runtime ownership with the existing control planes, and planning ownership with the Web model.
