- Runtime under measurement: `herdr-mcp 1.0.3` (repo test build, not an installed

## What this measures

| dimension | what is measured |
| --- | --- |
| fast path | typed decision routes (`decision`, `decision-vercel`) — the Jev heads the Runtime/browser fast path and the goal supervisor consume |
| fallback | (a) the typed routes behind the configured primary route in pool order, (b) all `openai-chat` routes — the chat stage the extension uses when the typed stage is uncertain or unavailable |
| correctness | expected vs actual per head: noul tri-state from the runtime's own `noul_result`, choice target ids, and — for chat — the shipped extension interpreters (`parseSupervisorDecision`, `interpretLlmJudgeReply`) |
| latency | wall clock around the provider call, p50/p95/max per route, plus the share of calls inside the production attempt deadline |
| rate limits | strictly sequential, one route at a time, 600 ms pacing between typed calls and 1200 ms between chat calls; a route that returns HTTP 429 or fails three times in a row stops early and is reported with a `stopped` reason |

Deliberate non-goals: no ChatGPT/WebChat/browser calls, no `config.json` edit, no
runtime install or dev sync, no production service interaction, no release.

## Harness

```
scripts/bench/generate-semantic-cases.mjs   # 12 typed + 7 chat cases from the shipped builders
scripts/bench/run-semantic-bench.mjs        # per-route run, scoring, table rendering
crates/herdr-mcp/src/semantic_bench.rs      # ignored, env-driven Rust test module
tests/bench/fixtures/semantic-cases.json    # committed, byte-stable case set
```

Every provider call is made by the runtime's own `HttpSemanticProvider` /
`OpenAiChatProvider` inside the Rust module, so the benchmark measures the shipped
protocols, parsers and timeouts instead of a script-side re-implementation. Typed
cases are converted from the fixture with `semantic_request_from_json` — the same
conversion `/extension/semantic/evaluate` uses. Chat replies are recorded verbatim
and scored by the shipped extension interpreters, so no interpreter logic is
duplicated outside the product.

Case provenance (all generated, never hand-written per run):

- `extension/jev-judge-core.js` — `buildJevPendingWorkRequest` (3 heads),
  `buildJevGoalSemanticRequest` (5 heads);
- `crates/herdr-mcp/src/mcp.rs` `browser_fast_path_decision` heads
  (`objective_done`, `external_blocked`, `safe_click_supported`, `click_target`);
- `extension/goal-supervisor-core.js` — `SUPERVISOR_SYSTEM_PROMPT` +
  `buildSupervisorInput`/`buildSupervisorUserMessage`;
- `extension/binding-core.js` — `buildLlmJudgeUserMessage`.

Each route runs only the cases valid for its protocol family: 12 typed cases × 3
runs for decision routes, 7 chat cases × 3 runs for chat routes. 210 provider
calls total (3 of them the stopped Vercel attempts).

## Findings

**F1 — the route-pool fallback tail is gone.** The primary route and the routes
behind it now cost the same: p50 296–315 ms and p95 439–518 ms on the three
`jev-latest` routes, p50 497 ms / p95 1250 ms on `jev-openrouter`, all inside the
1800 ms fast-path attempt budget and the 3600 ms pool budget. The 1.0 line
recorded fallback routes at 5044–8805 ms (3208 ms median across that mixed
sample) while the then-primary route ran at 889–1374 ms; that fallback behavior no
longer reproduces on this configuration, and the primary route is now faster as
well (case shapes and sample sizes differ, so read F1 as "no slow tail", not as a
like-for-like speedup claim). Measured cost per typed decision is ~0.3 s on the
primary route.

**F2 — `jev-vercel` is unusable as configured.** Every call returns HTTP 403 from
the Vercel AI Gateway (466–1544 ms), so the route can only ever burn one attempt
inside the pool and then sit in `SemanticError::cooldown`'s 300 s penalty. Nothing
in the runtime is wrong: failover is correct and bounded. The route needs its
gateway credential/entitlement repaired or the entry removed, and the
`decision-vercel` response parser (`parse_vercel_response`) therefore remains
unverified against live traffic.

**F3 — one chat fallback route can exceed the production chat attempt deadline.**
`SemanticService::chat` gives each route 5 s (`CHAT_ATTEMPT_TIMEOUT`) and the pool
12 s. `llm-whshang` (`deepseek-v4-flash`) exceeded 5 s in 4/21 calls (p95 7297 ms,
max 7941 ms), while `llm-qingxian` and `llm-ollama` stayed inside the deadline in
all 21 calls each. A chat reply slower than the attempt cap is discarded and the
pool fails over or gives up, so the supervisor/judge fallback is measurably less
reliable on that route than on the other two.

**F4 — three heads sit on or next to a noul boundary, and one can never cross it.**
With the fixed `>= 0.80 true / <= 0.20 false / otherwise uncertain` contract:

- `task_completed` — for a turn whose state says every requested item is complete
  and every TODO is closed, the true-side samples (1 case × 3 runs × 4 routes)
  returned 0.71–0.74 and **0 of 12 reached the `true` gate**; the 48 false-side
  comparisons were 0.02–0.05 and all matched. The head is stable and consistent
  across routes, it is simply under-confident, so no consumer can gate a positive
  completion claim on it today. The only current consumer is
  `deriveSupervisorLedger`, which requires `task_completed < 0.80` for its
  "declared remaining work" hint — an uncertain value satisfies that, so the
  effect there is benign.
- `useful_work_remaining` — the false side straddles the gate: 12 of its 24
  comparisons fell above 0.20 (0.21 ×10, 0.22 ×2; 2–4 of 6 false-side samples per
  route), on an input that explicitly offers only optional future help. The value
  is currently telemetry only (`jev_useful_work_remaining`,
  `jev_handoff_boundary_stable`), so nothing acts on it, but it is not a usable
  signal as-is.
- `can_continue` — the positive gate that `deriveSupervisorLedger` does use
  (`>= 0.80` for `jevRunnable`): the true side returned 0.79–0.81 across 12
  samples, with one 0.79. The same case on the same route therefore lands on both
  sides of the gate across runs, so a jitter-induced 0.79 removes the advisory
  "declared remaining work" hint for that boundary. The hint is advisory only, the
  deterministic ledger and guards stay authoritative, and the supervisor's continue
  budget bounds the consequence — but the margin is one rounding step, not a design
  margin.
- All other true-side heads were 12/12 or 24/24 correct with wide margins:
  `has_unfinished_work` 0.95–0.96, `needs_human` 0.95–0.96, `waiting_external`
  0.97, `needs_handoff` 0.97–0.98, `objective_done` 0.89–0.90, `external_blocked`
  0.96–0.97, `safe_click_supported` 0.95–0.96; their false sides, where the case
  set has one, were ≤0.18.

**F5 — choice answers are hard, not hedged.** All 24 fast-path `click_target`
samples across 4 routes returned the correct target with `confidence = 1.0` and
`probabilities` of exactly `{1, 0, 0}`. The runtime's dual gate (chosen-target
confidence ≥ 0.80 **and** chosen-target probability ≥ 0.80) therefore passes
unconditionally on these routes, and a wrong choice would arrive maximally
confident. Safety still comes from the deterministic candidate filter (low-risk
`same_origin_navigation`/`reveal` refs only) plus the postcondition/verification
path, not from the probability value.

## Bugs found and fixed

Both fixes are in fast-path/fallback interpretation code and both ship with tests
named in the `user … | Given … | When … | Then …` form.

**B1 — a malformed Jev probability became a decision** (`extension/jev-judge-core.js`,
commit `1154f037`). `interpretJevPendingWorkAnswer` and
`interpretJevGoalSemanticAnswer` coerced the provider value with `Number(...)`, so
`null`, `""`, `false`, `[]` all became `0` — which reads as the 0.20 false
boundary and produced `signal = "done"` → `decideJevAutoPolicy` → `stop`. A Goal
reply whose five heads were all `null` returned `ok: true` with every signal
`false`. Numeric strings (`"0.9"`) were accepted too. The fix accepts only a
finite JSON number inside `[0, 1]` and returns `bad_response` otherwise; valid
numbers, including the exact 0.20 boundary, are unchanged.

Reachability, stated honestly: today the only production caller
(`fetchJevJudgeOnce` / `fetchJevGoalSemanticPrior` in `extension/background.js`)
receives payloads already parsed by `crates/herdr-mcp/src/semantic.rs`, which
rejects a non-numeric probability first. The defect was therefore latent rather
than live, but it violates the helper's own contract (already pinned by an
existing test for `noul = 2`), it fails in the least-safe direction (silently
claiming the work is done), and it contradicts the stated policy that malformed
output preserves the pre-semantic behavior. Tests:
`tests/jev-judge.test.mjs` — "user never gets a stop decision from malformed
provider output …" and "user never gets an all-false Goal prior from malformed
provider output …".

**B2 — the supervisor contract did not state the vocabulary it enforces**
(`extension/goal-supervisor-core.js`, commit `12f95e09`). This one was reproduced
live by the benchmark before the prompt revision: `parseSupervisorDecision`
rejects a `todo_updates[].status` outside `TODO_STATUSES` with
`todo_update_status_required`, but `SUPERVISOR_SYSTEM_PROMPT` enumerated the
allowed values for `decision` and `retry_class` only. The configured
`deepseek-v4.1-flash` route answered a valid `CONTINUE` with
`status: "in_progress"`, and all 3 of 3 measured replies were discarded as "no
executable decision" — while the supervisor still owned the boundary, so the
legacy judge did not act either. The internal repair message named only the error
string, which says "status required" for a status that *was* provided, so the
bounded retry could not correct it.

The fix names every allowed status and evidence kind in the prompt, and makes both
repair messages carry the full allowed-value list (`decision`, `retry_class`,
`todo_updates[].status`, `evidence[].kind`) from the same constants the parser
uses. After the fix the same route scored 7/7 accepted on a check run and 21/21 on
the measured run. Tests: `tests/goal-supervisor.test.mjs` — "user gets a repairable
rejection …" and "user is told the executable vocabulary up front …".

Not treated as bugs, by design or by prior agreement:

- the `decision-vercel` 403 (F2) is a provider-side entitlement problem;
- F4 is prompt/model calibration on a fixed threshold contract, not a code defect;
- `cargo fmt --check` currently reports pre-existing drift in
  `crates/herdr-mcp/src/mcp.rs` (late-acceptance readback code, untouched by this
  task); `semantic_bench.rs` and `semantic.rs` are formatted.

## Reproduce

```bash
node scripts/bench/generate-semantic-cases.mjs --check   # fixture matches the shipped builders
node scripts/bench/run-semantic-bench.mjs --results-dir=/tmp/semantic-bench --runs=3
```

The runner is resumable: a route whose `route-<name>.json` already exists in the
results directory is reused unless `--force` is passed, and `--routes=a,b`,
`--runs=n`, `--pacing-ms=n`, `--chat-pacing-ms=n`, `--attempt-ms=n` bound a smaller
sweep. Raw per-call samples (latency, error code, head probabilities, route name,
model) are written to the results directory; `config.json` is never modified,
never copied, and no API key is printed or written to any artifact. The full sweep
takes about 10 minutes and ~210 provider calls.
