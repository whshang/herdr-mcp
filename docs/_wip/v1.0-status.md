### 1.0 cross-cutting — Herdr 0.9.1 native multi-machine/recovery boundary

- Herdr 0.9.1 native `herdr --machine <label-or-id> <command>` is the preferred saved-machine maintenance/UAT/recovery path for supported API command families; Edge `device_id` remains the Web-AI routing identity. 1.0 does **not** add a second `machine` selector to the 18 Runtime tools and does not infer equivalence between the two namespaces.
- `herdr_inspect` keeps historical `herdr_version` as the running server version and adds explicit `herdr_server_version` plus `herdr_native`: installed CLI version, feature-detected machine-forwarding support, bounded saved-machine inventory, client/server version state, and safe-handoff blocking evidence. This closes the silent-wrongness case where CLI 0.9.1 is installed while a compatible 0.9.0 server is still preserving live panes.
- `version_state=server_restart_pending` is diagnostic only. It must not stop/restart Herdr or close panes automatically. `handoff_blocked_reason=legacy_sender_pane_limit` means the older sender still exceeds its first-upgrade 64-pane handoff limit; existing user/other-task panes are preserved until a safe convergence window exists.
- Recovery transport is fail-closed: Edge stays primary; native `--machine` may be used after `delivery_state=not_delivered` or live proof that the earlier mutation was not applied, while the target Herdr server is reachable; raw SSH is the final bootstrap/recovery path when the server/forwarder itself is unavailable. Generic transport failure, uncertain/delivered state, or missing delivery evidence never authorizes cross-transport replay.
- Acceptance before GA: focused Rust regression must distinguish CLI-new/server-old, older CLI capability=false, unavailable CLI capability=unknown, and preserve the cross-transport retry fence; public Runtime tool count/hash stays unchanged; EN/zh-CN multi-machine docs and remote-planner Skill remain aligned. Real device evidence should include at least one successful read-only `--machine` command and one observed client/server divergence without destructive restart.

### 1.0 cross-cutting — Async Agent Task Lifecycle / Parent Wake

- PR #530 is merged as `a28b9bd4`. Normal Agent orchestration is `submit once -> immediate task identity -> Parent continues -> Runtime terminal -> durable parent inbox -> parent adapter wake`; a planner no longer needs to remain blocked on the Child's global Agent status. The #530 browser candidate was extension `0.1.115`; the live Air standalone/Chrome endpoint has since advanced to `0.1.116` in the provider lane and was intentionally not downgraded during this closeout.

Runtime also returns a stable `turn_id` envelope immediately; Herdr 0.9.x still lacks a native prompt-turn ID, so `exact_native_turn=false` remains explicit. When the child was already working at submit time, Runtime consumes the prior settle first and requires fresh activity before attributing a terminal state to the new task.
- Runtime reuses the existing StateStore `operations` ledger for durable `awaiting_activity / awaiting_prior_settle / running / completed / blocked / failed / delivery_uncertain` records. No second task database or scheduler authority is introduced. Private `agent.task.status / inbox / ack` plus `herdr-mcp agent dispatch/status/inbox/ack` expose the same ledger; optional wait is a task-ID compatibility mode rather than native Agent-status waiting. A submitted task that never produces fresh activity becomes terminal `delivery_uncertain` after the bounded activity-start window and is surfaced to the Parent without automatic replay.
- CLI parent notification is persisted before delivery and uses `pending -> in_flight -> delivered`; ambiguous delivery becomes `uncertain` and is not blindly replayed. WebChat caller provenance resolves through the exact `principal_ref + provider + opaque caller session` mapping to one durable browser `session_ref`; extension wake reads only that session-scoped inbox and acknowledges a task only after wake submission succeeds. Existing workspace settled wake remains fallback for legacy/non-task flows.

### 1.0 cross-cutting — Semantic/Jev advisory expansion
