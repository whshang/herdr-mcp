## 1. Positioning

v0.4.5 is a follow-up maintenance release after v0.4.4 with two compatible tracks: **less orchestration overhead, clearer evidence, and lower context cost** for the Web Planner, plus **safer onboarding and Link network resilience** for real users. It does not expand the public MCP contract.

The starting point is the v0.4.4 baseline:

- multi-device routing and device provenance are explicit;
- Agent identity is addressable and separate from Agent kind;
- DEV/PROD activation truth is reconciled;
- capability/model evidence is observational and bounded;
- long commands are routed through durable exec sessions by the planner Skill;
- completed exec evidence survives runtime replacement;
- small non-secret UTF-8 text can be copied explicitly between enrolled devices through private local methods;
- workstation contract remains epoch 2 / 18 public tools.

v0.4.5 should preserve those boundaries unless a measured user-visible problem proves that a contract change is worth the migration cost.

## 2. Goals

1. Reduce repeated Web Planner round trips and oversized state payloads.
2. Make freshness and provenance explicit enough that planners can avoid acting on stale evidence.
3. Make planner orchestration follow the minimum-entity rule, useful parallelism, progress correction, cross-audit/regression validation, and safe reclamation without creating an automatic workspace/pane/worktree manager.
4. Improve local-method ergonomics and capability evidence only where the existing contract can express it safely.
5. Keep reliability work focused on silent-wrongness cases observed in real use.
6. Make first-install and second-device onboarding safe, including a core Cloudflare path that does not require R2.
7. Separate stable MCP/OAuth identity from workstation Link transport so direct, local-proxy, and shared-relay paths can fail over without changing the Connector origin.
8. Clean up macOS background-service residue and freeze a safe Runtime Supervisor direction without prematurely collapsing fault domains.
9. Ground prior or multi-device project discussion through `device -> project/workspace -> continuity/history -> live Git/runtime`, and use one-question-at-a-time requirements grilling only when material implementation decisions remain ambiguous after discoverable facts are read.
10. Make GitHub PR/Auto-merge verification explicitly fresh and delta-friendly so Connector cache lag and repeated `gh run watch` output do not waste planner context or cause stale conclusions.

## 3. Explicit non-goals

- No automatic model/provider selection system.
- No herdr-mcp-owned Agent credential registry.
- No automatic cross-device failover for mutations.
- No automatic file/directory synchronization.
- No broad binary transfer API merely because v0.4.4 added bounded text copy.
- No automatic worktree cleanup daemon.
- No fixed panes-per-tab limit.
- No generic runtime natural-language task classifier.
- No server-side wait/condition primitive by default.
- No pytest/cargo/npm-specific parser matrix by default.
- No HMAC/authentication layer for device refs unless the ref itself later becomes an authorization capability.
- No PLM/GitLab-project CI changes in this repository; those belong to the affected project.
- No Herdr-hosted replacement for the user's OAuth/MCP/Device Registry/WorkstationDO control plane.
- No generic public forward proxy, VPN, or arbitrary host/port relay.
- No silent OAuth issuer migration as a side effect of repairing Link connectivity.

## 4. Recommended workstreams

### A. Freshness and provenance for planner-visible state

Add or normalize `observed_at`, `source`, and `stale`/freshness evidence on planner-visible state where the planner may use that fact to gate a mutation.

Candidate surfaces:

- project/Git-derived facts exposed by inspect/planning;
- capability inventory observations;
- runtime/link/device summaries where source timestamps are currently implicit.

Reason:

v0.4.4 fixed several cases where plausible-looking stale state caused wrong conclusions. The next useful step is to make freshness machine-readable instead of relying on prose or planner memory. This directly targets silent wrongness without adding another state owner.

Tasks:

1. Inventory planner-visible facts that can become stale while a mutation decision is pending.
2. Reuse existing event/read timestamps instead of creating a new watcher or cache owner.
3. Define one small freshness vocabulary (`observed_at`, `stale`, and source/unknown semantics) and apply it only where it changes a planner decision.
4. Add stale-vs-unknown regressions for Git/project and capability evidence.

Acceptance:

- no new watcher solely for timestamps;
- timestamps come from existing authoritative reads/events;
- stale/unknown is represented explicitly rather than inferred as fresh;
- mutation advice can distinguish fresh evidence from unavailable evidence.

### B. Inspect/context reduction without breaking compatibility

Continue reducing high-frequency context cost while preserving the existing default response shape for older clients.

Preferred order:

1. remove duplicated evidence;
2. bound large histories and deep capability tables;
3. add optional detail/section selectors only if they can be introduced without changing the frozen public tool contract;
4. use compact summaries plus stable identifiers that can be expanded on demand.

Reason:

Real development sessions still spend substantial model context on repeated topology and history that has not changed. v0.4.4 already bounded exec history and removed pure scroll churn; further gains should come from payload discipline rather than a second state cache.

Tasks:

1. Capture representative `herdr_inspect` byte/field counts before changing the payload.
2. Remove only evidence proven duplicate; do not delete a legacy default field merely because a sibling field is newer.
3. Bound large histories/capability detail and continue suppressing pure scroll noise in incremental state.
4. Evaluate an optional detail/section selector only if it can be added without a public contract migration.
5. Keep a compatibility fixture for the default response shape and a size regression for representative topology.

Do not remove default fields until compatibility evidence proves older callers do not depend on them.

### C. Read-only resource reclaim evidence

Improve planner-visible evidence for whether a pane/workspace/worktree is reclaimable, but keep the actual cleanup decision with the Web Planner/user.

Useful evidence:

- working Agent present or absent;
- dirty/clean status;
- branch merged/gone/unmerged;
- last meaningful activity;
- uncertain mutation/session evidence;
- `safe_to_reclaim = true | false | unknown` with reasons.

Reason:

The recurring problem is resource accumulation after work completes, while automatic deletion is too risky. Read-only evidence gives the planner enough information to close resources deterministically without introducing a cleanup daemon.

Tasks:

1. Derive reclaim evidence from existing Git/workspace/Agent/session facts; do not add a cleanup daemon.
2. Return `safe_to_reclaim=true|false|unknown` only when each contributing fact has a known source/freshness.
3. Include bounded reasons such as dirty worktree, working Agent, unmerged branch, uncertain mutation, or recent activity.
4. Keep actual close/remove operations explicit and planner-owned.

### D. Tab/pane topology advice only if Skill guidance proves insufficient

v0.4.4 already teaches the planner:

- workspace = project/mutation lane;
- tab = human-readable activity grouping;
- pane = one Agent/terminal surface;
- distinct Agent activity should normally start in a new tab;
- pane splits are for tightly related side-by-side work.

For v0.4.5, first measure whether planners still create unreadable single-tab layouts. If the problem persists, `planning.advise` may expose **read-only topology suggestions** based on current tab/pane structure.

Reason:

A runtime auto-layout state machine would add ownership and lifecycle complexity. Skill guidance is cheaper and already executable through `tab.create`, `pane.move`, and `tab.close`. Add code only if real evidence shows guidance is insufficient.

### E. Exec-session ergonomics after v0.4.4 durability

v0.4.4 solves the correctness requirement: when a command has already completed, a later planner/runtime can recover its completion evidence without rerunning the command.

Possible v0.4.5 improvements are deliberately lower priority:

- more compact framework-neutral progress/failure summaries;
- an explicit recoverable execution identifier for synchronous utility execution, if utility execution remains common despite Skill guidance;
- optional bounded read-wait semantics only if polling round trips remain a measured bottleneck.

Reason for not adding server-side wait now:

A wait/condition primitive reduces polling calls but does not solve a correctness problem once completion evidence is durable. It also introduces timeout/cancellation semantics and another long-held RPC path. The current `session_id + next_offset` pattern is simple, explicit, and recoverable across model turns. Add wait only if telemetry or repeated real sessions show meaningful latency/context savings.

Reason for not adding framework-specific parsers now:

Special parsers for pytest/cargo/npm create a maintenance matrix and can silently misclassify output as those tools evolve. Prefer generic bounded head/tail/failure evidence first; add a parser only for a repeatedly observed, high-value format with deterministic tests.

Tasks:

1. Measure whether Web planners still spend material turns polling completed/running sessions after v0.4.4 durability ships.
2. Prefer generic bounded final/failure excerpts before any framework-specific parser.
3. If synchronous utility execution still hosts long commands despite Skill guidance, design a recoverable execution ID rather than scraping terminal scrollback.
4. Add a server-side wait/read condition only if measured round-trip savings justify its cancellation/timeout semantics.

### F. Capability/model evidence for additional Agent adapters

Extend safe provider/model/capability evidence beyond Pi only when an Agent exposes a stable, bounded, non-secret source of truth.

Rules:

- distinguish `configured_default`, `active_session`, and `unknown`;
- never infer model/provider from Agent name;
- never parse arbitrary session transcripts for convenience;
- never copy credentials into herdr-mcp state;
- adapter-specific absence remains unknown rather than false.

Reason:

v0.4.4 proved the useful boundary: herdr-mcp can observe evidence without becoming a model manager. Additional adapters should follow the same pattern, one verified source at a time.

For `startable_candidates`, provider/model must remain `unknown` until a stable pre-launch source exists. Do not infer it from a historical live session, an Agent name, or a guessed default. A CLI `print-config` / model-catalog path is acceptable only when it is bounded, non-secret, and deterministic enough to regression-test.

Tasks:

1. For each additional Agent adapter, identify one bounded authoritative pre-launch and/or active-session evidence source.
2. Add only non-secret allowlisted fields with explicit source labels.
3. Keep unsupported adapters unknown and regression-test that absence is not converted to a guessed default.
4. Do not persist credentials or arbitrary transcript content.

### G. Device-ref threat-model review only if authority changes

Do not add HMAC signing to device refs in v0.4.5 by default.

Revisit only if a ref gains authority that an authenticated caller cannot already obtain through an explicit device selector.

Reason:

Today a device ref is routing/affinity metadata for an already authenticated user. v0.4.4 additionally requires private cross-device text read/write calls to carry an explicit top-level device selector and rejects ref-derived routing for that data path. Signing refs would therefore add key distribution, rotation, compatibility, and recovery state without closing a demonstrated remaining authorization gap.

### H. Occupant-bound Agent references only after a demonstrated stale-pane incident

Do not add `occupant_seq` to the v1 pane/workspace ref format by default. A pane ref identifies a pane and can outlive the Agent that once occupied it; planner guidance therefore prefers the unique addressable Agent name for Agent operations.

If real long-conversation evidence shows stale pane refs repeatedly targeting a replacement Agent, design an explicit Agent/occupant ref contract rather than silently extending pane-ref semantics. Such a design must define occupant authority, stale-ref rejection, compatibility, and lifecycle ownership before implementation.

Reason:

Adding an occupancy counter to every ref creates a new cross-layer identity contract. The current unique Agent identity fixes most practical targeting needs more cheaply, while pane refs remain useful for topology operations.

### I. Runtime-local routing error evidence

Background:

Edge routing failures in v0.4.4 already return bounded device evidence (`failure_layer`, `delivery_state`, selected/candidate devices, requested target, and `next_action`). The remaining weak path is a target that reaches the correct workstation but fails locally with a bare `workspace_not_found` / pane or Agent lookup error. The planner then has to issue another topology query to discover the local alternatives.

Goal:

Make a local target failure actionable in one response without introducing cross-device filesystem/topology probing or automatic failover.

Solution:

Reuse only evidence already authoritative on the selected workstation. Local target errors may include a bounded `candidate_local_targets` list, the requested target, the selected device provenance, and a precise next action. Keep the same fail-closed delivery semantics used by Edge routing errors. Field-level invalid input may use the existing `invalid_params` style, but do not build a new global error framework merely for wording consistency.

Tasks:

1. Identify the high-frequency local lookup failures for workspace, pane, and Agent targets.
2. Attach bounded candidates only when they are available from the current workstation snapshot/schema; never probe another device to manufacture hints.
3. Preserve `delivery_state=not_delivered` for failures that occur before a mutation is forwarded to the target operation.
4. Add focused tests for local target-not-found, explicit device/ref conflict, and unavailable default-device behavior.
5. Measure response size so candidate hints do not recreate inspect-scale payloads.

Acceptance:

- one local lookup failure provides enough bounded evidence to choose a valid local target when such evidence exists;
- no silent device failover;
- no cross-device inventory query is added;
- existing error codes and old callers remain compatible.

### J. Browser Control Center fleet visibility and actionable disabled states

The previously discussed browser monitoring surface belongs in the existing Chrome Side Panel Control Center rather than a second web dashboard. The extension already owns local workspace/pane visibility and a tokenless Native Messaging trust path; v0.4.5 should extend that same surface with bounded Worker-device evidence.

Scope:

1. Add a read-only Worker device section showing the registered device name, current-device marker, authorization, connection, health, runtime version/generation, last-seen freshness, and local Link-generation alignment where available.
2. Fetch the fleet only through the trusted Native Messaging -> local runtime path. Chrome never stores or receives a Worker device credential, MCP bearer, or OAuth token.
3. Reuse the current owner/operator authorization boundary for the full inventory. A joined member device without owner permission must show a precise explanation rather than silently widening device credential authority.
4. Keep authorization (`active` / `suspended` / `revoked`), connection (`online` / `stale` / `offline`), and health as separate facts; do not collapse them into one generic online/offline light.
5. Do not add fixed device polling. Refresh on Control Center open/manual refresh and when a previously hidden panel becomes visible with stale data.
6. Every visible disabled browser action must expose its current blocking reason from existing state: unbound page, Auto/manual exclusion, working Agent, active handoff, stale target, in-flight binding/action, or unavailable capability.

Manual ChatGPT Project handoff also needs one v0.4.5 reliability correction. A manual Handoff click must never submit a `HERDR_HANDOFF_V1` summary request into the source conversation. Resolve the durable Continuity Journal from the binding first, then from the current `conversation_id` if binding metadata is missing/stale. If no durable chain exists, use the already-configured bounded fallback LLM over a read-only source transcript. If neither source is available, fail closed and leave the current conversation and route unchanged. z.ai remains on its conversation-scoped handoff contract.

Acceptance:

- no separate browser dashboard and no new public MCP action;
- no new browser permission or browser-side credential storage;
- an owner device can read a sanitized fleet inventory and a member device gets an explicit owner-permission explanation;
- device freshness/runtime-generation evidence is visible without adding another resident watcher;
- manual ChatGPT Project Handoff never writes a handoff request into the source conversation;
- missing/stale binding continuity metadata can recover from the current conversation identity;
- fallback-LLM failure leaves the source conversation unchanged;
- every visible disabled Handoff/Control Center action explains why it cannot currently run.

## 5. External finding: duplicate PLM GitLab pipelines

Observed outside the herdr-mcp repository:

- one source SHA can trigger both a normal branch `push` pipeline and a `merge_request_event` pipeline;
- both run backend/frontend dependency installation and tests;
- the project currently lacks a top-level `workflow:rules` policy that suppresses the branch pipeline when the branch already has an open merge request;
- dependency install time is also repeated because no useful project-level pip/npm cache is configured.

Recommended order in the PLM project:

1. eliminate the duplicate pipeline first using GitLab `workflow:rules` / `CI_OPEN_MERGE_REQUESTS` while preserving protected-main and MR behavior;
2. then add lockfile-keyed pip/npm caches if installation cost remains material;
3. verify the same SHA produces one intended validation pipeline before tuning cache hit rate.

Reason:

Removing an entire duplicate pipeline saves more compute, queue time, and feedback latency than optimizing dependency installation inside two redundant pipelines. This change belongs to the PLM repository and must follow that project's own requirements/CI rules; it is not a herdr-mcp v0.4.5 implementation item.

## 9. Onboarding, network resilience, Relay Pool, and macOS lifecycle

This track is driven by real v0.4.3/0.4.4 installation and network evidence. It is additive to the planner-efficiency workstreams above and preserves the same epoch-2 public MCP contract.

### Evidence from v0.4.3 user installation feedback

The following feedback came from a real first-time installation on another Mac and should be treated as product evidence, not as a one-off operator mistake.

#### PATH discovery

Observed: Herdr existed at `~/.local/bin/herdr`, but the interactive shell did not include `~/.local/bin`, producing `command not found`.

0.4.5 requirement:

- installation preflight must test the actual executable and the user's interactive-shell PATH separately;
- Agent install instructions must export `~/.local/bin` for the current process before subsequent commands;
- installation must leave a durable, idempotent shell-PATH fix when required, or clearly report why it could not safely modify shell startup configuration;
- `doctor` should report `installed_but_not_on_shell_path` rather than claiming Herdr is absent.

Do not create multiple competing PATH owners or repository-linked user CLIs.

#### macOS permission preflight

Observed: the stable TCC broker required Full Disk Access before local runtime, Herdr socket, and project access were all usable.

0.4.5 requirement:

- permission readiness must be checked near the beginning of onboarding;
- present one stable binary/broker identity to authorize;
- after the user authorizes it, verify the permission once and continue;
- avoid repeated path-by-path permission prompts;
- do not infer permission success merely because the runtime process starts.

The 0.4.4 stable helper/TCC identity work remains the implementation baseline; 0.4.5 focuses on onboarding sequencing and diagnostics.

#### Cloudflare token permissions and R2

Observed: a token could be valid yet still return 403 when reading the account `workers.dev` subdomain. The successful token included Workers Scripts Edit, Workers R2 Storage Edit, Account Settings Read, Memberships Read, and User Details Read.

The v0.4.4 baseline already treated `ARTIFACT_BUCKET` as optional in product code, but the user Wrangler template still declared an R2 bucket by default. The 0.4.5 core-install change removes that default binding and keeps R2 as an explicit opt-in capability.

0.4.5 requirement:

- split Cloudflare permissions into core and optional-R2 capabilities;
- core install must not require Workers R2 Storage permission;
- core install must not provision an R2 bucket;
- R2 artifact relay becomes an explicit optional feature;
- enabling R2 may request the additional R2 permission and Cloudflare billing/subscription step;
- preflight should identify the exact missing Cloudflare permission instead of reporting only generic deployment failure.

Core onboarding should remain usable on Workers Free + Durable Objects without requiring the user to enable R2.

#### Workstation/device identity contract mismatch

Observed: v0.4.3 installation documentation allowed a generic `WORKSTATION_ID`, while current Rust config requires an immutable `dev_` plus canonical 26-character ULID.

This is a documentation/runtime contract defect. The strict immutable `device_id` is useful and should remain; users and Agents should stop inventing workstation IDs.

0.4.5 requirement:

- one canonical device-ID generator/validator owns this identity;
- onboarding generates the device ID automatically;
- human-readable computer naming is kept in `device_name` and may use the macOS Computer Name;
- docs must never describe `WORKSTATION_ID` as a free-form hostname-derived identifier.

#### First-owner Link bootstrap

Observed: `herdr-mcp link install` represented a candidate Link path and did not by itself make a newly deployed Worker production-ready, which made first-owner setup hard to reason about.

Current `worker connect` already contains a transaction that stores the per-device credential, updates local edge config, activates the runtime/production Link, and compensates on failure. Preserve that behavior.

0.4.5 requirement:

- ordinary first-owner install should expose one production onboarding operation, not require the user to understand candidate/cutover internals;
- candidate Link commands remain maintainer/diagnostic surfaces;
- successful first-owner onboarding must end with the same production Link ownership invariants as successful `worker connect`.

#### Stale Custom Domain / OAuth issuer

Observed: an older device referenced a Custom Domain whose DNS no longer resolved. The backing `workers.dev` Worker remained reachable, but OAuth metadata still named the dead Custom Domain.

0.4.5 requirement:

- detect configured public origin, backing `workers.dev` origin, OAuth issuer, and actual health separately;
- never assume a configured Custom Domain is healthy because the Worker exists;
- provide an explicit origin migration path that validates the replacement origin before changing OAuth issuer/configuration;
- treat ChatGPT Connector origin changes as an operator-visible identity migration, not as a silent Link repair;
- pairing a new computer to an old Worker must first verify that the Worker public contract and origin are usable.

#### Older Worker missing current components

Observed: the reused Worker lacked Device Registry, private artifact bucket, and newer contract components until it was upgraded.

0.4.5 requirement:

- existing-Worker onboarding performs an Edge capability/version preflight;
- upgrade the existing Worker in place when safe instead of deploying another Worker;
- preserve existing OAuth identity and credentials unless an explicit origin migration is necessary;
- R2 remains optional even when upgrading an older Worker;
- verify Device Registry migrations before creating a pairing session.

#### `worker pair` omitted-name regression inherited from 0.4.4

The v0.4.3 failure was real: an omitted optional name was serialized as JSON null and Device Registry rejected it as `invalid_device_name`. This is no longer an open 0.4.5 implementation item. v0.4.4 fixed it in `3b29ced`, merged by PR #282 into current main `69805e5`.

0.4.5 keeps the regression gate only: bare `herdr-mcp worker pair` must continue to work without `--name`, while an explicit display name remains supported. Do not duplicate or fork the 0.4.4 implementation in an onboarding lane.

#### Second-device intent must be explicit before Worker creation

A major contributor to the incident was that the second computer's Agent was not told to reuse the existing Worker and therefore started a fresh deployment path.

0.4.5 onboarding rule:

- before provisioning a Cloudflare Worker on an unconfigured machine, determine whether this is a first fleet or an existing fleet;
- if a pairing address is supplied, always take the existing-Worker path;
- if the machine is unconfigured and no pairing address exists, ask one explicit onboarding question: first Herdr computer vs join an existing Herdr Worker;
- never deploy a second Worker merely because the new computer has no local Edge credentials;
- for an existing fleet, the preferred flow remains `worker pair` on an authorized owner computer followed by `worker connect` on the new computer.

### `workers.dev` network incident interpretation

A real A/B observation showed the same machine and router DNS resolving/reaching two hostnames for the same Cloudflare Worker differently:

- `*.workers.dev` resolved to changing addresses and TCP 443 timed out;
- the Worker Custom Domain resolved to Cloudflare addresses and `/health` returned 200 while unauthenticated `/mcp` returned the expected 401;
- after Link moved to the Custom Domain, both machines passed the real GPT -> Edge -> Link -> local filesystem/Git path.

Engineering conclusion:

- Cloudflare CDN IP changes are normal and are not themselves evidence of a DNS fault;
- the hostname-specific timeout plus same-Worker Custom Domain success is strong evidence of a `workers.dev` DNS/network-path/filtering problem in that network;
- this is enough evidence to justify transport fallback and to recommend Custom Domain for long-lived production use;
- record the RCA as high-confidence hostname/network-path failure, not as proven DNS poisoning unless stronger capture evidence exists.

Cloudflare currently recommends production Workers use a Route or Custom Domain rather than treating `workers.dev` as business-critical production naming:
<https://developers.cloudflare.com/workers/configuration/routing/workers-dev/>.

### Separate public identity from Link transport

Current configuration effectively derives one Link URL from one public Edge origin. 0.4.5 should separate three concepts:

```text
public_origin
  Stable MCP/OAuth identity used by ChatGPT.

link_upstream_origin
  The user's own Worker origin that ultimately owns /ws and WorkstationDO.
  Usually the backing workers.dev origin, even when public_origin is a Custom Domain.

link_transport
  How the workstation reaches link_upstream_origin: direct, local proxy, or shared relay.
```

Example with a Custom Domain:

```text
ChatGPT -> https://herdr.example.com/mcp

workstation -> wss://relay-a.../v1/... ->
               wss://my-worker.my-account.workers.dev/ws/<device-id>
```

OAuth remains on `https://herdr.example.com`. Relay infrastructure never becomes the OAuth issuer.

When a Custom Domain exists and is healthy from the workstation, direct Custom Domain Link remains preferred. Keeping the backing `workers.dev` route enabled provides a transport target for a relay when local `workers.dev` access is blocked.

### Automatic transport ladder

Normal users should not select a relay provider.

The Link transport policy is:

```text
1. healthy Custom Domain direct, when configured
2. workers.dev direct
3. validated explicit/system local proxy
4. sticky preferred shared relay
5. next healthy relay in the pool
```

Rules:

- actual connectivity probes decide; geography or locale never decides;
- an explicit `HERDR_LINK_PROXY` remains authoritative when it validates;
- discover existing HTTP/HTTPS/ALL_PROXY and macOS system proxy configuration;
- add SOCKS support if the current Link transport can do so without introducing a second proxy stack;
- PAC detection may produce an actionable diagnostic without implementing a full PAC interpreter;
- a successful route is sticky for the current healthy connection;
- ordinary reconnect backoff runs before provider failover;
- fail over after bounded transport-specific failures, not on every short socket drop;
- successful direct/proxy recovery may move a later connection back off shared relay;
- never replay an in-flight mutation merely because the Link transport changes.

`status`/`doctor` should expose non-secret evidence such as:

```text
MCP origin       custom-domain | workers.dev
Link upstream    workers.dev
```

### Provider-neutral Shared Relay v1

Shared Relay is a bounded WebSocket transport proxy only.

It must not implement MCP, OAuth, Device Registry, artifact storage, or workstation state.

Minimum protocol constraints:

- inbound WSS only;
- outbound target port fixed to TLS 443;
- shared public deployment may target only the exact Herdr Worker upstream authorized for that connection; a `*.workers.dev` suffix check alone is insufficient authorization;
- path must be the Herdr Link `/ws/<device-id>` shape;
- require the `herdr-link.v1` WebSocket subprotocol;
- preserve the normal Herdr upstream authentication handshake;
- upstream must successfully return WebSocket 101 before the client-side relay session is accepted and before any Link frame can be dropped or forwarded;
- do not accept an arbitrary upstream override from query parameters or generic headers; target selection must come from a bounded Herdr-specific authorization mechanism or an operator-owned exact allowlist;
- if a relay capability is used, it is separate from the Link credential, is bound to the exact upstream/path and expiry, and is never a reusable generic proxy token;
- reject IP literals, userinfo, arbitrary ports, redirects to unapproved hosts, generic CONNECT, arbitrary HTTP proxying, and non-Herdr WebSocket paths;
- bounded request headers and URL sizes;
- no frame logging, Link-credential logging, relay-capability logging, or upstream URL leakage in public error bodies;
- TLS termination at the shared relay is an explicit trust boundary and must be documented;
- provider implementations must pass the same relay conformance tests.

A self-hosted Docker relay may allow an operator-configured upstream allowlist, but the public Herdr pool remains deliberately narrow.

### Relay Pool and cloud updates

#### Bootstrap must not depend on the cloud manifest

Each herdr-mcp release embeds:

- the Relay Pool schema version;
- verification public key(s) when signed manifests are enabled;
- at least two known-good bootstrap relay endpoints when production evidence supports them.

A machine can therefore connect even when the manifest host is unavailable.

#### Remote manifest

The client may periodically fetch a small public manifest:

```json
{
  "schema": 1,
  "revision": 7,
  "generated_at": "2026-09-02T00:00:00Z",
  "expires_at": "2026-10-02T00:00:00Z",
  "relays": [
    {
      "id": "relay-deno-1",
      "url": "wss://example.deno.net/v1",
      "priority": 100,
      "failure_domain": "deno:herdr-mcp",
      "enabled": true
    },
    {
      "id": "relay-render-1",
      "url": "wss://example.onrender.com/v1",
      "priority": 90,
      "failure_domain": "provider-or-account-id",
      "enabled": true
    }
  ],
  "signature": "..."
}
```

The manifest identifies protocol endpoints, not provider-specific client code. A Deno app, Cloudflare Worker, Render service, Koyeb service, or VPS/Docker process can all join the same pool when they pass Relay v1 conformance.

#### Distribution and failure behavior

Initial canonical source should be a versioned public file in this GitHub repository or release assets. Do not deploy a separate directory Worker for the first version: the manifest is advisory because embedded relays remain available. Add an independent mirror later only when observed availability justifies the extra infrastructure.

Requirements:

- HTTPS alone is not the runtime trust model if mirrors can vary; require a real public-key signature (for example Ed25519) over canonical manifest bytes, with embedded verification key IDs; never ship an HMAC signing secret in the client;
- cache the last accepted non-expired manifest and its accepted revision/key identity;
- ignore malformed, invalidly signed, expired/not-yet-valid, unsupported-schema, unknown-key, or rollback-revision manifests;
- remote fetch failure never erases the embedded pool;
- manifest fetch is bounded and asynchronous to normal healthy Link operation;
- do not continuously poll; refresh on install/update and at a coarse TTL while the service is healthy;
- relay removal/disablement can take effect through a newer signed revision without requiring a runtime release.

```text

  -> Supabase Edge Functions
```

This mapping has several potential advantages: a relational registry/ledger is easier to inspect and migrate; Supabase gives an independent network/provider failure domain; and monthly Realtime/Function quotas avoid Cloudflare's exact daily DO rows-written reset boundary.
```text
ChatGPT / OpenAI -> user's Cloudflare Worker (OAuth / MCP / registry / WorkstationDO)
workstation      -> direct / local proxy / provider-diverse Relay -> user's Worker
```

Keep a **Supabase full-edge DR PoC** as a follow-up architecture task, not a 0.4.5 release dependency. Its acceptance criterion is semantic parity for pairing, auth, socket ownership, fencing, request settlement, reconnect/resume, and `workstation_offline` before any production traffic can switch.

A separate future **local-software -> OpenAI/API outbound relay** may reuse provider infrastructure, but it must use a separate application protocol/capability and an explicit upstream allowlist. Never broaden the current `*.workers.dev` Link Relay into a generic CONNECT/forward-proxy/VPN surface. Deno is a better first candidate for long-lived outbound WebSocket APIs than hosted Supabase Edge Functions because of Supabase's hard function lifetime.

### Relay infrastructure account boundary

Shared relay infrastructure belongs to the Herdr project/operator, not to each Herdr user.

Users do not register relay-provider accounts and do not select a relay provider.

User-owned resources remain:

```text
Cloudflare account
  -> user's Herdr Edge Worker
  -> OAuth / MCP
  -> Device Registry / WorkstationDO
  -> optional R2
```

Project-operated shared infrastructure is separate:

```text
Herdr Relay Pool
  -> Deno node A (proven protocol path)
  -> qualified independent node B, Supabase first to prototype
  -> optional low-capacity Railway / card-verified Render node
  -> optional separate Cloudflare Custom Domain or VPS/Docker node
```

A relay outage therefore does not change the user's Connector identity, and users with working direct/proxy paths do not depend on shared relay infrastructure.

### Acceptance gates

#### G1 — fresh first install

- Herdr and herdr-mcp commands work in the current shell and a new login shell;
- required macOS permission is verified with the stable broker identity;
- core Cloudflare deploy succeeds without enabling R2;
- first-owner production Link becomes healthy without exposing candidate/cutover internals;
- ChatGPT reaches the user's MCP endpoint.

#### G2 — second-device onboarding

- an Agent cannot silently create another Worker before resolving first-vs-existing fleet intent;
- bare `worker pair` works without `--name`;
- joining machine gets a canonical immutable device ID and detected human display name;
- existing Worker is upgraded in place when required;
- successful pair automatically reconciles the production Rust Link;
- no unused Worker/R2/candidate Link is left behind after a normal successful flow.

#### G3 — origin health/migration

- stale Custom Domain is detected independently of Worker health;
- `workers.dev` fallback health is tested independently;
- OAuth issuer changes only in an explicit validated migration;
- normal Link repair never silently changes the ChatGPT Connector identity.

#### G4 — local network fallback

- healthy Custom Domain direct works;
- healthy `workers.dev` direct works;
- a validated local proxy works when direct `workers.dev` is blocked;
- when both fail, Relay Pool connects the same local runtime to the same user Worker;
- changing transport does not duplicate a mutation.

#### G5 — Relay Pool resilience

- every embedded relay endpoint has passed the same conformance suite and exact-host mainland UAT when it is intended for mainland fallback;
- when two independent providers are embedded, node A failure moves a new Link attempt to node B after bounded retries;
- successful relay selection is sticky;
- equal-priority providers are assigned with deterministic per-workstation capacity weights so a fleet is distributed without per-request WebSocket churn; production weights keep Deno as the dominant long-lived provider and Supabase as a small capacity shard/full failover;
- Relay routes are not offered when a Custom Domain exists; without a Custom Domain the order remains direct `workers.dev` -> validated local proxy -> shared Relay;
- a direct Edge `/health` transport outage may defer the preflight contract probe only when a fresh signed cached Relay route exists; any reachable HTTP/protocol error, malformed contract, or epoch/hash mismatch still fails closed, and authenticated Edge hello remains the final runtime-contract fence;
- remote manifest failure does not disable embedded relays;
- invalid manifest cannot replace a valid pool;
- relay never accepts arbitrary generic proxy traffic.

#### G6 — zero-user-relay-setup

A normal Herdr user does not create a Deno/Render account, does not choose a relay provider, and does not paste a relay URL into ChatGPT. The Connector continues to use the user's own Cloudflare Worker MCP origin.

#### G7 — macOS background lifecycle hygiene

- normal runtime generation rotation still retains only the active and rollback-safe generation set; generation GC is not coupled to Background Item count;
- `herdr-mcp uninstall` leaves no Herdr-MCP-owned default-instance server, Link, updater, watchdog, or dependency-supervision LaunchAgent behind;
- uninstalling Herdr-MCP does not uninstall or disable the independent Herdr runtime;
- named-instance/UAT uninstall removes only that named instance and cannot remove the default production cohort;
- rollback/recovery backup plists are not durably stored in `~/Library/LaunchAgents`;
- `status`/`doctor` can identify owned current items versus stale/orphan residue without requiring `sfltool resetbtm` or another system-wide Background Task Management reset.

- deployed version 6 is `ACTIVE`, `/functions/v1/herdr-relay/health` returns Relay v1 health with HTTP 200 from `ap-southeast-1`;
- a real temporary enrolled device reached the same production Cloudflare Worker through Supabase, negotiated WSS 101 + `herdr-link.v1`, received `hello_ack.ok=true` from the real WorkstationDO, and was revoked after UAT;
- a 90-second soak with Herdr heartbeats stayed open for 90,133 ms and the temporary device was revoked afterward;
- the Supabase adapter reuses the Deno Relay handler instead of copying protocol/security logic, and injects only provider path normalization plus `EdgeRuntime.waitUntil()` lifecycle ownership; the focused gate is 16/16 tests plus Deno fmt/lint/check.

Hard product constraint: hosted Supabase Edge Functions have a 150-second Free-plan wall-clock limit (400 seconds on paid plans). `EdgeRuntime.waitUntil()` prevents an upgraded WebSocket from being retired merely because the request handler returned, but it does not override the hard wall-clock limit. Therefore Supabase Edge Functions are a **reconnect-capable fallback/capacity provider**, not the preferred indefinite Link transport. Pool admission still requires a forced-close/reconnect UAT close to and beyond the 150-second boundary before enabling automatic fallback for normal users.

The 2026-09-03 real-device acceptance extended that gate to 397 seconds: the enrolled `yitaidiannao` Link stayed routable across more than two 150-second Free-plan wall-clock windows, real workstation filesystem RPCs succeeded after the boundaries, a one-shot mutation nonce remained exactly once, and the production Direct Link was restored with the same runtime generation afterward. This proves reconnect-capable fallback semantics under the authenticated production path; Dashboard invocation/log charts remain delayed telemetry rather than the acceptance truth source.

Current Free-plan quota signals also matter for pool policy: 500,000 Edge Function invocations/month and 5 GB egress are organization-plan resources. A persistent Link forced to reconnect near every 150 seconds can consume function invocations much faster than an indefinite Deno connection, so selection must not treat Deno and Supabase as equivalent capacity nodes.

### macOS Background Items and the Herdr MCP Runtime Supervisor direction

#### Background and observed problem

The runtime-generation model and the macOS Background Item model are separate lifecycles.

Real-device inspection on two Macs showed that generation GC is already bounded correctly: the normal steady state retains the active generation plus the rollback-safe previous generation, with a third candidate only during an install transaction. The multiple entries visible in **System Settings -> General -> Login Items / Allow in the Background** are therefore not multiple installed runtime versions.

macOS registers the current Herdr-MCP launchd jobs independently. A normal default installation can include:

```text
dev.herdr-mcp.server
dev.herdr-mcp.link-prod
dev.herdr-mcp.herdr-supervisor
dev.herdr-mcp.auto-update
dev.herdr-mcp.health-watchdog        # optional
```

Most of these jobs execute the same stable user-visible path:

```text
~/.config/herdr-mcp/runtime/current/herdr-mcp
```

but Background Task Management still records them as separate legacy agents because they have separate launchd labels/plists.

The audit also found a separate lifecycle-hygiene class that must not be confused with the normal multi-job architecture:

- historical named UAT instances can leave their own server LaunchAgents/config roots behind when teardown is incomplete;
- rollback/cutover backup files have historically been left under `~/Library/LaunchAgents` even though they are not active jobs;
- the current product-level uninstall path can remove Herdr-MCP while missing the Herdr-MCP-owned dependency-supervision LaunchAgent, leaving a job that points at a removed `runtime/current` path.

These are real cleanup bugs. They should be fixed independently of any future background-topology consolidation.

#### Naming boundary

Use **Herdr MCP Runtime Supervisor** for the proposed Herdr-MCP product component.

Do not call the new component `herdr-supervisor`. The existing `herdr_supervisor` implementation is specifically a dependency manager for the separate Herdr runtime and the name is easy to misread as the top-level Herdr-MCP process manager. If the unified architecture is implemented later, rename or demote that responsibility conceptually to **Herdr dependency management** under the Runtime Supervisor.

The long-term launchd label should be explicit, for example:

```text
dev.herdr-mcp.runtime-supervisor
```

This label is a Herdr-MCP product identity. It must not claim ownership of the independent `dev.herdr.*` product lifecycle.

#### Architecture review outcome

Two independent local read-only architecture reviews (Droid and Grok) were run against the current service manager, Link lifecycle, updater, generation fencing, watchdog, dependency supervisor, and product uninstall code on 2026-09-02.

Both reviews rejected a direct 0.4.5 cutover from the current multi-LaunchAgent topology to one ordinary parent process.

The converged findings were:

1. **Independent launchd jobs are not required by macOS, but they currently provide real fault isolation.** A Link crash does not take down port 8772; a local MCP failure does not destroy the WSS; Herdr dependency recovery has its own backoff; updater scheduling does not depend on the MCP event loop.
2. **Moving the parent to `runtime/current` is unsafe.** The top-level process that owns restart/adoption/rollback must not disappear merely because the active runtime generation is corrupt or being replaced.
3. **The current independent auto-update LaunchAgent is not, by itself, a rescue path for a corrupt `runtime/current`.** Its ProgramArguments also point to `runtime/current/herdr-mcp`. The durable safety comes from staged candidate verification, the detached updater worker, mutation fencing, health gates, and rollback. A future unified design can move the periodic update trigger into the Runtime Supervisor, but the apply worker must remain detached and rollback-safe.
4. **A single LaunchAgent must not mean a single monolithic event loop.** Server, Link, and Herdr dependency execution need separate failure domains/processes. Health/update scheduling can be lightweight internal timers or one-shot children.
5. **Parent crash behavior is the hardest gate.** A restarted Runtime Supervisor must adopt already-running healthy children instead of blindly respawning duplicates. Server/Herdr have observable port/socket evidence; an existing Link WSS cannot simply be recreated or "adopted" by another Link process without dropping the connection, so Link child ownership/liveness needs an explicit durable design.
6. **Current generation fencing and rollback were designed around existing owners.** A unified parent introduces a new cross-component state owner; it must not bypass `RuntimeGenerationManager`, Link request leases, service mutation locks, product uninstall fences, or the existing rollback ledger.

Conclusion for this release: **do not make single-LaunchAgent production cutover a 0.4.5 acceptance criterion.** Fix the lifecycle residue now, freeze the safe target architecture, and migrate only through independently reversible stages.

#### Long-term target: one launchd identity, multiple isolated components

The target remains worthwhile if the prerequisites are met:

```text
macOS launchd
    |
    `-- dev.herdr-mcp.runtime-supervisor
          |
          |-- local MCP server process        (8772)
          |-- production Link process         (persistent WSS)
          |-- Herdr dependency process        (separate Herdr product)
          |-- health/update timer tasks
          `-- detached staged update worker   (only during apply)
```

The design principle is:

> one launchd identity, multiple supervised failure domains

The Runtime Supervisor is orchestration infrastructure, not another application runtime. It must not implement MCP tools, Git/filesystem work, OAuth, Cloudflare routing, or user credential access.

#### Stable bootstrap requirement

Do not point the eventual sole LaunchAgent directly at the rotating runtime generation as the long-lived supervisor authority.

Preferred shape:

```text
~/Library/LaunchAgents/dev.herdr-mcp.runtime-supervisor.plist
        |
        `-- ~/.config/herdr-mcp/runtime-supervisor/herdr-mcp-runtime-supervisor
                |
                `-- resolves and validates runtime/current
```

The bootstrap should be a minimal, stable, separately versioned compatibility boundary, similar in lifecycle philosophy to the stable TCC broker and credential helper but with a different responsibility.

Requirements:

- ordinary runtime generation updates do not replace the bootstrap bytes merely because application code changed;
- bootstrap replacement is a rare explicit compatibility migration with rollback evidence;
- the bootstrap does not read protected project files and must not become a replacement TCC/Keychain authority;
- it validates the active/rollback runtime-generation state before launching children;
- if `runtime/current` is missing or invalid, it can select the recorded rollback-safe generation or invoke a verified staged recovery path rather than executing an untrusted/missing current binary;
- bootstrap/runtime protocol compatibility is explicit and versioned.

A stable pathname alone is not enough. The purpose of this boundary is to keep the process that can recover the runtime independent from the runtime generation it may need to recover.

#### Child-process and failure-domain rules

Server, Link, and Herdr dependency execution should remain independent OS processes even under one LaunchAgent identity.

Required semantics:

- each child has an explicit durable identity: component, PID/process identity, runtime generation, start time, and expected endpoint/socket evidence;
- component restart backoff is independent; Link reconnect failures cannot starve Herdr recovery or update timers;
- killing/restarting the local MCP server must not intentionally tear down a healthy Link;
- killing/restarting Link must not take port 8772 down;
- Herdr dependency failure must not restart the local MCP server or Link unless a proven dependency requires it;
- supervisor restart must first perform **adopt-not-respawn** reconciliation and refuse duplicate ownership when an existing healthy child can be proven;
- exact macOS launchd descendant/process-group behavior must be proven in UAT before relying on children surviving a supervisor restart; do not assume process-group isolation from shell behavior alone;
- explicit `service stop` / product uninstall must still stop the complete owned cohort and must not leave orphan children that a later supervisor incorrectly adopts.

The implementation must preserve existing child-process orphan/reaper protections and strengthen them where the new parent/child topology changes ownership.

#### Update and rollback semantics

The periodic auto-update trigger does not need its own permanent LaunchAgent after the Runtime Supervisor design is proven. It may become an independent timer/task inside the stable supervisor because the current scheduler already launches the same rotating runtime path.

However, update **apply** must remain isolated:

1. discover/download candidate;
2. verify release trust and candidate health;
3. start a detached staged worker from verified candidate bytes;
4. acquire the existing service/update mutation fences;
5. switch generation using the recorded runtime-generation transaction;
6. roll children to the new generation without accepting mixed-generation request ownership;
7. preserve Link continuity where the existing generation manager allows it;
8. health-gate the replacement;
9. roll back to the recorded previous generation on failure;
10. never let a stale timer or detached worker resurrect a product after the product-uninstall fence is armed.

The Runtime Supervisor must consume the existing generation authority; it must not create a second generation ledger.

#### Migration stages

Do not remove all current LaunchAgents in one transaction.

##### Stage A — 0.4.5 lifecycle hygiene

- fix product uninstall coverage;
- fix named-instance/UAT teardown;
- move backup artifacts out of `~/Library/LaunchAgents`;
- add residue diagnostics;
- keep current server/Link/updater/Herdr-dependency launchd ownership unchanged.

This is the only stage required for 0.4.5 release acceptance.

##### Stage B — stable Runtime Supervisor candidate, no ownership cutover

- implement the minimal stable bootstrap and a versioned supervisor/runtime protocol;
- run it in diagnostic/shadow mode without binding 8772, opening the production WSS, or owning Herdr;
- prove it can classify/adopt current child identities and active/rollback generations without mutation;
- retain all current LaunchAgents as production authority and preserve instant rollback by uninstalling the candidate.

Stage B may be developed during the 0.4.5 cycle only if it does not become a release blocker or production owner.

##### Stage C — limited canary ownership

- move one low-risk component at a time under Runtime Supervisor ownership;
- keep production Link separately launchd-owned until parent-crash/adoption/generation-handoff evidence is complete;
- after every component move, preserve a bounded transaction that restores its old plist/label and loaded state.

##### Stage D — Link ownership migration

Move production Link only after all of these are demonstrated:

- supervisor crash/restart does not create a duplicate WSS owner;
- healthy Link child remains alive or reconnects within an explicitly accepted outage budget;
- Link generation/request leases still come from the existing generation manager;
- service/server rollback does not accidentally restart or supersede the wrong Link generation;
- `workstation_offline` recovery remains bounded and no worse than the current independent-LaunchAgent path.

##### Stage E — single-background-identity cutover

Only after server, Link, Herdr dependency, timer, update, uninstall, and rollback gates are green:

- retire the old default-instance LaunchAgent plists transactionally;
- leave only `dev.herdr-mcp.runtime-supervisor` as the default Herdr-MCP background identity;
- preserve named-instance isolation for maintainer/UAT cases rather than folding test instances into the production supervisor;
- verify macOS Background Task Management shows the intended single default Herdr-MCP item without system-wide BTM reset commands.

#### Future Runtime Supervisor acceptance gates

These gates are not 0.4.5 release blockers; they gate a later production ownership cutover.

1. **Single identity:** exactly one default Herdr-MCP LaunchAgent is registered after migration; the independent Herdr product remains separately owned.
2. **Server isolation:** kill the server child; 8772 recovers while the existing production Link remains healthy.
3. **Link isolation:** kill the Link child; WSS reconnects while 8772 stays healthy and no mutation is replayed.
4. **Herdr isolation:** kill the Herdr dependency child; bounded dependency recovery occurs without restarting healthy MCP/Link children.
5. **Supervisor crash:** kill the Runtime Supervisor; launchd restarts it and it adopts/proves surviving children or performs bounded restart without duplicate port/WSS/socket owners.
6. **Generation switch:** update from generation A to B; every accepted request has one generation lease, `runtime/current`/runtime-control/loaded children converge, and Link continuity meets the accepted budget.
7. **Rollback:** force B health failure; A returns without rebuilding A and without destroying a healthy independent Herdr child.
8. **Damaged current:** make `runtime/current` missing/invalid in an isolated UAT; stable bootstrap can reach a recorded rollback-safe runtime or verified staged recovery without depending on the broken current binary.
9. **Stop/uninstall:** explicit stop leaves no child auto-resurrecting; product uninstall removes the complete Herdr-MCP cohort while preserving the separate Herdr product and the uninstall resurrection fence.
10. **Named instances:** named UAT instances remain isolated and do not share the default Runtime Supervisor's child ownership.

Until these gates pass on real macOS launchd, keep the current independent production ownership rather than trading visible Background Item count for a larger correlated failure domain.
