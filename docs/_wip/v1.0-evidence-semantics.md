# Herdr-MCP 1.0 — Evidence Semantics Addendum

Status: cross-cutting implementation addendum for later 1.0 integration.

Baseline: `main` at `6113046` (Alpha 4 ChatGPT adapter spec merged).

This addendum borrows evidence-contract ideas from `xcjy8bao/baoer_signal_grep` without copying its implementation. The reference project is AGPL-3.0-only; Herdr implements the concepts independently inside the existing Rust/Extension architecture.

## Goal

Make Herdr's existing Work Memory evidence materially safer and cheaper for planners to consume across long conversations, provider handoff, and multi-device work.

The concrete gains are:

1. planners can distinguish complete evidence from partial evidence;
2. planners can distinguish verified source state from stale/unverified source state;
3. pagination continues over the same accepted evidence boundary instead of silently observing newly appended evidence;
4. automatic Work Memory projection shrinks under conversation pressure without changing authoritative checkpoint/evidence semantics;
5. statements such as "test candidate found", "test executed", "postcondition observed", and "source verified" remain separate facts.

## Non-goals

This addendum does not:

- add a code-search engine, AST parser, impact analyzer, import navigator, or test-discovery subsystem to Herdr core;
- copy `baoer_signal_grep` snapshots, cursor store, parser workers, or source-inspection implementation;
- add a new database, daemon, resident timer, or fleet-wide raw-evidence replication plane;
- change public Edge epoch 3 / 19 actions or workstation Runtime Execution epoch 2 / 18 tools;
- change Alpha 4's minimum ChatGPT adapter vertical or pull beta.1/beta.2 work into Alpha 4;
- make provider-native Memory authoritative;
- infer task success from evidence presence.

## Existing 1.0 primitives to reuse

Alpha 2 already provides the required authority and storage primitives:

- append-only raw turns and local evidence in `state.db`;
- verified rolling checkpoints and checkpoint revision/CAS;
- `through_message_id` / `through_evidence_id` checkpoint boundaries;
- FTS5 search over the same local StateStore;
- strict portable Git evidence refs containing repo identity, full commit object id, repo-relative path, line range, and evidence digest;
- bounded `resume` views while retaining the complete raw history locally.

Alpha 3/4 already provide generation fencing and explicit postcondition semantics for browser state. The Extension already owns conversation-pressure estimation. This addendum composes those mechanisms; it must not duplicate them.

## 1. Dimension-specific evidence quality

Do not introduce one generic `quality = good|bad` flag. Evidence quality is multi-dimensional.

Every Work Memory query/resume projection that returns a bounded set should expose a compact coverage object derived from facts the kernel actually knows:

```json
{
  "coverage": {
    "boundary": {
      "checkpoint_revision": 17,
      "through_evidence_id": "ev_..."
    },
    "retention": "complete",
    "source_verification": "verified",
    "limitations": []
  }
}
```

The exact JSON field names belong to implementation review, but the semantics are normative:

### Retention / result completeness

`retention` describes whether the requested evidence result set is completely represented by the retained/queryable result, independently from how much text is displayed in this response.

Minimum states:

```text
complete
partial
```

A response-byte/token display limit must never silently change `complete` into an implied complete answer. Display truncation and retained-result incompleteness are different conditions and should have different limitation reason codes.

### Source verification

Source verification applies only where the evidence claims a source revision. Minimum states:

```text
verified
mixed
unverified
stale
not_applicable
```

A portable Git ref is `verified` only when its repo identity, full object id/path/range and evidence digest can be checked against the referenced source. Current-worktree bytes must not be combined with an older evidence revision and presented as verified.

### Execution / validation facts stay typed

Do not fold execution facts into source verification or result completeness. Examples:

```text
test candidate discovered != test executed
test executed != test passed
browser message accepted != generation settled
postcondition observed != whole work-chain task complete
same spelling occurrence != semantic binding
```

Use the evidence kind's existing typed fields/status when they exist. Add only the minimum field required when an existing evidence kind cannot express these distinctions.

### Limitations

`limitations` is a bounded list of stable reason codes, not prose-only warnings. Examples that may be needed after implementation review:

```text
response_budget_exhausted
result_retention_partial
source_revision_unverified
source_revision_stale
source_unavailable
```

Do not create speculative codes for states Herdr cannot currently observe.

## 2. Stable evidence cursors over an append-only boundary

Work Memory search pagination should continue over one accepted evidence boundary. Appending new evidence must not make page 2 refer to a different logical result set than page 1.

Reuse Alpha 2's append-only ordering and checkpoint/evidence boundary. Do not add a second durable snapshot store merely for pagination.

A cursor should be opaque to callers but logically bind at least:

```text
project_ref
repo_id
work_chain_id
checkpoint_revision or equivalent accepted boundary
through_evidence_id
query/filter digest
page offset / continuation position
cursor kind
```

Required behavior:

1. first query fixes the evidence boundary used for the result;
2. later evidence appended after that boundary is excluded from cursor continuation;
3. replaying the same valid cursor is idempotent;
4. a cursor cannot silently change query/filter/path selection;
5. malformed, expired, conflicting, unavailable, or later-pruned source state fails explicitly;
6. cursor failure never degrades into a fresh search;
7. cursor continuation does not count as a new semantic query in passive/session accounting, if such accounting exists.

Alpha 2 currently retains all raw evidence, so initial implementation should not invent prune/reconciliation machinery. Future retention/prune work must define an explicit cursor failure when the referenced boundary no longer exists.

## 3. Context-adaptive Work Memory projection

Herdr already estimates ChatGPT conversation pressure in the Extension. Reuse that signal; do not build a second tokenizer or independent pressure model in Work Memory.

Map conversation pressure to a projection tier only:

```text
healthy / context_warning
  -> full

handoff_prepare / rollover_recommended
  -> tight

rollover_required / high_risk
  -> critical
```

The exact limits should be measured during Alpha 5 dual-provider UAT rather than frozen prematurely.

Projection tier may reduce only automatic/bounded presentation such as:

- recent raw turn count/bytes;
- recent evidence preview count/bytes;
- automatic search preview text.

Projection tier must not alter:

- the verified checkpoint body/digest/revision;
- accepted requirements/decisions/task state;
- portable evidence refs;
- evidence quality/coverage metadata;
- explicit evidence inspection requested by the planner;
- Fleet authority/lease state;
- durable raw retention.

If pressure information is absent or untrusted, preserve the current default behavior.

## 4. Evidence inspection / resolution

Do not add a new public tool for evidence inspection.

For 1.0, first prove the workflow using existing private Work Memory plus Git/fs primitives:

1. resolve a portable Git evidence ref;
2. read the exact referenced commit/path/range;
3. verify its digest;
4. return explicit stale/unavailable/unverified state on mismatch;
5. never substitute current worktree content for a fixed Git object.

Only add a private `work_memory.evidence.inspect`/`resolve` helper if Alpha 5 UAT shows repeated caller boilerplate or correctness failures that cannot be prevented cheaply with the existing primitives. A helper must remain an adapter over the same StateStore/Git authority, not a new evidence store.

## 5. Stage placement

### Alpha 4

No scope change. Keep the current minimum ChatGPT vertical and its immediate `not_applied / applied / uncertain / rejected / browser_offline / resource_unavailable / stopped` semantics.

### Alpha 5

Before declaring Planner Handoff and Cross-WebChat Delegation production-complete, integrate and UAT the minimum pieces that materially affect cross-provider continuation:

- dimension-specific evidence coverage in Work Memory responses;
- stable evidence cursor/boundary behavior;
- context-adaptive projection using the existing conversation-pressure signal when available.

The Gemini adapter itself remains provider-specific; evidence semantics remain provider-neutral.

### Beta 1

Integrate the same evidence vocabulary with browser late settlement/recovery:

- an `uncertain` delivery later settling to applied is appended as a new fact/evidence transition;
- stale/reloaded browser observations do not rewrite earlier evidence;
- browser settlement state, source-verification state, and Work Memory result completeness remain separate dimensions.

### Beta 2 / RC

No extra scheduling/reservation feature is created by this addendum. Beta 2 may consume the same evidence semantics for multi-device/account failover. RC should include migration/compatibility checks if an implementation changes any private response schema or StateStore schema.

## 6. Minimum acceptance scenarios

### A. Stable continuation while evidence grows

1. Work Memory contains evidence E1-E100.
2. Query returns page 1 and a cursor fixed through E100.
3. E101-E120 are appended.
4. Cursor page 2 continues the E1-E100 result only.
5. A fresh query may see E101-E120.

PASS requires no silent rerun and no duplicate/missing evidence caused by the append.

### B. Partial result cannot masquerade as complete

Force the result/response budget so only part of a large evidence set can be retained or displayed. PASS requires explicit coverage/limitation state that distinguishes retained-result partiality from display truncation.

### C. Stale source cannot masquerade as verified

Record source evidence against a fixed Git object, mutate the worktree, then inspect/resume. PASS requires the fixed-object evidence to remain bound to its original object; current bytes may be reported separately but never merged as verified source evidence.

### D. Test evidence remains truthful

Discover a test-related file without executing it. PASS requires the evidence to describe discovery only. Execute a relevant test afterward and append a separate execution result. No earlier evidence is rewritten into "passed".

### E. Context pressure changes presentation only

Run the same Work Memory resume/search under full and critical projection tiers. PASS requires smaller automatic payload under critical pressure while checkpoint revision/digest, portable refs, evidence boundary and coverage semantics remain identical.

### F. ChatGPT -> Gemini handoff

ChatGPT forms a verified checkpoint and bounded evidence view; Gemini resumes the same `work_chain_id`. PASS requires Gemini to recover the same checkpoint authority and be able to continue the same frozen evidence view or start an explicitly fresh query. Provider-native Memory is not used as authority.

## 7. Validation boundary

Prefer existing tests. Add tests only for behavior introduced by implementation:

- one stable-cursor append-growth path;
- one key failure path such as conflicting cursor options or stale source verification, only if existing tests cannot detect the regression;
- one projection test proving pressure changes presentation without changing authority, only if this behavior is implemented in that change.

Do not add a new test framework, generic snapshot suite, parser matrix, or repository-wide evidence harness.

## 8. Integration rule

This branch is deliberately documentation-only. It defines the minimum semantics for later implementation on the active 1.0 feature line. Merge/cherry-pick it only after the mainline Agent reconciles it with the then-current Alpha 5/Beta 1 spec and confirms that no already-merged contract conflicts with these rules.
