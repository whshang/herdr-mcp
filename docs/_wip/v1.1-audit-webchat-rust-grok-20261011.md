# v1.1 WebChat correctness and security audit (Grok, read-only)

Date: 2026-10-11
Scope: `feat/v11-t9e-audit-grok-20261011` @ `c44dc7cb` (same tree as `feat/v11-opencli-browser-controls-20261008`).
Surfaces: Rust MCP WebChat in `crates/herdr-mcp/src/mcp.rs` and the `state_store.rs` reservation/settlement functions it calls; ChatGPT activation in `extension/content/wake.js` and `extension/content/injector/chatgpt.js`. `extension/background.js` is cited only where it decides whether the content-script fallback actually runs.
Method: static review. No code changes, no browser, no ChatGPT, no Herdr tools, no runtime install. Tests were not executed.

Severity is about delivery: a wrong or duplicate provider mutation outranks a stuck retry.

## Findings

### 1. Critical — any navigation, or a missed before-snapshot, binds whatever user message the landed page returns

`submitBrowserActuationOnce` treats every URL change as provider acceptance, and the post-submit poll records the landed conversation's latest user-message id without comparing its text to the message that was just submitted.

Evidence:

- `extension/content/wake.js:1058-1067`. `submitWasAccepted` returns true when `location.href !== baseline.href`, before any text check. The text check that follows is only a 120-character bidirectional `includes` (finding 2).
- `extension/content/wake.js:1080-1116`. The MCP create/dispatch path uses this predicate once. A false true is returned as `{ ok: true, attempted: true }`.
- `extension/content/wake.js:2249-2251`. `expectedConvKey` is checked only before typing. It is not checked again after the URL changes.
- `extension/content/wake.js:2437-2453` and `2476-2511`. The before-snapshot is allowed to fail (`{ ok: false }`). `serverAdvanced` is then `afterServer.userMessageId !== beforeServer?.userMessageId`. A missing before-id makes the existing latest id look new. For session create, that id is stored with no comparison to `afterServer.userText` (the snapshot already carries `userText` at `wake.js:3751` and `3776`).
- `extension/content/wake.js:2555-2563`. `generation_status_observed` is set when the snapshot's current node role is `"user"` or `"assistant"`. An idle existing conversation satisfies the dispatch generation fence.
- `extension/content/wake.js:2512-2522`. Session create then calls `registerCurrentConversation` for whatever conversation is now open and sets `stable_resource_ref_observed`.
- `crates/herdr-mcp/src/mcp.rs:2363-2376` and `2406-2411`. `SessionCreate` / `DispatchSubmit` become `Applied` once that ref is present, the generation flags are set, and the pre-submit app readback matches. They do not hash the provider text on this path.

Impact: a create that starts on a Project home (where a URL change is the designed success signal) and lands on an already-open conversation materializes that conversation as the new session and records someone else's user-message id. A dispatch whose before-snapshot times out or returns 429 can be marked `Applied` against the previous turn. The idempotency key is then consumed, so the intended message is not retried. Work-memory settlement follows the foreign id.

Suggested fix: require the provider user text (raw or the existing whitespace-canonical form) to equal the submitted message before `accepted_user_message_ref` is set. Treat a missing before-snapshot as "no server proof", not as advancement. After submit, fail closed unless `location` is still the expected conversation, or, for create, unless the new `/c/<id>` message digest matches. Do not set `generation_status_observed` from the mere presence of a user or assistant node.

Suggested test: `user create stays not applied | Given a Project-home tab whose URL changes to an existing conversation whose latest user text differs | When session.create submits | Then delivery is not Applied and the existing session_ref is not materialized`. Pair it with `user dispatch stays uncertain | Given the before-snapshot fails and the latest user id is unchanged | When dispatch.submit acks | Then the previous user-message id is not recorded`.

### 2. High — a 120-character overlap accepts a different new user turn

The DOM acceptance checks match prefixes in either direction. A short new turn whose text occurs inside the outgoing message is enough.

Evidence:

- `extension/content/wake.js:1060-1066`. A new user node is accepted when `latestText.includes(sentText.slice(0, 120))` or `sentText.includes(latestText.slice(0, 120))`.
- `extension/content/wake.js:1754-1769`. `exactDomAcceptedUserMessageRef` uses the same 120-character test and then returns that node id. Dispatch uses this id whenever the server snapshot did not advance (`wake.js:2501-2506`).
- `extension/content/wake.js:2488-2497`. Session create also treats `afterDom.count > beforeDom.count`, or any new message id, as `accepted_message_observed` / `message_baseline_advanced` with no text equality.

Impact: the user (or another automation) sending "ok", "herdr", or any short string that appears in the prepared prompt produces `{ ok: true }` from the submit-once path. Dispatch then persists that other turn's id. Create can report the baseline advanced even though the prepared message was not the new turn. Combined with finding 1, the runtime settles `Applied`.

Suggested fix: compare whitespace-canonical full text, or the canonical body after stripping only the required-app tokens, for equality. Reject a candidate whose id changed but whose text does not match. Do not treat a count increase alone as acceptance.

Suggested test: `user dispatch does not adopt a short overlapping turn | Given the composer holds a long prompt containing "ok" and a new user node "ok" appears without the prompt | When dispatch.submit waits for ack | Then the result is uncertain or not-applied and accepted_user_message_ref is absent`.

### 3. High — handoff, queue, recovery, and generic wake submit up to three times

MCP create and dispatch call `submitBrowserActuationOnce` (one Enter, no click retry). The other WebChat activation entry points call `submit`, which clicks Send and also dispatches Enter, then repeats that pair up to three times.

Evidence:

- `extension/content/wake.js:1162-1197`. Each attempt clicks a ready Send button, waits 4s, then sends Enter, waits 3s, and loops. A slow but successful first click still falls through to Enter and to the next attempt.
- `extension/content/wake.js:1348-1355` and `1401-1407`. `browserActuation: true` is the only path that uses submit-once.
- Callers that omit it: handoff prompt `wake.js:3008-3013`, handoff seed `wake.js:3042-3047`, queued insert `wake.js:3137-3142`, generic `h2w_wake` `wake.js:3164`, explicit-error continue `wake.js:4719-4724`, recovery probe `wake.js:4907-4912`, stale-view activation `wake.js:4996-5001`.
- ChatGPT's adapter sets `jsonBridge: false` (`extension/content/injector/chatgpt.js:17`), so the handoff `sendRaw` branch at `wake.js:1329-1333` does not apply and handoff reaches `submit()`.

Impact: a handoff or recovery prompt that ChatGPT accepts on the first click, but whose new user node is not visible within 4 seconds, is submitted again. That is a second user turn and a second model run. The 8 second dedupe at `wake.js:1301-1303` does not cover a retry inside the same `submit()` loop, and it does not cover a different template.

Suggested fix: route handoff, queue delivery, and recovery through the same single-attempt helper as MCP actuation. Return uncertain when the ack window expires after a click or Enter, and do not click again for that attempt.

Suggested test: `user handoff is submitted once | Given the first Send click appends the handoff turn only after 5 seconds | When h2w_handoff_prompt runs | Then Send/Enter is issued once and the second turn is absent`.

### 4. High — the required-app gate is not a property of the accepted provider message, and the store fallback can click the wrong control

Rust requires the pre-submit composer readback to equal the requested app list. Late acceptance then promotes an uncertain create from text digests alone. The production extension never uses trusted keystrokes, so app selection is a synthetic `@keyword` insert plus a page-wide click.

Evidence:

- `extension/background.js:10126-10128`. A store build (`manifest.update_url` or no `chrome.debugger`) answers `h2w_type_trusted_mention` with `trusted-input-unavailable`. `wake.js:952-980` then inserts `@` and the keyword through `insertMainWorld`.
- `extension/content/injector/chatgpt.js:189-203`. `getComposerAppSuggestionButtons` collects every visible enabled `button` / `[role=button]` outside the composer whose text equals the keyword. The baseline subtraction in `wake.js:949-990` only drops buttons that already existed. Exactly one new button is clicked (`wake.js:998-1022`).
- `extension/content/injector/chatgpt.js:235-240`. Menu candidates match when `text.includes(wanted)`, so one loosely labeled option is enough.
- `extension/content/wake.js:1029-1033` and `867-884`. Failure clears the composer only when the leftover text is exactly `@app` or `app`. A wrong pill (text without pills is empty) is left in place. `clearAutomationDraft` (`wake.js:895-904`) also ignores pills.
- `extension/content/wake.js:2415-2427`. `required_apps_readback` is `getSelectedComposerApps()` captured before `performWake`. It is not read back from the accepted provider message.
- `extension/content/wake.js:2340-2344`. ChatGPT unions the learned Herdr keyword with `params.required_apps`. The Rust compare is exact (`mcp.rs:2328-2332` and `2396-2404`). Extra pills fail the gate and the delivery stays `Uncertain` even though the message was sent.
- `crates/herdr-mcp/src/mcp.rs:3414-3432`. Late acceptance promotes when any of the full, body, or whitespace-canonical digests equals `sha256(message.trim())` or the canonical message. Body is the stored text with leading required-app tokens removed (`wake.js:2183-2205`). There is no check that the provider message carried an app mention. A sole visible user message of `herdr` + the create text matches a create whose message omitted that prefix.
- `crates/herdr-mcp/src/mcp.rs:2325-2326`. An empty `required_apps` list skips the readback check entirely, so a learned app attached only by the extension is invisible to the gate.

Impact: a newly appeared control labeled with the app keyword (a toast, a sidebar row, a second product named as a substring) receives `pointerdown` through `click`. The wrong pill can remain for the next turn. An uncertain create is then marked `Applied` when the only visible user text matches after app-token stripping, including a plain-text send that never attached the Herdr app. The initial `Applied` path has the same hole: the app list is composer state from before Enter, not evidence on the accepted message.

Suggested fix: click only a suggestion row inside the composer-owned popup (`aria-controls` / the popper that appeared for this search), and require an exact keyword attribute plus a non-empty `app-mention-path`. After submit, read app identity from the accepted user message (the same metadata late readback already walks) and pass that list as `required_apps_readback`. Run that check inside `browser_session_create_late_acceptance_readback` before promotion. On selection failure, remove unexpected pills, not only `@app` text. Do not union learned apps into the requested set; if the caller omitted apps, report the learned selection explicitly so Rust can require it.

Suggested test: `user create does not promote a plain-text prefix | Given required_apps is ["herdr"], the uncertain create message is "ship the patch", and the only visible user text is "herdr ship the patch" with no app-mention metadata | When the same idempotency key is replayed | Then delivery stays uncertain`. And `user app search does not click a foreign button | Given one new button outside the composer is labeled "herdr" and no mention popup exists | When ensureRequiredComposerApps("herdr") runs | Then that button is not clicked and the result is required-app-not-found`.

### 5. High — a current-turn archive miss archives the previously bound conversation

When `current_user_message` matches no stored source turn, archive resolution falls back to the opaque caller binding and does not check the message.

Evidence:

- `crates/herdr-mcp/src/mcp.rs:4206-4239`. On `browser_current_turn_not_found`, a ChatGPT caller with a resolved `browser_caller_sessions` row gets that `session_ref` and its `observation_generation`. The message hash is not compared to the bound session.
- `crates/herdr-mcp/src/mcp.rs:4257-4280`. The matching path rebinds only when the hash hits a stored turn and the grant covers that account. The miss path skips that proof. The in-file test at `mcp.rs:10839-10889` documents that one opaque Connector session is reused across conversations and must follow the latest exact turn; the miss path does the opposite and keeps the old target.
- `crates/herdr-mcp/src/mcp.rs:5351-5409`. A direct `session.archive` (after this normalization, or when the caller already passed `session_ref`) validates `idempotency_key` (`mcp.rs:5525-5527`) and then actuates on every call. The key is not reserved, unlike dispatch (`mcp.rs:2564-2576`, `state_store.rs:4694-4735`).
- `extension/content/wake.js:1957-2011`. If the archive GET is not ok, the menu/PATCH still runs. The PATCH response status is ignored, so HTTP 429 never becomes `rate_limited`. The function returns `uncertain` after 6 seconds with `delivered: true`.

Impact: a model that has moved to a new ChatGPT conversation, whose latest user text was not observed as a source turn, archives the previous conversation that still holds the opaque session binding. A same-key retry of a direct archive whose readback was rate-limited clicks or PATCHes again. Archive-status itself does map 429 to `rate_limited` and stays read-only (`mcp.rs:5286-5321`); create/dispatch late readback only stores `readback_fetch_http_429` and stays uncertain (`mcp.rs:3386-3387`), which is safe, but the live submit path still treats a 429 before-snapshot as missing evidence (finding 1).

Suggested fix: on a source-turn miss, return `browser_current_turn_not_found` even when a caller binding exists. Reserve direct archive on the idempotency digest the same way dispatch does, and do not actuate an existing uncertain/applied row. Surface PATCH/GET `http-429` as `rate_limited` with `retry_after_s`, and do not click or PATCH until a later attempt is explicitly outside that window.

Suggested test: `user archive does not follow a stale binding | Given caller session S is bound to conversation A and current_user_message matches no stored turn | When session.archive runs | Then the result is browser_current_turn_not_found and A is not actuated`. And `user archive retry does not patch twice | Given the first archive GET returns 429 after a PATCH was not acknowledged | When the same idempotency key is repeated | Then the provider PATCH/click count stays 1 and the code is rate_limited`.

### 6. High — source-anchored create and handoff pick the newest session for one URL

The strict locator resolver refuses two sessions that share a canonical URL. Source routing uses the newest observation instead.

Evidence:

- `crates/herdr-mcp/src/state_store.rs:3365-3393`. `browser_session_ref_for_canonical_url` returns `browser_canonical_url_ambiguous` when more than one session resource shares the URL.
- `crates/herdr-mcp/src/state_store.rs:3397-3444`. `browser_latest_session_ref_for_canonical_url` returns the newest `observed_at` when the timestamps differ.
- `crates/herdr-mcp/src/mcp.rs:3904-3956`. `browser_source_route` uses the newest-wins lookup, then copies that session's endpoint, account, space, and generation.
- `crates/herdr-mcp/src/mcp.rs:3807` and `4064-4083`. Both `browser_session.create` with `source_url` and `browser_handoff.prepare` call `browser_source_route`. Automatic delivery is a create against that route (`mcp.rs:4152-4162`).

Impact: two observations of the same `https://chatgpt.com/c/<id>` (two profiles, or two accounts that both registered the URL) send the continuation, and the handoff create, to whichever account was observed later. The grant check then authorizes that other account if the caller holds its grant. This is the wrong-account case the strict resolver was written to prevent.

Suggested fix: use the strict unique-session resolver for create and handoff. If the caller also passed an account or endpoint, require it to equal the resolved route before returning `automatic_delivery`.

Suggested test: `user source create fails closed on two sessions | Given two chatgpt sessions share one canonical URL and the later observation is a different account | When session.create is called with that source_url | Then the code is browser_canonical_url_ambiguous and no reservation is inserted`.

### 7. Medium — handoff preparation does not bind a stable idempotency key

`browser_handoff_prepare` builds a stable `handoff_id` and then omits it from the mutation packets.

Evidence:

- `crates/herdr-mcp/src/mcp.rs:4117-4123`. `handoff_id` is `hh_` plus a digest of continuity, source URL, objective, and work chain, unless the caller passed one.
- `crates/herdr-mcp/src/mcp.rs:4152-4172`. `automatic_delivery.params` is `source_url`, `message`, and `work_chain_id`. `existing_session_delivery.params` is only `message`. Neither includes `idempotency_key`, `expected_generation`, or `session_ref`.
- `crates/herdr-mcp/src/mcp.rs:5510-5552`. `session.create` and `dispatch.submit` reject a body that lacks `idempotency_key`. A caller that adds a fresh key per attempt passes validation and reserves a second mutation. Dispatch correctly conflicts when the same key is reused with a different digest (`state_store.rs:4715-4729`); the packet never supplies that key.

Impact: two prepare-then-send attempts for one continuity create two ChatGPT conversations, or append the handoff twice. The Copy Prompt is byte-identical; the automatic path is not idempotent.

Suggested fix: set `idempotency_key` to the stable `handoff_id` (or `hh_` + digest) on both delivery packets, and include the resolved `session_ref` and `expected_generation` on `existing_session_delivery` when `source_route` is present. Refuse automatic delivery when `source_route` is null instead of handing the caller a partial params object.

Suggested test: `user handoff replay uses one key | Given one continuity and one source URL | When browser_handoff.prepare is called twice | Then both automatic_delivery params carry the same idempotency_key and a second session.create with that key does not actuate twice`.

### 8. Medium — learned apps and pill-only composer state disagree with the Rust app list

Evidence:

- `extension/content/wake.js:1291-1299` and `2340-2344`. Explicit apps, else the learned keyword, else whatever pills are already selected, are unioned for ChatGPT.
- `extension/content/base.js:113-119`. `inputHasContent` is true when a pill's text is non-empty. After a failed selection leaves a pill, the next create/dispatch hits `wake.js:2403-2411` and returns `browser_create_composer_busy` / `browser_dispatch_composer_busy` even though the draft text was cleared (`wake.js:2458-2466`).
- `crates/herdr-mcp/src/mcp.rs:6274-6278`. Rust sorts and dedupes the requested list. The extension readback is DOM order of every selected pill, so a superset stays `Uncertain` until finding 4 promotes it.

Impact: a successful send with an extra learned app is reported uncertain, then late-accepted without an app check. A failed app click leaves the composer busy for later WebChat turns on that tab.

Suggested fix: read back only the requested apps, in the sorted order Rust already uses, from the accepted message. On the busy path, treat a composer that `composerHasOnlyAppPills` would accept as empty of user text, and clear unexpected pills before returning.

Suggested test: `user dispatch readback is the requested set | Given the composer already has pill "other" and required_apps is ["herdr"] | When app selection is attempted | Then either both are rejected as a superset or the readback sent to Rust is exactly ["herdr"] after the extra pill is removed`.

### 9. Low — failure evidence and logs can carry composer or DOM detail; cookies and access tokens do not

Evidence:

- `crates/herdr-mcp/src/mcp.rs:4616-4626`. A non-applied session create returns `delivery_evidence: evidence.result` with no allowlist. The extension puts `app_selection_probe` on that object (`wake.js:2421-2425`). The probe includes mention names, sanitized mention paths, ancestor chains, and editor attribute values (`extension/content/injector/chatgpt.js:264-345`). The uncertain reconcile path allowlists booleans and small counts (`mcp.rs:3697-3735`) and does not.
- `extension/content/wake.js:435`. A retry logs the first 30 characters of the inserted text. `extension/background.js:10224` returns the first 40 characters of the composer to the content script as `text`.
- `extension/content/wake.js:4068-4088`. The ChatGPT access token is read from `/api/auth/session` into a local and sent only as an `Authorization` header. It is not written to evidence, `sessionStorage`, or `console.log`. Fetch failures return fixed reason tokens (`auth`, `http-<status>`, `timeout`). HUD `innerHTML` at `wake.js:5919` is a static template.

Impact: an MCP client that receives a create refusal also receives DOM structure and app identifiers. A console or extension-message log can contain a prompt prefix. Session cookies and the bearer token were not found on the WebChat result path.

Suggested fix: run the create failure probe through the same allowlist as `app_selection_probe` in the reconcile response. Drop `text` from the `h2w_insert_main` result and remove the message prefix from the insertion warning.

Suggested test: `user create refusal has no probe strings | Given app selection fails with a probe that includes inline_mention_names | When session.create returns | Then delivery_evidence has no string fields other than a fixed error token`.

### 10. Low — an actuation throw is reported as command accepted

Evidence:

- `extension/content/wake.js:2913-2922`. The `h2w_browser_actuation` rejection handler sets `command_accepted: true` on a fresh evidence object.
- `crates/herdr-mcp/src/mcp.rs:2428-2431`. Accepted-but-unproven evidence becomes `Uncertain`. Session create has already moved the reservation from `not_applied` to `uncertain` before the call (`mcp.rs:4500-4513`), so a throw before Enter cannot return to the retry-safe `not_applied` path (`mcp.rs:4560-4565` requires `retry_safe` and `message_submitted: false`).

Impact: a content-script exception before submit consumes the create key. That avoids a duplicate, and it also prevents a clean retry. Dispatch has the same pre-claim while holding the store lock (`mcp.rs:2564-2576`), which is the right duplicate fence; the extension catch should not widen it to failures that never reached the page.

Suggested fix: set `command_accepted` in the catch only when a submit was already attempted. Otherwise return `rejected` with `retry_safe: true` and `message_submitted: false`.

Suggested test: `user create exception before submit is retry-safe | Given performBrowserActuationCommand throws before Enter | When the listener answers | Then command_accepted is false and a same-key replay is allowed to actuate once`.

## Checked, and holding

- Dispatch idempotency is claimed inside the store lock before actuation, and an existing row is returned without a second send (`mcp.rs:2505-2576`). A digest, session, app, generation, or caller mismatch is `browser_dispatch_idempotency_conflict` (`state_store.rs:4708-4735`).
- Session-create reservations conflict on account, space, label, generation, or request digest (`state_store.rs:4248-4261`). A proved-not-applied create may actuate again; an applied row does not (`mcp.rs:4462-4498`). Same-account concurrency is serialized by `BrowserMutationAdmission` on the HTTP runtime (`mcp.rs:5131-5148`, `mcp_http.rs:2644`).
- Postcondition generation mismatch returns `stale_capability_generation` (`mcp.rs:2342-2347`). Open and archive on the page require `registeredBrowserGeneration` (`wake.js:2071-2073`, `2276-2278`).
- Provider app identity for a selected pill requires `app-mention-path` (`extension/content/injector/chatgpt.js:136-139`). Plain text alone does not satisfy `getSelectedComposerApps`.
- Archive-status maps `http-429` to `rate_limited` with a bounded `retry_after_s` and does not mutate (`mcp.rs:5286-5321`).
- Self-archive in the page dedupes by idempotency key and persists the click claim before the menu click (`wake.js:1878-1930` and `1973-1986`).
