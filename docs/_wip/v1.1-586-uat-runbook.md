## 2. 状态库：路径、只能读、以及"键是摘要"这个坑

- 状态库路径：`<config_dir>/state.db`。默认实例（`HERDR_MCP_INSTANCE` 未设置）的 `<config_dir>` 就是 `~/.config/herdr-mcp`（默认 config leaf 见 `instance.rs:22-23`，根目录解析见 `paths.rs:18-25`；`HERDR_MCP_CONFIG_DIR` / `XDG_CONFIG_HOME` 会覆盖它，但本手册**不要**设置这两个变量）。独立扩展探针同样用 `config_dir/state.db`（`standalone_extension.rs:986-992`）。
- 查询一律：

```bash
DB="$HOME/.config/herdr-mcp/state.db"
sqlite3 -readonly "$DB" "<SQL>"
```

- **`operations.idempotency_key` 与 `browser_dispatches.idempotency_key_digest` 存的是 SHA-256 摘要，不是明文 key**（`state_store/schema.rs:83-94` 注释 "The stored idempotency value is an application-provided digest rather than the raw public key"）。所以**不要**用明文 key 去 where 查；用命令返回的 `session_ref`（`br_…`）、`dispatch_id`、`reservation_ref`（`bsr_…`）、`op_id`（`op:browser_page_action:<32hex>`）来定位行。
- 表名/列名全部取自 `crates/herdr-mcp/src/state_store/schema.rs`：`browser_endpoints`(:303)、`browser_provider_state`(:318)、`browser_resources`(:329)、`browser_dispatches`(:352)、`browser_resource_locators`(:391)、`browser_session_reservations`(:400)、`browser_source_turns`(:488)、`browser_session_archive_intents`(:529)、`operations`(:47)。
- `browser_source_turns` 只存 `user_text_sha256`，**永不存明文用户轮次**（`schema.rs:478-486` 注释）。

## 3. 全局不变式（每个条目都适用）

1. **一次意图 = 一个 idempotency key。** 同一个 key 重放只会返回已记录结果（`replayed=true`），不会二次执行：`operations` 的唯一索引 `idx_operations_kind_idempotency`（`schema.rs:90-92`）、`browser_dispatches` 的唯一索引 `idx_browser_dispatches_idempotency`（`schema.rs:379-381`）。
2. **`uncertain` / `delivery_unknown` / 超时之后绝不换 key 重试。** 只有 `not_applied` 且 `retry_safe=true`（命令证明没越过投递边界）才算安全重试；换 key 是"新的意图"，必须显式记录为第二次尝试。
3. **不要用 `applied` 反推"用户已看到"**；settle 只能由 `dispatch-status` 的 `execution_state`/`result.settled` 或 provider 侧独立只读回读证明。
4. 每个 mutation 都要有清理与"没有第二次执行"的对照证据（行数、provider 侧用户气泡数、标签页数）。

### 5.5 stop（**没有 CLI**）

`parse_webchat` 只接受 `endpoints`、`resources`、`inspect`、`create`、`send`、`dispatch-status`、`open`、`archive`、`archive-status`、`handoff`（`cli/webchat.rs:10-57`；帮助文本 `:375-415`）。**不存在 `herdr-mcp webchat stop`**。

stop 是私有方法 `herdr_mcp.browser_dispatch.stop`（方法名常量 `progressive_skills.rs:62`，实现 `mcp.rs:4126-4200`），参数：

| 参数 | 说明 | 依据 |
| --- | --- | --- |
| `dispatch_id` | 被停止的**父** dispatch（必须是 `browser_dispatch.submit`） | `mcp.rs:4161-4164` |
| `expected_generation` | 必须等于父 dispatch 的 generation | `mcp.rs:4165-4167` |
| `idempotency_key` | 一次停止一个 key | `mcp.rs:4146-4149` |

前置：父 dispatch `delivery_state=applied` 且 `generation_owner == expected_generation`，否则 `browser_dispatch_not_stoppable`（`mcp.rs:4171-4178`）；父已 `stopped` 时同 key 重放返回 `replayed=true`（`mcp.rs:4168-4170`）。

期望结果：`operation=browser_dispatch.stop`、`delivery_state=stopped`、`target_dispatch.execution_state=stopped`（`mcp.rs:4441-4453` + `:8847-8862`）；扩展侧的判定是 "stop 按钮消失且 `isTurnInProgress()` 为假"（`wake.js:2637-2670`），非 `stopGeneration` provider 返回 `browser_stop_control_unavailable`（`wake.js:2638-2640`）。

**可达性（1.1 的验收口径）**：只有 CLI 的操作者**发不出** stop——`parse_webchat` 和 `webchat_help` 里都没有 `stop`（`cli/webchat.rs:10-57`、`:375-415`）。1.1 的 stop 验收走**已授权的 connector**：由持有 provider 级 WebChat control 授权的远端 Edge 调用方发出私有方法 `herdr_mcp.browser_dispatch.stop`，参数就是上表三个字段（`dispatch_id` / `expected_generation` / `idempotency_key`）。没有 caller 的 webchat control 授权时运行时 fail-closed（`mcp.rs:4126-4200`；对应回归测试 `mcp.rs:18206`），所以：

- 有可用授权 connector → 正常验收，按上面的期望结果判读。
- **没有**可用授权 connector → 该项**记为 blocked**，写清楚缺的是"已授权的 connector"，不要伪造通过。
- **禁止**用"在页面上手动点了一下 stop 按钮"冒充 `browser_dispatch.stop` 验收：被这样停掉的 dispatch 会停在 `submitted` 而永不 settled（历史记录见 `docs/_wip/v1.1-browser-adapter-platform.md:2501`）。

## 8. Gate 4 / Gate 7 P0 UAT：MV3 service worker 中途重载 → 不重复执行

### 8.1 安全的触发方式

| 方式 | 是否用 | 原因 |
| --- | --- | --- |
| `chrome://extensions` → 该 unpacked 扩展的 **Reload** 按钮 | **用这个** | 完整的扩展重启：SW 结束、内容脚本重注入、SSE 重连；最接近"真实中途丢失上下文" |
| 修改 `extension/manifest.json` 版本号触发现有 DEV 自重载 | **不要** | 只在磁盘版本号变化时触发（`background.js:13335-13358`，`chrome.runtime.reload()` 在 `:13345`）；会静默更换被测版本 |
| 从 SW 控制台手工 `chrome.runtime.reload()` | **不要** | 自伤式重启，且会与在飞请求竞争；不是可复现的外部触发 |
| `chrome://serviceworker-internals` 里对扩展 SW 点 Stop（可选二次验证） | 可选用 | 只停 SW，内容脚本仍活着，是更弱的模拟；不同 Chrome 版本 UI 位置可能不同 |

要求：重载前后都要记录扩展版本（`webchat endpoints` 的 `extension_version`）必须**相同**，否则本次不算数。

### 8.2 时序

1. 记录基线：`webchat send` 之前的 `dispatch-status`（或空）、`browser_dispatches` 行数、会话里用户气泡数。
2. 发起一次**长回复**的 `webchat send`（同一 key 只发一次）。
3. 在命令仍在飞（Runtime 投递窗口 22s，`mcp_http/actuation.rs:25`）时，点一次扩展 Reload。
4. 等待命令返回，记录完整 JSON。
5. 用**同一个 key** 重放一次同样参数；必须 `replayed=true` 且不产生第二行 `browser_dispatches`。
6. 最多等 60s（`BROWSER_LATE_COMPLETION_TTL`，`mcp_http/actuation.rs:27`），再 `dispatch-status` 一次；如果扩展在重启后补交了完成证据，运行时会用 `reconcile_dispatch` 把同一条 dispatch 收敛（`mcp.rs:4349-4460`、`mcp_http/actuation.rs:536-556`），**不会**重新执行页面动作。

### 8.3 结果判读（两种 API 面必须分开看）

**注意两种 API 面暴露的字段不同**（最容易记错的地方）：

- `herdr_mcp.browser_dispatch.submit`（即 `webchat send`）只暴露 `ok` / `code` / `reason` / `dispatch{delivery_state, execution_state, …}`，`reason` 仅在 `resource_unavailable` / `rejected` 时有值（`mcp.rs:4069-4085`）。所以中途重载在 send 上表现为 **`code=uncertain`**、`dispatch.delivery_state=uncertain`、`dispatch.execution_state=null`（uncertain 故意不投影执行态，`mcp.rs:8856`）。
- 细分的 `completion_timeout` / `queued_untaken_at_timeout` / `endpoint_offline` / `command_not_accepted` 只出现在 **BrowserPage 操作**的 `browser_page_unavailable` / `browser_page_delivery_unknown` 形状里（`mcp.rs:3304-3356`、`:11428-11440`）。

| 观测（按操作类型） | 含义 | 是否“无重复执行”通过 |
| --- | --- | --- |
| BrowserPage：`code=browser_page_delivery_unknown`、`delivery_state=delivery_unknown`、`reason=completion_timeout`、`retry_safe=false`，之后同 key 重放 `idempotent_replay=true` | 命令**已越过** SSE 边界（hand-off），结果未知 | **通过**（前提：行数/气泡数为 1） |
| BrowserPage：`code=browser_page_unavailable`、`delivery_state=not_delivered`、`reason=queued_untaken_at_timeout`、`retry_safe=true` | 命令**从未**被扩展取走，原子撤回 | 是安全重试的证据，**不能**当作“无重复执行”通过 |
| BrowserPage：`reason=endpoint_offline` / `command_not_accepted` | 从未离开 runtime / 扩展明确拒绝 | 不构成通过，属重跑前置失败 |
| `webchat send`：`code=uncertain` + `dispatch.execution_state=null` | 与第 1 行同义（submit 面不暴露细分 reason） | **通过**（前提同上） |

（三种 BrowserPage 情形的定义见 `mcp.rs:3304-3356` 与 `mcp_http/actuation.rs:404-470`。）

### 8.4 证据：单次执行的三个必要条件

```sql
-- 1) 该次意图只有一行 dispatch
SELECT COUNT(*) FROM browser_dispatches
WHERE idempotency_key_digest = (SELECT idempotency_key_digest FROM browser_dispatches WHERE dispatch_id = '<dispatch_id>')
  AND operation = 'browser_dispatch.submit';
-- 期望 1

-- 2) ChatGPT 会话的来源轮次只有一行
SELECT COUNT(*) FROM browser_source_turns WHERE session_ref = '<br_session…>';
-- 期望 1

-- 3) 状态机停在 uncertain 而不是被二次写入
SELECT dispatch_id, delivery_state, generation_owner, accepted_user_message_ref, updated_at
FROM browser_dispatches WHERE dispatch_id = '<dispatch_id>';
```

4) provider 侧：用一个**任务自有**的只读 BrowserPage 标签页 open 该会话 URL，`observe`/`extract` 数一遍该消息对应的用户轮次，必须只有 1 个；随后 `finalize` 关闭并验证（见第 10 节）。不要把"运行时没有报错"当作单次执行证据。

### 8.5 清理与恢复

- 关闭任务自有的只读标签页（`finalize`，`tab_closed=true`、`tab_cleanup_verified=true`、`same_url_tabs_open=0`）。
- 会话本身按第 5.8 节处理。
- 恢复原则：`uncertain` 只对账不复发；`not_delivered` 且 `retry_safe=true` 才可"决定重试"（同 key 会重放记录，要真正重发必须换新 key 并记录为第二次尝试）。

## 9. Gate 4 / Gate 7 P0 UAT：`delivery_unknown` 持久化、同 key 不重放、2048 上限

代码位置（`bf38b997` 已含 #863）：

- 预留与崩溃后的终态：`state_store.rs:966-1082`。过期的 `browser_page.action` pending 行**不会被删除**，而是被改写成"durable non-retryable unknown tombstone"，`result_json` 固定为
  `{"ok":false,"code":"browser_page_delivery_unknown","delivery_state":"delivery_unknown","retryable":false,"retry_safe":false,"reason":"pending_expired_after_crash"}`（`state_store.rs:982-999`）。
- 未知终态写入：`complete_operation_unknown`（`state_store.rs:1127-1156`）→ `phase='settled'`, `state='unknown'`, `expires_at=NULL`。
- 上限：`BROWSER_PAGE_UNRESOLVED_CAP: i64 = 2048`（`state_store.rs:1028`），统计条件是
  `op_id GLOB 'op:browser_page_action:*' AND kind='browser_page.action' AND state IN ('pending','unknown')`（`state_store.rs:1030-1041`）。超限时预留被回滚、**不执行页面动作**，返回 `browser_page_unknown_capacity_exhausted`（`mcp.rs:11276-11290`，`delivery_state=not_delivered`、`retryable=false`）。
- 同 key 重放：`state='unknown'` 分支直接把已存 verdict 原样回放，附 `idempotent_replay=true`、`delivery_state=delivery_unknown`、`retry_safe=false`（`mcp.rs:11311-11344`）；`state='complete'` 分支只回放记录（`:11345-11366`）。两者都不会再次触发页面动作。
- v1.1.0 发布说明同一事实：只有 `applied` 使用有界保留期，其他不可安全重试的结果保持持久记录。

### 9.0 实机结果（2026-11-07，MacBook Air Chrome / 本地 `127.0.0.1` fixture）：PASS

- **如何做出一个真实的 `delivery_unknown`：** owned 页 `action reload`（`page_generation` 1 → 2）之后**立即**发 mutating `scroll`，在新文档内容脚本重新挂上前会返回 `code="browser_page_action_transport_failed"`、`detail="Could not establish connection. Receiving end does not exist."`、`delivery_state="delivery_unknown"`、`mutation_submitted=true`、`retry_safe=false`。不需要崩溃注入。
- **同 key 同参数重放（两次）：** 都返回 `code/error="browser_page_action_transport_failed"`、`delivery_state="delivery_unknown"`、`idempotent_replay=true`、`retry_safe=false`，**`op_id` 与首次完全相同**，且没有再执行页面动作。
- **同 key 改参数：** `code="idempotency_key_conflict"`，回带同一个 `op_id`。重放必须逐字节同一请求（含 `direction`/`amount`）。
- **页面未被改动：** 在新开的 owned 页（`reload` 前 `scroll.y=0`、`max_y=1799`）上做完上述流程后 `observe` 仍为 `scroll.y=0`，即那次 unknown 从未落地；随后用**新 key**（新意图，记为第二次尝试）把 `scroll` 从 0 推到 200 才 `applied`。（注意：Chrome 会在 `reload` 后恢复滚动位置，所以“未被改动”的证明要用 reload 前 `y=0` 的页面，不要用已有偏移的页面。）
- **未知 key 不是重放证据：** 用一个在本机账本里没有终态记录的 key 去调用，会按**新意图**执行（`idempotent_replay=false`）。要验证重放分支，必须用本机真实产生过终态记录的那个 key。
- **仍未实机：** 崩溃墓碑分支 `pending_expired_after_crash`（由单测覆盖）与 2048 准入上限（破坏性，不实机凑）。

### 9.1 只读观察（不写库）

```sql
-- 当前未收敛集合
SELECT op_id, state, phase, expires_at, updated_at, result_json
FROM operations
WHERE kind = 'browser_page.action' AND state IN ('pending', 'unknown')
ORDER BY updated_at DESC LIMIT 20;

-- 上限计数（与运行时同一口径）
SELECT COUNT(*) FROM operations
WHERE op_id GLOB 'op:browser_page_action:*'
  AND kind = 'browser_page.action'
  AND state IN ('pending', 'unknown');
```

判读：`pending` 是"已预留、结果未知（进程崩溃）"，`unknown` 是"永久的不可重试墓碑"。两者都计入 2048。

实机部分只验"同 key 不重放"（这是 1.1 的 P0 UAT 判据）。**不要**为了看上限去凑 2048 行：那需要 2048 次崩溃，属于不可接受的破坏性操作。上限本身由单元测试覆盖（`mcp.rs:24997-25064`）：已有 2047 条未收敛记录时**第 2048 条准入**；再插入即**超过 2048（第 2049 次）被拒绝**，拒绝会回滚该次 pending 预留，**拒绝后计数保持 2048**（判定条件是 `unresolved_count > 2048`，且计数含刚插入的 pending 行，见 `state_store.rs:1028-1044`），实机部分记为"不适用（原因：需要 2048 次未收敛崩溃，破坏性）"。

### 9.2 明确结论：目前**没有**受支持的运维路径去查看或核销这些行

- 没有 CLI 子命令读写 `operations`：`cli.rs:619-700` 的命令表里没有任何 operations/unknown 相关子命令；`herdr-mcp status` / `doctor` 也不改写数据库（`status.rs:1038-1057` 明确 doctor 不得写状态）。
- 核销只能通过内部函数 `complete_operation_unknown` / `put_operation_ledger`，外部无法调用。
- 因此**"可信人工核销（trusted manual write-off）"仍是缺口**，且是 2048 上限被打满后唯一的恢复路径。后续跟踪见 [#869](https://github.com/whshang/herdr-mcp/issues/869)（1.1.x），设计方案也在那里讨论。
- 本项仍是 1.1 的 P0 UAT（实机只验"同 key 不重放"与计数口径）；但**人工核销能力的实现**归入 1.1.x（#869），本文档不重写设计方案。

## 10. Gate 4 / Gate 7 P0 UAT：自有标签页被关闭、用户自己的标签页不受影响

### 10.0 实机结果（2026-11-07，MacBook Air Chrome / 本地 `127.0.0.1` fixture）

- **owned 半：实机通过。** `lifecycle open` 返回 `ownership="owned"`、`page_generation=1`、`reused=false`（lifecycle 响应不含 `delivery_state`）；`lifecycle finalize` 返回 `finalized=true`、`tab_closed=true`、`tab_cleanup_verified=true`、`same_url_tabs_open=0`；随后对同一 `page_ref` 发 `observe` 返回 `code="browser_page_not_found"`，即 10.3 的 owned 判据成立。
- **owned 页 `release` 拒绝（2026-11-07 实机，补上 UAT5 审计指出的 `release` 实机记录缺口）：**

  ```json
  {"error": "browser_page_owned_requires_finalize", "ok": false}
  ```

  exit 1。拒绝**不会**关闭标签页：紧接着 `observe` 同一 `page_ref` 仍返回 `ok:true`、`ownership="owned"`、`page_generation=1`，直到 `lifecycle finalize` 才关。拒绝信封依旧只有 `ok` / `error`（无 `code` / `delivery_state` / `retry_safe`）。
- **claimed 半：仍未打通。** 对一个当前没有用户标签页的 URL 发 `lifecycle claim` 会 fail closed，返回 `{ok:false, error:"target_tab_not_found"}`（lifecycle 拒绝不带 `code` / `delivery_state` / `retry_safe`）。受支持的 CLI 既不能创建非 owned 的用户标签页，也不能列出标签页，因此 10.2 步骤 1（记录用户自有标签页清单）与 `claim → release` 在纯 CLI 路径上不可生产，仍是前台用户浏览器的人工检查项。不要用 CLI `open` 冒充 claimed（`open` 永远产出 owned），也不要为了凑这一半去用 GUI 自动化。
- **10.4 同 URL 双标签残留：已实机复现（不再是“未执行”）。** 两个 owned 标签页停在同一个 URL（实测 `/goal.html` 与 `/scroll.html` 各一次）时，先 finalize 的那个返回 `tab_closed=true` 但 `tab_cleanup_verified=false`、`same_url_tabs_open=1`；关掉第二个后才回到 `true` / `0`。所以 10.3 的判据必须读 `same_url_tabs_open`，不能只看 `tab_closed`。

### 10.1 语义（源码权威）

- `open` 产生 `ownership="owned"`（`background.js:9004-9012`）；用户已有标签页只能 `claim`，得到 `ownership="claimed"`。
- `release` 只允许 claimed；对 owned 调用会返回 `browser_page_owned_requires_finalize`（`background.js:9043-9046`）。
- `finalize` 对 claimed 页**只删记录、不关标签**：`finalized:true, tab_closed:false, tab_cleanup_verified:true`（`background.js:9057-9066`）。
- `finalize` 对 owned 页：按精确 `tab_id` 关闭 → 复核 `chrome.tabs.get` 失败 → 再统计同 URL 的其它标签页，`tab_cleanup_verified = (same_url_tabs_open === 0)`（`background.js:9070-9120`）。已关闭的历史页会给出 `already_closed:true` 与 `same_url_tabs_open`（`background.js:9074-9084`）。

### 10.2 步骤

1. 记录用户自有标签页清单（URL 或标题，不要记录账号信息）。
2. 打开一个任务自有页并复现一次失败（例如第 6 节的第二账号拒绝，或第 8 节的中途重载）：

```bash
herdr-mcp browser-page lifecycle --params-json '{"endpoint_ref":"<bep_…>","action":"open","url":"https://chatgpt.com/","target_origin":"https://chatgpt.com","idempotency_key":"uat-586-tab-<日期>-a"}'
herdr-mcp browser-page action    --params-json '{"endpoint_ref":"<bep_…>","page_ref":"<bp_…>","action":"observe"}'
herdr-mcp browser-page lifecycle --params-json '{"endpoint_ref":"<bep_…>","action":"finalize","page_ref":"<bp_…>","idempotency_key":"uat-586-tab-<日期>-b"}'
```

（`lifecycle` 允许的 action 只有 `open|claim|release|finalize`，见 `mcp.rs:12506-12515`；`action` 的允许集合见 `mcp.rs:10533-10545`。参数必须带 `endpoint_ref`，CLI 会强制校验，`local_agent_cli.rs:222-238`。）

3. `finalize` 后立刻用同一 `page_ref` 再发一次只读 `observe`，必须 `browser_page_not_found`（`background.js:9036-9037`）。

### 10.3 通过判据

- `tab_closed=true`、`tab_cleanup_verified=true`、`same_url_tabs_open=0`。
- 用户自有标签页的 URL/数量与步骤 1 完全一致（不要用扩展自己统计，用独立的标签页清单）。
- 一个 claimed 页 `finalize` 后标签页仍然存在且 `tab_closed=false`。

### 10.4 已知坑（必须覆盖）

`webchat create` 会留下它自己的会话标签页；如果之后又用别的方式打开了同 URL 的 owned 页，`finalize` 会诚实地给出 `tab_cleanup_verified=false` + `same_url_tabs_open=1`（历史根因见 `docs/_wip/v1.1-browser-adapter-platform.md:2458-2463`）。所以判据必须包含 `same_url_tabs_open`，不能只看 `tab_closed`。

## 11. Gate 4 / Gate 7 P0 UAT：失败之后"可读、可恢复"的错误状态

### 11.0 实机结果（2026-11-07，MacBook Air Chrome / 本地 `127.0.0.1` fixture）：LIVE-VERIFIED PASS

- **代际推进：** `action reload` 返回 `delivery_state="applied"`、`reloaded=true`，把 `page_generation` 从 `1` 推到 `2`；旧 document 的 `generation` token 从此失效。
- **字符串 token 围栏：** 用 reload 前的 `generation` token 发 `scroll` 被 fail closed 拒绝，完整信封为 `code="stale_generation"`、`error="stale_generation"`、`delivery_state="not_applied"`、`mutation_submitted=false`、`idempotent_replay=false`、`retry_safe=true`、`page_generation=2`。
- **整数 `page_generation` 围栏：** 用过期或离谱的整数（`1` 与 `999`）发 `navigate`，两次都返回 `code="browser_page_generation_stale"`、`delivery_state="not_applied"`、`mutation_submitted=false`、`retry_safe=true`。仓库里**没有**名为 `stale_page_generation` 的错误码，不要照着写。
- **恢复：** 重新 `observe` 取得新 `generation` 后，同一意图的 `scroll`（`direction="down"`、`amount=200`）返回 `delivery_state="applied"`、`before_y=0`、`after_y=200`、`moved=true`，随后 `observe` 读到 `scroll.y=200`，闭环成立。
- **reload 后的挂载竞态（必须写进记录）：** 在 reload 之后、新文档内容脚本重新挂上前立即发 action，会返回 `code="browser_page_action_transport_failed"`、`delivery_state="delivery_unknown"`、`mutation_submitted=true`、`retry_safe=false`。这一条**不是** `stale_generation`：命令没有到达页面。恢复动作是只读的 `observe`（证明上一次意图没有生效）后再用新 key 作为第二次尝试；不得凭“未知”就直接重试。
- **未覆盖：** 第二账号拒绝（第 6 节）与 MV3 中途重载（第 8 节）本轮没有跑，11 节的两条判据只由上述 stale / 恢复场景佐证。

选一个 fail-closed 场景（推荐两个都做：stale generation、第二账号拒绝），要求把**完整响应体**原样贴进验收记录，而不是只写"失败了"。

期望可读字段（`mcp.rs:3321-3356`、`:4055-4075`、`:5480-5525`）：

| 字段 | 作用 |
| --- | --- |
| `ok` | `false` |
| `code` | 稳定的机器码（如 `stale_capability_generation`、`browser_dispatch_not_stoppable`、`browser_page_unknown_capacity_exhausted`） |
| `reason` | 固定词汇的原因。BrowserPage 形状：`completion_timeout` / `endpoint_offline` / `queued_untaken_at_timeout` / `command_not_accepted`（`mcp.rs:3304-3356`）；create：拒因白名单或 `null`（`mcp.rs:5390-5407`）；dispatch：仅 `resource_unavailable`/`rejected` 才有值（`mcp.rs:4069-4085`） |
| `delivery_state` | `not_delivered` / `applied` / `uncertain` / `delivery_unknown` / `rejected` / `resource_unavailable` / `browser_offline` / `stopped` |
| `retry_safe` / `retryable` | 唯一可以据此决定"能不能重试"的字段 |
| `endpoint_last_seen_age_ms` | 区分"从没连上"（无该字段）与"45 秒前掉线"（`mcp.rs:3345-3347`） |
| `delivery_evidence.*` | create 场景的白名单证据（`message_submitted` / `tab_closed` / `tab_cleanup_verified` / `scope_failure` / `registration_status` / `identity_relation` / `composer_busy_probe`），见 `mcp.rs:5596-5720` |
| `hint` | 仅有固定文案的可操作提示（如 composer 忙，`mcp.rs:5461-5490`） |

可恢复性要求（逐条打勾）：

1. 错误响应里不含页面文本、token、账号标识（只有固定枚举）——抽查一次。
2. `retry_safe=false` 的错误**没有**被重放（用 `browser_dispatches` / `operations` 行数证明）。
3. 恢复动作是只读的：`webchat inspect`、`dispatch-status`、`browser-page action observe`。
4. 只有在 `delivery_state=not_delivered` 且 `retry_safe=true` 时，才允许"决定重试"；重试用**同一个 key**（回放）或显式记录"新 key = 第二次尝试"。
