# Herdr-MCP 1.0 Alpha 4 — ChatGPT Adapter Minimum Vertical Slice

Status: implementation baseline for `feat/v1.0-chatgpt-adapter-alpha4-20260905`.

Planning SSOT: [`docs/history/architecture/v1.0-architecture-plan.md`](../history/architecture/v1.0-architecture-plan.md).

## Goal

Alpha 4 adds the first provider adapter that may actuate a WebChat session, using ChatGPT as the proof of the adapter seam. It turns Alpha 3's fail-closed identity resolution into a real, fenced, provider-neutral actuation path: stable Project/Conversation targeting, semantic reasoning/app selection, message append, dispatch submit/status/stop, accepted-message evidence, and canonical conversation URL.

The model/provider is only an adapter. Herdr core recognizes only the provider-neutral `device -> browser_endpoint -> provider_account -> space? -> session` hierarchy and typed semantic operations. ChatGPT concepts appear only in the adapter mapping table (`Project -> space`, `Conversation -> session`, `tab/view -> local observation`); they never become core vocabulary.

Alpha 4 does **not** add a second provider, browser resource reservation/failover, or any public contract epoch change.

## Existing boundaries reused

- Browser transport/auth: existing Chrome Native Messaging origin admission and `extension.sock`; no browser bearer/token.
- Trusted local mutation path: the existing `trusted_extension_ipc=true` Axum router. Registry writes and actuation observations are accepted only there and require the caller profile seed to derive the authoritative endpoint ref, preventing cross-profile mutations.
- Remote read/actuation path: the existing `herdr_call` workstation routing; no new public MCP tool/action or contract epoch.
- Device identity: the enrolled `edge.device_id` from local runtime configuration; the extension cannot supply or override it.
- Local durable state: the existing `StateStore` SQLite/WAL database and migration chain. Alpha 4 may add only the minimum dispatch identity/idempotency anchor defined below; it does not create a second state source, resident daemon, alarm, timer, or Edge persistence.
- Fleet routing/revocation: existing Edge device routing and revocation; Alpha 4 adds no second device registry.
- Identity model: Alpha 3's stable opaque endpoint/account/space/session refs, capability snapshot fencing, and three default-OFF local consent bits are inherited unchanged.
- Work Memory: Alpha 2's `work_chain` evidence/execution-lane state and portable evidence ref rules are inherited unchanged.

## Milestone boundary

The architecture plan places browser resource reservation/failover in `1.0.0-beta.2` and the Gemini second-provider slice in `1.0.0-alpha.5`. Alpha 4 therefore has:

- no browser reservation table or acquire/renew/release/takeover state machine;
- no multi-device endpoint scheduler/failover;
- no Gemini/Claude/Grok adapter;
- no Tool Bridge (reverse-direction) actuation — the Tool Bridge and workstation-mutation consent bits remain inherited but are not exercised by Alpha 4's Control-path operations.

Cross-device calls continue to select the workstation through the existing explicit device-routing layer.

### Alpha 4 vs beta.1 delivery boundary

The roadmap assigns uncertain-delivery settlement, late confirmation, reload/stale-view recovery, and reliability/postcondition reconciliation to `1.0.0-beta.1`. Alpha 4 therefore owns only the minimum delivery semantics required to make its first real browser mutation fail closed:

- a stable `dispatch_id` and durable idempotency/fencing anchor in the existing `state.db`, so a repeated `idempotency_key` cannot become a second browser mutation after a runtime restart;
- the immediate result vocabulary `not_applied / applied / uncertain / rejected / browser_offline / resource_unavailable / stopped` for one fenced operation attempt;
- `applied` only when the operation's required postcondition is observed in the same current-generation attempt;
- `uncertain` when actuation may have happened but Alpha 4 cannot prove the postcondition; Alpha 4 records and returns that state but does not resolve it later;
- no implicit retry or replay of an `uncertain` dispatch. This is a safety invariant, not an Alpha 4 recovery feature;
- `browser_dispatch.status` reports the persisted current Alpha 4 state; `browser_dispatch.stop` may act only against the currently verified generation and does not reconstruct ownership after a reload/runtime restart.

Beta.1 owns the recovery/settlement layer that Alpha 4 intentionally does not implement:

- append-only delivery-transition history (`browser_delivery_events`) and any migration needed to add it;
- late-confirmation settlement of a previously `uncertain` dispatch;
- reload, stale-view, detached-tab, provisioning, and runtime-restart reconciliation;
- retry/replay policy after reconciliation, including proof that a retry cannot duplicate an already-applied mutation;
- richer postcondition history and long-running settlement semantics.

The `uncertain` value itself cannot be postponed to beta.1: without it Alpha 4 would have to mislabel a may-have-applied request as either `applied` (false success) or `not_applied` (unsafe to retry). What is deferred is **settling or recovering** that state, not representing it fail-closed.

## Identity model

Alpha 4 reuses Alpha 3's canonical hierarchy verbatim:

```text
device
  -> browser_endpoint
       -> provider_account
            -> space?        # only for providers with a native grouping object
                 -> session
                      -> view* # local observation only; never durable identity
```

Endpoint refs and provider resource refs remain opaque and must not encode a URL, tab id, workspace id, absolute path, account id, or selector. `space` is optional and is never synthesized for a provider without a native grouping object.

### Adapter mapping table

The only place ChatGPT vocabulary is permitted is the adapter's mapping:

| ChatGPT concept | Provider-neutral concept | Notes |
| --- | --- | --- |
| Project | `space` | optional; only when a native Project exists |
| Conversation | `session` | stable opaque ref |
| browser tab / view | local `view` observation | never durable identity |
| reasoning control | `reasoning_effort` semantic enum (`economy` / `balanced` / `thorough`) | adapter maps to provider-native value |
| app / custom GPT / MCP tool selection | `required_apps` semantic capability list | adapter maps `"herdr"` to the Herdr app |

## Authorization handoff

Alpha 3's `browser_resource.resolve` always returned `actuation_available:false`. Alpha 4 defines the exact conditions under which it becomes `true`, following the §6.5 least-privilege intersection:

```text
actuation_available = true  iff ALL of:
  1. authenticated caller grant includes WebChat Control for this (endpoint, provider, account);
  2. Alpha 4 policy gate is the constant `true` (no persisted/configured policy source in this phase);
  3. local Extension consent: WebChat Control bit = ON for this endpoint;
  4. provider/account capability allowlist includes the operation;
  5. current capability snapshot (generation == latest observed) includes the operation.
```

When any factor fails, resolution returns `actuation_available:false` plus a reason code rather than a bare boolean:

```text
caller_grant_missing
local_consent_off
capability_not_allowed
capability_unknown
stale_capability_generation
```

Alpha 4 deliberately does **not** invent a fleet/business-policy store or second policy authority. Factor 2 is a compile-time/spec constant and has no field in StateStore, Edge, Extension storage, or request parameters. Real fleet/business dispatch policy is deferred to beta.2 together with reservation/failover, where its authority and fencing can be designed against the settled Fleet Control model instead of being smuggled into Alpha 4.

Hard rule: there is no method, private or public, that enables or widens local Extension consent from a remote caller. Local consent is mutated only through trusted Extension IPC. Remote authority can only reduce what is effectively allowed through its existing authenticated caller grant; the Alpha 4 constant policy gate cannot widen local consent or capabilities.

`actuation_available:true` is a permission signal, not a guarantee. Every mutation re-evaluates the intersection at mutation time and additionally requires the caller's `expected_generation` to equal the current capability snapshot generation.

## Typed operations

All operations are provider-neutral and remain behind the existing `herdr_call` private gateway. Workstation Runtime Execution stays epoch 2 / 18 tools; public Edge stays epoch 3 / 19 actions. Method names and schemas are frozen in this spec.

### Common fencing envelope

Every mutation accepts:

```text
expected_generation : positive int   # capability snapshot generation the caller planned against
idempotency_key     : opaque string  # caller-supplied; scoped to (endpoint, provider, operation)
```

`expected_generation` must equal the current snapshot generation or the call fails `stale_capability_generation`. A request planned against generation N must never silently run against N+1.

### Space / session lifecycle

```text
herdr_mcp.browser_space.create
  in:  endpoint_ref, provider, account_ref, display_label (bounded), expected_generation, idempotency_key
  out: space_ref (opaque), canonical URL
  fail: unsupported (no native space), capability_unknown, stale_capability_generation,
        consent_denied, resource_unavailable

herdr_mcp.browser_space.open
  in:  space_ref, expected_generation, idempotency_key
  out: postcondition (space opened in view), canonical URL
  fail: browser_resource_not_found, browser_offline, stale_capability_generation, consent_denied

herdr_mcp.browser_space.inspect
  in:  space_ref (or provider-neutral filter)
  out: space metadata, current capability snapshot, actuation_available + reason
  read-only

herdr_mcp.browser_session.create
  in:  endpoint_ref, provider, account_ref, space_ref?, display_label (bounded),
       expected_generation, idempotency_key
  out: session_ref (opaque), canonical URL
  fail: unsupported, capability_unknown, stale_capability_generation, consent_denied, resource_unavailable

herdr_mcp.browser_session.open
  in:  session_ref, expected_generation, idempotency_key
  out: postcondition (session opened in view), canonical URL
  fail: browser_resource_not_found, browser_offline, stale_capability_generation, consent_denied

herdr_mcp.browser_session.inspect
  in:  session_ref
  out: session metadata, current capability snapshot, actuation_available + reason
  read-only
```

### Message

```text
herdr_mcp.browser_message.append
  in:  session_ref, message (bounded text), expected_generation, idempotency_key
  out: accepted message identity (provider-qualified message_ref)
       OR provider-observed message baseline advance
  fail: unsupported, capability_unknown, stale_capability_generation, consent_denied,
        browser_offline, resource_unavailable
```

`browser_message.append` appends without submitting. `browser_dispatch.submit` is the append-and-submit path. If neither an accepted message identity nor a provider-observed message baseline advance is observable, the operation settles `uncertain`, never `applied`.

### Composer intent

```text
herdr_mcp.browser_composer.set_reasoning
  in:  session_ref, reasoning_effort ("economy" | "balanced" | "thorough"), expected_generation, idempotency_key
  out: reasoning effort read-back confirmation
  fail: unsupported (provider has no reasoning-effort control), capability_unknown,
        stale_capability_generation, consent_denied

herdr_mcp.browser_composer.set_apps
  in:  session_ref, required_apps (semantic capability list, e.g. ["herdr"]),
       expected_generation, idempotency_key
  out: required app/capability selection read-back
  fail: unsupported, capability_unknown, stale_capability_generation, consent_denied
```

`reasoning_effort` and `required_apps` are semantic, provider-neutral. The Alpha 4 core enum is intentionally **not** ChatGPT's native vocabulary:

| Core `reasoning_effort` | ChatGPT adapter mapping |
| --- | --- |
| `economy` | `low` |
| `balanced` | `medium` |
| `thorough` | `high` |

The ChatGPT adapter owns that mapping. If a provider cannot map a requested core value exactly, the operation returns `unsupported`; it must not silently downgrade, approximate, or introduce an adapter-only compatibility branch. Alpha 5 must evaluate the same semantic enum against Gemini. If the enum does not survive that second-provider proof, the enum changes through an explicit spec revision and compatibility review, not hidden provider-specific fallbacks.

### Dispatch

```text
herdr_mcp.browser_dispatch.submit
  in:  session_ref, message (bounded text), reasoning_effort?, required_apps?,
       expected_generation, idempotency_key, work_chain_id?, lane_id?
  out: dispatch_id, initial delivery state, generation ownership
  fail: unsupported, capability_unknown, stale_capability_generation, consent_denied,
        browser_offline, resource_unavailable

herdr_mcp.browser_dispatch.status
  in:  dispatch_id
  out: delivery state, generation status, postcondition evidence
  read-only

herdr_mcp.browser_dispatch.stop
  in:  dispatch_id, expected_generation, idempotency_key
  out: delivery state = stopped, generation stop confirmation
  fail: dispatch_not_found, stale_capability_generation, consent_denied
```

`browser_dispatch.stop` stops only the WebChat generation owned by that dispatch. If the target conversation launched a local coding agent, that agent is a separate resource with its own ownership/cancel semantics and is not implicitly killed.

## Capability snapshot fencing

Alpha 4 inherits Alpha 3's fencing rules and applies them to every mutation:

- capabilities adhere to the strict provider-neutral allowlist (`{"operations":[...]}`); arbitrary JSON, unknown keys, and credentials/native IDs are rejected;
- generation is a positive monotonic integer;
- a strictly newer generation replaces the current snapshot; same generation with same payload is idempotent; same/older generation with different state fails `stale_capability_generation`;
- resource observations must name the current capability generation or fail closed;
- every mutation carries `expected_generation` and fails `stale_capability_generation` on mismatch.

## Authoritative postconditions

A successful browser mutation requires authoritative postconditions, not merely a successful extension message send. Per operation:

| Operation | Required postcondition evidence |
| --- | --- |
| `browser_space.create` / `browser_session.create` | stable ref resolution + requested create/lifecycle state observed |
| `browser_space.open` / `browser_session.open` | stable ref resolution + open/lifecycle state observed + canonical URL |
| `browser_message.append` | accepted message identity OR provider-observed message baseline advance |
| `browser_composer.set_reasoning` | reasoning effort read-back confirmation |
| `browser_composer.set_apps` | required app/capability selection read-back |
| `browser_dispatch.submit` | accepted message identity/baseline advance + generation ownership/status |
| `browser_dispatch.stop` | generation stop confirmation |

Unsupported capabilities return explicit `unsupported` or `capability_unknown`. An adapter must not emulate an unverified lifecycle action merely to present a uniform surface.

The canonical conversation URL is returned as clickable output evidence only. It is never accepted as a mutation target and is never the cross-device resource identity.

## Immediate delivery result (Alpha 4)

The Alpha 4 immediate delivery-state vocabulary is frozen for the typed operation seam:

```text
not_applied / applied / uncertain / rejected / browser_offline / resource_unavailable / stopped
```

Rules in this phase are intentionally one-attempt and fail-closed:

- `uncertain` is persisted as the current dispatch state and is never blindly replayed by Alpha 4. Alpha 4 does not perform late settlement or recovery.
- A later explicit caller action may inspect `browser_dispatch.status`, but Alpha 4 does not reinterpret an `uncertain` row based on late browser evidence.
- Reload, stale-view, detached-tab, provisioning, runtime-restart reconciliation, and late confirmation are beta.1 work. Alpha 4 fails closed rather than attempting those recovery paths.
- `browser_offline` and `resource_unavailable` are terminal for the current attempt and require re-resolution before a new attempt; they are not retried in place.

## Work Memory write-back

Dispatch evidence flows into the same `work_chain` evidence/execution-lane state defined by Alpha 2:

- `browser_dispatch.submit` may carry `work_chain_id` and optional `lane_id`; when present, the Alpha 4 immediate result is appended to that partition's evidence lane via the existing `work_memory.append_evidence` path. If beta.1 later settles an `uncertain` dispatch, it appends a new settlement evidence item rather than rewriting the Alpha 4 evidence.
- The appended evidence is local raw evidence (local `evidence_id` + digest). The provider-qualified message identity (`provider + account_ref + space_ref + session_ref + message_ref`) is the structured content; the canonical URL is clickable output evidence, not a portable ref.
- A portable evidence ref is generated only when the caller additionally supplies verifiable Git source identity, exactly as Alpha 2 defines. Dispatch evidence without Git source identity stays local and never enters a Fleet portable ref.
- The dispatch result does not grant Fleet Control authority and does not change the Alpha 1 principal boundary. Provider/session binding remains Memory provenance, not an authorization identity.

This write-back is the mechanism that later enables Alpha 2's two cross-WebChat modes (Planner Handoff and Cross-WebChat Delegation). Alpha 4 exercises only the ChatGPT side; the Gemini side arrives in Alpha 5.

## Forbidden inputs

External callers may provide stable endpoint/account/space/session/binding refs, a bounded message, semantic reasoning effort, semantic required capabilities, an idempotency key, and expected generations. They may not provide:

- CSS selectors, XPath, or DOM traversal instructions;
- arbitrary JavaScript, CDP commands, or keyboard/mouse macros;
- arbitrary navigation or raw URL mutation targets;
- shell commands or workstation filesystem paths as browser actions;
- cookies, bearer tokens, refresh tokens, or provider credentials.

Any such input is rejected fail-closed before reaching the adapter.

## Explicit non-goals

Alpha 4 does not add:

- Gemini adapter (belongs to `1.0.0-alpha.5`);
- browser resource reservation/failover (belongs to `1.0.0-beta.2`);
- GitLab/GitHub/Feishu/Jira consumer business policy;
- provider feature parity;
- Playwright, CDP, OpenCLI, or external browser automation;
- Tool Bridge (reverse-direction) actuation;
- destructive lifecycle operations (rename/archive/delete/move_to_space);
- a new public MCP tool/action or any contract epoch change.

## Decisions added this phase

The frozen baseline deferred these points to the implementation-phase spec. Alpha 4 fixes them:

1. **Frozen browser private method names.** Twelve methods (`browser_space.create/open/inspect`, `browser_session.create/open/inspect`, `browser_message.append`, `browser_composer.set_reasoning`, `browser_composer.set_apps`, `browser_dispatch.submit/status/stop`) are frozen here. Rationale: §6.4 explicitly deferred exact names/schemas to the implementation spec, while the existing private namespace already contains `herdr_mcp.browser_endpoint.*`, `herdr_mcp.browser_resource.*`, `herdr_mcp.work_chain.*`, `herdr_mcp.planner_lease.*`, `herdr_mcp.execution_lane.*`, `herdr_mcp.text.*`, `herdr_mcp.device.*`, `herdr_mcp.connector.*`, `herdr_mcp.skill.*`, `herdr_mcp.planning.advise`, and `herdr_mcp.github.status`. Generic top-level `space.*` / `session.*` / `message.*` / `composer.*` / `dispatch.*` would therefore claim names broader than the browser/WebChat subsystem and collide conceptually with future non-browser resources. The `browser_` families align with Alpha 3 and remain provider-neutral; no ChatGPT name enters core vocabulary.

2. **Frozen immediate delivery result vocabulary, not a beta.1 settlement ledger.** The seven values `not_applied / applied / uncertain / rejected / browser_offline / resource_unavailable / stopped` are frozen for Alpha 4 operation results and the current dispatch row. Rationale: Alpha 4 cannot safely implement a real mutation without distinguishing proven `applied`, proven `not_applied`, and may-have-applied `uncertain`. Durable transition history, late settlement, reload recovery, and retry policy remain beta.1.

3. **`actuation_available` truth conditions and reason codes.** The five-factor expression is retained, but Alpha 4 factor 2 is the literal constant `true`; there is no fleet/business policy state in this phase. The four dynamic authority/capability factors map to five fail-closed reason codes (`caller_grant_missing`, `local_consent_off`, `capability_not_allowed`, `capability_unknown`, `stale_capability_generation`). Rationale: this preserves §6.5's least-privilege shape without inventing a second policy store. Real fleet/business dispatch policy is a beta.2 design together with reservation/failover.

4. **`message.append` vs `dispatch.submit` split.** Append-without-submit is a distinct operation; submit is append + submit + generation observation. Rationale: the architecture lists both `message.append` and `dispatch.submit`; separating them keeps the non-submitting path observable without forcing a generation.

5. **Provider-neutral `reasoning_effort` enum (`economy` / `balanced` / `thorough`).** The ChatGPT adapter maps these to `low` / `medium` / `high`. Rationale: core vocabulary must not copy one provider's native tokens. An unmappable value returns `unsupported` without downgrade. Alpha 5 revalidates the enum against Gemini; any needed change is a spec revision, not an adapter-internal compatibility branch.

6. **`required_apps` as a semantic capability list (e.g. `["herdr"]`).** Rationale: §6.4 names `required_apps:["herdr"]`; the core stores semantic capability names, and the adapter maps them to native app/MCP selection.

7. **Dispatch-to-Work-Memory linkage via `work_chain_id`/`lane_id` on `dispatch.submit`.** Rationale: Alpha 2 defined the evidence lane but not how dispatch results enter it; carrying the partition identity on the dispatch closes that gap without a new state source.

8. **Schema v7 -> v8 is limited to one minimal `browser_dispatches` table.** It stores dispatch identity, target session ref, request/message digest (not raw provider-native identity), semantic reasoning/app intent, expected generation, idempotency key, current immediate delivery state, generation ownership, and optional work_chain/lane refs. This cannot be postponed: `browser_dispatch.submit/status/stop` need a stable identity/idempotency anchor across runtime restart, otherwise replaying the same `idempotency_key` could silently create a second browser mutation. Alpha 4 does **not** add `browser_delivery_events`; append-only delivery transition history and late settlement belong to beta.1.

9. **`applied` requires observable message acceptance.** A dispatch/message settles `applied` only when at least one of (accepted message identity, provider-observed message baseline advance) is observed; otherwise it settles `uncertain`. Rationale: §6.6 lists these as postconditions; without this rule an extension send could be misreported as applied.

## Acceptance matrix

### Storage / Rust

- schema v7 -> v8 migration and fresh DB creation with only the minimal `browser_dispatches` table;
- existing v5 -> v6 -> v7 -> v8 migration path remains valid;
- dispatch record persists identity, expected generation, idempotency key, delivery state, and generation ownership;
- no `browser_delivery_events` table, late-confirmation settlement, or reload/restart reconciliation is implemented in Alpha 4;
- idempotency key replay returns the same dispatch without a second actuation;
- `expected_generation` mismatch fails `stale_capability_generation` and never actuates;
- raw provider-native identity and credentials are absent from persisted rows and returned payloads;
- delivery state enum rejects unknown values fail-closed.

### Trusted Extension IPC

- actuation observations and postcondition read-backs are accepted only with `trusted_extension_ipc=true`;
- TCP request to the same route is unauthorized/fail-closed;
- extension cannot provide/override device id or caller grant;
- unknown fields, oversized bodies, and invalid kinds fail closed;
- local consent bits remain mutable only through trusted Extension IPC.

### MCP private method surface

- all twelve typed operations route through existing `herdr_call` local dispatch;
- no remote consent mutation method exists;
- `actuation_available` is computed from authenticated caller grant + constant-true Alpha 4 policy gate + local consent + provider/account allowlist + current capability snapshot, and returns a reason code when a dynamic factor fails;
- public runtime catalog remains epoch 2 / 18 tools;
- public Edge catalog remains epoch 3 / 19 actions;
- forbidden inputs (selector/XPath/JS/CDP/macro/navigation/shell/credential) are rejected fail-closed.

### Extension

- ChatGPT Project/Conversation observation maps to `space`/`session` without leaking native identity;
- reasoning effort and required-app selection are read back, not assumed;
- accepted message identity or baseline advance is observed before `applied`;
- canonical URL is returned as output evidence only;
- extension smoke remains green.
